Abstract Base Classes and Function Templates

Two ideas that both say "write it once": a base class you are forbidden to instantiate, and a function you write once for every type there will ever be.

1.Where polymorphism runs out

Class 24 gave you the machinery. A method marked virtual is dispatched on the dynamic type of the object, not on the static type of the pointer or reference you reached it through. A base-class pointer aimed at a derived object calls the derived override. A base class with virtual methods needs a virtual destructor so that delete through a base pointer runs the right destructor chain. That is polymorphism, and with it you can write code today that correctly drives classes nobody has written yet.

Now think about what "nobody has written yet" really costs you. Suppose you are writing a software library for an accounting system: customers, suppliers, sales and receipts, income and expenses, inventory. Who buys it? A department store. A restaurant. A trucking company. A medical billing firm, which has legal regulations that apply to nobody else on that list. What your library provides is a service. What it emphatically does not have is a model of the objects it operates on — you have no idea what a "sale" looks like at a trucking company.

And yet the library has to operate on something. Every virtual call in it has to go through a base-class pointer or reference, so:

Key Idea

You cannot write virtual functions without a base class of some sort. But in a library like this you never want to create a base-class object — there is no such thing as a generic "ledger entry." The base class exists only to describe the functionality that the library calls. Users of the library write the derived classes and instantiate the actual objects. You never instantiate anything.

So the question this class opens with is a strange one, and it is worth asking out loud before we answer it: why would anyone want to write a class such that objects of it cannot be instantiated? The answer is exactly the paragraph above. The base class is a contract, not a thing.

Definition— abstract class, abstract base class

An abstract class is a class such that objects of the class cannot be instantiated. All objects must be of derived classes only.

  • You can only declare pointers and references to an abstract class.
  • Pointers and references are not objects, so they are permitted to exist.

If an abstract class sits at the root of an inheritance tree we call it an abstract base class. In practice almost every abstract class is an abstract base class, and the two terms get used interchangeably. Abstract base classes are everywhere in commercial software.

C++ gives you two ways to make a class abstract. We will do both, in the order the professor teaches them: first the standard mechanism, the pure virtual function; then his own preferred alternative, protected constructors.

2.Pure virtual functions

Definition— pure virtual function

A pure virtual function is a virtual member function declared with = 0 in place of a body:

virtual string name() = 0;

The = 0 means the method name() has no function body — not here, not in a .cpp file, not anywhere in the compiled project. There is nothing to call. Any class that contains (or inherits) even one pure virtual function is abstract, and the compiler will refuse to create an object of it.

The 0 is not a value being assigned. It is a piece of syntax, chosen decades ago because it looks like "the slot in the vtable is null." Read = 0 as one token meaning "no implementation."

Here is the professor's example class. Read it carefully — it has one of each of the four kinds of member you can put in a base class, and the differences matter.

Worked Example— PVFname, and what a base pointer does with it

PVFname — the name is short for "pure virtual function" — has a virtual destructor, an ordinary virtual method x() that does have a body, a non-virtual print() that calls the virtuals, and one pure virtual name(). Aname overrides both. Bname overrides only x(). Cname derives from Bname and overrides name().

The same thing happens with new, with a slightly different wording worth recognizing:

newabstract.cpp:13:22: error: invalid new-expression of abstract class type 'PVFname'
   13 |     PVFname *p = new PVFname;
      |                      ^~~~~~~
newabstract.cpp:5:7: note:   because the following virtual functions are pure within 'PVFname':

The declaration PVFname *p; is fine. It is new PVFname — the part that would actually build an object — that fails. Pointer: yes. Object: never.

Warning— an erratum in the course notes

The lecture handout explains = 0 by saying "the notation = 0 means that the method string has no function body", and repeats "the method string" in the very next sentence. There is no method called string. string is the return type; the method is name(). Read those two sentences as "the method name()".

It matters more than a typo normally would, because on the exam you have to name the unimplemented method to decide whether a class is abstract. Get in the habit of pointing at the identifier before the parentheses, never at the type in front of it.

Quick Check 25.1

Given the PVFname hierarchy above, decide for each line whether it compiles. If it does not, say which pure virtual is to blame.

(a) PVFname *p;

Compiles. It declares a pointer and does not create anything. The pointer is uninitialized, which is a separate (and real) hazard, but not a compile error.

(b) Aname a; PVFname &r = a;

Compiles. Aname is concrete (it overrides name()), so a is a legal object, and a reference to an abstract base class is allowed — a reference is not an object. This is the ordinary way library code takes its parameter.

(c) Cname c;

Compiles. Cname overrides name() itself and inherits a perfectly good x() from Bname. Nothing is left pure, so Cname is concrete.

(d) void f(PVFname q) { q.print(); }

Does not compile. A by-value parameter is an object; the compiler would have to construct a PVFname to hold the copy. g++ reports "cannot declare parameter 'q' to be of abstract type 'PVFname'", blaming PVFname::name().

This is worth internalizing beyond abstract classes: passing a polymorphic base class by value is nearly always wrong even when it compiles, because it slices the derived part off the object. When the base is abstract, C++ upgrades that design mistake into a compile error for you.

3.Which derived classes are still abstract?

This section is the highest-value fifty minutes of the semester per point scored. Some version of this question has been the last problem on every single final this professor has given, worth 10 to 15 points, no partial credit.

Key Idea

A derived class inherits its base's pure virtual functions as pure virtual functions. If a derived class does not override every one of them, the derived class is abstract too, and declaring an object of it is a compile error.

A class becomes concrete at the exact point in the tree where the last remaining pure virtual gets a body — and it may inherit the other overrides from anywhere above it.

Apply it to the tree from §2. There is only one pure virtual in play, name():

Read the fourth column top to bottom. Nothing else in the class matters. A derived class can add data, add methods, override half the tree, and still be abstract because of one method it never mentioned.

Procedure— deciding if a class is abstract, on an exam, in 20 seconds
  1. Go to the base class and list every method marked = 0. Write them in the margin. Usually there are one or two.
  2. For the class you are asked about, walk up its own chain of ancestors, from itself to the base, ticking off each pure virtual the moment you find a version of it with a body.
  3. Any pure virtual still unticked when you reach the base means the class is abstract. Declaring an object of it is an ERROR.
  4. If every one is ticked, the class is concrete. Now answer the output part: for each virtual call, the version that wins is the first one you found walking up.

Only walk up that class's own chain. A sibling's override is invisible — Bname overriding x() does nothing for Aname.

4.An abstract class as an interface

Back in Class 1 we defined an interface as the contract a class offers the rest of the program, and there was a warning box attached to it: C++ has no interface keyword, and the nearest thing C++ has to a Java interface is an abstract base class whose methods are all pure virtual, "which we build in Class 25." This is Class 25. Here it is.

Definition— interface (the abstract-class sense)

An interface, in this second sense, is an abstract base class that consists of nothing but a virtual destructor and pure virtual functions. It holds no data and implements no behavior. It is a pure statement of what an implementing class must be able to do.

Java has a keyword for this because in Java it is a special language construct. In C++ it is not a construct at all — it is a class you happened to write a certain way. There is no implements either; you inherit publicly, exactly as you inherit from any other base:

class Sale : public LedgerEntry { ... };   // C++ has no "implements"

Here is the accounting-library idea from §1, shrunk to something you can compile. The library half is written once and knows nothing about retail. The customer half is written years later by somebody else.

Worked Example— a library that operates on classes that do not exist yet

LedgerEntry is a pure interface: a virtual destructor and two pure virtuals, no data. report is the library's service; it never mentions Sale or Payroll. Predict the four output lines — and watch the formatting of the money values, which is not what you might guess.

ledger.cpp
// ledger.cpp -- an abstract base class used as a pure interface
#include <iostream>
#include <string>
using namespace std;

// ---------- the library ----------
// Written once. It has no idea what a Sale or a Payroll entry is.
class LedgerEntry {
public:
    virtual ~LedgerEntry() {}
    virtual string label() const = 0;   // every entry must name itself
    virtual double amount() const = 0;  // every entry must have a signed amount
};

void report(LedgerEntry *entries[], int n) {
    double total = 0;
    for (int i = 0; i < n; ++i) {
        cout << entries[i]->label() << ": " << entries[i]->amount() << endl;
        total += entries[i]->amount();
    }
    cout << "net: " << total << endl;
}

// ---------- the customer's code, written years later ----------
class Sale : public LedgerEntry {
public:
    Sale(double d) : dollars(d) {}
    string label() const { return "Sale"; }
    double amount() const { return dollars; }
private:
    double dollars;
};

class Payroll : public LedgerEntry {
public:
    Payroll(double d) : dollars(d) {}
    string label() const { return "Payroll"; }
    double amount() const { return -dollars; }
private:
    double dollars;
};

int main() {
    Sale s1(1200.50), s2(300.00);
    Payroll p1(900.25);
    LedgerEntry *book[3] = { &s1, &s2, &p1 };

Quick Check 25.4

In LedgerEntry, the destructor virtual ~LedgerEntry() {} has an empty body and the class has no data members. Why not just delete the line?

Because the destructor that matters is not this one — it is Sale's and Payroll's. If a program ever writes

LedgerEntry *e = new Sale(50.0);
delete e;

then delete looks at the static type LedgerEntry * to decide which destructor to run. Without virtual, it runs ~LedgerEntry only, and ~Sale never executes — undefined behavior, and a memory leak the moment a derived class holds anything dynamic. With virtual, the call is dispatched to ~Sale, which then runs ~LedgerEntry automatically.

The rule from Class 24: if a class has any virtual method, give it a virtual destructor. An abstract base class always has virtual methods — that is what makes it abstract — so an abstract base class always needs one. Writing it empty costs nothing; leaving it out costs correctness. Every abstract base class in this professor's exams has one, and it is always the first line of the class.

Quick Check 25.5

Someone reads the phrase "an abstract class has methods with no bodies" and concludes: an abstract class is just an incomplete class definition, so it is not a real design idea, only a placeholder you have not finished writing. What is wrong with that argument?

Two things.

First, "incomplete" mischaracterizes what the missing body means. A pure virtual is not a body the author forgot; it is a body the author has deliberately declined to write, because at this level of the hierarchy there is no sensible answer. There is no generic amount for a generic ledger entry. The class is complete as a specification. What is missing is the part only a derived class can know.

Second, and this is the professor's own rebuttal: you can build a perfectly good abstract base class with no pure virtual functions at all. Section 5 does exactly that. If a class can be abstract while every one of its methods has a body, then "abstract" and "incomplete" cannot be the same idea. Abstract is a statement about instantiation, not about missing code.

The fair version of the objection is the practical one: with pure virtuals, it is not enough to write a derived class — the derived class must override all of them, or inherit from something in the tree that already did. That is a genuine obligation the design imposes on your users, and it is the trade-off §5 weighs.

5.The other way: protected constructors

Pure virtual functions are the textbook mechanism, and they are what the exams test. But they are not the only way, and they are not the professor's preferred way.

Procedure— making a class abstract with protected constructors
  1. Make every constructor protected — the default constructor, the copy constructor, any non-default constructors. Add the assignment operator too, for the reason in the note below.
  2. They must be protected, not private. A derived class's constructor has to be able to call the base constructor, and private would block it — making the class not merely abstract but unusable.
  3. Leave the destructor public, and virtual. Client code deletes objects through base pointers, so the destructor has to be reachable from outside.
  4. Everything else can stay exactly as it was. No = 0 anywhere.

Outside code cannot construct an object of the class, because it cannot reach a constructor. Derived classes can, because protected is precisely "my derived classes and nobody else."

Worked Example— ABC, abstract with no pure virtuals at all

ABC has a virtual destructor, two ordinary virtual methods that both have bodies, a non-virtual print(), and a protected: section holding the constructors and operator=. Aabc overrides nothing. Babc overrides x(). Cabc overrides name().

Common Mistake— what the protected operator= is actually for

The handout puts the constructors and the assignment operator in the protected: section together, as if both were needed to make the class abstract. They are not. It is the constructors alone that prevent instantiation — an assignment operator is never what builds an object.

Protecting operator= is still a good idea, but for a different reason: it stops outside code from writing *basePtr1 = *basePtr2;, which would copy only the base part of one object over the base part of another and leave the derived halves untouched — the slicing problem from Class 21. Group them if you like, but know why each one is there.

While you are looking at that section: ABC& operator=(const ABC &rhs) { return *this; } has no self-assignment guard, contrary to the six-step recipe from Class 15. Here the class has no data at all, so there is genuinely nothing to guard, but do not copy this shape into a class that holds a pointer.

Warning— the sentinel that never gets caught

Look again at what ABC does when a derived class forgets to override: name() returns the string "unset". That is a sentinel — a made-up value meaning "nobody filled this in." It is exactly the design pure virtual functions were invented to eliminate, and it converts a compile-time error into a run-time surprise. Babc above is a finished, shippable class that reports unset forever, and nothing anywhere warned anybody.

The honest summary: = 0 gives you an error the moment you build the object; the sentinel gives you a wrong answer six months later in production. Protected constructors are the more flexible design; pure virtuals are the safer one. Use pure virtuals when a derived class genuinely cannot have a sensible default — and that is nearly always the situation an abstract base class is in.

Quick Check 25.6

Consider three variations on ABC.

(a) What breaks if you move the constructors from protected: to private:?

The class stops being usable. Aabc's implicitly generated default constructor has to call ABC(), and a private member is invisible even to derived classes, so Aabc a; fails with "'ABC::ABC()' is private within this context". You would have made the class not abstract but uninheritable — a class nobody can instantiate and nobody can derive from, which is to say a class with no purpose.

This is why the handout stresses "protected (not private)". protected means "derived classes yes, everybody else no", which is exactly the access rule an abstract base class wants.

(b) What breaks if you move the destructor into protected: as well?

Two things. Outside code can no longer create an Aabc object on the stack either, because destroying it at the end of scope needs access to ~ABC. And delete basePtr; in library code fails for the same reason. This is why the procedure says the destructor stays public and virtual — it is the one special member that outside code legitimately needs.

(c) Could you make a class abstract by giving it a pure virtual function and protected constructors?

Yes, and the professor's Fall 2023 final does exactly that: class T has virtual int x() = 0; in its public section and T(), the copy constructor and operator= under protected:. The two mechanisms are independent and stack happily.

When you meet that hierarchy on an exam, do not be distracted by the protected: block — it makes T itself uninstantiable, but the question is always about the derived classes, and there the only thing that matters is which of them still carry an unoverridden pure virtual. 6.The same function, written three times

That should bother you. Three copies is three places to fix a bug. And the list is not finished: what about char? long? bool? The Money class you wrote last week? You cannot enumerate every type your users will ever invent.

So do what you would do in algebra. Replace the type with a symbol — call it T:

void printInput(T x) {
    cout << x << endl;
}

That is not C++ yet; T is not a type and the compiler has never heard of it. But it is the right idea, and the whole of templates is the syntax for making it legal. All you need is a way to tell the compiler "T is a placeholder, and here is which type to substitute for it."

Quick Check 25.7

Before we fix it: why can't you get the same effect just by writing the function once as void printInput(double x) and letting C++ convert everything to double at the call?

Because conversion only exists between types that are related, and it loses information even then.

  • printInput(s) with a string argument does not compile at all — there is no conversion from string to double.
  • printInput(3) would work, but a long long value of 9007199254740993 converted to double prints as 9.00720e+15. You asked it to print your value and it printed a different one.
  • A user-defined type — Money, Complex, Polynomial — converts to nothing.

Overloading and templates both avoid this by giving the compiler a function that actually takes your type, so no conversion happens. The difference is that with overloading you write one function per type by hand, and with a template the compiler writes them for you, on demand.

7.template <typename T>

To finish the job you prepend one line:

Definition— function template

A function template is a pattern from which the compiler generates real functions. You write it by putting a template header in front of an ordinary function definition:

template <typename T>
void printInput(T x) {
    cout << x << endl;
}

template <typename T> introduces T as a type parameter: a name that stands for a type not yet chosen. Inside the function, T may be used anywhere a type name may be used — parameter types, the return type, local declarations, new T[n].

The keyword class is an accepted synonym for typename in this position:

template <class T>
void printInput(T x) {
    cout << x << endl;
}

template <typename T> and template <class T> mean exactly the same thing. It is purely a matter of personal taste. (typename reads better, because T is very often not a class — T = int is completely normal.) The professor's exam rubrics use template <typename T>; write that and you will never have to think about it again.

Key Idea

A template is not a function. It is a prescription for writing a function. Nothing is compiled from a template until somebody names a type for T; at that moment the compiler generates the code for a real C++ function with that type substituted throughout, and compiles that. Ten different Ts in your program means ten real functions in the executable. Zero uses means zero functions — a template you never call generates no code at all.

The generation is called instantiation, and it happens on demand, per type, at compile time.

So printInput<int>(n) says: take the prescription, put int everywhere T appears, and call the resulting function. What gets compiled is exactly

void printInput(int x) {
    cout << x << endl;
}

— the first of the three overloads from §6, written by the compiler instead of by you. That equivalence is the single most useful mental model in this topic, and §9 turns it into a test you can apply.

8.Deduction versus explicit template arguments

You have now seen both call forms. It is worth being precise about when each is required, because the professor's exam drivers always use the explicit form, while ordinary C++ code usually does not.

Definition— template argument deduction

Template argument deduction is the compiler working out what T must be by matching the types of the arguments you passed against the types of the parameters in the template. If the match is unambiguous, you never have to write <T> at all.

printInput(s);          // s is a string  ->  T = string
printInput<string>(s);  // the same call, with T stated

Both forms produce identical code. The second one is what the exams show you, so learn to read it; the first is what you will write in practice.

Deduction handles references and pointers too, without you doing anything special. Here are the professor's two variants:

The lecture handout states that we must always specify a data type to use a templated function and that we cannot call the templated function "as is" in programming code. Taken literally that is not true, and §7's program proves it: printInput(n) with no <int> compiles and runs.

Write explicit arguments on this professor's exams, since every one of his drivers does (reverse<int>(a,5), contain<string>(vs,ts)) and his rubrics pay for the <T> syntax. Use deduction everywhere else.

9.When T does not cooperate

A template body makes demands on T. cout << x demands that T can be streamed. a + b demands an operator+. T sum; demands a default constructor. Nothing in template <typename T> restricts what T may be, so those demands are not checked when you write the template — they are checked when you instantiate it, against the actual type.

Key Idea— the test to apply before you call a template

Would the code compile if you wrote ordinary, non-templated code with MyClass written in place of T everywhere?

If yes, the template call compiles. If no, it does not. That is not an analogy — it is literally what the compiler generates. Every requirement a template imposes on T can be found by doing the substitution on paper and reading the result as ordinary C++.

So for printInput<MyClass>(m), the generated function is void printInput(MyClass x) { cout << x << endl; }, and reading that as ordinary C++ tells you two things immediately: MyClass needs a public copy constructor (the parameter is by value, so the argument gets copied), and operator<< must be overloaded for MyClass or the cout line is meaningless. The copy constructor may be the compiler-generated one or one you wrote, but it must be public.

Break the second requirement and you meet the thing templates are notorious for.

Money has all four, so it works. And here is the design point the handout is reaching for and never quite states: the default constructor must produce something that behaves like zero. Money() : cents(0) does. If Money's default constructor left cents uninitialized, or set it to 100, sumArray would return a wrong answer with no error anywhere. What "an empty object" means depends entirely on the class, and only the class's author can decide it.

The last line, sumArray(5, ai) with no <int>, deduces T = int from the array's element type — and prints 15, same as the explicit call.

Key Idea— the closing line of the lecture

Not everything can be templated. A template is only as general as the operations its body uses. Write a + b and you have restricted T to types with an operator+; write T sum = T(); and you have restricted it to types with an accessible default constructor. There is no way to be generic and assume nothing — the body always demands something. The skill is knowing what your body demands, so you can say so in the documentation instead of leaving your users to discover it in 231 lines of error output.

int main() {

}

Plan. Reversing in place means swapping the outermost pair, then the next pair in, and stopping in the middle. Element i pairs with element size - i - 1, and the loop runs while i < size / 2 — integer division does the right thing for both even and odd sizes, since a middle element in an odd-length array does not need moving. The swap needs a temporary of type T. The function returns nothing; it modifies the caller's array, which works because an array parameter is really a pointer.

reverse_t.cpp
#include <iostream>
#include <string>
using namespace std;

template <typename T>
void reverse(T arr[], int size) {
    for (int i = 0; i < size / 2; ++i) {
        T temp = arr[i];
        arr[i] = arr[size - i - 1];
        arr[size - i - 1] = temp;
    }
}

int main() {
    int a[5] = {1, 2, 3, 4, 5};
    string b[2] = {"Hello", "Bye"};

    reverse<int>(a, 5);
    reverse<string>(b, 2);

    for (int i = 0; i < 5; i++) cout << a[i] << " ";
    cout << endl;
    for (int i = 0; i < 2; i++) cout << b[i] << " ";
    cout << endl;

}

  • Three of the ten points are for the title line alone. template <typename T> on its own line, then void reverse(T arr[], int size). Write that first, even if the body then goes wrong.
  • T arr[] has no const, unlike sumArray. This function modifies the array, so a const parameter would be a compile error. Deciding const or not is part of designing the signature.
  • The rubric accepts a second answer that copies into a temporary array:

    T *temp = new T[size];

Lecture Summary
  • An abstract class is one you cannot create objects of. You may declare pointers and references to it — they are not objects — and that is the whole point: library code takes Base * or Base & and works with derived classes written years later.
  • A pure virtual function is declared virtual T f() = 0; and has no body anywhere. One of them makes the class abstract.
  • Trying to create the object gives "cannot declare variable 'x' to be of abstract type 'C'", and the note: lines name the pure virtual that is still unimplemented.
  • A derived class that fails to override every inherited pure virtual is itself abstract. This is the single most-tested idea on this professor's finals. Build the table: one column per pure virtual, one row per class.
  • For a virtual call, the version that wins is the one in the nearest ancestor that defines it, which may be several levels up — and may be the base's own version, so a class can print a name that is not its own.
  • An abstract class with nothing but pure virtuals is C++'s version of a Java interface. There is no interface keyword and no implements; you just inherit publicly.
  • The alternative technique is protected constructors: no = 0 anywhere, derived classes are forced to override nothing, and outside code gets "'C::C()' is protected within this context". Constructors protected, never private; destructor public and virtual. It buys flexibility and pays for it with sentinel values that fail at run time instead of compile time.
  • A function template is written template <typename T> (or template <class T>, identical) in front of an ordinary function. It is not a function; it is a prescription from which the compiler instantiates a real function, on demand, once per type used.
  • f(x) deduces T from the argument types; f<int>(x) states it explicitly. Deduction never converts, so mixed argument types fail with "deduced conflicting types for parameter 'T'" — name T yourself to fix it. This professor's exam drivers always use the explicit form.
  • Not every int becomes T. Counts, indexes and "is it there" answers stay int and bool; only quantities that really have the element's type become T.
  • Ask of any template call: would this compile if I wrote the type name in place of T everywhere? That is literally what the compiler generates, and it tells you what T must provide — a public copy constructor, operator+, operator<<, a default constructor for T sum = T();, and so on.
  • Template errors are long. Find required from here: the line above names the instantiation, the line below is the real error, and the other 200 lines are the compiler listing every candidate it rejected.
  • Not everything can be templated — a template is only as general as the operations its body performs.
