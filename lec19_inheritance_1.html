1.The problem: two classes, one body of code

Classes 9 through 18 gave you one class at a time. You can build a type, initialize it, copy it, destroy it and overload its operators. What you cannot yet do is say that one of your types is a kind of another one — and that turns out to be the single most common relationship between real types.

As the professor puts it: "as with much else in object-oriented programming, we observe the fundamental concepts all around us in everyday life." You can motivate inheritance without mentioning a computer at all. Take rectangles and squares:

  1. Every square is a rectangle.
  2. Every square has — inherits — all the properties of a rectangle. It has a height, a width, an area, a perimeter.
  3. A square also has specialized properties that not all rectangles share. It has an edge length, a single number that describes it completely.
  4. A square is therefore a specialization of the parent, or base case, of a rectangle.

Now write those two ideas as two independent C++ classes and watch what happens.

Worked Example— the duplication you are trying to avoid

Two classes, written the way you would have written them in Class 10. Before you open the toggle, count how many lines of Square are character-for-character identical to a line of Rectangle.

dupe.cpp
// dupe.cpp -- the problem inheritance solves: one class copy-pasted into another
#include <iostream>
using namespace std;

class Rectangle {
public:
    void set(double ht, double wd) { h = ht; w = wd; }
    double height() const    { return h; }
    double width() const     { return w; }
    double area() const      { return h * w; }
    double perimeter() const { return 2 * (h + w); }
    void print() const {
        cout << "Rectangle " << w << " x " << h << ", area " << area() << endl;
    }
private:
    double h, w;
};

class Square {
public:
    void set(double e)       { h = e; w = e; }
    double height() const    { return h; }        // copied
    double width() const     { return w; }        // copied
    double area() const      { return h * w; }    // copied
    double perimeter() const { return 2 * (h + w); }  // copied
    double edge() const      { return h; }        // new
    void print() const {
        cout << "Square edge " << h << ", area " << area() << endl;
    }
private:
    double h, w;
};

int main() {
    Rectangle r;
    r.set(3.0, 4.0);
    r.print();

    Square s;
    s.set(2.5);
    s.print();
    return 0;
}
Rectangle 4 x 3, area 12
Square edge 2.5, area 6.25

Four method bodies plus the two data members are duplicated verbatim. That is not a style complaint — it is a maintenance bomb with a timer on it:

  • Suppose you decide that area() should never return a negative number, so you change it to fabs(h * w). You must remember to change it in both places. Miss one and you have a bug that only shows up for one of the two types.
  • Add a third shape and the copying happens again.
  • Nothing in the code says a square is a rectangle. To the compiler these two classes are as unrelated as string and ifstream. You cannot write a function that accepts "any rectangle" and pass it a square.

Both of those problems have the same fix.

Definition— inheritance, base class, derived class

Inheritance is a mechanism by which one class acquires all the members of another class, and may then add to them or replace some of them.

The class being inherited from is the base class (also called the parent). The class doing the inheriting is the derived class — we say it derives from, or inherits from, the base class.

Inheritance is a computer-science concept, not a C++ feature. It is a major feature of Java, C#, Python and many other languages, and the vocabulary above travels with it.

The relationship does not stop at one level. Step back from rectangles and take polygon as the base case:

  • Every triangle is a polygon.
  • Every rectangle is also a polygon.
  • Every equilateral triangle is a triangle.
  • Every square is a rectangle.
  • However, a rectangle is not a triangle, and a triangle is not a rectangle.

Drawn out, that is a tree: each shape inherits from its parent, and from its parent's parent, and so on up to the root. The tree can go as many levels deep as you like — there is no upper limit — and each branch can have sub-branches.

0 (root)Polygon— nothing

2EquilateralTriangle (under Triangle), Square (under Rectangle)its own parent — and, through it, Polygon
Key Idea

Inheritance buys you two things at once, and you should be able to name both. First, code reuse: the derived class gets the base class's members without retyping them. Second, and more importantly, a modelling claim: the code now states that a square is a kind of rectangle, and the compiler will act on that statement.

Quick Check 19.1

Look again at dupe.cpp above.

(a) If Square were made to inherit from Rectangle, which of its members would you delete outright?

Everything that was copied: height(), width(), area(), perimeter(), and the data members h and w. Six members gone.

What survives is exactly the part that is special about squares: edge(), the one-argument set(), and a print() that says "Square" instead of "Rectangle". That is the shape a good derived class has — small, and made only of the differences.

(b) Name one bug that the duplicated version makes possible and the inherited version does not.

Any change applied to one copy and not the other. Concretely: change Rectangle::area() to fabs(h * w) so it copes with negative sides, forget Square::area(), and now Rectangle and Square disagree about what "area" means. Nothing in the program flags it; the two functions were never connected in the first place.

With inheritance there is only one area() in the program. There is nothing to keep in sync, because there is nothing to sync with.

(c) Give a pair of classes from earlier in this course that are not in an inheritance relationship, and say why not.

Point and Rectangle from Classes 9 and 13, for example. A rectangle is not "a kind of point" and a point is not "a kind of rectangle" — a rectangle might well have a corner point, which is a different relationship entirely (§4).

The test to apply is the English sentence. If "every X is a Y" is true and useful, inheritance is on the table. If it reads as nonsense, it is not.

2.The syntax: class B : public A

The professor introduces the syntax on the smallest possible example: a class with four methods and no data at all. Here it is on its own first, so that the output of the next program has something to be compared with.

Worked Example— the base class A, by itself

Four public methods, no data members. Nothing here is new; predict the four lines anyway, because the next program looks almost identical and prints something different.

classa.cpp
// classa.cpp -- the base class A on its own
#include <iostream>
#include <string>
using namespace std;

class A {
public:
    string name() const { return "class is A"; }
    void f1() const { cout << "A::f1" << endl; }
    void f2() const { cout << "A::f2" << endl; }
    void f3() const { cout << "A::f3" << endl; }
};

int main() {
    A a;
    cout << a.name() << endl;
    a.f1();
    a.f2();
    a.f3();
    return 0;
}

Each call goes to the only place it could go. Keep this output on screen; the interesting part is which of these four lines survives in the next program.

Now derive a second class from it. The syntax is one clause bolted onto the class head:

class B : public A {
public:
    string name() const { return "class is B"; }
    void f1() const { cout << "B::f1" << endl; }
};

Read : public A out loud as "which inherits publicly from A". Three statements are now true, and all three are worth saying separately:

  1. B is a derived class of A; B derives from A.
  2. A is the base class of B; A is the parent of B.
  3. B has access to all the public members of A as if they were members of B itself — just as a square has all the properties of a rectangle.

The word public in that clause is doing real work; there are two other spellings (protected and private inheritance) and they mean different things. They are rare, and they are Class 21's business. For this course, when you write a base-specifier you write public. Leave it out of a class and you silently get private inheritance, which is almost never what you meant.

Worked Example— four calls on a B object

This is the same main as before with A a; changed to B b;. B declares only two of the four methods. Write down all four lines you expect before opening the toggle — especially the last two.

Two small housekeeping points about this listing, since it is the pattern for everything that follows. All four methods are marked const, because none of them changes the object — the same rule you have applied to accessors since Class 10, and it applies to inherited and overriding methods just as much. And an overriding method should print in exactly the same style as the one it replaces: B::f1 here, matching A::f1, not B :: f1. When a trace question asks you for the exact output, spacing inside the string literal is part of the answer.

Quick Check 19.2

Using the classes A and B above:

(a) Which class is the base class, which is the derived class, and which one has more members?

A is the base class (the parent); B is the derived class.

B has more members. This trips people up, because B's declaration is shorter. A derived class is written smaller and is bigger: it has all four methods (two of its own, two inherited) where A has four, and as soon as it declares a data member of its own it occupies more memory too. Inheritance only ever adds.

(b) Can an object of type A call B's version of f1()?

No. Inheritance runs one way only. B knows about A; A has never heard of B and was compiled without any knowledge that B would ever exist.

Concretely, A a; a.f1(); prints A::f1, and there is no spelling of that call that reaches B::f1. The base class is the general case; it cannot depend on its own specializations.

(c) B declares no data members and no methods called f2 or f3. Is B therefore the same type as A?

No. A and B are two distinct types, related by inheritance. A function declared as void g(B x) will not accept an A; the compiler rejects it, because an A is not a B. (The reverse direction — handing a B to something expecting an A — is allowed, and it is exactly the topic of Class 21.)

"Same members" never means "same type" in C++. Two classes with identical bodies and different names are still two types.

What is inherited, and what is not

The short answer is: everything, except four things. A derived class inherits every data member and every member function of its base — public, protected and even private ones (they are there, occupying memory, they are just not reachable; see §6). What it does not inherit is:

Not inheritedWhy not, and what happens instead
The base class's constructorsA constructor's job is to build an object of its own class. The derived class gets its own constructors — either ones you write, or a compiler-generated default. Class 20 shows how a derived constructor asks the base constructor to run.
The base class's destructorSame reason. The derived class gets its own, and the base destructor still runs automatically as part of destroying the base part — again, Class 20.
The base class's assignment operatorThe compiler declares a fresh operator= for the derived class, which hides the inherited one. This is the derived-class end of the Big Three, and it is Class 20's material.
FriendshipA friend of the base is not a friend of the derived class. Friendship is granted to a named function or class, and it is not passed down.
Worked Example— constructors really are not inherited

Rectangle has a two-argument constructor. Square derives from it and declares nothing at all. Does Square s2(2.0, 2.0); compile?

Quick Check 19.3

A base class Widget has: a public method run(), a private data member int serial, a public non-default constructor Widget(int), a destructor, and a public operator=. A class Gadget : public Widget declares nothing except a public method calibrate().

(a) How many methods can you call on a Gadget object from main?

Three, in the sense of ordinary named methods: calibrate() (its own), run() (inherited and public), and assignment through operator= — but the operator= being called is the compiler-generated Gadget one, which copies the base part by calling Widget::operator= underneath.

You cannot call Widget(int) on a Gadget, and you cannot touch serial from anywhere outside Widget.

(b) Does a Gadget object contain the member serial? Can calibrate() read it?

Yes, and no. Every Gadget physically contains a serial — it is part of the Widget sub-object and it takes up space. But it is private to Widget, so Gadget::calibrate() cannot name it. It exists and is untouchable.

This is the situation the professor calls "terribly inconvenient for an inherited class", and it is what protected is designed to fix (§7).

(c) Does Gadget g; compile?

No. Gadget gets a compiler-generated default constructor, and that constructor must build the Widget part — but Widget declares a non-default constructor and therefore has no default constructor at all (Class 13's rule: write any constructor and the free one disappears). So there is nothing for Gadget's default constructor to call, and it is rejected.

3.What a derived object actually contains

The professor's question at this point is exactly the right one: "What exactly does the class B consist of?" The answer is the thing that makes inheritance more than a copy-paste shortcut.

Definition— IS-A and the base sub-object

Many textbooks use the IS-A buzzword to express the concept of inheritance: a Square IS-A Rectangle, a B IS-A A.

What that means in C++ is concrete, not poetic. An object of the derived class implicitly contains an object of the base class. That contained piece is called the base sub-object, and:

object of class B  =  the A component  +  the B component

In practice, for the simple single inheritance we use in this course, the compiler lays the base part out first and adds the derived class's extra members after it.

The professor is emphatic that this is not a metaphor: "This is not just symbolic… There really is a base class object implicitly inside a derived class object." Two consequences follow, and you can observe both.

Worked Example— measuring the base sub-object

Base holds two ints; Derived adds a third. Predict the three sizes, then predict which of the two show methods can see which members.

subobject.cpp
// subobject.cpp -- a derived object physically contains a base object
#include <iostream>
using namespace std;

class Base {
public:
    void showBase() const { cout << "base part: " << b1 << " " << b2 << endl; }
    int b1, b2;
};

class Derived : public Base {
public:
    void showAll() const {
        cout << "derived part: " << d1 << ", base part: " << b1 << " " << b2 << endl;
    }
    int d1;
};

int main() {
    cout << "sizeof(Base)    = " << sizeof(Base) << endl;
    cout << "sizeof(Derived) = " << sizeof(Derived) << endl;
    cout << "sizeof(int)     = " << sizeof(int) << endl;

    Derived d;
    d.b1 = 10;      // inherited from Base
    d.b2 = 20;      // inherited from Base
    d.d1 = 30;      // Derived's own
    d.showBase();   // inherited method, sees only the base part
    d.showAll();    // Derived's own method, sees everything
    return 0;
}

sizeof(Derived) = 12
sizeof(int)     = 4
base part: 10 20
derived part: 30, base part: 10 20

A Derived is exactly a Base plus one more int: 8 + 4 = 12. Here is the memory picture, which is worth drawing on paper once so it sticks:

Byte offsetMemberBelongs toReachable from
0–3b1the Base sub-objectBase's methods, Derived's methods, and (because it is public here) main
4–7b2Base's methods, Derived's methods, main
8–11d1the Derived partDerived's methods and main — not Base's methods

Look hard at the last column. showBase() was compiled as part of Base, long before Derived was written, so it can only see the first eight bytes. It is not that it refuses to print d1; the name d1 does not exist in the scope it was compiled in. That asymmetry — the derived class sees the whole object, the base class sees only its own part — is the structural fact behind everything in this class and the next two.

Warning— "base first" is what compilers do, not what the standard promises

The course notes state that "when the compiler allocates memory for an object of the class B, it first allocates memory for an object of the class A, then adds on whatever extra memory is required." For simple single inheritance with no virtual functions, that is exactly what g++ does, and the byte offsets above confirm it.

It is worth knowing that the C++ standard does not guarantee that layout in general. With multiple base classes (Class 21) or virtual functions (Class 24, where the compiler also slips a hidden pointer into every object) the picture gets more complicated and sizeof(Derived) stops being a simple sum. Do not write code that depends on the offsets; do keep the mental picture, because it explains the behavior you will actually see.

The other consequence is about construction. If a B object contains an A object, something has to build that A. It does: the compiler invokes A's constructor first, then B's. In classb.cpp neither class had a constructor, so the compiler generated defaults for both and called them in that order — silently, because they printed nothing. Class 20 opens by making them print, which turns this claim into something you can watch happen.

Quick Check 19.4

Given these declarations:

class Animal {
public:
    void breathe() const;
private:
    double weight;
    int    age;
};

class Bird : public Animal {
public:
    void fly() const;
private:
    double wingspan;
};

(a) On a machine where double is 8 bytes and int is 4, what would you expect sizeof(Animal) and sizeof(Bird) to be?

sizeof(Animal) is 16: 8 for the double, 4 for the int, and 4 bytes of padding so that the whole thing stays 8-byte aligned. sizeof(Bird) is 24: the 16-byte Animal sub-object plus 8 for wingspan.

Padding is the reason to say "expect" rather than "is". The point of the question is the structure — a Bird is an Animal with something appended — not the arithmetic.

(b) Can Animal::breathe() read wingspan? Can Bird::fly() read age?

breathe() cannot read wingspan, for two independent reasons: wingspan is private to Bird, and in any case Animal was compiled with no knowledge that Bird exists.

fly() also cannot read age — but for a different and much more fixable reason. The member is right there inside every Bird; it is only the private label that stops the derived class. Change that label to protected and fly() can read it. That is §7.

(c) Is it true that "a Bird object contains an Animal object"? Is the reverse true?

The first is true, and literally so: bytes 0 through 15 of every Bird are an Animal. That is the base sub-object.

The reverse is false. An Animal object is 16 bytes and contains no Bird, no wingspan, and no way of reaching either. Every bird is an animal; not every animal is a bird. The English sentence and the memory layout agree, which is the whole reason IS-A is a useful test.

4.IS-A or HAS-A? Inheritance versus composition

Inheritance is not the only way two classes can be related, and choosing it when you should not is the most common design mistake in an object-oriented program. The alternative has its own buzzword.

Definition— HAS-A (composition)

HAS-A indicates that a class has a data member of another class type. This is called composition, and it is not inheritance.

If Owner has a data member of type Cat and one of type Dog, we say Owner HAS-A Cat and Owner HAS-A Dog. Nothing is inherited; Owner simply contains two objects.

Worked Example— composition, in full

The course notes give this one as a sketch with the bodies left out. Here it is filled in and running. Read the private section of Owner first — that is where the relationship lives.

hasa.cpp
// hasa.cpp -- composition: an Owner HAS-A Cat and HAS-A Dog
#include <iostream>
#include <string>
using namespace std;

class Cat {
public:
    void setName(const string &n) { name = n; }
    void speak() const { cout << name << " says meow" << endl; }
private:
    string name;
};

class Dog {
public:
    void setName(const string &n) { name = n; }
    void speak() const { cout << name << " says woof" << endl; }
private:
    string name;
};

class Owner {
public:
    void set(const string &who, const string &catName, const string &dogName) {
        person = who;
        c.setName(catName);
        d.setName(dogName);
    }
    void morning() const {
        cout << person << " feeds the pets:" << endl;
        c.speak();
        d.speak();
    }
private:
    string person;
    Cat c;      // Owner HAS-A Cat
    Dog d;      // Owner HAS-A Dog
};

int main() {
    Owner o;
    o.set("Maria", "Mochi", "Rex");
    o.morning();
    return 0;
}
Maria feeds the pets:
Mochi says meow
Rex says woof

Three things distinguish this from inheritance, and all three are visible in the source:

  • There is no : in any class head. Composition is expressed entirely by declaring data members.
  • Owner cannot call speak() as if it were its own method. It has to say which pet: c.speak(), d.speak(). With inheritance the inherited method is called with no object in front of it at all.
  • Owner can hold two Cats, or a vector<Cat>, or swap one out at run time. Inheritance gives you exactly one base sub-object, fixed at compile time.

Note also that Owner goes through Cat's public interface exactly like any other outside code. Being the containing class buys no special access — Owner cannot read Cat::name directly any more than main can.

Procedure— deciding between inheritance and composition
  1. Write the English sentence both ways: "every X is a Y" and "every X has a Y". Say them out loud. Usually one of them is obviously silly.
  2. Apply the substitution test: anywhere the program uses a Y, could you hand it an X and have every promise Y makes still hold? If yes, IS-A. If you find even one method of Y that makes no sense on an X, it is not IS-A.
  3. Count the members you would inherit and actually want. If a derived class inherits fifteen methods and only three of them are meaningful, you have picked the wrong relationship.
  4. When both readings seem defensible, prefer composition. It is the looser coupling: a data member can be replaced, held more than once, or dropped, and the containing class is not committed to anyone else's interface.
Common Mistake— inheriting because it is convenient

Each of these compiles perfectly and each is wrong:

  • class Car : public Engine — written because a car needs the engine's start() and rpm(). But a car is not a kind of engine. Give Car an Engine data member instead, and it can then have two of them, or none.
  • class Owner : public Cat — the owner would inherit speak() and start meowing. Absurd, and the compiler will not stop you.
  • class Stack : public vector<int> — the classic. A stack promises that you can only touch the top; vector hands the outside world operator[], insert and erase, so your stack is now a stack that anybody can reach into the middle of. The substitution test catches this one: code that expects a vector may legitimately insert in the middle, which breaks every promise Stack was written to make.

The tell is always the same. You reached for inheritance because you wanted the methods, not because the sentence "X is a Y" was true.

Quick Check 19.5

For each pair, say whether the relationship is IS-A, HAS-A, or neither, and give the C++ that expresses it.

(a) Rectangle and Point (a rectangle knows the coordinates of its lower-left corner).

HAS-A. A rectangle is not a kind of point — it has a corner that happens to be one.

class Rectangle {
    // ...
private:
    Point corner;      // Rectangle HAS-A Point
    double h, w;
};

Try the substitution test on the inheritance reading and it collapses immediately: anywhere the program expects a point — say, to compute the distance between two points — handing it a rectangle is meaningless.

(b) SavingsAccount and Account.

IS-A. Every savings account is an account: it has a balance, it accepts deposits and withdrawals, and it adds an interest rate on top.

class SavingsAccount : public Account {
public:
    void addInterest();
protected:
    double rate;
};

The substitution test passes: anywhere the bank's software handles "an account" — printing a statement, taking a deposit — a savings account behaves correctly.

(c) Course and Student (a course has a roster of enrolled students).

HAS-A — and note the multiplicity, which is the giveaway. A course has many students:

class Course {
    // ...
private:
    string title;
    vector<Student> roster;    // Course HAS-A (many) Student
};

Inheritance can never express "many". A derived class has exactly one base sub-object of each base class. Whenever the English sentence contains a number other than one, the answer is composition.

(d) Square and Circle.

Neither. A square is not a circle, a circle is not a square, and neither contains the other. They are siblings: both are shapes.

The right move, if you need to treat them uniformly, is to give them a common base class — class Square : public Shape and class Circle : public Shape. That is the standard shape of a hierarchy, and it is exactly the structure the polymorphism questions on this professor's finals are built on (Class 24).

5.Overriding, and how the compiler resolves a call

In §2 the class B declared its own name() and f1(), and those won over A's versions. That has a name.

Definition— override

When a derived class declares a method with the same name and parameter list as one in its base class, we say the derived method overrides the base method. For an object of the derived class, the derived version is the one that runs.

In the classes A and B: B overrides name() and f1(), and does not override f2() and f3(). Overriding is opt-in, one method at a time.

Now make the hierarchy deeper, which is where the rule gets interesting. The professor's example has five classes:

  • A is the base.
  • B derives from A.
  • C and D both derive from B.
  • E derives directly from A.

Drawn as a table — read the last column as "what is physically inside one object of this class":

Two consequences the professor draws out explicitly. First, each class in the tree is a base class for all the others above it: A is a base class of every other class here, B is the base class of C and D (and has its own base, A), and if some later class F derived from C the chain would be F → C → B → A. Second, C and D know about B and therefore about A; E knows only about A, and knows nothing about B, C or D — and they know nothing about it.

Procedure— how the compiler resolves obj.f()

Given a call obj.f() where obj was declared to be of class X:

  1. Look for f in the declaration of X. If it is there, that is the one. Stop.
  2. Otherwise, move to X's base class and look there.
  3. Repeat, walking up the chain one class at a time, until f is found.
  4. If the root is reached and f was never found, it is a compile error — "no member named f".

The search only ever moves along X's own chain. Starting from C the compiler searches C, then B, then A. It will never look in E, or in D, or in any other branch — those classes are not on C's chain, and C has no way of even naming them. The compiler works the structure of the tree out for itself; you never tell it.

Now give C, D and E some overrides and see the rule bite:

There is a word for the decision the compiler just made, and the course notes never say it. It is worth learning now, because in Class 24 you will meet a completely different mechanism described in almost the same words, and students who cannot name the two mechanisms separately mix them up permanently.

Definition— static binding (added — not in the original notes)

Binding is the act of deciding which function body a call will run.

Static binding — also called early binding or compile-time binding — means the decision is made by the compiler, once, while it is compiling the call, using the declared type of the expression to the left of the dot. The finished executable contains a call to one specific function and cannot change its mind.

Every method call you have written so far in this course — including all twenty in tree.cpp — is statically bound. c is declared to be a C, so c.f1() is compiled as a call to B::f1 and stays that way forever.

The alternative is dynamic binding (late binding, run-time binding), where the choice is deferred until the program is running and made from the type of the object that is actually there. C++ gives you that only when you ask for it with the keyword virtual, which is Class 24. Until then, everything is static.

Key Idea

With non-virtual methods, the declared type of the variable decides which function runs — not the object, not the run-time situation, not the call site. Walk the inheritance chain upward from that declared type and take the first match. That single rule answers every "which version runs?" question on this page.

6.private is an absolute lock-out

Up to now every example class in this lecture has had public methods and no data. Real classes are the other way around: private data, public methods. So the questions the professor asks next are the practical ones. How does a derived class access data members in a parent class? What about private data? Private methods?

Take the running example. Rectangle stores its height and width the way Class 10 taught you — privately — and Square derives from it and wants its edge length, which is just the height under another name.

Everything here is legal-looking. Square IS-A Rectangle, every Square object physically contains an h, and edge() only wants to read it. Does it compile?

  • A derived class cannot access private data and methods.
  • It does not matter that a Square IS-A Rectangle.
  • It does not matter that a Square object implicitly contains a Rectangle object.
  • The keyword private is an absolute lock-out: nothing outside of a class can access its private data and methods. The only way in is through public accessor and mutator methods.
  • The same applies to private methods. A private helper function in the base is uncallable from the derived class.

Notice the exact wording of the error: "is private within this context". The member h exists, the compiler found it, and it knows the type. It refused on access grounds alone. That is a different failure from "has no member named h", and telling the two apart tells you whether your problem is spelling or permissions.

There is a workaround, and it is the one Class 10 would have you use: go through the public interface. double edge() const { return height(); } compiles and works. But look at what it costs. Square is family — it is made of a Rectangle — and it is being made to knock on the front door like a stranger. Worse, a derived class that needs to modify the base's data is stuck entirely unless the base happens to provide a public mutator, and adding a public mutator hands that power to every other line of code in the program too.

The professor's verdict: "This situation is terribly inconvenient for an inherited class. By definition, an inherited class is related to the base class and would like to use its data and methods." The keyword protected is designed to remedy this situation.

Quick Check 19.9

A base class Timer has a private data member int seconds;, a public method int get() const, and a private helper void tick();. A class Stopwatch : public Timer is being written.

(a) Which of seconds, get() and tick() can a method of Stopwatch name?

Only get(). Both seconds and tick() are private to Timer, and private excludes derived classes just as firmly as it excludes main.

Every Stopwatch object still contains a seconds. It just cannot say the word.

(b) Stopwatch needs to reset the count to zero. Give two ways to make that possible, and say which you would choose.

Option 1 — add a public mutator to Timer: void reset() { seconds = 0; }. Now Stopwatch can call it — and so can every other piece of code in the program, including code that has no business resetting a timer.

Option 2 — change seconds from private to protected: now Stopwatch can write seconds = 0; directly, and main still cannot touch it.

Which to choose depends on whether resetting is part of what a timer publicly is. If it is, option 1 is better design: it is a real operation with a name, and the base class stays in control of its own data. If the derived class needs raw access for reasons the base class knows nothing about, option 2 is what protected exists for. §7 argues that option 1 should be your default.

7.protected, and when not to use it

Definition— the access specifier protected

A member declared protected is accessible to the class itself and to every class derived from it, but not to anyone else.

The three properties to memorize, in the professor's own order:

  1. Derived classes have access to all the protected data and methods.
  2. Outside applications cannot access protected data and methods.
  3. Effectively, protected means — (a) private to the outside world, and (b) public to derived classes.

Protected members are visible to all the classes above the declaring class in the inheritance tree, however deep. A class can reach every protected member down its whole inheritance chain, not just its immediate parent's.

C++ therefore has exactly three access specifiers, and it is worth having the table in your head as a single picture:

The professor adds a personal note at this point: "Personally, I find the keyword protected to be much more useful than private." Warning— protected data reopens the hole private closed

Class 10 argued that data should be private so that the class can enforce its own rules. Every rule you enforce inside a mutator is a rule that protected data lets a derived class walk straight past — and unlike main, a derived class can be written years later by somebody who never read your base class.

protbreak.cpp
// protbreak.cpp -- protected data lets a derived class break the base class's rules
#include <iostream>
using namespace std;

class Rectangle {
public:
    Rectangle() { h = 1.0; w = 1.0; }
    void setSize(double ht, double wd) {         // the base class checks its inputs
        if (ht <= 0.0 || wd <= 0.0) {
            cout << "Rectangle: refusing a non-positive side" << endl;
            return;
        }
        h = ht;
        w = wd;
    }
    double area() const { return h * w; }
protected:
    double h, w;
};

class Square : public Rectangle {
public:
    void setEdge(double e) { h = e; w = e; }     // no check at all
};

int main() {
    Rectangle r;
    r.setSize(-3.0, 4.0);
    cout << "rectangle area = " << r.area() << endl;

    Square s;
    s.setEdge(-3.0);                              // straight past the check
    cout << "square area    = " << s.area() << endl;
    return 0;
}
Rectangle: refusing a non-positive side
rectangle area = 1
square area    = 9

The Rectangle defended itself. The Square now claims to have an edge of −3 and an area of 9, and every method of Rectangle that assumed positive sides is now working on impossible data.

There is a second cost, less dramatic and more expensive in the long run: a protected data member is part of your class's public promise to every future derived class. You can change a private member's name, type or representation freely, because only your own methods touch it. Change a protected one and you break every class anyone ever derived from yours.

The rule of thumb to leave with: make data private and provide protected methods when a derived class needs controlled access. Reach for protected data when the alternative is genuinely worse — which, in a small class like Rectangle where the derived class is written by the same person on the same day, it sometimes is. This professor's exam questions use protected data freely, so you must be fluent in it; just know what you are trading away.

  • A default constructor and a non-default one, so a Rectangle can be built either way.
  • A destructor that does nothing but announce itself. A class with no dynamic memory does not need a destructor at all; this one exists purely so that you can watch the order of events when a derived class is added.
  • h and w are protected, precisely so that Square can use them.
  • print() is const, as are all three accessors.
Common Mistake— abs on a double, and the missing headers

The original listing of this class writes return abs(h*w); and includes no headers at all — no <iostream>, despite using cout, and no <cmath>, despite using abs. Both are worth fixing rather than copying.

In C++, <cmath> (and, as it happens, <cstdlib>) declares a double overload of abs, so on g++ 13 the original line does compute 6.25 for a 2.5-by-2.5 square. But that is luck, not design. If the only declaration in scope is the C library's int abs(int) — which is what you get from <stdlib.h>, and what happens in plenty of real code bases — then abs(2.5 * 2.5) converts to int, returns 6, and your program is silently, unfixably wrong with no warning of any kind.

Two habits protect you: include the header for every facility you use, and use fabs for floating-point absolute values, where the name itself says "floating". Both are applied in the listing above.

The derived class is where Class 20 picks up. Here is its declaration, exactly as the course notes give it, so you can see the shape of what is coming:

class Square : public Rectangle {

    Square();
    Square(double e, bool c);
    ~Square();
    double edge() const;
    void print() const;

    bool centered;

Read it as a summary of this whole lecture. Square declares five members and gets height(), width(), area(), h and w free. It adds a data member of its own, centered, which is protected so that classes derived from Square can reach it in turn. It adds a method the base class does not have at all — edge(), because a square has an edge length where a rectangle has a height and a width — which is the professor's point that derived classes can declare extra methods that are not in the base class. And it overrides print().

Key Idea— what is still missing

The bodies of those constructors and that destructor are not written here, and you cannot write them yet with what this class has given you. Square() must somehow arrange for the Rectangle part to be built, and Square(double e, bool c) must pass e down to it. There is a specific syntax for that handover, and a fixed order in which the pieces are constructed and destroyed. That is Class 20, and it starts from exactly this declaration.

One further caution to carry forward: Square::print() hides Rectangle::print() rather than overriding it in the polymorphic sense, because neither is declared virtual. For an object declared Square s; that makes no difference — s.print() runs the Square version. It starts to matter the moment a Square is handled through a Rectangle pointer or reference, which is Class 21, and it is fixed with virtual in Class 24.

The class Polynomial below stores coefficients and a degree, and prints itself as a polynomial in x. Implement a Pfunction class that inherits from it, with these requirements:

  • Pfunction has one additional double data member, x.
  • Implement a constructor taking three arguments: the coefficient array, the degree, and the value of x.
  • Override print() so that it replaces the symbol x with the actual value.
const int MAXDEG = 10;

Problem 5 — IS-A and HAS-A in one model (added)

A registrar's office needs three types: an Address (street and city), a Student (name, ID, home address), and a GradStudent, which is a student who also has a thesis advisor and prints itself differently. Decide which relationships are IS-A and which are HAS-A, then write all three classes and a main that prints one of each.

Plan. Say both sentences out loud. "A graduate student is a student" — true, and everything a student can do a graduate student can do, so the substitution test passes: IS-A, inheritance. "A student is an address" — nonsense; "a student has an address" — obviously true: HAS-A, composition. So Address becomes a data member of Student, and GradStudent derives from Student. Student's data is protected because GradStudent::print() needs to read the name and ID.

// prac_student.cpp -- IS-A and HAS-A in one small model

#include <string>

    string street, city;

        cout << endl;

Lecture Summary
  • Inheritance lets one class acquire the members of another. It solves duplicated code, and — more importantly — it lets the program state that one type is a kind of another.
  • The syntax is class Derived : public Base { ... };. Base is the base class or parent; Derived is the derived class. Inheritance forms a tree of any depth.
  • A derived object contains a base sub-object. That is what IS-A means concretely: an object of class B is an A component plus a B component, and for simple single inheritance the compiler lays the base part out first.
  • A derived class inherits every member of the base except its constructors, its destructor, its assignment operator, and its friendships.
  • IS-A means inheritance; HAS-A means a data member of another class type — composition. Test with the English sentence and with substitution, and prefer composition when both readings look plausible.
  • A derived class overrides a method by declaring one with the same name and parameter list. To resolve obj.f() the compiler starts at the declared class of obj and walks up its own chain, taking the first match; it never looks in another branch of the tree.
  • That decision is static binding (early binding): it is made at compile time from the declared type, and cannot change while the program runs. Its opposite, dynamic binding, arrives with virtual in Class 24.
  • A name declared in the derived class hides every base member of that name, including overloads with different parameter lists.
  • private is an absolute lock-out — derived classes are shut out exactly like everyone else. protected means "private to the outside world, public to derived classes", at every depth of the tree.
  • protected data is convenient and is what this course's examples and exams use, but it lets a derived class bypass the base class's own rules and freezes the base's representation. Prefer private data with protected methods when you have the choice.
