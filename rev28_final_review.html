1.What the final actually looks like

This is the last class meeting. The final sits outside the twenty-eight classes, it is cumulative, and it is nothing like a typical multiple-choice final. There is no true/false, no multiple choice, no matching, no vocabulary, and no essay anywhere on it. Every single question is code in, code out: you either write C++ or you say exactly what C++ prints.

That is unusually good news, because it means the exam is predictable. The last four finals given in this course have the same skeleton, in the same order, with only the identifiers changed:

Key Idea— the exam is a known quantity

Four consecutive finals used the same six formats. The class is renamed each term — Box, Circle, MyList, BookShelf — and the templated function is renamed — reverse, merge, contain, findIndex — but the shape does not move. If you can do these six things cold, you can do the final.

How this paper is marked

Knowing the marking rules is worth real points, and they are not symmetric between question types.

Definition— title-line credit

On every write-code question, a fixed chunk of the marks is awarded for the title line alone — the signature, with nothing after it. Writing

template <typename T>
int findIndex(vector<T> x, T target) {

and then freezing is worth 4 points out of 10 on that question. The same rule pays 2 points for Box& operator=(const Box &rhs), 2 points for class SquareBox : public Box {, and — genuinely — 1 point for the closing }; at the end of a class.

Never leave a write-code question blank. Write the signature even if you cannot write the body.

Warning— output prediction has no partial credit

Every rubric in this course says the same thing about the trace questions and the polymorphism question: 2 or 3 points each part, no partial credit. A trace line that is right except for one word scores zero for that line. "Almost" is not a grade band.

The write-code questions are the opposite. Every one of them closes with the sentence "If a program follows a different (but reasonable) plan, try to award partial credit for meeting similar goals in the program." So on those, an imperfect answer that shows the right plan scores well.

The practical consequence for how you spend 100 minutes: be fast and generous on the write-code questions, slow and paranoid on the prediction questions.

Procedure— a 100-minute budget for an 80-point final
  1. 0–5 min. Read all six problems. Find the class in Problem 2 and read its data members — everything in Problems 2, 3 and 4 depends on them.
  2. 5–15 min. Problem 1 (10 pts). The skeleton. It is the easiest ten points on the paper and it is pure recall. Do it first while you are fresh.
  3. 15–40 min. Problem 2 (20 pts). The special members. Biggest single block of points on the paper.
  4. 40–58 min. Problem 3 (15 pts). The derived class.
  5. 58–70 min. Problem 4 (10 pts). The trace. Write one line of output per event, in order, and count your lines — the rubric is one point per line.
  6. 70–82 min. Problem 5 (10 pts). The templated function. Write template <typename T> first, immediately, before you think about the body.
  7. 82–95 min. Problem 6 (15 pts). The polymorphism trace. Build the override table (§4) before you write a single answer.
  8. 95–100 min. Go back and put a signature on anything you left blank.

Notice that the two hardest questions are last, and that they are worth 25 points between them. Do not let Problem 2 eat the hour.

Quick Check 28.1

You have eight minutes left. Problem 5 (the templated function, 10 pts) is completely blank and Problem 6 (the polymorphism trace, 15 pts) has three of its five lines filled in.

(a) Where do the eight minutes go?

Problem 5, and it is not close. Writing

template <typename T>
void reverse(T arr[], int size) {

takes about fifteen seconds and is worth 3 points on its own. Another three minutes of loop-writing very plausibly gets the rest. That is up to 10 points from a standing start.

The two remaining lines of Problem 6 are worth 3 points each, with no partial credit — you either work out the whole override chain or you get nothing. Eight minutes of panicked guessing there has an expected value near zero.

(b) If you truly cannot remember how the body of the templated function goes, is it worth writing anything?

Yes. Write the template <typename T> line and the signature, then write the body as if T were int. A loop that is correct for int and just needs T substituted in one place is a "different but reasonable plan" and attracts substantial partial credit; a blank page attracts none.

This is the single highest-value exam habit in the course: the signature is free money and the plan is worth most of the rest.

Every problem on every final is one of those three ideas wearing a costume.

Quick Check 28.2

Fast recall, spanning the whole course. One line each.

(a) What is the difference between p1 = p2; and *p1 = *p2;?

p1 = p2; copies an address — afterwards both pointers point at the same variable and one of them has abandoned whatever it used to point at. *p1 = *p2; copies a value — the two pointers still point where they always did, and the variable p1 points at has been overwritten.

This is the single most examined distinction in Class 7, and it is the reason a shallow copy is a bug: the compiler-generated copy constructor does the first one when you needed the second.

(b) Name the three members of the Big Three, and the one-sentence rule for when you need them.

The destructor, the copy constructor, and the assignment operator.

The rule: if a class owns memory allocated with new, you must write all three, and writing one of them is a sign you need the other two. The compiler-generated versions copy the pointer rather than what it points at, which gives you two objects sharing one block and two destructors trying to free it.

(c) Box a; Box b = a; — which special member runs on the second line? What about Box a; Box b; b = a;?

Box b = a; is initialization, so the copy constructor runs. The = sign is misleading; b is being born, not being changed.

b = a; on an already-existing b is assignment, so operator= runs.

This distinction is worth two lines of the trace question on every final. Read the line and ask: does the thing on the left already exist? If it is being declared on that same line, it is the copy constructor.

(d) What does virtual change about a call p->f() where p is a Base * pointing at a Derived?

Without virtual, the compiler picks the function from the declared type of p, at compile time — so Base::f runs. That is static binding.

With virtual, the choice is made at run time from the actual object, so Derived::f runs. That is dynamic binding, and it is the whole point of the inheritance machinery.

One sentence to memorize: without virtual the pointer decides; with virtual the object decides.

(e) What makes a class abstract, and what may you still do with an abstract type?

A class is abstract if it has at least one pure virtual function — one declared virtual T f() = 0; — that no one has overridden. You cannot create objects of it.

You may still declare pointers and references to it, and that is exactly what it is for: a function taking Base * works for every derived class, including ones written years later.

The exam consequence, which is worth up to 15 points: a derived class that fails to override an inherited pure virtual is itself still abstract, and declaring an object of it is the ERROR the last question is fishing for.

3.The Big Five, one more time

Problem 2 of the final is worth 20 points, a quarter of the paper, and it is the same question every term. Get this one cold and you have bought yourself twenty points and a lot of calm.

Definition— the Big Five, as this course means it

Class 15 gave you the Big Three — destructor, copy constructor, assignment operator — the three members you must write yourself as soon as a class owns heap memory. The final's Problem 2 asks for those three plus two more:

  1. a non-default constructor that takes the initial data;
  2. the destructor, ~ClassName();
  3. the copy constructor, ClassName(const ClassName &orig), doing a deep copy;
  4. the assignment operator, ClassName& operator=(const ClassName &rhs);
  5. a binary operator+ or operator* returning a new object.

Every one of them must cout a fixed announcement message such as "BookShelf: copy constructor". That is not decoration — it is what makes the Problem 4 trace gradeable, so the exact wording is load-bearing. Copy the string out of the question character for character.

The class you are given always comes in one of two shapes. Either its data is a plain value (three ints in a Box, one double in a Circle) or it is a pointer to a dynamically allocated array (string *items; int size). The pointer version is the one that appears on the recent finals and it is the one worth practicing, because it is the only one where "deep copy" means anything.

Procedure— the six steps of a correct operator=

Write these six lines in this order, every time, without thinking about it:

  1. Signature: ClassName& operator=(const ClassName &rhs) — returns a reference, takes a const reference. (2 points.)
  2. Self-assignment guard: if (this == &rhs) return *this;. (Explicitly paid for in the rubric.)
  3. Copy the size / count member across.
  4. delete [] oldStorage; — release what you already own, before you overwrite the pointer.
  5. new fresh storage of the new size, and copy the elements one by one.
  6. return *this;. (Also explicitly paid for.)

Plus the cout announcement, in the position the question asks for — read that sentence twice, see the warning below.

Worked Example— all five special members, compiled and leak-checked

This is the Summer 2025 final's BookShelf class, completed. The two constructors and display() were printed on the exam paper; everything from ~BookShelf() down is what a student had to write for 20 points. Read the main at the bottom and predict the exact sequence of lines before you open the toggle — that prediction is Problem 4.

bookshelf.cpp
#include <iostream>
#include <string>
using namespace std;

class BookShelf {
public:
    BookShelf(): titles(NULL), count(0) {                    // given on the exam
        cout << "BookShelf: default constructor" << endl;
    }

    BookShelf(const string arr[], int n): titles(new string[n]), count(n) {   // given
        for (int i = 0; i < count; i++) titles[i] = arr[i];
        cout << "BookShelf: non-default constructor" << endl;
    }

    ~BookShelf() {                                           // (a) 3 points
        cout << "BookShelf: destructor" << endl;
        delete [] titles;
    }

    BookShelf(const BookShelf &orig) {                       // (b) 5 points
        cout << "BookShelf: copy constructor" << endl;
        count  = orig.count;
        titles = new string[count];
        for (int i = 0; i < count; i++) titles[i] = orig.titles[i];
    }

    BookShelf& operator=(const BookShelf &rhs) {             // (c) 6 points
        cout << "BookShelf: assignment operation" << endl;
        if (this == &rhs) return *this;
        count = rhs.count;
        delete [] titles;
        titles = new string[count];
        for (int i = 0; i < count; i++) titles[i] = rhs.titles[i];
        return *this;
    }

    BookShelf operator+(const BookShelf &other) {            // (d) 6 points
        cout << "BookShelf: operator+" << endl;
        string *temp = new string[count + other.count];
        for (int i = 0; i < count; i++) temp[i] = titles[i];
        for (int i = 0; i < other.count; i++) temp[count + i] = other.titles[i];
        BookShelf newShelf(temp, count + other.count);
        delete [] temp;
        return newShelf;
    }

    void display() const {                                   // given on the exam
        cout << "BookShelf (" << count << " books): ";
        for (int i = 0; i < count; i++) cout << titles[i] << ", ";
        cout << endl;
    }

protected:
    string *titles;
    int count;
};

int main() {
    string a[2] = {"Dune", "Solaris"};
    string b[1] = {"Emma"};

    BookShelf s1(a, 2);
    BookShelf s2(b, 1);
    BookShelf s3 = s1;          // copy constructor
    s3.display();

    BookShelf s4 = s1 + s2;     // operator+, then copy-initialization
    s4.display();

    s2 = s4;                    // assignment operation
    s2.display();

    return 0;
}

Warning— "as its first instruction" vs "as its last instruction"

Read the wording of each sub-part. The requirement flips between terms:

  • Fall 2023 and Summer 2025 say the message must be the first instruction — so the destructor is cout then delete [].
  • Summer 2024 and Winter 2025 say last — so the destructor is delete [] then cout.

It does not change the printed output of the destructor by itself, but it absolutely changes it in a derived class, where "print the base message first" and "print the derived message first" give different traces. And it is a stated requirement, so the marker can take the point.

The one-word fix: underline the word "first" or "last" in the question before you start writing.

Common Mistake— two errata in the published answer keys

Two of the model answers circulating for this question do not compile, and if you learn them as written you will reproduce the mistake.

The BookShelf copy-constructor key is the wrong class. The Summer 2025 answer key prints, under part (b), an answer belonging to the previous term's MyList question:

    items = new string[size];
    for(int i = 0; i < size; i++) items[i] = orig.items[i];

Quick Check 28.3

A student writes this operator= for the BookShelf class:

BookShelf& operator=(const BookShelf &rhs) {
    cout << "BookShelf: assignment operation" << endl;
    count = rhs.count;
    titles = new string[count];
    for (int i = 0; i < count; i++) titles[i] = rhs.titles[i];
    return *this;
}

(a) Two of the six required elements are missing. Which two, and what does each omission cost at run time?

Missing 1: delete [] titles; before the new. The object's old array is never released; the pointer is simply overwritten. Every assignment to this object leaks its previous contents. The program still runs and still prints the right thing, which is exactly why nobody notices.

Missing 2: if (this == &rhs) return *this;. On its own that is only a wasted copy here — but add the delete [] back in, as you must, and s = s; becomes a disaster: the function frees titles, allocates a new array, then copies from rhs.titles… which is the same pointer it just freed. That is a read of released memory, and the values you copy are garbage.

That is the whole reason the guard exists, and it is why the rubric pays for it as a named line rather than folding it into "correctness."

(b) Why must the return type be BookShelf& and not BookShelf?

So that assignment chains. a = b = c; groups right to left as a = (b = c);, so the inner assignment's result is the right-hand operand of the outer one. Returning by reference hands back the actual object b; returning by value would hand back a temporary copy — an extra copy constructor call and an extra destructor call on the trace, and a subtly different object being assigned from.

It also matters for a legal-but-ugly expression like (a = b).display();, which calls display() on a itself when the return is a reference.

(c) The question says the message must be the object's first instruction. Does putting the cout before the self-assignment guard change any output?

Yes, for the self-assignment case only. With the cout first, s = s; prints BookShelf: assignment operation and then returns immediately. With the guard first, s = s; prints nothing at all.

The exam asks for the message first, so put it first. It is also the more honest behavior: the operator really was called, and the trace should say so.

One more class is worth revisiting here, because it is the one that appears on both problem sets and it is where the deep copy actually bites: Polynomial, which stores its coefficients in a dynamically allocated double array.

Worked Example— Polynomial, and what its print() really produces

The constructor stores coefficients[i] = c[i], so index i holds the coefficient of x to the power i. But print() walks down from degree to 0. Work out what the three print() calls produce before you open the answer — the ordering is the trap.

polynomial.cpp
#include <iostream>
using namespace std;

class Polynomial {
public:
    Polynomial(): coefficients(nullptr), degree(-1) {}

    Polynomial(const double c[], int d): coefficients(new double[d + 1]), degree(d) {
        for (int i = 0; i <= degree; i++) coefficients[i] = c[i];
    }

    ~Polynomial() { delete [] coefficients; }

    Polynomial(const Polynomial &orig) {
        degree = orig.degree;
        coefficients = new double[degree + 1];
        for (int i = 0; i <= degree; i++) coefficients[i] = orig.coefficients[i];
    }

    Polynomial& operator=(const Polynomial &rhs) {
        if (this == &rhs) return *this;
        delete [] coefficients;
        degree = rhs.degree;
        coefficients = new double[degree + 1];
        for (int i = 0; i <= degree; i++) coefficients[i] = rhs.coefficients[i];
        return *this;
    }

    Polynomial operator+(const Polynomial &p) {
        int d = (degree > p.degree) ? degree : p.degree;
        double *sum = new double[d + 1];
        for (int i = 0; i <= d; i++) {
            sum[i] = 0;
            if (i <= degree)   sum[i] += coefficients[i];
            if (i <= p.degree) sum[i] += p.coefficients[i];
        }
        Polynomial result(sum, d);
        delete [] sum;
        return result;
    }

    void print() const {
        for (int i = degree; i > 0; i--)
            cout << coefficients[i] << "*x^" << i << " + ";
        cout << coefficients[0] << endl;
    }

protected:
    double *coefficients;
    int degree;
};

int main() {
    double a1[3] = {1.1, 2.2, 3.3};
    double a2[2] = {2, 1};
    Polynomial p1(a1, 2);
    Polynomial p2(a2, 1);
    p1.print();
    p2.print();
    Polynomial p3 = p1 + p2;
    p3.print();
    return 0;
}

The array {1.1, 2.2, 3.3} reads backwards when printed, because a1[2] is 3.3 and print() starts at index degree. Students routinely write the coefficients out in the order they appear in the literal and lose the whole question.

The middle term of the sum is 2.2 + 1, that is 3.2. And {2, 1} prints as 1*x^1 + 2 — note that 2.0 and 1.0 print with no decimal point at all, the Class 3 rule again.

4.Polymorphism and abstract classes

This is the last problem on every final, it is worth 10 to 15 points, and it is the question students most often leave blank. It looks intimidating — six classes, a two-level inheritance lattice, a function taking a base pointer — and it is actually the most mechanical question on the paper once you know the procedure.

Definition— pure virtual function, abstract class

A pure virtual function is declared with = 0 in place of a body:

    virtual string type() = 0;

It has no implementation anywhere. It says "every concrete class in this family must supply this, and I refuse to guess a default."

A class with at least one pure virtual function that nobody has overridden is abstract. You cannot create an object of it. You can still declare pointers and references to it, and that is the whole point — a function taking Shape * works for any shape, including ones written after that function was compiled.

The rule that the exam turns on: a derived class inherits its base's pure virtual functions, and if it does not override every one of them it is abstract too.

Procedure— answering the polymorphism question in four steps
  1. List the pure virtuals of the base. Usually two. Give each one a column of a table.
  2. One row per class, in inheritance order. In each cell write the class that supplies that function — either this class, or the nearest ancestor that defines it, or a dash if nobody does.
  3. Any row with a dash is abstract. Declaring an object of it is the ERROR the question wants.
  4. For every other row, read the non-virtual print() / display() in the base and substitute the two winning functions. That string is your answer.

The table takes ninety seconds to build and it answers all five parts at once. Building it is the difference between 15 points and 0.

Quick Check 28.6

Using the Shape hierarchy above:

(a) Rectangle is abstract, yet shape_test(Shape *p) takes a pointer to an even more abstract type. Why is that legal?

Because a pointer is not an object. Shape *p is 8 bytes of address; it does not contain a Shape and so nothing has to be constructed. The prohibition is only on creating an object of an abstract type.

This is not a loophole, it is the design. shape_test is written once, against the abstract interface, and works for Circle, Square, Triangle, Polygon, and any shape added next year. Take the parameter by value — void shape_test(Shape p) — and it does not compile at all, for exactly the reason above.

(b) What is the smallest change to Rectangle that makes Rectangle r; legal?

Give it a type():

5.Function templates

Problem 5 of every final is "write a templated function called something". It has appeared five times, and it has been reverse, merge, contain and findIndex. It is worth 10 to 15 points, of which 3 or 4 are for the signature alone.

Definition— function template

A function template is a prescription from which the compiler manufactures a real function, once for each type you use it with. You write it by putting

template <typename T>

in front of an ordinary function and replacing the concrete type with T. (template <class T> means exactly the same thing; typename is the modern spelling.)

The template itself compiles to nothing. reverse<int>(a, 5) causes the compiler to stamp out an int version; reverse<string>(b, 2) stamps out a string version. They are two separate functions in the executable.

Key Idea— the exam's dialect of templates

Three things are true of every templated question this course has ever set, and they narrow the problem a great deal:

  • It is always a function template, never a class template.
  • The driver always calls it with an explicit template argument — contain<string>(vs, ts), not contain(vs, ts) — so you never have to reason about deduction.
  • The parameters are always taken by value in the model answers (vector<T> x), never by const reference. A const reference is better code and will not be penalized, but by value is what the key shows.

And one thing to be careful of: not every int becomes T. An index is an int, a count is an int, "is it there" is a bool. Only the things that genuinely have the element's type become T.

Worked Example— a template over a raw array

The Fall 2023 final asked for a reverse that takes an array of any type and its size and reverses it in place. Predict both the output the exam's own driver produces and the output it claims to produce — they are not the same.

templ_reverse.cpp
#include <iostream>
#include <string>
using namespace std;

template <typename T>
void reverse(T arr[], int size) {
    for (int i = 0; i < size / 2; ++i) {
        T temp = arr[i];
        arr[i] = arr[size - i - 1];
        arr[size - i - 1] = temp;
    }
}

Three points about the template body itself:

  • size / 2 is integer division on purpose. For size = 5 it is 2, so i takes the values 0 and 1 and the middle element (index 2) is left where it is, correctly.
  • T temp = arr[i]; — the temporary must have type T, not int. This is exactly the Class 1 swap, one level more general.
  • T arr[] as a parameter is a pointer; the array is never copied, so the reversal is visible to the caller with no & anywhere. That is why the function can be void.

Things to notice.

  • The forward version is equally acceptable: 
    template <typename T>

    int found = -1;

  3. public: then the non-default constructor, whose base initializer forwards the base's arguments: Library(string s, const string arr[], int k): BookShelf(arr, k) {

6.2 — The trace

Procedure— how to trace a main for points
  1. Go through main one statement at a time, writing the output line or lines for that statement before moving on. Do not try to hold it in your head.
  2. For each declaration, ask which constructor: no arguments means default; arguments means non-default; X b = a; means copy constructor.
  3. For each derived-class construction, write the base's line first, then the derived's. Construction runs base → members → body.
  4. For an assignment a = b; where a already exists, write the operator= line. If a is a base object and b is derived, only the base's operator= runs — that is slicing.
  5. For X d = a + b;, write the operator+ line, then whatever constructor runs inside it. Do not add a copy-constructor line for the return — C++17 elides it.
  6. At the end of main, write the destructor lines in reverse order of construction. For a derived object, derived destructor first, then base.
  7. Count your lines and compare with the point value. Ten points usually means ten lines.

These seven are not on any syllabus topic list, and between them they decide more marks than any single topic on this course. Every one of them is demonstrated below by a program that was actually compiled and run.

Trap 4 — object slicing on base = derived

You saw it in Quick Check 28.10 and it is worth stating flatly: assigning a derived object to a base variable runs the base's operator=, copies only the base part, and prints only the base's message. Three of the four finals put this in the trace question. The tell is a main that declares a base object and a derived object and then assigns one to the other.

The converse, derived = base;, does not compile at all — there is no way to invent the derived class's extra data. Derived-to-base is automatic and lossy; base-to-derived is impossible.

Quick Check 28.12

Six one-line claims. Which are true?

(a) "A class with a virtual destructor cannot be abstract."

False, and the two ideas are almost always found together. Shape in §4 has a virtual destructor and two pure virtuals. A polymorphic base class needs a virtual destructor so that delete through a Shape * runs the derived destructor; being abstract is about pure virtuals. Different questions entirely.

(b) "delete [] on a null pointer crashes."

False. Deleting a null pointer is a guaranteed no-op. That is what makes BookShelf(): titles(NULL), count(0) safe to destroy, and it is why p = nullptr; immediately after a delete defuses a double delete.

(c) "The copy constructor's parameter could be passed by value if you wanted."

False, and not just as a style matter — it does not compile. Passing by value means making a copy, and making a copy means calling the copy constructor, which needs to make a copy… The parameter must be a reference, and it should be const so the constructor can also copy from a temporary or a const object.

(d) "A derived class inherits its base's constructors."

False. Constructors, the destructor, operator= and friendships are the four things a derived class does not inherit. What it does instead is call the base constructor, through the base initializer : Box(size, size, size). If you name none, the base's default constructor runs — and if the base has no default constructor, that is a compile error.

(e) "template <class T> and template <typename T> mean different things."

False in this context — they are interchangeable for a type parameter, and T can still be int or double when you write class. Use typename; it reads better and it is what the modern style guides say.

(f) "On this final, a blank answer and a wrong answer score the same."

True for the output-prediction questions (Problems 4 and 6): no partial credit either way, so a guess costs nothing and might win.

False for every write-code question (Problems 1, 2, 3 and 5). A blank scores zero; a signature alone scores 2 to 4 points; a signature plus a reasonable plan scores most of the marks. This asymmetry is the single most useful thing on this page.

Things to notice. Put together, the two halves give one strategy: on a prediction question, always write something, because there is no penalty. On a write-code question, always write the signature, because it is worth real points on its own. Never hand in a blank box.

Problem 1 — Complete the code skeleton [10 points, ~10 min] (from the Summer 2025 Final)

Given the following code skeleton in C++, complete the code by performing the tasks written in the comments.

#include <iostream>
#include <string>
using namespace std;

int main() {
    string course = "OOP in C++";
    int grades[5] = {78, 85, 92, 88, 96};

    /* Task 1: Pointer Declaration [2 pts]
       - Create a pointer pCourse that points to 'course'
       - Create a pointer pGrades that points to 'grades'
    */

    /* Task 2: Single Value Dynamic Allocation [2 pts]
       - Create a dynamic variable dynCourse that copies the value from pCourse
    */

    /* Task 3: Array Dynamic Allocation [4 pts]
       - Create a dynamic array dynGrades that copies values from pGrades
    */

    /* Task 4: Memory Management [2 pts]
       - Properly delete all dynamically allocated memory
    */

    return 0;
}

Plan. Four tasks, and the only one with any subtlety is Task 1. course is a string variable, so you need its address: &course. grades is an array, and an array name already is a pointer to its first element, so you must not write &grades. That distinction — &name for a variable, bare name for an array — is explicitly graded, one point each.

Task 2 is two statements, not one: allocate, then copy. Task 3 is an allocation plus a loop — dynGrades = pGrades; would copy the address, not the values, and score nothing. Task 4 needs delete for the single object and delete [] for the array; using the wrong form is a real bug, not a style point.

skeleton.cpp
#include <iostream>
#include <string>
using namespace std;

int main() {
    string course = "OOP in C++";
    int grades[5] = {78, 85, 92, 88, 96};

    // Task 1
    string *pCourse = &course;                             // 1 point
    int *pGrades = grades;                                 // 1 point

    // Task 2
    string *dynCourse = new string;                        // 1 point
    *dynCourse = *pCourse;                                 // 1 point

    // Task 3
    int *dynGrades = new int[5];                           // 2 points
    for (int i = 0; i < 5; i++) dynGrades[i] = pGrades[i]; // 2 points

    // proof that the copies really happened
    cout << *dynCourse << endl;
    for (int i = 0; i < 5; i++) cout << dynGrades[i] << " ";
    cout << endl;

    // Task 4
    delete dynCourse;                                      // 1 point
    delete [] dynGrades;                                   // 1 point

    return 0;
}

Things to notice.

  • string *dynCourse = new string; then *dynCourse = *pCourse; is two statements because the rubric pays for two. You could write string *dynCourse = new string(*pCourse); in one line and it is better code — but on this question, write it the long way and collect both points.
  • delete dynCourse; has no brackets and delete [] dynGrades; does. Mixing them up is undefined behavior, not a warning. One new form, one matching delete form, always.
  • The word "copies" in Tasks 2 and 3 is doing real work. Both tasks are asking you to prove you know the difference between copying a pointer and copying what it points at — the Class 7 distinction, and the same one that makes a deep copy necessary in Problem 2.
  • This exact question, with the identifiers changed, has been Problem 1 of four consecutive finals. It is the cheapest ten points on the paper.

Problem 2 — Implement the special members [20 points, ~25 min] (from the Winter 2025 Final)

Given the following program with a MyList class:

#include <iostream>
using namespace std;

class MyList {
public:
    MyList(): items(nullptr), size(0) {
        cout << "MyList: default constructor" << endl;
    }

    MyList(const string s[], int n): items(new string[n]), size(n) {
        for (int i = 0; i < size; i++) items[i] = s[i];
        cout << "MyList: non-default constructor" << endl;
    }

    void print() const {
        cout << "MyList (" << size << " items): ";
        for (int i = 0; i < size; i++) cout << items[i] << ", ";
        cout << endl;
    }
    // destructor, copy constructor, assignment operation,
    // and operator+ overloading omitted here

protected:
    string *items;
    int size;
};

(a) Implement a destructor that prints "MyList: destructor" as its last instruction. [3 points]

The class owns one new string[n] array, so the destructor releases it — and because the message must be last, the delete [] comes first.

    ~MyList() {
        delete [] items;
        cout << "MyList: destructor" << endl;
    }

delete [] items; on the nullptr left by the default constructor is a guaranteed no-op, so no guard is needed. The brackets are not optional: delete items; on an array allocated with new[] is undefined behavior.

(b) Implement a copy constructor that does a deep copy and prints "MyList: copy constructor" as its last instruction. [5 points]

    MyList(const MyList &orig) {
        size = orig.size;
        items = new string[size];
        for (int i = 0; i < size; i++) items[i] = orig.items[i];
        cout << "MyList: copy constructor" << endl;
    }

Three things earn the five points: the signature MyList(const MyList &orig) with const and a reference; the fresh new string[size], which is what makes the copy deep; and the element-by-element loop. Leave out the allocation and you have written the compiler's shallow copy by hand, which means two objects pointing at one array and two destructors freeing it.

Note there is no delete [] here. The object is being born; it does not own anything yet, so there is nothing to release. That is the one structural difference between a copy constructor and an operator=.

(c) Implement an assignment operation that prints "MyList: assignment operation" as its last instruction. [6 points]

    MyList& operator=(const MyList &rhs) {
        if (this == &rhs) return *this;
        size = rhs.size;
        delete [] items;
        items = new string[size];
        for (int i = 0; i < size; i++) items[i] = rhs.items[i];
        cout << "MyList: assignment operation" << endl;
        return *this;
    }

All six required elements, in order: the reference return type, the const reference parameter, the self-assignment guard, the release of the old array, the fresh allocation with the copy loop, and return *this;. The rubric names the guard and the return *this; individually.

Because the message must be last, self-assignment now prints nothing at all — the guard returns before the cout is reached. That is a legitimate consequence of the wording, and it is why you underline "first" or "last" before you start writing.

(d) Implement operator+ overloading that adds a string item to the list and returns the result as a new MyList, printing "MyList: operator+" as its last instruction. [6 points]

Plan. The right operand is a string, not a MyList — read the requirement carefully. Build a scratch array one element longer, copy the existing items in, put the new item at the end, hand the scratch array to the two-argument constructor, and release the scratch.

    MyList operator+(const string &newItem) {
        string *temp = new string[size + 1];
        for (int i = 0; i < size; i++) temp[i] = items[i];
        temp[size] = newItem;
        MyList newList(temp, size + 1);
        delete [] temp;
        cout << "MyList: operator+" << endl;
        return newList;
    }

Tested with a small driver:

Things to notice.

  • Two non-default constructor lines before operator+ announces itself: one for m, one for newList built inside the operator. The operator's own message is last because the question said last.
  • The return type is MyList by value. Returning MyList& would be a reference to newList, which is destroyed the instant the function returns.
  • Only two destructor lines, for m and n. newList was moved into n by copy elision and never separately destroyed.
  • delete [] temp; matters. Without it every call to operator+ leaks the scratch array; the program still prints the right answer, which is exactly what makes leaks hard to find.
Warning— three typos in the printed class, and one in the key

The MyList class as printed on the Winter 2025 paper contains three things that do not compile, all reproduced faithfully in the version above only after correction:

  • MyList(): items(null), size(0) — lowercase null is not a C++ keyword. It should be NULL or, better, nullptr.
  • for(int i = 0; i < size; i++) cout << item[i] inside print() — the member is items, not item. The same typo is repeated in the answer key's derived class.
  • sting *items; in the protected section — the type is string.

None of these is the question. Fix them silently in your head and answer what was asked. But do take the general point: the professor is reading your member names against the class declaration, so read his the same way. A string member misspelled sting is caught by the compiler; a logic error is not.

Problem 3 — Implement a derived class [15 points, ~18 min] (from the Winter 2025 Final)

Implement a NameList class that inherits from the MyList class with the following requirements:

  • NameList has one additional variable, name.
  • Implement a non-default constructor that constructs the object and prints the name of the object followed by ": non-default constructor" as its last instruction.
  • Implement a destructor that destroys the object and prints the name of the object followed by ": destructor".
  • Implement a print method similar to MyList's, but with "MyList" replaced by the name of the NameList object.
int main () {
    string s[3] = {"red", "blue", "yellow"};
    NameList clist("Colors", s, 3);     // Colors: non-default constructor
    clist.print();                      // Colors (3 items): red, blue, yellow,
    return 0;
}                                       // Colors: destructor

Plan. Three arguments come in — the name, the array, and the count — and two of them belong to the base. So the constructor forwards them with a base initializer, : MyList(l, k), and keeps only name for itself. The print override copies the base's body and swaps the literal "MyList" for the member name; it can reach items and size directly because the base declared them protected. The destructor prints and does nothing else — the base destructor runs automatically afterwards and does the delete [].

mylist.cpp
class NameList: public MyList {
protected:
    string name;
public:
    NameList(string s, const string l[], int k): MyList(l, k) {
        name = s;
        cout << name << ": non-default constructor" << endl;
    }

    ~NameList() {
        cout << name << ": destructor" << endl;
    }

    void print() const {
        cout << name << " (" << size << " items): ";
        for (int i = 0; i < size; i++) cout << items[i] << ", ";
        cout << endl;
    }
};

Things to notice.

  • Note the two lines the main comment does not mention: MyList: non-default constructor at the start and MyList: destructor at the end. Base first on the way in, base last on the way out. The exam's comments only show the derived class's own messages, which is exactly the omission Problem 4 tests you on.
  • name = s; happens in the constructor body, not the initializer list. That is what the published key does and it is fine here. : MyList(l, k), name(s) would be marginally better because it initializes rather than default-constructs-then-assigns, and it is worth knowing that the base initializer and member initializers share one comma-separated list.
  • void print() const — the const must match the base's print() const exactly. Drop it and you have not overridden anything; you have hidden the base version with a different function, and a call through a MyList & would find the base's.
  • name is protected, not private, so a class derived from NameList could still use it. That is the convention this course's exams follow throughout.
  • The published answer key for this question repeats the item[i] typo from the printed class. Write items[i].

Problem 5 — Write a templated function [10 points, ~12 min] (from the Fall 2023 Final; reprinted on the Final Problem Set)

Write a templated function called reverse that takes in an array of any datatype and the array size, and reverses the array entries. For example, a program that uses the function follows:

int main () {
    int a[5] = {1, 2, 3, 4, 5};
    string b[2] = {"Hello", "Bye"};
    reverse<int>(a, 5);
    reverse<string>(b, 2);
    for(int i = 0; i < 5; i++) cout << a[i] << " ";     // print: 5 4 3 2 1
    cout << endl;
    for(int i = 0; i < 2; i++) cout << b[i] << " ";     // print: Bye Hello
    cout << endl;
    return 0;
}

Plan. Swap the ends and work inwards. Element i trades places with element size - i - 1, and you only need to go halfway — going all the way would swap everything back. size / 2 is integer division, so an odd-length array correctly leaves its middle element alone. The temporary must have type T.

templ_reverse.cpp
#include <iostream>
#include <string>
using namespace std;

template <typename T>
void reverse(T arr[], int size) {
    for (int i = 0; i < size / 2; ++i) {
        T temp = arr[i];
        arr[i] = arr[size - i - 1];
        arr[size - i - 1] = temp;
    }
}

int main() {
    int a[5] = {1, 2, 3, 4, 5};
    string b[2] = {"Hello", "Bye"};

    reverse<int>(a, 5);
    reverse<string>(b, 2);

    for (int i = 0; i < 5; i++) cout << a[i] << " ";
    cout << endl;
    for (int i = 0; i < 2; i++) cout << b[i] << " ";
    cout << endl;
    return 0;
}

Bye Hello

An equally acceptable answer, and the second one the key offers, copies the array and reads it back in reverse:

template <typename T>
void reverse(T arr[], int size) {
    T *temp = new T[size];
    for (int i = 0; i < size; i++) temp[i] = arr[i];
    for (int i = 0; i < size; i++) arr[i] = temp[size - i - 1];
    delete [] temp;
}

Where the 10 points come from: 3 for the title line — that is template <typename T> plus void reverse(T arr[], int size) — and 7 for correctly reversing the array.

Things to notice.

  • The exam's own driver starts its print loops at i = 1, which skips element 0 and makes the real output 4 3 2 1 and Hello — not what its comments claim. The loops above are corrected to start at 0. If a question ever asks you what a printed driver outputs, answer what the code does, not what the comment says.
  • T arr[] is a pointer parameter, so the array is not copied and the reversal is visible in main with no & anywhere. That is also why size has to be passed separately: an array parameter does not carry its own length.
  • The second version allocates with new T[size] and must delete [] temp;. Forget that line and every call leaks. The in-place version has nothing to leak, which is a real argument for preferring it.
  • reverse<int>(a, 5) states the type explicitly. The compiler could deduce it here, but every driver on every paper in this course writes it out, so write it out.
  • The standard library has its own std::reverse in <algorithm>. Because of using namespace std;, naming yours reverse too can produce an ambiguity in a larger program. The explicit reverse<int>(...) at the call site is what keeps this one unambiguous.

Problem 6 — Polymorphism trace [15 points, ~18 min] (from the Summer 2025 Final)

Consider the following C++ program. What output will the program print for each of the following lines? If a line causes a compiler or run-time error, write ERROR, then comment out the line and proceed to the next line.

class Shape {
public:
    Shape() {}
    Shape(const Shape &orig) {}
    Shape& operator=(const Shape &rhs) { return *this; }
    virtual ~Shape() {}
    virtual string type() = 0;
    virtual double area() = 0;
    void display() { cout << type() << ": " << area() << endl; }
};

class Rectangle: public Shape {
public:  double area() { return 4.0; }
};

public:  string type() { return "Circle"; }

Things to notice.

  • Square: 4, not Square: 4.0. Rectangle::area() returns the double 4.0, and cout with no formatting instructions drops the trailing zero and the decimal point entirely. One character, three points, no partial credit. This is the Class 3 rule deciding the last question of the final.
  • Rectangle is the trap, and it is deliberately the first line so that a student who does not build the table starts by writing Rectangle: 4 and never recovers. It overrode area(), which makes it look finished; the function nobody supplied is type().
  • Square and Triangle each define only type() and inherit their area() — from Rectangle and Circle respectively. The two virtual calls inside display() are resolved independently, so the two halves of a printed line routinely come from different classes.
  • The real compiler error, if you leave Rectangle r; in, is "cannot declare variable 'r' to be of abstract type 'Rectangle'", and the note: lines name Shape::type() as the reason. That is the same reasoning as your table, done by g++.
  • display() is not virtual, and it does not need to be: it is the fixed part of the behavior, calling the two varying parts. Writing the invariant once in the base and letting pure virtuals fill in the blanks is the whole design pattern this question is built on — and it is the thing from this course you are most likely to use again.
Lecture Summary
  • The final is 80 points, six problems, and the six formats have not changed across four consecutive papers: complete the skeleton, implement the special members, implement a derived class, trace the program, write a templated function, trace the polymorphism.
  • Write-code questions pay for the signature alone — 2 to 4 points for a title line, 1 point for the closing }; — and their rubrics explicitly award partial credit for a reasonable plan. Output-prediction questions give no partial credit at all. Never leave a box empty either way.
  • Everything on the paper rests on three ideas: a pointer to memory you allocated, a class that owns that memory, and a base-class handle to a derived object. Pointers and dynamic memory appear on ten papers out of ten; the copy constructor and operator= on nine.
  • Four topics have never been examined in this course — file I/O, static members, friend functions and recursion — and the STL has never been examined past vector and string. Revise accordingly, and learn them anyway for what comes next.
  • The Big Five: non-default constructor, destructor, deep-copy copy constructor, operator= with if (this == &rhs) return *this; and return *this;, and a binary operator+ returning by value. Announce each one with the exact message the question printed, in the position it asked for — first or last instruction.
  • A class with an unoverridden pure virtual is abstract and cannot be instantiated. Build the table: one column per pure virtual, one row per class, the nearest supplying ancestor in each cell. Any empty cell is an ERROR, and the two virtual calls in one printed line are resolved independently.
  • Function templates only. template <typename T> in front of an ordinary function; parameters by value; explicit template arguments at the call site. An index stays int, a yes/no answer stays bool; only real quantities become T.
  • Construction runs base, then members in declaration order, then the body; destruction is the exact mirror. X b = a; is the copy constructor, b = a; is operator=, and X d = a + b; elides the copy entirely so there is no extra copy-constructor line.
  • Object slicing: base = derived; runs the base's operator=, copies the base part, prints one line, and quietly drops the rest. It appears in three of the four finals.
  • The traps that cost the most: increment side effects carried into the next line; break versus continue; size() printed next to back(); slicing; construction order and the elided temporary; the abstract class hiding two levels down; and cout printing 4.0 as 4.

That is the semester. You started in Class 1 with a program that printed the area of a circle, and you finish able to write a class that owns memory and cleans up after itself, build a hierarchy of types that behave correctly through a base pointer, and write one function that works for every type there will ever be. That is not a small distance to have covered in twenty-eight meetings.

For the final: work the practice final above under time, then go back and re-work Problems 2, 3 and 4 with a different class of your own invention — a Playlist, a Roster, anything that owns a new[] array. If you can write the Big Five for a class you made up yesterday, the one on the exam paper holds no surprises.

And after the final: everything here is the foundation of what comes next. The Big Three become smart pointers and move semantics; the abstract base class becomes the interface at the heart of every large C++ system you will ever read; templates become the STL you met in Class 27 and, from there, the algorithms and data structures course.
