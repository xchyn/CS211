Operator Overloading I — Member and Free Functions

Why p1 + p2 is a function call, how to write that function, and the one decision — class method or free function — that everything else in operator overloading turns on.

Learning Objectives

By the end of today's class you should be able to:

  1. Explain why P1plus(P1plus(p1, p2), p3) is a bad design and what writing p1 + p2 + p3 instead actually buys you.
  2. Read operator+ as what it is — an ordinary function with an unusual name — and name its operands and its return type.
  3. Write a binary operator for a class of your own as a free (non-member) function.
  4. Write the same operator as a class method, and say why the parameter count drops by exactly one.
  5. Explain why p * 2.0 can be a method but 2.0 * p cannot, and write the free function that repairs the asymmetry.
  6. Write unary operators in both forms, and say how the compiler tells unary - from binary -.
  7. State which operators cannot be overloaded, and why you can neither invent a new operator nor change precedence.
  8. Decide whether an overloaded operator should return by value or by reference, and predict the failure when you get that wrong.

1.Functions that do arithmetic but don't look like it

You already know how to write a function that adds two objects. Take the Point1 class you have been carrying since Class 9 — two private double members, a set, two accessors and a print — and write a function that produces the point whose coordinates are the sums of two other points' coordinates. Worked Example— adding points with named functions

Two ordinary free functions, P1plus and P1minus, plus a main that uses them. The last two statements in main are the interesting part: they each add three points, grouped two different ways. Work out all four lines of output before you open the toggle.

p1funcs.cpp
// p1funcs.cpp -- adding Point1 objects with ordinary named functions
#include <iostream>
using namespace std;

class Point1 {
public:
    Point1() { x = 0.0; y = 0.0; }
    Point1(double a, double b) { x = a; y = b; }

    void set(const double &a, const double &b) {
        x = a;
        y = b;
    }
    double getx() const { return x; }
    double gety() const { return y; }
    void print() const {
        cout << "print x,y " << x << " " << y << endl;
    }
private:
    double x, y;
};

Point1 P1plus(const Point1 &u, const Point1 &v) {
    double xsum = u.getx() + v.getx();
    double ysum = u.gety() + v.gety();
    Point1 p;
    p.set(xsum, ysum);
    return p;
}

Point1 P1minus(const Point1 &u, const Point1 &v) {
    double xdiff = u.getx() - v.getx();
    double ydiff = u.gety() - v.gety();
    Point1 p;
    p.set(xdiff, ydiff);
    return p;
}

int main() {
    Point1 p1, p2, p3;
    p1.set(4.4, 3.3);
    p2.set(2.2, 1.1);
    p3.set(0.4, 0.5);

    Point1 pa = P1plus(p1, p2);
    Point1 pb = P1minus(p1, p2);
    pa.print();
    pb.print();

    Point1 p123a = P1plus(P1plus(p1, p2), p3);
    Point1 p123b = P1plus(p1, P1plus(p2, p3));
    p123a.print();
    p123b.print();

    return 0;
}
print x,y 6.6 4.4
print x,y 2.2 2.2
print x,y 7 4.9
print x,y 7 4.9

The arithmetic is exactly what you would expect: 4.4 + 2.2 is 6.6, 3.3 + 1.1 is 4.4, and both three-point sums come out to (7, 4.9) — addition doesn't care how you group it, so the two nested calls agree.

The code, on the other hand, is a mess. Read the two nested calls out loud:

Point1 p123a = P1plus(P1plus(p1, p2), p3);
Point1 p123b = P1plus(p1, P1plus(p2, p3));

The professor's own comment on this slide is blunt: "The expressions to add three objects p1 + p2 + p3 are particularly ugly." And then: "Although it works, it is a bad software design."

Why is it bad, specifically? Because the notation has stopped matching the idea. The idea is arithmetic. The notation is nested function calls, in which the operands drift further and further from the operation as the expression grows. Four points would give you P1plus(P1plus(P1plus(p1, p2), p3), p4) — five tokens of punctuation before you reach the first thing being added. Every reader of that line has to unpick the parentheses to recover a meaning they would have grasped instantly from p1 + p2 + p3 + p4.

Notice too that we have already been forced into a second design decision that nobody asked for. Suppose we also want to scale a point by a number, the way you would multiply a vector by a scalar. Now there are two operations, not one:

Point1 pc = c1 * p1;      // number on the left, point on the right
Point1 pd = p2 * c2;      // point on the left, number on the right

To a mathematician those are the same thing. To the compiler they are not, and the professor is explicit about it: "To the compiler, these are distinct operations because the operands are different. The compiler does not automatically know they are equal." Hold on to that sentence. It is the whole of §7.

Quick Check 17.1

Stay with P1plus and P1minus for a moment.

(a) Using only those two functions, write the statement that computes (p1 + p2) - (p3 + p1) and stores it in a Point1 called pz.

Point1 pz = P1minus(P1plus(p1, p2), P1plus(p3, p1));

Count what you had to do to write that: decide the outermost operation first, then work inward, then match up three pairs of parentheses. The mathematical expression it encodes is eleven characters long.

(b) P1plus takes its parameters as const Point1 &. What would go wrong if it took them as plain Point1 instead — and what would go wrong if it took them as plain Point1 &?

Plain Point1 (by value): nothing breaks, but every call copies both objects. For a two-double class that is cheap; for a class holding a dynamically allocated array it means two full deep copies per addition, and (as Class 14 showed) it means the copy constructor runs twice on every call. Passing by const reference avoids all of it.

Plain Point1 & (non-const reference): this one actually breaks. A non-const reference cannot bind to a temporary, and P1plus(p1, p2) is a temporary the moment you try to feed it into another P1plus. So the nested call in the program above would stop compiling. We will see the exact error message in §3 — it is worth recognizing, because the same trap catches people writing operators.

The rule that comes out of this, and it holds for the rest of the semester: an operand you only read should be a const reference.

2.operator+ is a function name

Here is the idea that fixes everything above, and it is smaller than it looks. C++ lets you choose a function's name from a short list of symbols instead of from the usual alphabet of identifiers. If you name your function operator+, then the compiler will call it whenever it sees a + between two things of the types your function accepts.

Definition— operator overloading

Operator overloading is defining what a built-in operator symbol means when at least one of its operands is an object of a class you wrote. You do it by writing a function whose name is the keyword operator followed immediately by the operator's symbol — operator+, operator-, operator*, operator==, operator=.

The professor's phrasing: "As well as writing functions, C++ permits us to write operators." That is true, but it slightly undersells how mechanical the trick is. You are not writing a new kind of thing. You are writing an ordinary function with a strange name, and the compiler agrees to let you call it with infix notation.

Definition— operand, unary, binary

The input arguments of an operator are called its operands. They are ordinary function parameters; the only difference from a normal call is where they are written. As the professor puts it: "The operator + acts on the operands on its left and its right."

An operator with two operands is binary: a + b, a * b, a == b. An operator with one operand is unary: -a, !a, ++a. Some symbols are both — - is binary in a - b and unary in -a.

Procedure— writing an overloaded operator, in three decisions
  1. The name. Instead of a function name, write the keyword operator and then the operator symbol, with no space between them in the name itself: operator+. (A space before the parenthesis is fine: operator+ (...) and operator+(...) are the same declaration.)
  2. The operands. Decide how many there are and what type each one is. This is just a parameter list. For a binary operator written outside a class, the first parameter is the left operand and the second is the right operand, in that order.
  3. The return type. Decide what the expression a + b should evaluate to, and write that type in front. This is the decision students skip, and it is the one worth thinking about.

The professor asks a good question at this point about step 3: "Is the return type obvious?" Most people's instinct is yes — surely adding two things gives you a thing of the same type. But look at what C++ already does with the + you have used since your first week. It is, in the professor's words, "one of the most heavily overloaded operators. We make use of the overloading all the time without even thinking."

Two of those four rows return a type that is neither operand's type in the naive sense — int + double gives a double. And there are combinations with no answer at all: the professor asks what + returns for a double and a string, and the answer is that the operation simply does not exist. Key Idea

An overloaded operator is a function. Its name happens to be spelled with a symbol, and the compiler happens to let you call it in infix position. Everything you already know about functions — parameters, const references, return types, overload resolution — applies unchanged. When an operator confuses you, rewrite the expression as an explicit function call in your head and the confusion usually evaporates.

Quick Check 17.2

For each expression below, say (i) how many operands the operator has, (ii) what type each operand is, and (iii) what return type is the sensible choice. Assume Point1 is the class from §1 and c is a double.

(a) p1 + p2

Two operands, both Point1. The sensible return type is Point1 — the sum of two points is a point. This is the easy case, and it is the case that makes people believe the return type is always obvious.

(b) c * p1

Two operands: a double on the left and a Point1 on the right. The return type is Point1. Note that the two operand types differ, and that their order is part of the function's identity — operator*(double, const Point1&) and operator*(const Point1&, double) are two different functions, exactly as f(double, int) and f(int, double) would be.

(c) p1 == p2

Two operands, both Point1, and the return type is bool — not Point1. Here the "obvious" instinct fails outright. A comparison answers a question; it does not produce a point.

This is why the professor's summary slide lists the return types separately by family: comparisons return bool; +, - and * typically return an object; operator= returns a reference. You are free to choose, but the choice has to make the expression mean something.

(d) -p1

One operand, of type Point1, returning Point1. This is unary minus, and it is a different function from the binary operator- even though the symbol is the same. The professor's aside is worth repeating: "We do not normally think of the expression −p as an operator, but it is."

The wrap-up for all four parts: the operator symbol alone tells you almost nothing. What identifies the function is the symbol plus the number and types of the operands, in order. That triple is the signature, and overload resolution matches on it exactly the way it does for functions with ordinary names.

3.Operators as free functions

The quickest route to a working operator is to take the free function you already have, and change its name. That is literally all that separates the next listing from §1: P1plus becomes operator+, P1minus becomes operator-. Nothing else about the bodies changes.

Definition— free function

A free function (also called a non-member function) is a function declared outside any class, at namespace scope. It has no this pointer and no automatic access to any class's private members — it reaches an object's data only through that object's public interface, exactly as main does.

An operator written as a free function is a perfectly ordinary free function. When you write p1 + p2, the compiler rewrites it internally as the call operator+(p1, p2).

Its whole body is one line that flips the operands and hands the work to the other operator*. Writing the arithmetic once and delegating is exactly right — if you ever change how scaling works, there is only one place to change it. But it does introduce an ordering dependency, which the next box is about.

Common Mistake— a delegating operator declared too early

operator*(const Point1&, double) calls c * u, which means it needs operator*(double, const Point1&) to already be declared. In the listing above it is — it sits immediately before. Swap the two functions and the program stops compiling, even though not one character inside either body changed:

order_bad.cpp: In function 'Point1 operator*(const Point1&, double)':
order_bad.cpp:16:15: error: no match for 'operator*' (operand types are 'double' and 'const Point1')
   16 |     return (c * u);            // needs operator*(double, const Point1&) -- not yet declared
      |             ~ ^ ~
      |             |   |
      |             |   const Point1
      |             double
order_bad.cpp:15:8: note: candidate: 'Point1 operator*(const Point1&, double)'

This is the ordinary C++ rule that a name must be declared before it is used, not a special operator rule — but it bites harder here because the call site says c * u and does not look like a call to anything. Note the compiler's note: line: the only candidate it could find was the function we are inside, which is a good clue that something above is missing.

If you would rather not depend on listing order, declare both overloads up front (a prototype line each, before either body) and then define them in whatever order you like. That is the same fix you used for mutually recursive functions in Class 2.

Quick Check 17.3

A student drops the two const keywords from the operands of operator+, so it reads Point1 operator+ (Point1 &u, Point1 &v). The line Point1 pa = p1 + p2; still compiles. The line Point1 pe = p1 + p2 + p3; does not.

(a) Why does the three-term version fail when the two-term version succeeds?

p1 + p2 + p3 groups as (p1 + p2) + p3. The inner addition produces a brand-new Point1 that has no name and no home — a temporary. That temporary then has to become the left operand of the outer +.

A non-const reference parameter is a promise that the function might write to the caller's object, so C++ refuses to bind one to a temporary: writing to something that is about to be destroyed is almost certainly a bug, so the language makes it an error. A const reference makes no such promise and binds to temporaries happily.

Here is the real message, and it is worth reading all the way to the last line:

nonconst.cpp: In function 'int main()':
nonconst.cpp:29:25: error: no match for 'operator+' (operand types are 'Point1' and 'Point1')
   29 |     Point1 pe = p1 + p2 + p3;     // p1 + p2 is a temporary
      |                 ~~~~~~~ ^ ~~
nonconst.cpp:16:8: note: candidate: 'Point1 operator+(Point1&, Point1&)' (near match)
nonconst.cpp:16:8: note:   conversion of argument 1 would be ill-formed:
nonconst.cpp:29:20: error: cannot bind non-const lvalue reference of type 'Point1&' to an rvalue of type 'Point1'

"no match for operator+ (operand types are Point1 and Point1)" is a wonderfully unhelpful first line — the types plainly do match. The useful line is the (near match) note, and then "cannot bind non-const lvalue reference ... to an rvalue." When you see that phrase, look for a missing const on a reference parameter.

(b) The same student's operator+ compiles fine on its own. Is there a stronger reason than "temporaries" to mark the operands const?

Yes: it is a statement of intent that the compiler enforces. a + b should not change a or b. Marking the operands const means that if you ever slip and write u.set(...) inside the body, you get a compile error instead of an addition with a side effect — and an addition with a side effect is very close to unfindable, because nobody reading p1 + p2 suspects it.

The same argument produces the const on the method form of these operators in §6. The professor states the principle there: "Unlike the assignment operator=, the operators + and - do not change 'this' object. They create a new object internally and return it as the return value."

Things to notice.

  • The order of the parameters is the meaning. u is the left operand, v is the right one, and u.getx() - v.getx() is subtraction in that order. Swap the two names in the body and p1 - p2 will quietly compute p2 - p1. Nothing warns you; both lines still print numbers.
  • Because the operator is a free function, it can only see x and y through the public accessors getx() and gety(). That is slightly clumsy, and the professor says so directly: "it would be nice if the code for operator+ did not have to use the accessor functions." There are two ways out. One is to make the operator a class method (§6). The other is friend, which Class 18 takes up.
  • You could shorten the body to return Point1(u.getx() - v.getx(), u.gety() - v.gety()); now that the class has a two-argument constructor. That is better modern style. The three-step "make a Point1, set it, return it" shape is kept here because it is the shape the professor's notes use, and it is the shape the exam rubrics reward.

4.Precedence and grouping come for free

Look again at four statements from the program in §3:

Point1 pe = p1 + p2 + p3;
Point1 pf = c1 * p1 * c2;
Point1 pg = p1 + p2*c2;
Point1 ph = c1*(p1 + p2*c2);

We wrote five short functions. At no point did we tell the compiler that * binds tighter than +, or that + groups left to right, or what parentheses do. And yet pg came out as (11, 6.6), which is p1 + (p2 * 3.0) and not (p1 + p2) * 3.0. The professor flags this as the elegant part: "The compiler implements the rules of operator precedence automatically. This is a truly elegant feature of operator overloading."

Key Idea

Precedence and associativity belong to the symbol, not to your function. The compiler parses the expression first, using the same fixed table it uses for int arithmetic, and only then decides which function each operator node calls. You inherit the whole grammar of arithmetic for free — and you cannot change any of it, which is §8's topic.

So p1 + p2*c2 is parsed as p1 + (p2*c2) before the compiler has looked at a single one of your overloads. Then it works outward from the leaves:

StepSub-expressionFunction calledValue
1p2 * c2operator*(const Point1&, double)(6.6, 3.3)
1a  — which delegates tooperator*(double, const Point1&)(6.6, 3.3)
2p1 + (6.6, 3.3)operator+(const Point1&, const Point1&)(11, 6.6)

The professor's question about this slide is "Is this really true? Why?" — and the answer is the one above. It is true because precedence is settled at parse time, by the symbol, before overload resolution ever runs.

(c) Suppose you wanted + to bind more tightly than * for Point1 objects, so that p1 + p2*c2 meant (p1 + p2)*c2. How would you do it?

You cannot. Precedence is fixed by the language and is not part of what an overload can change. If you want (p1 + p2)*c2, you write the parentheses at the call site — and that is a feature, not a limitation.

Things to notice. Imagine the alternative for a moment. If a class could redefine precedence, then the meaning of a + b * c would depend on the types of a, b and c, which are often not visible on the line you are reading. Nobody could parse C++ by eye again. The fixed table is what keeps + and * readable no matter whose class they are acting on, and it is the strongest argument for the rule in §8 that an overloaded operator should do something recognizably like what the symbol already means.

5.Unary operators

Everything so far has been binary. But -p1 is an operator too, and it has exactly one operand. The professor makes the point twice, because students routinely miss it: "A unary operator has only one argument", and "Actually the operator - is both a unary and a binary operator."

As a free function, unary minus is a one-parameter operator-:

Point1 operator- (const Point1 &u) {          // one operand: unary
    double xneg = -u.getx();
    double yneg = -u.gety();
    Point1 p;
    p.set(xneg, yneg);
    return p;
}

That function and the two-parameter operator- from §3 coexist in the same program with the same name. They are ordinary overloads of each other, distinguished by parameter count, and the compiler picks between them the same way it picks between f(int) and f(int, int).

Key Idea

Operand count is part of the signature. The compiler does not decide "is this minus sign unary or binary?" by looking at your functions — it decides from the grammar. In p1 - p2 there is an expression on both sides of the -, so it is binary. In -p1 there is nothing usable on the left, so it is unary. Only then does it look for a matching operator-.

Quick Check 17.6

The program in §3 defines both a one-parameter and a two-parameter operator-.

(a) Which one runs in Point1 pk = p1 - -p2;? Give the value of pk, with p1 = (4.4, 3.3) and p2 = (2.2, 1.1).

Both run. The inner -p2 is unary and produces (−2.2, −1.1). Then p1 - (that) is binary, giving (4.4 − (−2.2), 3.3 − (−1.1)) = (6.6, 4.4).

Note the space in p1 - -p2. Writing p1 --p2 would be read as p1 -- p2 — the decrement operator — and would not compile, because we never overloaded --. When two operator symbols meet, put a space between them.

(b) If you deleted the one-parameter operator- but kept the two-parameter one, would Point1 pj = -p1; compile?

No. The grammar has already decided that this - is unary, so the compiler looks for an operator- taking one Point1 operand, finds only a two-operand one, and reports "no match for operator- (operand type is Point1)". It will not "helpfully" rewrite -p1 as 0 - p1; that would require converting 0 to a Point1, which nothing has told it how to do.

Things to notice. Overloading one form of a symbol never gives you the other for free. If your class wants both a - b and -a, you write two functions. The same is true of +: overloading binary + does not give you unary plus.

6.Operators as class methods

Every operator so far has been a free function sitting outside the class. The alternative is to make it a class method, and this is where the shape of the code changes rather than just its name.

Definition— an operator as a class method

An overloaded operator declared inside a class is a member function like any other. It is called on an object, so the left operand is the object the method is called on — the object this points to (Class 15).

The consequence is the rule the professor states in bold on his slide: "The signature of the binary operators have only one argument. The left operand is 'this object' (of the method)." A binary operator written as a method takes one parameter, not two. A unary operator written as a method takes no parameters at all.

ExpressionAs a free functionAs a class method

That middle column is not pseudo-code. You really can write p1.operator+(p2) and it compiles and means exactly the same as p1 + p2. Nobody writes it that way, but typing it once is the fastest cure for confusion about where the operands went.

Two other things change when the operator moves inside the class. Both are improvements:

  • You get direct access to the private data. Inside a method, x and y mean this object's coordinates, and v.x and v.y mean the parameter's — a class method may reach into the private members of any object of its own class, not just its own. No accessors needed. This is the clumsiness the professor complained about, gone.
  • You mark the method const. a + b must not change a, and a is now the object the method runs on, so the method promises not to modify it. Leave the const off and the operator stops working on const objects — see Quick Check 17.7.

7.2.0 * p: the asymmetry that forces a free function

Now the case that decides the whole method-versus-free question. We want both of these to work:

Point1op pd = p2 * c2;      // object on the left
Point1op pc = c1 * p1;      // number on the left

The first one is a method: the left operand is a Point1op, so it can be p2.operator*(c2). The second one cannot be, and the reason is mechanical rather than deep. A method is called on its left operand. The left operand here is a double. You cannot add a method to double — it is a built-in type, you did not write it, and C++ gives you no way to reopen it.

Key Idea

The professor states the constraint exactly: "The left operand is 'this object' hence only the operator (object * double) can be declared as a class method."

Whenever the left operand of an operator is not an object of your class, that operator must be a free function. There is no other option. This single fact is why operator<< for output must be a free function, which is where Class 18 begins.

So, member or free? Here is the decision, compressed:

Procedure— choosing between a method and a free function
  1. Is the left operand an object of your class? If not — 2.0 * p, cout << p — it must be a free function. Decision made.
  2. Is it an operator the language requires to be a method? =, [], (), -> must be members. Decision made.
  3. Otherwise you may choose. Prefer a method when the operation is intrinsic to the object and wants the private data: +, -, * on two objects of the class, +=, comparisons. You get direct member access for free.
  4. Prefer a free function when you want both operand orders to behave symmetrically, or when the operator is more about the pair than about either object. If the free function needs the private data, Class 18's friend mechanism gives it access.
  5. Never write both for the same pair of operand types. A free operator+(A, A) and a method A::operator+(A) are equally good matches for a + a, and ISO C++ calls that ambiguous. (g++ by default only warns and picks one — see Quick Check 17.8 — which is worse than an error, because the code appears to work.)
Common Mistake— expecting a * b and b * a to be the same function

They never are. The professor said it in the very first slide of this material: "To the compiler, these are distinct operations because the operands are different. The compiler does not automatically know they are equal."

Multiplication being commutative is a fact about numbers, not about C++. If you define only Point1 * double and then hand a student 2.0 * p, they get a compile error and no suggestion of what is wrong. Whenever you overload a symmetric-looking binary operator with mixed operand types, write both orders, and implement one in terms of the other so the arithmetic exists in exactly one place.

8.The limits, and what to return

Operator overloading is generous but not unlimited. Four rules, and none of them is negotiable.

You cannot invent new operators

You may only overload symbols that C++ already has. There is no operator** for exponentiation, because ** is not a C++ token at all — the compiler reads it as * followed by * and gets lost:

newop.cpp:10:17: error: expected initializer before '*' token
   10 | Point1 operator** (const Point1 &u, const Point1 &v) {   // no such operator
      |                 ^

A few operators cannot be overloaded at all

The one the professor names is the dot: you cannot overload the member-selection operator .. Try it and the compiler does not even reach a semantic complaint:

    7 |     Point1 operator. (const Point1 &v) const;    // the dot operator
      |                    ^

The complete list of what you may not touch is short:

Everything else is fair game: + - * / %, the comparisons == != < <= > >=, && and ||, ++ and --, the shifts << and >>, [], (), ->, =, +=, and the rest. The professor points out that you have been relying on one of these all semester: "The widely used expression cout << (something) << endl; is an example of the overloading of the << operator." That is Class 18's subject.

Warning— three slips in the original list, and one real trap

The overloadable-operator slide in the course notes has picked up some damage in reuse, so the corrected version is what appears above. Specifically:

  • It lists "the division operator =". The division operator is /. = is assignment, and it is overloadable too — but as a separate entry.
  • It writes the comparison operators with typeset mathematical symbols for "less than or equal" and "greater than or equal". Those are not C++ tokens; the operators are <= and >=.
  • The sentence introducing the syntax survives a formatting accident as "we write the keyword \operator" and the symbol" — a stray backslash where an opening quotation mark belongs. Read it as the keyword "operator".

And the real trap, which the slide does not mention. && and || can be overloaded, but an overloaded && or || is an ordinary function call, and a function call evaluates all its arguments. You lose short-circuit evaluation, which is the entire reason those operators exist. A line like if (p != nullptr && p->ok()) stops being safe. In practice: do not overload && or ||.

At least one operand must be a class type

You cannot redefine arithmetic on the built-in types. Try to make + on two ints mean multiplication and g++ states the rule outright:

primop.cpp:5:5: error: 'int operator+(int, int)' must have an argument of class or enumerated type
    5 | int operator+ (int a, int b) {      // both operands are built-in
      |     ^~~~~~~~
Key Idea

The professor's summary says "We cannot overload operators to act on primitive data types." That is right, but the compiler's own wording is sharper and easier to apply: an overloaded operator must have at least one parameter of class or enumeration type.

So (double, int) is out, but (Point1, int), (double, Point1) and (Point1, Point1) are all fine — each has at least one operand you defined. The professor's own examples make the same point: "Can overload if one operand is a user-defined class object," giving (object, int) and (double, object).

Precedence, associativity and operand count are fixed

§4 showed you get precedence for free. The other side of that bargain is that you cannot change it. You also cannot change how many operands a symbol takes: + will always be written between its two operands (or before one, for unary plus), never with three. And you cannot change the meaning of an operator on the built-in types, so 3 + 4 is 7 in every program ever written.

The test to apply: does the thing I am returning outlive the function? For operator= the answer is yes — *this is the caller's object. For operator+ it is no, so return by value.

Which of these declarations are legal C++? For the illegal ones, say what rule they break. Vec is a class you wrote.

(a) Vec operator% (const Vec &a, const Vec &b);

Legal. % is a real C++ operator and both operands are class type. Whether it is a good idea is another matter — nobody reading a % b will guess what you meant unless the meaning is close to "remainder".

(b) Vec operator<> (const Vec &a, const Vec &b);

Illegal. <> is not a C++ operator, and you cannot invent one. Only symbols already in the language can be overloaded.

(c) bool operator< (int a, int b);

Illegal. Both operands are built-in types. The compiler says "must have an argument of class or enumerated type." You may not redefine what < means for two ints — and be glad, because if you could, every library you link against might have done so already.

(d) Vec operator+ (const Vec &a, const Vec &b, const Vec &c);

Illegal. + is unary or binary; there is no three-operand form to write a function for, so there is no expression that could ever call this. g++ rejects it with "operator+ must have either zero or one argument" for a member, or "must have either one or two arguments" for a free function.

Things to notice. Group the four rules the parts test: (a) the symbol must exist and (b) you may not create one; (c) at least one operand must be a class or enum type; (d) the operand count is fixed by the symbol. Add "you cannot change precedence" from §4 and you have the complete set of restrictions.

Quick Check 17.12

For each of these, say whether it should return by value or by reference, and why.

(a) Point1 operator+ (const Point1 &u, const Point1 &v)

By value. The sum is a new object created inside the function. Nothing outside owns it, so a reference to it would dangle the instant the function returns.

(b) Point1& Point1::operator= (const Point1 &rhs)

By reference. Assignment modifies an object that already exists and that will still exist after the statement finishes — the caller's left-hand side. Returning *this by reference is safe and it is what lets a = b = c chain. This is the Class 15 pattern; note that returning Point1 by value there would also compile, but would copy the object for no reason on every assignment.

(c) A student proposes Point1& operator+ (...) that returns a reference to u, the left operand, after adding v's coordinates into it. What is wrong?

Two things, and the second is worse than the first.

The mechanical problem: u is a const Point1&, so you cannot modify it, and you cannot return it as a non-const reference. That is a compile error.

The design problem: even if you dropped the const to make it compile, a + b would now change a. Every use of the operator would silently mutate its left operand, so Point1 pe = p1 + p2 + p3; would leave p1 holding the total, and the next line of the program that used p1 would be wrong. That behavior belongs to +=, not to +.

Things to notice. The pattern behind all three parts is a single question: does the operator create a new value, or modify an existing object? Create a new value (+ - * /, comparisons) → return by value, take const operands, mark the method const. Modify an existing object (= += -= ++) → return a reference to it, and do not mark the method const.

// polynomial.cpp -- Fall 2023 Exam 2, the operator+ part, made runnable
#include <iostream>
using namespace std;

class Polynomial {
public:
    Polynomial(double c[], int d) {
        degree = d;
        coefficients = new double[degree+1];
        for (int i = degree; i >= 0; i--) { coefficients[i] = c[i]; }
    }
    ~Polynomial() { delete[] coefficients; }

    Polynomial(const Polynomial &orig) {
        degree = orig.degree;
        coefficients = new double[degree+1];
        for (int i = 0; i <= degree; i++) { coefficients[i] = orig.coefficients[i]; }
    }
    Polynomial& operator= (const Polynomial &rhs) {
        if (this == &rhs) return *this;
        delete[] coefficients;
        degree = rhs.degree;
        coefficients = new double[degree+1];
        for (int i = 0; i <= degree; i++) { coefficients[i] = rhs.coefficients[i]; }
        return *this;
    }

    Polynomial operator+ (const Polynomial &p) const {
        int maxDegree = degree;
        if (maxDegree < p.degree) maxDegree = p.degree;

        double *newCoefficients = new double[maxDegree+1];
        for (int i = 0; i <= maxDegree; i++) {
            double coefficient = 0;
            if (i <= degree)   coefficient += coefficients[i];
            if (i <= p.degree) coefficient += p.coefficients[i];
            newCoefficients[i] = coefficient;
        }

        Polynomial result(newCoefficients, maxDegree);
        delete[] newCoefficients;
        return result;
    }

    void print() const {
        for (int i = degree; i >= 1; i--) {
            cout << coefficients[i] << "*x^" << i << " + ";
        }
        cout << coefficients[0] << endl;
    }

protected:
    double *coefficients;
    int degree;
};

// complexops.cpp -- scaling a complex number from both sides
#include <iostream>
using namespace std;

class Complex {
public:
    Complex() { re = 0.0; im = 0.0; }
    Complex(double a, double b) { re = a; im = b; }

    double getre() const { return re; }
    double getim() const { return im; }

    void print() const {
        cout << re << " + " << im << "i" << endl;
    }

    Complex operator+ (const Complex &other) const {   // method: one parameter
        return Complex(re + other.re, im + other.im);
    }
    Complex operator- () const {                       // unary: no parameter
        return Complex(-re, -im);
    }
    Complex operator* (double s) const {               // Complex * double
        return Complex(re * s, im * s);
    }
private:
    double re, im;
};

// double * Complex -- left operand is not a Complex, so this cannot be a method
Complex operator* (double s, const Complex &c) {
    return c * s;                                      // delegate to the method
}

int main() {
    Complex a(1.5, 2.5), b(3.0, -1.0);

    Complex sum  = a + b;
    Complex left = 2.0 * a;
    Complex right = a * 2.0;
    Complex neg  = -b;
    Complex mix  = 2.0 * a + b * 3.0;

    sum.print();
    left.print();
    right.print();
    neg.print();
    mix.print();
    return 0;
}

3 + 5i
3 + 5i
-3 + 1i
12 + 2i

Things to notice.

  • Three of the four are methods and exactly one is free, and which one is forced entirely by what sits to the left of the symbol. That is the decision procedure of §7, applied mechanically.
  • 2.0 * a and a * 2.0 print the same thing, but they took different routes: the first went through the free function and then into the method, the second went straight to the method. If you had written only the method, the first line would not compile at all.
  • neg.print() shows -3 + 1i, because negating 3.0 - 1.0i gives -3.0 + 1.0i. Any print built by concatenating " + " will render a negative imaginary part awkwardly; fixing that properly means testing the sign, which is a good use for the stream operators in Class 18.
  • 2.0 * a + b * 3.0 needs three operator calls in the right order: both multiplications (precedence) and then the addition. You wrote no code at all to make that ordering happen.
  • The bodies here use return Complex(...) directly rather than the professor's "declare, set, return" shape. Both are correct; the constructor form is shorter and is possible only because the class has a two-argument constructor.
Lecture Summary
  • An overloaded operator is a function whose name is the keyword operator followed by an operator symbol. The compiler rewrites p1 + p2 as a call to operator+. Everything you know about functions still applies.
  • Its inputs are called operands. Two operands means binary, one means unary; - is both, and the two forms are separate overloads.
  • The return type is not obvious and you choose it: an object for + - *, bool for comparisons, a reference for = and <<.
  • As a free function, a binary operator takes two parameters and reaches the object's data through public accessors. As a class method, it takes one — the left operand is the object itself — and it can use the private members directly. A unary operator as a method takes none.
  • Operators that do not change their operands take const reference parameters, and as methods are marked const. Forget it and the operator stops working on const objects.
  • If the left operand is not an object of your class, the operator must be a free function. p * 2.0 can be a method; 2.0 * p cannot. Write both orders, and have one delegate to the other.
  • Precedence, associativity and operand count are fixed by the symbol and come for free — p1 + p2*c2 groups correctly without you doing anything, and you cannot change that grouping.
  • You cannot invent operators (**), cannot overload . .* :: ?: sizeof, and every overload must have at least one operand of class or enumeration type. operator= must be a method; you wrote one in Class 15.
  • Return by value from + - * — the result is a new object, and a reference to it would dangle. Return by reference only when the thing returned outlives the call, as *this does in operator=.
