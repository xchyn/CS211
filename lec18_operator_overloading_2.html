1.Why cout << obj won't just work

In Class 17 you overloaded operator+, operator- and operator* as class methods, and the rule for a binary operator written that way was simple: the left operand is always this object. p1 + p2 compiled down to p1.operator+(p2), and the operator syntax just let you write p1 + p2 instead of that ugly dot-call.

Now think about the single most common line of output code you have written since Class 1:

cout << p1 << endl;

You would like that to work for your own classes the same way it works for int and double. Try the same trick you used for operator+: write operator<< as a method of Point1, and see what actually happens.

Worked Example— operator<< as a member, in the wrong order

Here is operator<< written as a Point1 method, exactly the way you wrote operator+ in Class 17. Predict what the call in main actually does before you open the answer — read it as "ask the object on the left to run its method."

memberorder_works.cpp
#include <iostream>
using namespace std;

class Point1 {
public:
    Point1() : x(0.0), y(0.0) {}
    void set(double a, double b) { x = a; y = b; }
    void operator<<(ostream &os) const { os << "(" << x << ", " << y << ")"; }
private:
    double x, y;
};

int main() {
    Point1 p;
    p.set(3.0, 4.0);
    p << cout;               // legal: p really is the left operand of this member
    cout << endl;
    return 0;
}
(3, 4)

It compiles and runs, because as a member function operator<< really does belong to Point1, and Point1 really is the left operand of << here. p << cout; means exactly what p.set(...) meant: "ask p to run its operator<< method, handing it cout." It just reads backwards from every cout << x; you have ever typed — and backwards is not what you want.

Now try the order you actually want:

    void operator<<(ostream &os) const { os << "(" << x << ", " << y << ")"; }
private:
    double x, y;
};

    Point1 p;
    p.set(3.0, 4.0);
    cout << p;                // the natural order -- does not compile
    return 0;
}

memberorder_fails.cpp:16:10: error: no match for 'operator<<' (operand types are 'std::ostream' {aka 'std::basic_ostream<char>'} and 'Point1')
   16 |     cout << p;                // the natural order -- does not compile
      |     ~~~~ ^~ ~
      |     |       |
      |     |       Point1
      |     std::ostream {aka std::basic_ostream<char>}

cout has type ostream, and ostream is a class from the standard library — you did not write it, and you cannot add a member to it. When the compiler sees cout << p, it looks for a method operator<< belonging to ostream's class that accepts a Point1, and there is no such method. Writing operator<< inside Point1 can never fix this, no matter how you write it, because a method-form operator always belongs to whichever operand sits on the left, and the operand on the left here is cout, not your object.

Key Idea

A binary operator written as a class method always takes its left operand as this. For cout << p1 to call a method, that method would have to belong to ostream. You cannot edit ostream — it lives in the standard library, outside your control. So operator<< (and, for the identical reason, operator>>) for your own class cannot be a method. It has to be a free function, taking both operands as ordinary parameters: the stream on the left, your object on the right.

Definition— insertion and extraction operators

operator<< used with a stream is called the insertion operator — you are inserting a value into the stream. operator>> is the extraction operator — you are extracting a value out of it. The names describe direction, not the arithmetic meaning <</>> have as bit-shift operators on integers; overloading, as you saw in Class 17, lets the same symbol mean something entirely different depending on the types on either side of it.

Common Mistake— a class with no constructor

The Point1 class you built operators for in Class 17 has no constructor: a plain declaration Point1 p1, p2, p3; leaves x and y holding whatever bytes happened to already be there, until set is called. That is exactly the danger Class 13 warned you about. Every Point1 on this page adds a small, deliberate fix, a default constructor:

Point1() : x(0.0), y(0.0) {}

so that a Point1 is well-defined the instant it is created. That matters even more today, because in §3 operator>> is about to read a value from the keyboard straight into an object that might never have been through set at all.

Quick Check 18.1

A Circle class defines void operator<<(ostream &os) const; as a member, exactly like the Point1 example above.

(a) Given Circle c;, which of these two lines compiles: cout << c; or c << cout;? For the one that compiles, describe in words what it actually does.

Only c << cout; compiles. As a member function, operator<< belongs to Circle, so Circle must be the left operand for the call to resolve. c << cout; is really c.operator<<(cout); — "ask c to print itself, handing it cout to print into." cout << c; fails for the same reason cout << p; failed above: the compiler looks for a member operator<< on ostream that takes a Circle, and there is none.

(b) Rewrite the declaration so that cout << c; compiles instead.

Move it out of the class entirely and make it a free function that takes both operands as parameters, with ostream first:

ostream &operator<<(ostream &os, const Circle &c) {
    // print c into os
    return os;
}

This is the whole point of §1: there is no member-function spelling of operator<< that makes cout << c; legal. The fix is always to step outside the class.

2.operator<< as a free function

Definition— the operator<< signature

For a class T, the insertion operator is always written this way:

ostream &operator<<(ostream &os, const T &t);
  • The first parameter, os, is the stream, taken by reference (not const) because inserting into it changes its internal state — and, as you will see in Quick Check 18.2, it could not be taken by value even if you wanted to.
  • The second parameter, t, is your object, taken by const reference: operator<< only reads it, and passing by reference avoids copying the whole object just to print it.
  • The return type is ostream& — a reference to the very stream you were handed. Returning it is what lets cout << p1 << p2; chain, which the next Worked Example proves two ways: once by showing it work, once by showing exactly how it breaks without that return value.
Worked Example— a free operator<<, and why it chains

Same Point1, now with public accessors and a free operator<<. Predict the output, and notice that main chains two insertions and an endl into one statement.

freeinsert.cpp
#include <iostream>
using namespace std;

class Point1 {
public:
    Point1() : x(0.0), y(0.0) {}
    void set(double a, double b) { x = a; y = b; }
    double getx() const { return x; }
    double gety() const { return y; }
private:
    double x, y;
};

ostream &operator<<(ostream &os, const Point1 &p) {
    os << "(" << p.getx() << ", " << p.gety() << ")";
    return os;
}

int main() {
    Point1 p1, p2;
    p1.set(3.0, 4.0);
    p2.set(-1.5, 2.0);
    cout << "p1 = " << p1 << ", p2 = " << p2 << endl;
    return 0;
}
p1 = (3, 4), p2 = (-1.5, 2)

The whole statement is a chain of ordinary binary calls, evaluated left to right, because << is left-associative: cout << "p1 = " returns cout; that result becomes the left operand of the next <<, giving operator<<(cout, p1), which again returns cout; and so on through p2 and endl. There is nothing magic about a "multi-argument cout" — there is exactly one binary operator, applied repeatedly.

This course's own lecture notes ask, about operators in general: "Can the return type be void? Yes. (Try it.)" Let's try it for operator<< specifically — the answer turns out to be more interesting here than it looks.

Worked Example— returning void instead of ostream&

This version compiles: nothing in the language stops you from returning void. Predict whether it still runs correctly used by itself.

voidinsert_works.cpp

Used alone, cout << p1; prints fine. operator<< does not need to return anything in order to run — the return value only matters to whoever wants to do something with the result of the whole expression.

Quick Check 18.2

For each proposed signature of operator<< for a class Fraction, say whether it compiles as a free function and, if it does, whether cout << f1 << f2; still works.

(a) void operator<<(ostream os, const Fraction &f) — note os is taken by value, not by reference.

This does not compile, and not for the reason you might guess first. ostream has no accessible copy constructor — streams represent a real, singular resource (the console, a file), so the standard library deletes their ability to be copied. Trying to pass cout by value produces:

error: use of deleted function 'std::basic_ostream<_CharT, _Traits>::basic_ostream(const std::basic_ostream<_CharT, _Traits>&) [with _CharT = char; _Traits = std::char_traits<char>]'
   17 |     cout << f;
      |             ^
note: declared here
  438 |       basic_ostream(const basic_ostream&) = delete;
      |       ^~~~~~~~~~~~~

This is the deeper reason os is always a reference: it is not just an efficiency choice, it is the only option the language gives you.

(b) ostream &operator<<(ostream &os, Fraction f) — note f is taken by value.

This compiles, and chaining still works, because Fraction (unlike ostream) is an ordinary, copyable class. Every call now makes a full copy of the Fraction argument, which is wasted work for no benefit — operator<< never needs to modify its object. It is a real program, verified below, but it is a style mistake, not an error.

qc_by_value_arg.cpp
#include <iostream>
using namespace std;

class Fraction {
public:
    Fraction() : numerator(0), denominator(1) {}
    void set(int n, int d) { numerator = n; denominator = d; }
    friend ostream &operator<<(ostream &os, Fraction f);   // f taken by value
private:
    int numerator, denominator;
};

ostream &operator<<(ostream &os, Fraction f) {   // a full copy of f is made on every call
    os << f.numerator << "/" << f.denominator;
    return os;
}

int main() {
    Fraction f1, f2;
    f1.set(1, 2);
    f2.set(3, 4);
    cout << f1 << " and " << f2 << endl;
    return 0;
}

3.operator>> and chained input

Definition— the operator>> signature

The extraction operator is operator<<'s mirror image:

istream &operator>>(istream &is, T &t);

Two differences from operator<<, both for the same reason — extraction writes into your object instead of reading it. The stream parameter is istream& instead of ostream&. And the object parameter is a plain reference, T&, not const T& — is >> t.x; assigns into t.x, and you cannot assign into a member of a const reference. The return type is still istream&, for exactly the reason operator<< returns ostream&: so cin >> a >> b; can chain.

Worked Example— operator<< and operator>> together

A complete Point1 with both stream operators. Predict what prints, keeping in mind that this run's input was piped in rather than typed, so you will not see the digits echoed after the prompt.

point1_streams.cpp
#include <iostream>
using namespace std;

class Point1 {
public:
    // Erratum fix: the classic Point1 has no constructor, so x and y are
    // indeterminate until set() is called. Added here (see the box warn in &sect;1).
    Point1() : x(0.0), y(0.0) {}

    void set(double a, double b) { x = a; y = b; }
    void print() const { cout << "print x,y " << x << " " << y << endl; }

    friend ostream &operator<<(ostream &os, const Point1 &p);
    friend istream &operator>>(istream &is, Point1 &p);

private:
    double x, y;
};

ostream &operator<<(ostream &os, const Point1 &p) {
    os << "(" << p.x << ", " << p.y << ")";
    return os;
}

istream &operator>>(istream &is, Point1 &p) {
    is >> p.x >> p.y;
    return is;
}

int main() {
    Point1 a, b;
    a.set(1.5, 2.5);

    cout << "a = " << a << endl;

    cout << "enter a point (x y): ";
    cin >> b;
    cout << "you entered b = " << b << endl;

    cout << "a and b together: " << a << " " << b << endl;
    return 0;
}
a = (1.5, 2.5)
enter a point (x y): you entered b = (9, -3.25)
a and b together: (1.5, 2.5) (9, -3.25)

The input for this run was 9.0 -3.25. is >> p.x >> p.y; chains the same way cout << chains: is >> p.x reads one number and returns is, which becomes the left operand for >> p.y. Notice too that operator>> writes straight into the private members p.x and p.y — legal because it is declared friend, which §5 covers next.

Quick Check 18.4

Suppose someone "fixes" operator>> by making its second parameter const, reasoning that const is always safer:

istream &operator>>(istream &is, const Point1 &p) {
    is >> p.x >> p.y;
    return is;
}

(a) Does this compile? If not, say exactly what goes wrong.

It does not compile. is >> p.x needs to assign the value it reads into p.x, but p is a reference to a const Point1, so p.x is itself const double — a value that cannot be written to. Compiling it for real gives:

constextract.cpp: In function 'std::istream& operator>>(std::istream&, const Point1&)':
constextract.cpp:13:8: error: no match for 'operator>>' (operand types are 'std::istream' {aka 'std::basic_istream<char>'} and 'const double')
   13 |     is >> p.x >> p.y;   // ERROR: cannot write into a member of a const object
      |     ~~ ^~ ~~~
      |     |       |
      |     |       const double
      |     std::istream {aka std::basic_istream<char>}

(b) Why is it correct for operator<<'s object parameter to be const T&, but wrong for operator>>'s?

const on a parameter is a promise: "this function will not modify what you handed it." operator<< keeps that promise — it only reads the object to build text. operator>> cannot keep it: its entire job is to overwrite the object with whatever was just read. Marking that parameter const would be lying to the compiler about what the function does, and the compiler catches the lie the moment the body tries to assign.

Quick Check 18.5

Complete the exercise above, adding operator<< too so the result can be printed back. Show the run for input 3/4 5/8.

Plan. operator>> needs a throwaway char to absorb the /; it is never used again, so its name (slash) just documents intent. Both operators need friend access to numerator and denominator.

fraction_extract.cpp
#include <iostream>
using namespace std;

class Fraction {
public:
    Fraction() : numerator(0), denominator(1) {}

    friend istream &operator>>(istream &is, Fraction &f);
    friend ostream &operator<<(ostream &os, const Fraction &f);

private:
    int numerator, denominator;
};

istream &operator>>(istream &is, Fraction &f) {
    char slash;                       // to consume the "/" between numerator and denominator
    is >> f.numerator >> slash >> f.denominator;
    return is;
}

ostream &operator<<(ostream &os, const Fraction &f) {
    os << f.numerator << "/" << f.denominator;
    return os;
}

int main() {
    Fraction f1, f2;
    cout << "enter two fractions as n/d: ";
    cin >> f1 >> f2;
    cout << "you entered " << f1 << " and " << f2 << endl;
    return 0;
}
enter two fractions as n/d: you entered 3/4 and 5/8

Things to notice. is >> f.numerator >> slash >> f.denominator; is one chained statement reading three tokens: an int, then whatever single non-whitespace character comes next (the /), then another int. cin's default behavior of skipping whitespace before each extraction is what lets 3/4 5/8 (space-separated, no space around the slashes) parse cleanly into two Fractions.

4.The wall: free functions and private data

Section 3's operator>> wrote directly into p.x and p.y. Try that without asking permission first, the way you would have to if Point1's data were private and operator<< were just an ordinary free function with no special standing.

private means "reachable only from a member function of this class." A free function — even one whose entire purpose is to print a Point1 — is not a member of Point1. It is just an ordinary function that happens to take a Point1 as a parameter, exactly as far outside the class as main is. operator<<'s free-function requirement (§1) and encapsulation (Class 1, §6) have collided: the only kind of function that can be cout << p's left-hand operator cannot see the data it needs to print.

You already know one way out: give the class public accessors, as §2's freeinsert.cpp did. That works, and for a class that already has getx()/gety() for other reasons, it is often the simplest choice. But writing accessors just so that one printing function can use them is exactly the situation this course's lecture notes call out about operator+: "the accessor functions getx() and gety() simply return the values… it would be nice if the code for operator+ did not have to use the accessor functions." C++ has a mechanism built specifically for this.

Quick Check 18.6

Two ways exist to fix noaccess.cpp: add getx()/gety() accessors, or grant operator<< friendship.

(a) If Point1 already has public getx() and gety() for other reasons (say, other code needs to read a point's coordinates), which fix has less code to write?

The accessor fix: operator<< just calls the getters that already exist, and nothing about the class declaration has to change.

(b) If Point1 has no other reason to expose x/y — nothing else in the program ever needs to read them — which fix adds less to the class's public interface?

The friend fix. Adding getx()/gety() widens Point1's public interface permanently, for every future piece of code that includes the header — even though the only reason you added them was to satisfy one printing function. friend grants access to exactly that one function and nobody else; the class's public interface stays exactly as small as it was. This is the design question §9 returns to at the end of the class.

5.The friend keyword

Definition— friend

A friend declaration inside a class grants one specific outside function (or every member function of one specific outside class) access to all of this class's private and protected members — data and methods both — exactly as if the friend were a member itself. The friend is still not a member: it has no implicit this for this class, and it is not part of the class's public interface.

Friendship is granted, never taken. Only the class whose data is being protected can write the friend line; a function cannot declare itself a friend of a class it does not belong to.

Worked Example— fixing noaccess.cpp with friend

One line added inside the class is the entire fix. Predict the output.

#include <iostream>
using namespace std;

class Point1 {
public:
    Point1() : x(0.0), y(0.0) {}
    void set(double a, double b) { x = a; y = b; }

    friend ostream &operator<<(ostream &os, const Point1 &p);

private:
    double x, y;
};

ostream &operator<<(ostream &os, const Point1 &p) {
    os << "(" << p.x << ", " << p.y << ")";   // legal now: operator<< is a friend
    return os;
}

int main() {
    Point1 p;
    p.set(3.0, 4.0);
    cout << p << endl;
    return 0;
}
(3, 4)

friend ostream &operator<<(ostream &os, const Point1 &p); inside Point1 looks exactly like the function's own declaration, with the word friend in front. That single line is what turned the private-access error in §4 into working code, without touching operator<<'s body at all.

One quirk worth knowing before you get burned by it: the friend line can go anywhere inside the class — the public section, the private section, the very top, the very bottom. Access is identical either way, because a friend declaration is not itself a member; it is a grant of permission that happens to be written inside the class body.

friend_anywhere.cpp
class Point1 {
    // friend declared in the PRIVATE section, in the MIDDLE of the class --
    // both are perfectly legal. Access is identical either way.
    friend ostream &operator<<(ostream &os, const Point1 &p);

private:
    double x = 1.0, y = 2.0;

public:
    void set(double a, double b) { x = a; y = b; }
};

This compiles and prints (7, 8) for p.set(7.0, 8.0); exactly the same as the more conventionally laid-out version above — there is no rule that friend lines belong at the end, or in public:, or anywhere in particular.

Key Idea— what friendship costs

Friendship is not free. Granting it means the friend function's correctness is now tied to this class's internal representation: if you later change Point1 from two doubles to, say, a std::array<double,2>, every friend that reaches directly into x and y breaks along with the class's own methods. A public accessor insulates outside code from that change; friend does not — it deliberately punches a hole through the insulation. Grant it where the coupling is already tight and permanent (streams are the textbook case: operator<< is called constantly and is logically part of the class's own printing behavior), not as a shortcut to avoid writing a getter.

Quick Check 18.7

A class BankAccount has a private double balance; and a private helper method void logTransaction(double amt); that appends to an internal history. BankAccount grants friend void printReceipt(const BankAccount &a);.

(a) Can printReceipt call logTransaction on the account it is given?

Yes. friend grants access to all private members, methods included, not just data. printReceipt can call a.logTransaction(...) exactly as if it were a member of BankAccount.

(b) A second free function, void printStatement(const BankAccount &a);, is written right next to printReceipt and also touches a.balance directly. Does it compile?

No. Friendship is granted to one named function at a time (or, as §6 covers next, to an entire class at once) — never automatically to "whatever is nearby" or "whatever looks similar." printStatement would need its own friend line inside BankAccount.

6.Friend classes

Definition— friend class

friend class Other; written inside class T grants every member function of Other the same private access to T that an individual friend function would get. It is the bulk version of §5 — useful when two classes are so tightly coupled that most or all of one's methods legitimately need to reach into the other, and writing a separate friend line for each one would be pure repetition.

Worked Example— Dashboard as a friend of Engine

Engine keeps rpm private — nothing outside the car should be able to set it directly — but the Dashboard needs to read it every frame to drive a tachometer needle. Predict the output.

friendclass.cpp
#include <iostream>
using namespace std;

class Engine {

    void setRpm(int r) { rpm = r; }

    friend class Dashboard;   // grants Dashboard access to ALL of Engine's private members

private:
    int rpm;
};

class Dashboard {
public:
    void report(const Engine &e) const {
        // Dashboard reaches directly into Engine's private data -- legal because
        // Engine declared "friend class Dashboard;"

    }
};

int main() {
    Engine e;
    e.setRpm(3200);

    Dashboard d;

Quick Check 18.8

Suppose Dashboard later grows a second method, void warnIfRedline(const Engine &e) const, that also reads e.rpm directly.

(a) Does Engine need to change at all to let the new method compile?

No. friend class Dashboard; already covers every member function Dashboard has now or ever will have. That is the difference from Quick Check 18.7(b): a friend class grant is not tied to one function's name.

(b) A completely unrelated class, Logger, also wants to read e.rpm for a debug printout. Does Logger get access automatically because Dashboard already does?

No. Friendship is never transferred to a third party just because it was granted to someone else — that is the non-transitivity property §8 proves with a real compile error. Logger would need its own friend class Logger; line inside Engine.

7.Granting friendship to one method

A full friend class hands over access to every method of the other class. Sometimes that is more than you want to grant: one particular method needs to write into your private data, and the rest of that class's methods have no business there at all. C++ lets you name a single method as the friend, leaving the rest of its class exactly as locked out as anything else.

Quick Check 18.9

(a) Why does class BFriend; have to appear before class AFriend { ... };, when BFriend is not fully defined until afterward?

AFriend::writeB takes a BFriend& parameter. A reference (or pointer) to a class only needs the compiler to know that the name is a class — it does not need to know the class's size or members, because a reference is just an address under the hood. The forward declaration class BFriend; supplies exactly that much, which is enough to declare (but not yet define) writeB.

(b) Why must AFriend be completely defined before BFriend's friend void AFriend::writeB(...) line, when the reverse ordering (forward-declare, then define later) was fine for BFriend itself?

BFriend's friend line does not just need to know that AFriend exists — it needs to know that AFriend has a member called writeB with exactly that signature, so the compiler can match the friend declaration to the real function. That information only exists once AFriend's full body, including writeB's declaration, has been compiled. A forward declaration alone is not enough for this particular kind of friend grant, which is why the file's order is fixed: forward-declare BFriend, fully define AFriend, then define BFriend.

8.What friendship does not do

Common Mistake— assuming friendship works like other permissions

Three properties of friend are easy to assume and all three are wrong. Friendship is not symmetric: A declaring friend class B; gives B access into A, and says nothing at all about whether A can reach into B. Friendship is not transitive: if B is a friend of A, and C is a friend of B, C gets no access to A — friendship never chains through a middle class. And, looking ahead to Class 19: friendship is not inherited. If a class D derives from B, D does not automatically inherit whatever friendships B was granted; the friend declaration named B specifically, not "B and anything that ever derives from it."

Worked Example— friendship is not symmetric

B declares friend class A;, so A can read B's private data. Predict whether B can read A's private data back.

9.friend vs. a public accessor

You now have two legitimate tools for letting outside code touch private data: a public accessor method, and a friend declaration. Neither one is "the right answer" in general — each costs something different, and a good design picks based on the shape of the problem, not habit.

Key Idea— friend is a scalpel, not a foundation
Favor a public accessor when…Favor friend when…
many unrelated pieces of code need read access, now or laterexactly one function or one tightly related class needs access
you want the freedom to change the internal representation without hunting down every callerthe caller is, conceptually, part of the class's own machinery (operator<</operator>> are the textbook case)
the access pattern is simple (just read a value)the caller needs to touch several private members together, and going through several getters would be clumsy or lose atomicity

When in doubt, start with a public accessor. Reach for friend only when you can name the one specific function or class that needs the exception — if you find yourself friending several unrelated things, that is usually a sign the data should have been public (or the design should be rethought) rather than a sign you need more friend lines.

This course's own exam bank makes the trade-off concrete. One of its questions gives you a Rational class with private numerator/denominator and a set method, and asks you to write a free function product that multiplies two Rationals — using only the public getters getn()/getd(), because the class was never given a friend declaration to work with:

Quick Check 18.12

For each scenario, say whether a public accessor or friend is the better fit, and why.

Public accessor (or, more precisely, a public logging method). "Many unrelated callers" is exactly the case where friend does not scale — you would need a new friend line for every caller, forever, and every one of those callers becomes permanently coupled to Logger's internals.

Problem 3 — stream operators for Time (added)

Give an implementation for operator<< and operator>> for a Time class holding private int hours, minutes;. operator<< should print as H:MM (minutes zero-padded to two digits: 9:05, not 9:5). operator>> should read two integers, hours then minutes.

Plan. Both operators must be free functions (§1), both need friend access to hours/minutes (§5), and the padding in operator<< is a single conditional: print a leading "0" only when minutes < 10.

time_streams.cpp
#include <iostream>
using namespace std;

class Time {
public:
    Time() : hours(0), minutes(0) {}

    friend ostream &operator<<(ostream &os, const Time &t);
    friend istream &operator>>(istream &is, Time &t);

private:
    int hours, minutes;
};

ostream &operator<<(ostream &os, const Time &t) {
    os << t.hours << ":" << (t.minutes < 10 ? "0" : "") << t.minutes;
    return os;
}

istream &operator>>(istream &is, Time &t) {
    is >> t.hours >> t.minutes;
    return is;
}

int main() {
    Time wake, meeting;
    cout << "enter wake time (H M): ";
    cin >> wake;
    cout << "enter meeting time (H M): ";
    cin >> meeting;
    cout << "wake = " << wake << ", meeting = " << meeting << endl;
    return 0;
}
enter wake time (H M): enter meeting time (H M): wake = 7:05, meeting = 9:30

Things to notice. This run's input was 7 5 then 9 30, piped in rather than typed, which is why no digits appear after either prompt. 7:05 proves the zero-padding branch actually ran; without it, minutes == 5 would print as the misleading 7:5.

Problem 4 — Gradebook as a friend class of Student (added)

Student holds a private string name; and a private double score;. Give Gradebook friend access to Student so that Gradebook::report(const Student &a, const Student &b) can compute and print the average of two students' scores by reading a.score and b.score directly, without adding any getter to Student.

Plan. Gradebook's whole job is to read Student internals, and it will plausibly grow more such methods later, so §6's full friend-class grant (friend class Gradebook;) fits better than naming one method at a time.

gradebook.cpp
#include <iostream>
using namespace std;

class Student {
public:
    Student(string n, double s) : name(n), score(s) {}

    friend class Gradebook;   // Gradebook may read every Student's private data

private:
    string name;
    double score;
};

class Gradebook {
public:
    void report(const Student &a, const Student &b) const {
        double avg = (a.score + b.score) / 2.0;   // reaches directly into both objects
        cout << a.name << " and " << b.name << " average " << avg << endl;
    }
};

int main() {
    Student s1("Amir", 88.0);
    Student s2("Priya", 94.0);
    Gradebook gb;
    gb.report(s1, s2);
    return 0;
}
Amir and Priya average 91

Things to notice. 91.0 prints as 91 — the same trailing-zero rule from Class 1. And Student itself is never given any public way to read score; the only route in is through Gradebook, which is exactly the point of choosing friend over an accessor here.

Problem 5 — predict the output, or explain the error (added, in the style of the Fall 2023 Exam 2 namespace question)

Given these declarations:

class Locker;

class Owner {
public:
    void open(const Locker &l) const;
};

class Janitor {
public:
    void peek(const Locker &l) const;
};

class Locker {
    friend class Owner;
public:
    Locker(int c) : code(c) {}
private:
    int code;
};

void Owner::open(const Locker &l) const {
    cout << "code is " << l.code << endl;
}

void Janitor::peek(const Locker &l) const {
    cout << "code is " << l.code << endl;
}

and this main, executed one line at a time:

Locker locker(1234);
Owner owner;
owner.open(locker);      // line (a)
Janitor j;
j.peek(locker);           // line (b)

(a) Does line (a) compile? If so, what does it print?

code is 1234

Locker declared friend class Owner;, so Owner::open may read l.code directly.

(b) Does line (b) compile? If not, explain exactly why the error occurs, quoting the specific rule from this class that applies.

It does not compile. Locker never granted friendship to Janitor — only to Owner. That Owner can read Locker's private data has no bearing on whether Janitor can; each friend line names one specific grantee, and access is never extended to anyone else by resemblance or proximity. Lecture Summary
  • A binary operator written as a class method always takes its left operand as this. Since cout << p1 needs cout (an ostream) on the left, and you cannot add a member to the standard library's ostream, operator<< (and operator>>) for your own class must be a free function.
  • The required signatures: ostream &operator<<(ostream &os, const T &t) and istream &operator>>(istream &is, T &t). Both return their stream by reference — not void, and not by value (streams cannot be copied) — so that << and >> can be chained: each call's return value becomes the left operand of the next <</>> in the statement.
  • Being a free function costs operator<</operator>> their automatic access to private data. A public accessor is one fix; friend is the other — a declaration, written inside the class being protected, that grants one named function or one named class full access to its private and protected members, data and methods alike.
  • A friend declaration can appear anywhere inside the class — public section, private section, top, bottom — access is identical regardless of placement.
  • friend class Other; grants every member of Other the same access an individual friend function gets. Granting friendship to one method of another class (rather than the whole class) requires a forward declaration of the method's own class first, then the friending class fully defined, then the friend line.
  • Friendship is not symmetric (granting it one direction says nothing about the reverse), not transitive (a friend of your friend is not your friend), and — a preview for Class 19 — not inherited by a derived class.
  • Neither friend nor a public accessor is universally "correct." Favor an accessor when many unrelated callers need access or the representation may change; favor friend when exactly one function or class is tightly, permanently coupled to this one (streams are the textbook case).
  • Exam note: friend has never appeared on any of this professor's ten graded exams — not one question requires declaring or reasoning about it. operator<< itself is likewise never the subject of a written-code question, though cout << inside a class's own print()/display() is everywhere. If your review time is limited, spend it on the member-function operator overloading from Class 17 (tested on 9 of 10 exams) before drilling friendship, which exists here mainly to make the streams material teachable, not to be tested directly.
