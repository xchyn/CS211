1.Templates and polymorphism: two roads to generality

In Class 25 you wrote your first function templates: one definition of swap or maximum, written once with a stand-in type T, and the compiler manufactured a separate real function for every type you actually used it with. Today we do the same thing to a whole class. That is the piece the Standard Library is built out of, and it is the piece that finally lets you explain what vector<int> really is.

Before the syntax, one comparison worth having straight in your head, because the two techniques look similar from a distance and are completely different underneath.

Templates and polymorphism have something in common: both are ways to write abstract code that is not restricted to a specific class or data type. But they get there by opposite routes.

Polymorphism (Classes 24–25)Templates (Classes 25–26)
How you write it A base class supplies some functionality plus a set of virtual functions. Derived classes inherit and override some or all of them. One definition with a stand-in type parameter. There is no inheritance tree at all.
Who can participate Only members of the inheritance tree. A class that does not derive from the base cannot be part of a polymorphic library, no matter how suitable it looks. Almost any class the user wants to write. Nobody has to have anticipated it.
The catch You must own, or at least be able to edit, the hierarchy. There are restrictions on the properties of the classes: whatever operations the template body performs, T had better support. Nothing declares those requirements — you find out when instantiation fails.
When it is decided At run time, through the virtual table. At compile time. By the time the program runs, the generality is gone and only ordinary machine code remains.
Key Idea

Templates and polymorphism are both useful techniques, but they implement "generality" in different ways. Polymorphism generalizes over a family of classes you have designed together. Templates generalize over types nobody has met yet — including types that will be written years after your code ships.

Quick Check 26.1

You are writing a container that stores a list of items and prints them all. You have two designs in mind.

(a) Design A stores Printable* pointers, where Printable is an abstract base class with a pure virtual print(). What must a user do to store their own Employee objects in it?

They must change Employee so that it derives from Printable and overrides print(). If Employee came from somebody else's library and they cannot edit it, they are stuck — they would have to write a wrapper class that derives from Printable and holds an Employee inside it.

That is the restriction the professor states plainly: the participating classes are restricted to be members of the inheritance tree.

(b) Design B is a class template List<T> whose printAll() does cout << items[i] for each element. What must a user do to store Employee objects in this one?

Nothing to the inheritance hierarchy — Employee does not have to derive from anything. But Employee does have to support the operations the template body performs on it. Here that means an operator<< taking an ostream and an Employee, plus whatever else List needs (usually a default constructor and an assignment operator).

So the requirement did not disappear; it changed shape. Instead of "inherit from this base class" it became "supply these operations." And unlike a base class, nothing writes that requirement down. You discover it when List<Employee> refuses to compile.

(c) One of these two designs makes the decision at compile time and one at run time. Which is which, and why does it matter?

Design A decides at run time: the Printable* could point at anything, and the virtual-table lookup picks the right print() while the program runs. Design B decides at compile time: List<Employee> and List<int> are two separate classes, each with its own compiled code, generated before the program ever starts.

Why it matters: the template version has no virtual-call overhead and can be optimized as ordinary code, but it produces a separate copy of the class for every type you use, and its error messages arrive at compile time in a heap. The polymorphic version compiles once and can accept objects whose types are chosen while the program is running — something a template flatly cannot do.

2.Two or more type parameters

Every template in Class 25 had exactly one type parameter. Nothing forces that. It is straightforward to write a templated function with two templated data types — you list them both inside the angle brackets, separated by a comma, each with its own typename keyword.

Definition— template parameter list

The template <...> line that precedes a template is its template parameter list. It names the stand-in types the definition below it is allowed to use. Each entry needs its own keyword:

template <typename T, typename U>   // two parameters: correct
template <typename T, U>            // wrong: U is missing its keyword

The parameters are independent. T and U can be deduced or specified as two different types, or as the same type — nothing links them.

Here is the professor's example: a function that prints two input parameters x and y whose data types are independent of each other.

template <typename T, typename U> void printInput(T x, U y) {
    cout << x << endl;
    cout << y << endl;
}

Code like the above gets messy to read once the parameter list grows. The convention used in this course — and the one you should copy — is to put the template line on a line of its own:

template <typename T, typename U>
void printInput(T x, U y) {
    cout << x << endl;
    cout << y << endl;
}

These two are the same code. The line break is purely for humans, and it matters more than it sounds like it should: once you start writing class templates, the template line and the thing it introduces get far apart, and a consistent layout is the only thing keeping them legible.

Quick Check 26.2

Working from the same printInput template:

It compiles and runs. The compiler performs template argument deduction (Class 25) on both parameters at once: d is a double, so T is double; s is a string, so U is string. Explicit template arguments are optional exactly when every parameter can be deduced from the call.

(b) Is printInput<int, int>(3, 4); legal, given that T and U are supposed to be two different parameters?

Perfectly legal. "Independent" means nothing links T and U, not that they must differ. Giving both the same type is allowed and produces exactly one more instantiation, the one where T and U are both int.

(c) A student writes template <typename T, U> and gets an error. What is missing, and what is the smallest fix?

Each parameter needs its own keyword. The fix is one word:

template <typename T, typename U>

You may also write template <class T, class U>. In a template parameter list class and typename mean exactly the same thing — it is a matter of taste, and you will see this professor use both, sometimes in the same lecture. class there does not mean the argument has to be a class type; printInput<int, double> is fine either way.

3.From a class to a class template

We can write a templated class, not just a templated function. The procedure is the one you already know from Class 25, applied to a bigger unit of code — and, as always, the way to get it right is to begin with a specific data type and generalize afterwards.

So start with string. Here is a small class the professor calls Sclass ("string class"). It has a private data member of type string, a non-default constructor, an accessor, a mutator and a public method:

sclass.cpp
class Sclass {
public:
    Sclass(const string &a) { x = a; }
    string get() const { return x; }
    void set(const string &a) { x = a; }
    void print() const { cout << x << endl; }
private:
    string x;
};

Nothing in that class is really about strings. Every one of those four functions would read identically for int, or double, or Rectangle. So generalize it.

Procedure— converting a class into a class template
  1. Write and test the class for one concrete type first. Debugging a template you have never seen work is much harder than debugging a plain class.
  2. Replace every occurrence of that concrete type with the stand-in name T — in the data members, the parameters and the return types.
  3. Prepend a template <typename T> line immediately before the word class.
  4. Rename the class if the old name mentioned the type (Sclass becomes Tclass).
  5. Everywhere outside the class, write the class name with its argument: Tclass<int>, never a bare Tclass.

Steps 2 and 3 give this. It is character-for-character the class above, with string replaced by T and one new first line:

template <typename T> class Tclass {
public:
    Tclass(const T &a) { x = a; }
    T get() const { return x; }
    void set(const T &a) { x = a; }
    void print() const { cout << x << endl; }
private:
    T x;
};
Definition— class template, instantiation

A class template is a pattern from which the compiler generates classes. Tclass by itself is not a type — you cannot declare an object of it, you cannot make a pointer to it, and it has no size.

When you write Tclass<int> you name a specialization, and the compiler performs an instantiation: it takes the pattern, substitutes int for every T, and compiles the result as an ordinary class. That generated class is a real type. So:

Tclass<int> it(n);      // "n" is type int
Tclass<double> dt(d);   // "d" is type double
Tclass<string> st(s);   // "s" is type string

The type is the whole phrase Tclass<int> — the name and its argument together. Read it aloud as "Tclass of int."

How do you print one of these? Class 18 gave you the pattern: overload operator<< as a free function taking an ostream reference and a const reference to the object. The templated version is the same thing with a template line on top — and one detail that trips everybody, so look at the parameter type carefully:

template <typename T>
ostream& operator<< (ostream &os, const Tclass<T> &t) {
    return os << "(" << t.get() << ")";
}

The parameter is const Tclass<T> &t, not const Tclass &t. Outside the class body, the class name has to carry its template argument, and here the argument is the parameter T of this function template. We will come back to exactly why in the next section.

Quick Check 26.3

Each line below is a separate attempted declaration, using the Tclass above. Say whether it compiles, and if not, why.

(a) Tclass<int> a(7);

Compiles. Tclass<int> is a real type and 7 is an int, which binds to the constructor's const T &a parameter.

(b) Tclass<int> b;

Does not compile. Tclass declares a non-default constructor, so the compiler does not supply a default one — exactly the rule from Class 13, unchanged by templates. There is no way to build a Tclass<int> without giving it an initial value.

That is worth noticing as a design flaw: it means you cannot write vector<Tclass<int>> v(10); either. If you want that, add a default constructor to the template.

(c) Tclass<int> c(7); Tclass<double> d(1.5); c = d;

The two declarations are fine; the assignment is rejected:

unrelated.cpp: In function 'int main()':
unrelated.cpp:17:10: error: no match for 'operator=' (operand types are 'Tclass<int>' and 'Tclass<double>')
   17 |     it = dt;                   // is this allowed?
      |          ^~
unrelated.cpp:6:7: note:   no known conversion for argument 1 from 'Tclass<double>' to 'const Tclass<int>&'

This is the single most important consequence of instantiation: Tclass<int> and Tclass<double> are two unrelated classes that merely happen to have been generated from the same source. They are no more assignable to each other than Rectangle and Employee would be. The shared template does not create a family relationship, and there is no base class lurking behind them.

(d) Tclass e(7); — no angle brackets.

This one deserves a careful answer, because the honest answer is "it depends on the C++ version, and you should write the brackets anyway."

Under -std=c++17 it compiles: C++17 added class template argument deduction, which lets the compiler work out from the constructor argument 7 that you meant Tclass<int>. Under the older C++11 or C++14 rules it is an error.

Do not rely on it. The deduction only works in a variable declaration; the moment you need the type anywhere else — a function parameter, a return type, a data member — the bare name is an error, which we will see in section 4. And every exam in this course writes the argument explicitly. Write Tclass<int> e(7);.

Quick Check 26.4

Write the templated version of DoublePair described above — call it MaxPair — and a main that uses it with int and with string. What does it print for the two strings "apple" and "banana"?

Replace both doubles with T, prepend the template line, and rename:

maxpair.cpp
// maxpair.cpp -- a class template over any type that supports <
#include <iostream>
#include <string>
using namespace std;

template <typename T>
class MaxPair {
public:
    MaxPair(const T &a, const T &b) { first = a; second = b; }
    T larger() const { return (first < second) ? second : first; }
private:
    T first;
    T second;
};

int main() {
    MaxPair<int> ip(3, 9);
    cout << ip.larger() << endl;

    MaxPair<double> dp(3.5, 2.25);
    cout << dp.larger() << endl;

    MaxPair<string> sp("apple", "banana");
    cout << sp.larger() << endl;

    return 0;
}

"banana" wins because string compares lexicographically — 'a' comes before 'b', so "apple" < "banana" is true. The template body never mentioned strings; it just asked T whether one value was less than another, and string answered.

First, the constructor takes const T & rather than T, which costs nothing for an int and saves a whole string copy for a string — the habit from Class 2 pays off doubly in templates, where you do not know how expensive T is. Try MaxPair<Rectangle> on a Rectangle class with no operator< and you get a compile error pointing at the line (first < second) — inside your template, not at the user's call.

4.What the class name means inside the template

Look again at that operator<< parameter: const Tclass<T> &t. Then look at a copy constructor declared inside a class template — you will meet one in section 7 — which is written Tclass(const Tclass &orig); with no brackets at all. Both are correct. That looks inconsistent until you know the rule.

Key Idea

Inside the body of a class template, the bare class name means "the class currently being instantiated" — inside Tclass<int>, the name Tclass means Tclass<int>. Outside the body, the bare class name is not a type at all and must be written with its argument: Tclass<T> or Tclass<int>.

So all three of these declarations mean the same thing when they appear inside the class body, and the first is what you will normally write:

template <typename T>
class Tclass {
public:
    Tclass(const Tclass &orig);         // "the current instantiation"
    // Tclass(const Tclass<T> &orig);   // identical meaning, more typing
private:
    T x;
};

Outside the body the shorthand is gone. Every one of these is a place where the bare name is an error: a function parameter, a return type, a data member of another class, a new expression, a variable declaration in main.

Quick Check 26.5

Here is a class template with three declarations in it. For each one, decide whether it is legal and say what type the name Node refers to.

template <typename T>
class Node {
public:
    Node(const T &v);
    Node combine(const Node &other) const;   // (a)
    void link(Node<T> *next);                // (b)
private:
    T value;
    Node *nextNode;                          // (c)
};

(a) Is Node combine(const Node &other) const; legal here?

Legal. It is inside the class body, so both bare Nodes mean Node<T> — the return type and the parameter type. When you define this function outside the class you will have to write the qualifier in full, which is the next section's subject.

(b) Is void link(Node<T> *next); legal here?

Legal, and identical in meaning to writing Node *next. Spelling out the argument inside the body is never wrong — it is just longer. Some people write it out deliberately for clarity; the professor's code uses the short form.

(c) Is the data member Node *nextNode; legal here?

Legal — still inside the body, so it means Node<T> *nextNode. A class template may hold a pointer to its own instantiation, which is how a templated linked list is built. None of the three is the illegal one; the trick question was whether you would flinch at (c). What would not be legal is a data member of type Node (no pointer, no argument) declared in some other, non-template class, or the bare name used in a free function — both are outside the body.

5.Defining members outside the class template

Everything so far defined its member functions inline, right inside the class body. That is fine for one-liners, and it is what the professor's Tclass does. But a real class has functions that are twenty lines long, and burying them inside the class makes the interface impossible to read. From Class 10 onwards you have been splitting them out:

class Sclass {
public:
    string get() const;          // declared here
private:
    string x;
};

string Sclass::get() const { return x; }   // defined out here

Some important modifications are required to do the same thing for a class template. There are exactly two, and students get one or the other wrong every single time.

Procedure— defining a member of a class template outside the class
  1. Write template <typename T> on its own line, immediately above the definition. Every definition needs its own copy of this line — it is not written once for the group.
  2. Write the return type as usual.
  3. Qualify the function name with ClassName<T>:: — the class name with its template argument. Not ClassName::.
  4. Repeat the parameter list and any const exactly as declared.

So the shape is always:

template <typename T>
ReturnType ClassName<T>::method(parameters) const { ... }

The T in the qualifier is the same T the template line just introduced. That is the whole trick: the template line creates the name T, and ClassName<T> uses it.

Here is the professor's Tclass, written out that way. Compare it line by line with the inline version in section 3 — the bodies are identical, only the packaging changed.

tclass_noninline.cpp
template <typename T>
class Tclass {
public:
    Tclass(const T &a);
    T get() const;
    void set(const T &a);
    void print() const;
private:
    T x;
};

template <typename T>
Tclass<T>::Tclass(const T &a) { x = a; }

template <typename T>
T Tclass<T>::get() const { return x; }

template <typename T>
void Tclass<T>::set(const T &a) { x = a; }

template <typename T>
void Tclass<T>::print() const { cout << x << endl; }
Key Idea

Notice that we must write Tclass<T>::, unlike Tclass:: for a non-templated class. The constructor is the one that looks strangest: Tclass<T>::Tclass(const T &a). The part before the :: is the type, which needs its argument; the part after the :: is the function name, which is just the class's own name and never takes brackets. Read it as "the Tclass constructor belonging to Tclass<T>."

6.Why it all has to live in the header

Class 2 taught you the standard way to split a C++ program across files: declarations in a .h header, definitions in a matching .cpp, and every source file that wants to use the class does #include "thing.h". Each .cpp is compiled on its own into an object file, and the linker joins them at the end.

Do that to a class template and it fails. Not with a compiler error — every file compiles perfectly — but at the very last step, with a message most students have never seen before. This is worth doing once, carefully, because it will otherwise eat an evening of your life.

Worked Example— the split that does not link

A template is not code — it is a recipe for making code. The compiler only produces a real Box<int>::get when it sees somebody actually use Box<int>. While compiling box.cpp it saw the recipe and no user, so it generated nothing. While compiling mainbox.cpp it saw a user and no recipe — the header has only the declarations — so it emitted a call and left the address for the linker to fill in. The linker then looked in both object files for Box<int>::get, and it genuinely is not in either of them.

Key Idea

A class template's definitions must be visible at the point of instantiation. In practice that means: put the whole class template — declarations and definitions together — in the header file. You cannot split it into a .cpp the usual way. This is the one place where the multi-file discipline from Class 2 does not apply.

The fix is a two-second edit: move the definitions out of box.cpp and paste them into box.h, below the class. Then delete box.cpp entirely — there is nothing left for it to hold.

Quick Check 26.7

A classmate has a working single-file program containing a class template Stack and a main. They split it up for their project and now cannot build it.

(a) They report: "g++ -c stack.cpp works, g++ -c main.cpp works, and then linking says undefined reference to Stack<int>::push(int)." What did they do, and what is the fix?

They put the class template's declarations in stack.h and its definitions in stack.cpp, which is correct for an ordinary class and wrong for a template. The compiler never instantiated Stack<int>::push while compiling stack.cpp, because that file never uses Stack<int>.

The fix: move every definition into stack.h, below the class, keeping the template <typename T> line and the Stack<T>:: qualifier on each one. Then remove stack.cpp from the build.

(b) Why does the error mention Stack<int> specifically, rather than Stack?

Because Stack is not a class and has no functions. The only function the program ever asked for was the one belonging to the instantiation Stack<int>, so that is the name the linker went looking for. If main had also used Stack<string>, you would see a second set of undefined references naming that one too.

This is a useful diagnostic habit generally: the names in a linker error tell you exactly which instantiations your program requested.

(c) Their header now contains full function bodies. Does it still need the #ifndef / #define include guard, or does that only matter for declarations?

It needs the guard more than ever. Without it, a source file that includes the header twice (directly and again through some other header) would see the class defined twice in one translation unit, which is an error. The guard is what makes a header safe to include repeatedly, and nothing about templates changes that.

Note the difference between the two kinds of duplication: within one translation unit the include guard prevents it; across translation units, the weak-symbol mechanism from the previous example handles it. You need both.

Common Mistake— the initialization list in the wrong order

The constructor above lists its members as len(0), obj(a), ptr(new T), array(nullptr). The course notes write the same list in a different order:

DynAlloc<T>::DynAlloc(T a, T b, int n) : obj(a), ptr(new T), array(NULL), len(0) {

Members are initialized in declaration order, not in the order you list them — the exact subtlety taught with the member initialization list in Class 13. The declarations are int len; T obj; T *ptr; T *array;, so len is initialized first no matter where you write it. Compile the notes' version and g++ tells you so:

reorder.cpp: In instantiation of 'DynAlloc<T>::DynAlloc(T, T, int) [with T = int]':

      |        ^~~~~

   10 |     int len;

Quick Check 26.8

Questions about stage 1 as it stands.

(a) Why is it delete ptr; for one member and delete [] array; for the other?

Because of how each was allocated. ptr came from new T — a single object — so it is released with delete. array came from new T[len] — an array — so it is released with delete [], which is what tells the run-time system to destroy every element, not just the first. Mismatching them is undefined behavior, and with a T like string it will leak every element after the first.

(b) If a caller passes n = 0, array stays nullptr. Is delete [] array; in the destructor then a bug?

No. delete and delete [] on a null pointer are defined to do nothing at all. That is why initializing array to nullptr in the list matters so much: it guarantees the destructor is safe on every path without needing an if. An uninitialized pointer, by contrast, holds garbage, and deleting it is a crash.

(c) The professor's version writes return NULL; in getElement and array(NULL) in the list; the version above writes nullptr. Does it matter?

Both work here, but nullptr is the right modern choice and is what you should write. NULL is an old macro that expands to the integer 0, so it is not really a pointer at all; it needs <cstddef> (usually pulled in by accident through another header) and it can pick the wrong overload when a function takes both an int and a pointer. nullptr is a genuine keyword with a genuine pointer type and none of those problems.

You will still see NULL throughout this course's materials and on the exams, where it is accepted. Read it as "null pointer" and write nullptr in your own code.

(d) The course notes call the mutator setPtr(T b), and its body is *ptr = b;. The version above renames it. Why?

Because the name lies. setPtr sounds like it changes which object ptr points at; what it actually does is overwrite the value that ptr already points to. The pointer itself never changes. That is why the listing above calls it setPtrValue.

This is not pedantry — a caller who believes the name will write d.setPtr(something) expecting the old target to be replaced, and will be surprised. Name mutators after what they modify.

Stage 3 — the Big Three, deep

Now add the two missing members. Nothing about them is template-specific except the two lines of packaging on each definition — compare them to the MyList and Polynomial versions you wrote in Classes 14 and 15 and you will find the bodies are the same code you already know.

The copy constructor allocates its own storage and copies the values:

template <class T>
DynAlloc<T>::DynAlloc(const DynAlloc &orig)
    : len(orig.len), obj(orig.obj), ptr(new T(*orig.ptr)), array(nullptr) {
    if (len > 0) {
        array = new T[len];
        for (int i = 0; i < len; ++i)
            array[i] = orig.array[i];
    }

Two details in that signature are worth pausing on. The parameter is const DynAlloc &orig with no <T>, because we are inside the class's own scope — section 4's rule. But the qualifier before the :: is DynAlloc<T>, because that part is outside. The same line shows both halves of the rule.

And the assignment operator, whose signature is the one the professor singles out for attention:

template <class T>
DynAlloc<T>& DynAlloc<T>::operator= (const DynAlloc &rhs) {
    if (this == &rhs) return *this;
    obj = rhs.obj;
    *ptr = *rhs.ptr;
    delete [] array;
    array = nullptr;
    len = rhs.len;
    if (len > 0) {
        array = new T[len];
        for (int i = 0; i < len; ++i)
            array[i] = rhs.array[i];
    }
    cout << "DynAlloc: assignment operation" << endl;
    return *this;
}

The return type is DynAlloc<T>& — with the argument, because a return type is outside the class body. The function name is DynAlloc<T>::operator=. The parameter is const DynAlloc &rhs, inside, so no argument needed. Students routinely write DynAlloc& DynAlloc::operator= and get the "used without template arguments" error from section 5, twice.

Common Mistake— assigning in the body instead of initializing in the list

The course notes' copy constructor starts with only : array(NULL) and then assigns the rest inside the body:

DynAlloc<T>::DynAlloc(const DynAlloc& orig) : array(NULL) {
    obj = orig.obj;          // default-construct obj, THEN overwrite it
    ptr = new T;
    *ptr = *orig.ptr;
    len = orig.len;
    // ...
}

It works for int and string, but it quietly imposes a requirement the rest of the class does not: obj = orig.obj; in the body means obj was default-constructed first and then assigned, so T must have a public default constructor. Meanwhile the ordinary constructor writes obj(a), which needs no such thing. The result is a class that accepts a given T when you construct an object and rejects it when you copy one — a confusing failure to debug, and one that only appears for the user who supplies that particular T.

The version used above initializes consistently: : len(orig.len), obj(orig.obj), ptr(new T(*orig.ptr)), array(nullptr). It is also faster, for the reason Class 13 gave: initializing once beats constructing and then assigning. Same for new T(*orig.ptr) versus new T; *ptr = ....

8.Generic programming, and what the STL is

Everything today has been machinery. Step back for the idea it serves.

Definition— generic programming

Generic programming is a style of programming in which the code is independent of any specific data type. The data type is specified later, not when the code is actually written.

It is a concept, independent of any programming language — other languages implement it by other means. Templates provide a mechanism to implement generic programming in C++.

Two examples make the idea concrete, and the professor picks exactly the two that this course has been circling all semester.

A dynamically resizable array. The fundamental software design of such an array — keep a block of storage, remember how much of it is used, allocate a bigger block and copy when you run out — does not depend on whether the elements are int or double or Employee. Not one line of that design mentions a type. The vector class in the STL is a dynamically resizable array, it is a templated class, and that is why you have been writing vector<int> and vector<double> since Class 5. You now know exactly what that syntax means: it is an instantiation, the same thing you did to Tclass this morning.

Sorting. The fundamental concept of sorting data does not depend on a specific data type either. To sort, you need only two things: an array of objects, and a comparison function that can say one object is "less than" another. Given those, you can establish a ranking — and the sorting algorithm itself never has to know what it is ranking. That is why MaxPair<string> in section 3 worked without being told anything about strings: it asked T whether one value was less than another, and let T answer.

Key Idea

The test for a generic design is this: can you describe the algorithm or the data structure completely without naming a type? If yes, the type is an accident of the version you happened to write first, and it belongs in a template parameter.

Which brings us to the library the whole thing is named after.

Definition— the STL

The STL (Standard Template Library) is a very important part of the standard C++ library. It employs the concept of generic programming: all of the classes in the STL are templated classes.

It provides support for four broad categories of functionality:

  1. Containers — classes that hold collections of objects. A vector (a dynamically resizable array) is a container.
  2. Algorithms — operations performed on those collections. Sorting is an example of an algorithm.
  3. Iterators — a generalization of the concept of pointers, used to walk over a container without knowing which kind of container it is.
  4. Function objects, also called functors — objects that can be called and used as if they were functions, which is how you hand a custom comparison to a sorting algorithm.
Quick Check 26.12

Two questions to close the loop on the whole semester.

(a) You have used vector since Class 5 without knowing any of today's material. What does the declaration vector<string> names; actually cause the compiler to do?

It instantiates the vector class template with T = string, generating a real class — a class with its own dynamically allocated array of string, its own destructor, its own copy constructor, its own assignment operator, all deep — and then declares an object of that class. Every one of those pieces is exactly what you built by hand in DynAlloc this morning.

And vector<int> is a completely different class, generated separately. The two are as unrelated as Tclass<int> and Tclass<double> in Quick Check 26.3.

(b) Given what you know about where a class template's definitions must live, what would you expect to find inside the file that #include <vector> pulls in — declarations, or declarations and definitions?

Both. There is no compiled vector.o sitting in the library for the linker to find, because there is no such thing as "the" vector — the compiler has to build vector<string> from source at the moment you ask for it. So the entire implementation of vector, bodies and all, is in the header you include.

That is also why C++ programs that use lots of templates compile slowly: every source file that includes <vector> re-reads and re-instantiates the whole thing. It is the price of section 6's rule, paid by every C++ program ever written.

    for (int i = 0; i < 5; i++) cout << a[i] << " ";    // print: 5 4 3 2 1
    cout << endl;
    for (int i = 0; i < 2; i++) cout << b[i] << " ";    // print: Bye Hello
    cout << endl;
    return 0;
}

(a) Write the function template reverse.

Swap the ends inward, stopping at the middle. Note the array is not const — the whole point is to modify the caller's array in place, and an array parameter is always a pointer to the caller's storage.

template <typename T>
void reverse(T arr[], int size) {
    for (int i = 0; i < size / 2; ++i) {
        T temp = arr[i];
        arr[i] = arr[size - i - 1];
        arr[size - i - 1] = temp;
    }
}

size / 2 is integer division, which is exactly right for both parities: with 5 elements the loop runs for i = 0, 1 and the middle element at index 2 correctly stays put. T temp inside the loop is the reason this needs a template at all — the temporary has to be of whatever type the array holds.

(b) Now write a class template Sequence<T> that owns a dynamic array of T and offers reverse() as a member function, along with the Big Three. Show that copying a Sequence and reversing the copy leaves the original alone.

Plan. The class stores int len; T *data;. The constructor copies from a caller-supplied array, so the object owns its data outright; that means a destructor, and that in turn means a copy constructor and an assignment operator. The reverse() member is the same loop as part (a) with arr replaced by data and size by len — which is the point: the algorithm did not change, only who owns the storage.

sequence.cpp
// sequence.cpp -- the exam's templated reverse, and the same idea as a class template
#include <iostream>
#include <string>
using namespace std;

// Part (a): the free function template, exactly as the final exam asks for it.
template <typename T>
void reverse(T arr[], int size) {
    for (int i = 0; i < size / 2; ++i) {
        T temp = arr[i];
        arr[i] = arr[size - i - 1];
        arr[size - i - 1] = temp;
    }
}

// Part (b): a class template that owns its array and can reverse itself.
template <typename T>
class Sequence {
public:
    Sequence(const T arr[], int n);
    ~Sequence();
    Sequence(const Sequence &orig);
    Sequence& operator= (const Sequence &rhs);
    void reverse();
    void print() const;
private:
    int len;
    T *data;
};

template <typename T>
Sequence<T>::Sequence(const T arr[], int n) : len(n), data(nullptr) {
    if (len > 0) {
        data = new T[len];
        for (int i = 0; i < len; ++i) data[i] = arr[i];
    }
}

template <typename T>
Sequence<T>::~Sequence() { delete [] data; }

template <typename T>
Sequence<T>::Sequence(const Sequence &orig) : len(orig.len), data(nullptr) {
    if (len > 0) {
        data = new T[len];
        for (int i = 0; i < len; ++i) data[i] = orig.data[i];
    }
}

template <typename T>
Sequence<T>& Sequence<T>::operator= (const Sequence &rhs) {
    if (this == &rhs) return *this;
    delete [] data;
    data = nullptr;
    len = rhs.len;
    if (len > 0) {
        data = new T[len];
        for (int i = 0; i < len; ++i) data[i] = rhs.data[i];
    }
    return *this;
}

template <typename T>
void Sequence<T>::reverse() {
    for (int i = 0; i < len / 2; ++i) {
        T temp = data[i];
        data[i] = data[len - i - 1];
        data[len - i - 1] = temp;
    }
}

template <typename T>
void Sequence<T>::print() const {
    for (int i = 0; i < len; ++i) cout << data[i] << " ";
    cout << endl;
}

int main() {
    int a[5] = {1, 2, 3, 4, 5};
    string b[2] = {"Hello", "Bye"};

    reverse<int>(a, 5);
    reverse<string>(b, 2);
    for (int i = 0; i < 5; i++) cout << a[i] << " ";
    cout << endl;
    for (int i = 0; i < 2; i++) cout << b[i] << " ";
    cout << endl;

    Sequence<int> si(a, 5);
    si.reverse();
    si.print();

    Sequence<string> ss(b, 2);
    Sequence<string> copy = ss;
    copy.reverse();
    ss.print();
    copy.print();

    return 0;
}

Bye Hello 
1 2 3 4 5 
Bye Hello 
Hello Bye

Things to notice.

  • The third line is 1 2 3 4 5 because si was built from the already reversed array a and then reversed again. Trace slowly; this is the sort of double reversal exam questions love.
  • Lines four and five are the proof of deep copy: copy.reverse() changed only copy. With the compiler-generated copy constructor both would read Hello Bye, and the program would then crash on the second destructor.
  • The member function and the free function have the same body. Neither is more "templated" than the other — what a class template buys you here is ownership and lifetime management, not generality.
  • The driver printed in the exam paper starts both its loops at i = 1, which would skip the first element and contradict the expected output written in its own comments. The version above starts at 0. If a stem contradicts itself like this, answer what it clearly intends and say so in a comment.

Problem 5 — A class template with two type parameters (added)

Write a class template Pair that stores one value of type T and one of type U. Give it a constructor, accessors and mutators for both members, a method swapped() that returns a Pair<U, T> with the two values exchanged, and an operator<< printing it as (first, second). Define every member function outside the class. Then build a Pair<string, int> and a Pair<int, double> and print them.

Plan. Two type parameters means every template line names both, and every out-of-class qualifier is Pair<T, U>::. The interesting member is swapped(): its return type is a different instantiation of the same class template, Pair<U, T>, which it builds and returns by value. That is legal and useful, and it is a good illustration of the fact that Pair<T,U> and Pair<U,T> are unrelated types — you cannot assign one to the other, only construct one from the other's parts.

pairtu.cpp
// pairtu.cpp -- a class template with TWO type parameters
#include <iostream>
#include <string>
using namespace std;

template <typename T, typename U>
class Pair {
public:
    Pair(const T &a, const U &b);
    T getFirst() const;
    U getSecond() const;
    void setFirst(const T &a);
    void setSecond(const U &b);
    Pair<U, T> swapped() const;
private:
    T first;
    U second;
};

template <typename T, typename U>
Pair<T, U>::Pair(const T &a, const U &b) : first(a), second(b) { }

template <typename T, typename U>
T Pair<T, U>::getFirst() const { return first; }

template <typename T, typename U>
U Pair<T, U>::getSecond() const { return second; }

template <typename T, typename U>
void Pair<T, U>::setFirst(const T &a) { first = a; }

template <typename T, typename U>
void Pair<T, U>::setSecond(const U &b) { second = b; }

template <typename T, typename U>
Pair<U, T> Pair<T, U>::swapped() const { return Pair<U, T>(second, first); }

template <typename T, typename U>
ostream& operator<< (ostream &os, const Pair<T, U> &p) {
    return os << "(" << p.getFirst() << ", " << p.getSecond() << ")";
}

int main() {
    Pair<string, int> student("Ann", 92);
    cout << student << endl;
    cout << student.swapped() << endl;

    Pair<int, double> reading(3, 98.6);
    cout << reading << endl;
    reading.setSecond(101.4);
    cout << reading << endl;

    return 0;
}
(Ann, 92)
(92, Ann)
(3, 98.6)
(3, 101.4)

Things to notice.

  • Every out-of-class definition repeats the full template <typename T, typename U> line. There is no way to write it once for the group. It is tedious and it is not optional.
  • The constructor uses a member initialization list, : first(a), second(b) { }, with an empty body. For a T like string that is one construction instead of a construction plus an assignment, and it is also the only way to initialize a member that has no default constructor.
  • operator<< is itself a template over both parameters, and its second parameter is const Pair<T, U> &p. Miss either type argument there and you get "used without template arguments."
  • cout << reading prints 98.6 and then 101.4, both to cout's default six significant digits — a double that happened to be 98.60000 would print as 98.6.

Problem 6 — Split it into files (added)

A classmate has a single file containing a class template Box and a main that uses Box<int>. For their project they must split it into box.h, box.cpp and mainbox.cpp. They do it the way Class 2 taught, both .cpp files compile cleanly, and the link step fails. Explain precisely why, and give the corrected file layout.

Plan. Identify what stage failed — the message comes from ld, not g++, so this is linking, not compiling. Then explain what is actually inside each object file. Then fix the layout.

What they saw.

g++ -c box.cpp
g++ -c mainbox.cpp
g++ mainbox.o box.o -o boxprog
/usr/bin/ld: mainbox.o: in function `main':
mainbox.cpp:(.text+0x31): undefined reference to `Box<int>::Box(int const&)'
/usr/bin/ld: mainbox.cpp:(.text+0x3d): undefined reference to `Box<int>::get() const'
collect2: error: ld returned 1 exit status

Why. A class template is a recipe, not code. The compiler only manufactures a real Box<int>::get when it sees the definitions and a use of Box<int> in the same translation unit. Compiling box.cpp it saw the definitions and no use, so it emitted nothing at all — nm -C box.o lists no symbols. Compiling mainbox.cpp it saw a use and, through the header, only declarations, so it emitted calls to functions it expected somebody else to provide. Neither object file contains the function, so the linker fails.

The fix. Put the entire class template — declarations and definitions — in the header, and delete box.cpp:

box.h
// box.h -- a class template: declarations AND definitions, together
#ifndef BOX_H
#define BOX_H

template <typename T>
class Box {
public:
    Box(const T &a);
    T get() const;
    void set(const T &a);
private:
    T item;
};

template <typename T>
Box<T>::Box(const T &a) { item = a; }

template <typename T>
T Box<T>::get() const { return item; }

template <typename T>
void Box<T>::set(const T &a) { item = a; }

#endif
g++ mainbox.cpp -o boxprog
./boxprog
42
99

Things to notice.

  • You may keep the definitions inline inside the class body instead. Both work; the layout above keeps the interface readable at the top of the file, which matters once the functions are longer than one line.
  • The include guard is still required. It stops one translation unit from seeing the class twice. A different mechanism — the linker treating template instantiations as weak symbols and keeping just one — handles the same function being generated in several translation units.
  • Ordinary classes and free functions in the same project still follow the Class 2 rule: declarations in the header, definitions in a .cpp. Templates are the exception, not the new rule.
  • If you ever truly need a template's definitions in a .cpp, there is a mechanism — explicit instantiation, which you met for functions in Class 25 — but it requires you to list in advance every type the template will ever be used with. That is almost never what you want, which is why the header is the standard answer.
Lecture Summary
  • Templates and polymorphism both produce code that is not tied to one type. Polymorphism works through an inheritance tree and decides at run time; templates have no inheritance tree and decide at compile time. Templates accept almost any class, subject to unwritten requirements on the operations T must support.
  • A template parameter list may name more than one type: template <typename T, typename U>. The parameters are independent, each needs its own typename (or class), and each definition repeats the whole line.
  • A class template is written by replacing the concrete type with T and prepending template <typename T>. Tclass alone is not a type; Tclass<int> is. Each instantiation is a separate, unrelated class — Tclass<int> cannot be assigned to Tclass<double>.
  • Inside the class body the bare class name means the current instantiation, so Tclass(const Tclass &orig) is fine. Outside it, the name must carry its argument: const Tclass<T> &t.
  • A member defined outside the class needs two things: its own template <typename T> line, and the qualifier Tclass<T>:: rather than Tclass::. Omit the <T> and g++ says "used without template arguments"; omit the template line and it says "'T' does not name a type".
  • A class template's definitions must be visible where it is instantiated, so they go in the header. Splitting them into a .cpp compiles cleanly and then fails at link time with undefined reference to Box<int>::get() — the object file for that .cpp is empty.
  • A class template that owns memory needs the whole Big Three, exactly as an ordinary class does: a destructor with matching delete/delete [], a copy constructor that allocates and copies values, and an operator= with if (this == &rhs) return *this;, an old-storage release, a fresh allocation, and return *this;. DynAlloc without them shares its arrays between objects and then frees them twice.
  • Write member initialization lists in declaration order, or -Wreorder will tell you about it — but only once somebody instantiates the template.
  • Generic programming is a style in which the code is independent of any specific data type, with the type supplied later. It is a language-independent concept; templates are C++'s mechanism for it.
  • The STL is built entirely from templated classes and supplies containers, algorithms, iterators and function objects. vector<int> has been an instantiation of a class template all along.
