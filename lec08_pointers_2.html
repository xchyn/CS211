Pointers II — Dynamic Memory

Using pointers to create variables that did not exist before — and giving every one of them back.

1.Where variables live: the stack and the heap

Class 7 was about pointing at things that already exist. Every pointer we wrote was aimed at a variable that some other line had already declared. Today we use pointers for the thing they were really invented for, and the course notes put it exactly this way:

Key Idea— from the course notes

All the pointers up to now pointed to variables which already exist in the program. We now come to one of the most useful features of pointers: we shall use pointers to create new variables which did not exist before. The process of doing so is called dynamic memory allocation.

Before the syntax, the motivation — because if you learn new and delete without understanding why anyone would want them, you will use them in places where an ordinary variable would have been simpler and safer.

The problem: you do not know how big it needs to be

Here is a program that averages some test scores. It is completely ordinary, and it has a flaw you have probably written yourself.

fixedsize.cpp
// fixedsize.cpp -- the problem dynamic memory solves
#include <iostream>
using namespace std;

int main() {
    const int MAX = 100;        // a guess, made when the program was written
    double scores[MAX];
    int n;

    cout << "How many scores? ";
    cin >> n;                   // the real answer arrives here, at run time

    if (n > MAX) {
        cout << "Sorry, this program can only handle " << MAX << " scores." << endl;
        return 1;
    }
    for (int i = 0; i < n; ++i)
        cin >> scores[i];

    double sum = 0.0;
    for (int i = 0; i < n; ++i)
        sum += scores[i];
    cout << "average = " << sum / n << endl;
    return 0;
}

The number MAX is a guess made by the programmer, at the time the program was written, about something only the user knows, at the time the program is run. Every guess is wrong in one of two directions. Guess too small and the program refuses perfectly reasonable work. Guess too large and every single run reserves 100 doubles — 800 bytes — to hold the three numbers the user actually typed. Neither is a disaster here. Change MAX to a million, or put this array inside a class that gets created ten thousand times, and both become one.

The obvious repair looks like this, and it is the first thing everybody tries:

vla.cpp
// vla.cpp -- looks reasonable, is not standard C++
#include <iostream>
using namespace std;

int main() {
    int n;
    cout << "How many scores? ";
    cin >> n;

    double scores[n];        // NOT standard C++
    for (int i = 0; i < n; ++i)
        cin >> scores[i];
    return 0;
}
Common Mistake— an array length must be a compile-time constant

double scores[n]; where n is an ordinary variable is not standard C++. The compiler has to decide how large every ordinary array is while it is compiling, long before n has a value. What makes this trap so effective is that g++ accepts it anyway, as a non-standard extension, so it appears to work. Ask the compiler to hold you to the actual language standard and it says so:

g++ -pedantic-errors vla.cpp -o vla
vla.cpp: In function 'int main()':
vla.cpp:10:12: error: ISO C++ forbids variable length array 'scores' [-Wvla]
   10 |     double scores[n];        // NOT standard C++
      |            ^~~~~~

You will see int n = 3; double a[n]; in the Class 7 notes and in plenty of textbooks, and on g++ it will run. Do not rely on it. It does not compile on the Microsoft compiler at all, and it is not what the exam is looking for — when the professor's exam says "set up just enough space to store those inputs," he means a vector or he means new[].

So we need memory whose size is decided while the program is running. That memory comes from a different place than your ordinary variables do.

Definition— static (automatic) and dynamic allocation

For ordinary variables, the compiler allocates the required memory at compile time. This is called static allocation. Statically allocated memory remains in place until the variable goes out of scope, at which point it is deallocated automatically, by code the compiler wrote for you.

The memory for a dynamically allocated variable is allocated at run time — that is why it is called dynamic. The compiler does not know how much memory is being requested. And, crucially:

dynamically allocated memory is not deallocated until you call delete or delete[]. Going out of scope does nothing to it.

Two vocabulary notes before we go on. The C++ standard calls static allocation automatic storage duration and dynamic allocation dynamic storage duration; the region the automatic variables come from is universally called the stack, and the region new draws from is called the heap (or the free store). The course notes say "static" where the standard says "automatic"; the two mean the same thing here. We will use stack and heap because they are what everyone says out loud.

Worked Example— the two regions are visibly far apart

You can see the split with your own eyes. This program declares one ordinary int, asks new for one more, and prints all three addresses in play. Before you open the toggle, predict which two of the three will look similar to each other.

#include <iostream>

int main() {

    int *heap = new int;            // dynamic storage: the heap
    *heap = 2;

    cout << "address of local     = " << &local << endl;
    cout << "address of heap int  = " << heap   << endl;
    cout << "address of the pointer variable itself = " << &heap << endl;

That asymmetry is the whole subject of today's class, and it is where every bug in it comes from.

2.new and delete: one variable at a time

Dynamic memory allocation is performed using two operators, new and delete. The procedure is slightly different for single variables and for arrays; we begin with single variables and deal with arrays in §3.

Definition— new and delete

new T asks the run-time system for enough heap memory to hold one object of type T, and returns a pointer to it. So the result of new int has type int * and must be stored in an int *.

int *ip = new int;        // allocate one int on the heap
*ip = 6;                  // reach it the only way you can: through the pointer

delete p hands that memory back to the run-time system, so it can be handed out again by some later new. It does not change p, and it does not destroy p.

delete ip;                // give the int back

Obviously, for a pointer to double we would write new double, and so on for every type.

Key Idea— the allocated variable has no name

Every variable you have declared until now had a name you chose. The variable new creates does not have a name. It is accessed via the dereference *ip and has no explicit name of its own.

That is not a curiosity, it is the central practical fact about the heap: if you lose the pointer, you lose the variable. There is no other way to name it, no other way to reach it, and no other way to delete it. Every bug in §5 is a version of losing the pointer.

The middle row is the one people misread. Note that although the memory was deallocated, the pointer ip is still in scope — it is an ordinary local variable and delete is not a magic spell that erases it. That is exactly why the second new can reuse it, and it is also exactly why §6 exists.

And the second question: the variable allocated on the second pass is not the same variable as the one allocated on the first pass. The first one was deallocated by the first delete and no longer exists. If you print the two addresses you may well see the same number twice, because the run-time system is free to hand you back the block you just returned — but "the same address was reused" is not "the same variable," and you may not assume either way.

Key Idea— the one rule to memorize

For every call to operator new, there must be a partner call to operator delete.

Not one per pointer — one per new. Two pointers into the same block get one delete between them; a loop that calls new a hundred times needs a hundred deletes. Count the calls, not the names.

Quick Check 8.2

Consider this program.

int *q = p; copies an address, exactly as in Class 7 §5. It does not allocate anything — there is no new on that line. So p and q are two names for one arrow, both aimed at the single anonymous int, and *q = 9; writes into the same storage that *p reads.

(b) Would adding delete q; after delete p; be correct, harmless, or a bug?

A bug — and a serious one. There was exactly one call to new, so there must be exactly one call to delete. delete p; already returned the block; delete q; would try to return the very same block a second time. That is a double delete, which is undefined behavior. We look at what actually happens in §6.

Note the trap: the code looks symmetric. Two pointers, two deletes. Counting pointers is the wrong instinct; count calls to new.

As written the program is safe even against this mistake, because both pointers were set to nullptr after the delete, and deleting a null pointer is defined to do nothing at all. That habit is §6 too.

3.new[] and delete[]: whole arrays

Now the version you will actually use. Allocating an array is the same idea with two syntax changes, and the second one is genuinely strange.

Definition— new[] and delete[]

new T[n] allocates a contiguous block big enough for n objects of type T and returns a pointer to the first one. For new, you must obviously specify the length of the array — and n may be any expression, including one whose value the program only learns while it is running.

int n = 5;
int *p = new int[n];      // n ints, contiguous, on the heap
p[0] = 1;                 // subscript it exactly like an ordinary array

delete [] p releases the whole block. The syntax is peculiar: you write a pair of empty brackets, and the length of the array is not specified. The run-time system already knows how much memory it handed you.

delete [] p;              // note the empty brackets, and no length

Everything you learned in Class 7 about the pointer/array duality applies unchanged. p[i] is *(p + i), the block is contiguous, and a function that takes a double * parameter cannot tell a new[] array from an ordinary one. What is different is only where the memory came from and who has to give it back.

Now the strange part, and the professor is not shy about it. Here is his own editorial comment on the two-form design, verbatim from the notes: "This is terribly inconvenient and causes many bugs. I have no idea why C++ was designed this way." He is right. Take the rule seriously anyway.

Common Mistake— mixing delete and delete[]

It is an error to invoke operator delete [] (with brackets) for a single variable, or delete (without brackets) to deallocate an array. The two forms are not interchangeable, and the compiler cannot check it for you in general, because the type of the pointer is int * either way.

Worked Example— the motivating program, finally correct

Back to the score-averaging program from §1. Now the array is exactly as big as the user says, decided while the program runs, with no MAX and no guess.

using namespace std;

    int n;

That sentence is the entire justification for this class. A statically allocated array cannot do it, because its length is fixed when the program is compiled.

Warning— a typo in the course notes worth knowing

The slide that makes the point above prints the statement as double pd = new double[n];, with no star. As written that does not compile: new double[n] produces a double *, and you cannot store a double * in a double. The intended line is

double *pd = new double[n];

The correction is one character, but the error message it produces — "cannot convert 'double*' to 'double' in initialization" — is one you should be able to read at a glance, because it means you dropped a star somewhere.

Quick Check 8.4

Each of the following fragments is wrong. Say what is wrong and give the fix.

(a) int *p = new int[10]; ... delete p;

Allocated as an array, released as a single object. Fix: delete [] p;. On this compiler -Wall catches it with "called on pointer returned from a mismatched allocation function", but do not count on that in general — if the allocation and the delete are in different functions, the compiler cannot see the pair.

(b) int *p = new int; ... delete [] p;

The mirror image: a single object released with the array form. Fix: delete p;. Also undefined behavior, also often silent.

(c) int n = 10; int *p = new int[n]; ... delete [n] p;

You never give the length back. delete [n] p; is a syntax error — the brackets must be empty. Fix: delete [] p;.

The reason the language can get away with empty brackets is that the run-time system recorded the block size when it handed the memory out. It knows; you do not have to tell it.

(d) double *p = new double[n]; p = q; delete [] p; where q is another valid pointer.

Two bugs from one line. The assignment p = q; overwrites the only copy of the address of the new block, so that block can never be released — a memory leak. And then delete [] p; releases whatever q points at, which the code that owns q will very reasonably also try to release later — a double delete.

Fix: release before repointing.

delete [] p;
p = q;

Better still, do not let two pointers own the same block at all. When we build classes that hold heap memory in Class 14, this exact situation — one block, two owners — is what the copy constructor and the assignment operator exist to prevent.

4.Allocating in one function, releasing in another

Here is the property that makes dynamic memory qualitatively different from everything you have used so far, and it follows directly from the definition: heap memory does not go out of scope.

Recall the warning from Class 7 §8: a function must never return the address of one of its own locals, because that variable dies at the closing brace. The compiler even says so.

returnlocal.cpp
int* makeFive() {
    int five = 5;
    return &five;          // returns the address of a variable that is about to die
}
returnlocal.cpp: In function 'int* makeFive()':
returnlocal.cpp:6:12: warning: address of local variable 'five' returned [-Wreturn-local-addr]
    6 |     return &five;          // returns the address of a variable that is about to die
      |            ^~~~~

Now change one word — new instead of a local — and the same shape of function is not just legal but useful, because what it returns a pointer to is not on the stack and therefore does not die when the function returns.

Worked Example— stringToArray, from the course notes

The function receives a string, dynamically allocates a char array to hold its individual characters, and returns a pointer to that array. The caller prints it and, when finished, releases it. stringtoarray.cpp
// stringtoarray.cpp -- allocate in one function, release in another
#include <iostream>
#include <string>
using namespace std;

char* stringToArray(const string &s) {
    int n = s.size();
    char *p = new char[n];          // dynamic memory allocation
    for (int i = 0; i < n; ++i) {
        p[i] = s[i];
    }
    return p;                       // return pointer
}

int main() {

    string s2("alpha");

    char *p1 = stringToArray(s1);   // memory allocated inside function
    char *p2 = stringToArray(s2);   // memory allocated inside function

        cout << p1[i] << endl;
    cout << endl;
    for (int i = 0; i < static_cast<int>(s2.size()); ++i)
        cout << p2[i] << endl;

    delete [] p1;                   // release memory
    delete [] p2;                   // release memory
    return 0;
}

The course notes list four things worth noticing about this program, and all four are worth having:

  1. The length of the input string is not known inside the function at compile time. The value of n = s.size() can be different on each call — and it is: 4, then 5.
  2. A fresh array is allocated on each call. It is not the same array being reused. p1 and p2 hold different addresses.
  3. The dynamically allocated memory does not go out of scope at function exit. Dynamically allocated memory is deallocated only when a call to delete[] is made, and no such call happens inside stringToArray. So p1 and p2 in main point at valid memory.
  4. The allocation and the deallocation happen in different subprograms. The memory is allocated in stringToArray and released in main. There is no reason why they must happen in the same scope — and this is completely unlike static allocation, where the closing brace decides everything.

Point 4 is a gift and a liability at once. It is what lets a function build and hand back a data structure. It is also why the question "who is responsible for deleting this?" now has to be answered in prose, in a comment, because the language will not answer it for you.

Warning— this array is not a C string

stringToArray allocates s.size() characters and copies exactly that many. It does not append a terminating '\0'. The program above is safe because it only ever prints the characters one at a time in a bounded loop — but a student who writes

cout << p1 << endl;      // DANGER: p1 is not NUL-terminated

gets a buffer overrun: cout will keep printing bytes past the end of the block until it happens to find a zero. If you want the result to be printable as a string, allocate one extra character and terminate it yourself:

char *p = new char[n + 1];
for (int i = 0; i < n; ++i)
    p[i] = s[i];
p[n] = '\0';                 // now it is a C string

The course notes do not mention this. It is the single most common way this particular example gets students into trouble when they adapt it.

Quick Check 8.5

In stringToArray, the local variables n and p are destroyed the instant the function returns.

(a) Why, then, is the array still there for main to use?

Because p and the array are two different things. p is an automatic pointer variable living on the stack inside stringToArray, and it is destroyed at the closing brace. The array is on the heap, and heap memory is released only by delete or delete[] — never by a scope ending.

What return p; does is copy the address out of the dying local before it dies. The address is just a number; copying it is free. main stores that number in p1, and the block it names is still there.

(b) What would go wrong if the function ended with delete [] p; return p; instead?

main would receive the address of memory that has already been released — a dangling pointer. Every subsequent p1[i] would be a read of freed memory, which is undefined behavior; and main's own delete [] p1; would be a double delete on top of that.

The function must not release what it is handing over. Somebody has to, later, and here that somebody is main. This is the "who owns it?" question from the worked example, and it is the whole reason the Big Three exists (Class 15).

5.Memory leaks

Now the failure mode that follows directly from §4. If heap memory is released only when you say so, then forgetting to say so means it is never released. That has a name.

Definition— memory leak, garbage

A memory leak occurs when dynamically allocated memory can no longer be reached by any pointer in the program, and therefore can never be released. The address has been lost; there is no way to deallocate it.

The resulting inaccessible memory is called garbage. If the quantity of garbage grows to an unacceptable level, other applications may not be able to obtain enough memory to run correctly.

Note what a leak is not. It is not a crash, it is not a wrong answer, and it is not anything the compiler will mention. A leaking program computes exactly the right result and exits with status 0. That is precisely what makes it dangerous: the only symptom is that a long-running program slowly consumes memory until the machine is in trouble, hours after the mistake ran.

Quick Check 8.7

Repair the leaking program above.

(a) Fix it by adding exactly one statement, keeping the single pointer p.

Release the first array before the address is overwritten:

    delete [] p;                    // release the first array BEFORE repointing

(b) Give a second, different fix.

    char *p1 = stringToArray(s1);
    char *p2 = stringToArray(s2);
    // ... use them ...
    delete [] p1;
    delete [] p2;

Two calls to new[], two partner calls to delete[]. Either fix is correct; which you choose depends on whether you still need the first array after the second exists.

(c) A student says "the leak does not matter, the memory is given back when the program exits anyway." Are they right?

They are technically right about this program and practically wrong about programming. Yes — on any modern operating system, every byte a process allocated is reclaimed when the process ends, leak or no leak. A four-byte leak in a program that runs for a millisecond harms nobody.

But look at where the leaking statement was: inside the flow of a function that gets called repeatedly. Put that pattern in a loop, or in a server that runs for a month, or in a class whose objects get created and destroyed thousands of times, and the leak is no longer four bytes — it is four bytes per iteration, forever, and the program dies of memory exhaustion with no clue as to why.

And the graded reason: from Class 14 onward, every destructor you write on an exam exists precisely to prevent this, and a missing delete in a destructor costs points every single time. Learn to see the leak now, while it is four bytes.

6.Dangling pointers, double delete, and the nullptr habit

A leak is memory you can no longer reach. This section is the opposite failure: a pointer you can still reach that no longer points at anything valid. Of the two, this one is worse, because a leak merely wastes memory while this one corrupts it.

Definition— dangling pointer

A dangling pointer is a pointer that holds the address of memory that has already been released (or of a variable that has already gone out of scope). It looks exactly like a valid pointer — it is not null, and testing it against nullptr will not catch it — but the thing it names no longer exists.

Dereferencing a dangling pointer is undefined behavior. Deleting through one a second time is undefined behavior too, and has its own name: a double delete.

Where do dangling pointers come from? Almost always from delete, because — as we saw in §2 — delete p; does absolutely nothing to p. It releases the block and leaves the pointer holding the address of memory that is no longer yours.

Both of these bugs have the same root: after delete p;, the pointer p still holds a number that looks like a perfectly good address. There is a one-line habit that fixes both.

Key Idea— set the pointer to nullptr after deleting

Write these two lines together, always:

delete p;

  • A null pointer can be tested. if (p != nullptr) now means something, where before the delete-and-forget it meant nothing.

And dereferencing null crashes immediately and predictably at the guilty line, instead of silently reading a stale value and failing somewhere else an hour later. A reliable crash is worth a great deal.

Classify each fragment as memory leak, dangling pointer, double delete, or correct. Assume everything else about the program is fine.

(c) int *p = new int[3]; delete [] p; p = nullptr; delete [] p;

Correct — pointless, but correct. The second delete [] p; operates on a null pointer and is defined to do nothing. One new[], one real delete[], no leak, no undefined behavior.

7.Arrays of pointers, and 2-D arrays built at run time

Everything so far has been one block of memory at a time. The last two sections put blocks together, and the building material is an idea that sounds like a tongue-twister but is completely ordinary: an array whose elements happen to be pointers.

Definition— array of pointers

It is perfectly possible to declare an array of pointers:

const int n = 10;
int *array_ptr[n];

Observe that the array length is n, and the data type of each element is pointer to int. So array_ptr[3] is an int *, and *array_ptr[3] is the int it points at.

Nothing is allocated on the heap by that declaration. It reserves ten pointers, on the stack, all uninitialized. Where they point is up to you.

Worked Example— rearranging pointers without moving data

// arrayofptr.cpp -- an array whose elements are pointers

That is the practical reason arrays of pointers exist. Sorting a thousand large objects by swapping pointers moves 8 bytes per swap instead of the whole object, and every pointer that already pointed into the collection keeps working. No new was involved here at all — an array of pointers is a useful idea on its own.

Now make the array of pointers itself dynamic. It is also perfectly possible to allocate one with new, and the notes give the shape directly:

int **pp = new int*[n];
// etc
delete [] pp;

Read the type slowly. new int*[n] allocates n objects of type int *, and returns a pointer to the first of them — a pointer to a pointer to int, so the variable holding it is declared int **pp. Class 7 asked "can we declare a pointer to a pointer?" and answered "oh yes"; this is where that answer starts earning its keep.

Key Idea— an array of pointers, each pointing at an array, is a 2-D array

A rectangular array of size m by n is m rows, each of which is an array of length n. So: allocate an array of m pointers, then point each one at its own array of n ints. The result supports the subscript syntax you already know — pp[i][j] — because pp[i] is a pointer and pp[i][j] is its j-th element.

Procedure— build and destroy an m by n array on the heap

Allocation is two steps, and the order is forced:

int **pp = new int*[m];        // 1. the array of pointers (length m)
for (int i = 0; i < m; ++i) {
    pp[i] = new int[n];        // 2. one row of n ints for each pointer
}

Release is the same two steps in reverse order, and that order is forced too:

for (int i = 0; i < m; ++i) {
    delete [] pp[i];           // 1. release each row
}
delete [] pp;                  // 2. then release the array of pointers

Count the calls: m + 1 allocations, m + 1 releases. Exactly as the rule demands.

Common Mistake— releasing the rows in the wrong order, or not at all

Two failures, both easy to write:

  • delete [] pp; on its own. As the notes put it: it is not adequate to simply write "delete [] pp;", because that does not release all the memory. There must be one call to operator delete [] to partner every call to operator new. You released the array of pointers and leaked every row.
  • delete [] pp; first, then the row loop. Worse. Once pp is released, pp[i] is a read of freed memory — a dangling-pointer read — and the addresses you get back are garbage that you then pass to delete[]. The rows must go first, because the only record of where they are lives inside pp.

(Five rather than three because the C++ runtime makes two allocations of its own before main starts; what matters is that the two numbers are equal.)

One honest caveat about this construction, since you will meet the alternative eventually: the rows are three independent blocks, not one contiguous rectangle. That is different from a statically declared int a[2][3];, which is a single 24-byte block. The subscript syntax is identical, which is exactly why it is easy to forget they are not the same thing.

Quick Check 8.10

A program builds a 4 by 7 array of double with the two-step method.

(a) How many calls to new are made, and how many calls to delete[] are needed?

Five of each. One new double*[4] for the array of pointers, plus four calls to new double[7], one per row. Therefore four delete [] pp[i]; calls and one delete [] pp;.

The general answer is m + 1, and it does not depend on n at all — each row is one allocation no matter how wide it is.

(b) Write the declaration of the pointer variable, and the allocation.

int m = 4, n = 7;

    pp[i] = new double[n];

Two stars in the declaration, one star in the new double*[m]. The rule to say out loud: the type of pp[i] is double *, so the array pp points at is an array of double *, so pp itself is a double **.

(c) A student writes the release as delete [] pp; followed by the loop of delete [] pp[i];. What happens?

Undefined behavior. Once delete [] pp; has run, the array of pointers is gone, so every pp[i] in the loop is a read of freed memory. The values that come back may look like the old addresses, in which case the deletes appear to work; or they may be garbage, in which case you are calling delete[] on an address that was never allocated.

Under valgrind this shows up as "Invalid read of size 8" followed by "Invalid free()". The fix is simply to put the loop first: rows before the row table, always, because the row table is the only place the row addresses are recorded.

8.Ragged arrays

One last payoff, and it is the one that cannot be imitated with a static array at all.

Key Idea— from the course notes

A statically allocated array must be rectangular. A dynamically allocated array need not be.

int a[4][4]; gives you sixteen ints in a rectangle and there is no way to ask for anything else. But the rows of a heap-built array are separate allocations, so nothing forces them to be the same length. Such an array is called ragged or jagged.

The notes' motivating case is a triangular calculation: suppose the only elements you need are the ones with column index at most the row index. Declaring a rectangular array wastes the entire upper half, which matters when the array is large. Row i needs exactly i + 1 elements, so ask for exactly that many:

const int m = 4;
int **pp = new int*[m];         // array of pointers
for (int i = 0; i < m; ++i) {
    pp[i] = new int[i + 1];     // allocate triangular array
}

The arrays pp[i] are allowed to have unequal lengths. The release code is unchanged from §7 — and this is the moment to appreciate why delete[] takes no length: the run-time system remembers how big each row was, even though the rows are all different sizes and your program no longer has that information anywhere.

for (int i = 0; i < m; ++i) {
    delete [] pp[i];            // release memory
}
delete [] pp;                   // release memory
Worked Example— Pascal's triangle in a ragged array

Here is a genuinely triangular problem to put in a triangular array. Each entry is the sum of the two above it, with 1s down both edges. Predict the four lines — and count the total number of ints the program allocates.

ragged.cpp
// ragged.cpp -- a triangular array: row i has i+1 elements
#include <iostream>
using namespace std;

int main() {
    const int m = 4;

    int **pp = new int*[m];             // array of pointers
    for (int i = 0; i < m; ++i) {
        pp[i] = new int[i + 1];         // allocate triangular array
    }

    // Pascal's triangle, one row at a time
    for (int i = 0; i < m; ++i) {
        pp[i][0] = 1;
        pp[i][i] = 1;
        for (int j = 1; j < i; ++j)
            pp[i][j] = pp[i-1][j-1] + pp[i-1][j];
    }

    for (int i = 0; i < m; ++i) {
        for (int j = 0; j <= i; ++j)
            cout << pp[i][j] << " ";
        cout << endl;
    }

    for (int i = 0; i < m; ++i) {
        delete [] pp[i];                // release memory
    }
    delete [] pp;                       // release memory
    return 0;
}

Three details in the code are worth naming:

LineWhy it is written that way
pp[i] = new int[i + 1];Row 0 gets 1 element, row 3 gets 4. The + 1 is because row indices start at 0 but lengths start at 1 — the usual place to be off by one.
for (int j = 0; j <= i; ++j)The printing loop bound is <= i, not < m. Every loop over a ragged array must know that row's own length. Using < m here would read past the end of the short rows — and it would compile, and it would usually print something.
pp[i][j] = pp[i-1][j-1] + pp[i-1][j];Reaching into the previous row, which is shorter. It is safe because j runs only to i - 1 here, and row i-1 has i elements.

The middle row is the real cost of raggedness: the array no longer knows its own row lengths. With a rectangle you can carry one n around; with a ragged array you have to carry a length per row, or derive it from the structure as we did here. Nothing in the pointers themselves records it, and valgrind's "Invalid read of size 4" is what you get when you guess wrong.

The release loop is identical to §7's. Rows first, then the table — four calls plus one, matching the one plus four allocations, and the run is leak-free.

Quick Check 8.12

You need a ragged array of double with m rows, where row i has 2*i + 1 elements (so 1, 3, 5, 7, …).

(c) Later, some other function receives only pp and m. Can it print the array?

So you must either hard-code the rule (2*i + 1), or pass an array of lengths alongside, or — the answer that the rest of this course gives — put the pointer and the lengths inside a class, so they cannot be separated. That is Class 9, and it is the reason the syllabus puts classes immediately after this material: everything you have seen today is a data structure held together by discipline instead of by the language, and a class is how you make the language hold it together for you.

    for (int i = 0; i < 3; i++)         // (b) copy y into the dynamic array
        p2[i] = y[i];

    cout << "*p1 = " << *p1 << endl;
    cout << "p2  = ";
    for (int i = 0; i < 3; i++)
        cout << p2[i] << " ";
    cout << endl;

    delete p1;                          // (c) release both
    delete [] p2;
    return 0;
}
*p1 = 7
p2  = 3 1 4

Things to notice.

  • Look at the given declaration line: int *p1 = new int, *p2 = new int[3]; declares two pointers because the star is repeated. Written int* p1 = new int, p2 = ... it would not even compile. This is Class 7 §2's rule, and the professor's own exam depends on it.
  • Every one of these five sub-tasks is one or two lines, worth two points, with no partial credit except on the last two. Nothing here rewards length; it rewards getting the stars and the brackets right.
  • The first two parts of this exam question — declaring px and py — were Class 7's Practice Problem 5. Together the five parts are a complete tour of both pointer classes in ten lines.
  • Valgrind: leak-free.

Problem 5 — Write a complete C++ program (added, in the format of the professor's midterm Problem 1)

Write a complete C++ program that asks the user how many numbers they have, reads exactly that many numbers into just enough space to store them, computes their average, and then prints every input that is above the average. Do not use a fixed-size array and do not use a vector — the point of this version is the new[] / delete[] pair. Sample run:

How many numbers? 6
Enter 6 numbers: 10 20 30 40 50 60
average = 35
above average: 40 50 60

Plan. Four stages, and the professor's rubric for this format pays for each one separately: the standard beginning and ending; declaring and filling the storage; computing the aggregate; printing the filtered subset. Because the count comes first, the allocation is straightforward — read n, then new double[n]. Two passes over the data are needed, one to total and one to filter, and both are cheap because the array is still there. (Had the input been sentinel-terminated, as on some of his papers, you would not know n in advance and a vector would be the better tool. Read the question.)

aboveaverage.cpp
// aboveaverage.cpp -- exam-style: read n, store exactly n values, report the above-average ones
#include <iostream>
using namespace std;

int main() {
    int n;
    cout << "How many numbers? ";
    cin >> n;

    double *a = new double[n];              // just enough space, decided at run time

    cout << "Enter " << n << " numbers: ";
    for (int i = 0; i < n; ++i)
        cin >> a[i];

    double sum = 0.0;
    for (int i = 0; i < n; ++i)
        sum += a[i];
    double avg = sum / n;

    cout << "average = " << avg << endl;
    cout << "above average: ";
    for (int i = 0; i < n; ++i)
        if (a[i] > avg)
            cout << a[i] << " ";
    cout << endl;

    delete [] a;
    a = nullptr;
    return 0;
}
How many numbers? Enter 6 numbers: average = 35
above average: 40 50 60

(The input was piped in from a file, so the digits do not echo after the prompts. In a terminal the transcript looks exactly like the sample run in the question.)

Things to notice.

  • sum is a double, and sum / n is therefore a floating-point division. Had sum been an int, sum / n would be integer division and the average of 10 through 60 would come out as 35 by luck here but as 34 for 10 20 30 40 50 61. Integer division is the most common silent wrong answer in this course.
  • The array is read once and used twice. Storing the input is what makes the second pass possible — a program that only accumulated a running total could print the average but could never go back and filter.
  • The comparison is strict: a[i] > avg. A value exactly equal to the average is not "above" it. Say which you chose if the question is ambiguous.
  • delete [] a; with brackets, then a = nullptr;. The rubric pays for the release; the null assignment is free insurance.
  • Valgrind: "All heap blocks were freed — no leaks are possible."

Problem 6 — Four bugs in twelve lines (added)

The program below has four distinct memory bugs. Name each one, say what class of error it is (leak, dangling pointer, double delete, mismatched delete), and rewrite the program correctly.

// bughunt.cpp -- four memory bugs in twelve lines
#include <iostream>

int main() {
    int n = 4;
    int *a = new int[n];
    for (int i = 0; i < n; ++i)

    *b = 100;

// bughunt_fixed.cpp -- the same program with every bug repaired
#include <iostream>
using namespace std;

int main() {
    int n = 4;
    int *a = new int[n];
    for (int i = 0; i < n; ++i)
        a[i] = i;

    int *b = new int;
    *b = 100;

    for (int i = 0; i < n; ++i)     // print a before letting go of it
        cout << a[i] << " ";
    cout << endl;

    delete [] a;                    // array: delete[]
    a = nullptr;

    cout << *b << endl;             // read b while it is still alive

    delete b;                       // single object: delete
    b = nullptr;
    return 0;
}

Things to notice.

  • Two news, two deletes, one of each form, and every read happens before the corresponding release. Valgrind reports zero errors and zero leaks.
  • The original a = b; looked like the most innocent line in the program. Assignment between pointers is never innocent when one of them owns heap memory: it leaks what the left-hand side used to own and duplicates ownership of what the right-hand side owns. Both halves of that sentence are bugs.
  • Fixing that one line properly — delete the old block, allocate a new one, copy the contents — is precisely what operator= has to do for a class that holds a pointer. Class 15 spends an entire session on those four steps. You have now seen why they are all necessary.
  • Both nullptr assignments are optional as the code stands. Leave them in. They cost nothing and they turn a future mistake into a null dereference at the guilty line instead of a silent corruption somewhere else.
Lecture Summary
  • Static (automatic) allocation is decided by the compiler and released automatically when the variable goes out of scope. Dynamic allocation happens at run time, comes from the heap, and is released only when you call delete or delete[].
  • The honest reason to use the heap is that the size is not known until run time. double a[n]; with a variable n is not standard C++, however willingly g++ accepts it.
  • new T returns a T * to one anonymous object; delete p releases it. The allocated variable has no name — lose the pointer and you lose the variable.
  • new T[n] returns a T * to n objects; delete [] p releases them. The brackets are empty: you never give the length back.
  • For every call to new there must be a partner call to delete, of the matching form. Count calls to new, not pointer variables.
  • Heap memory does not go out of scope, so a function may allocate and return a pointer that its caller later deletes. Which means somebody has to write down who owns it.
  • A memory leak is heap memory no pointer can reach any more; the unreachable memory is garbage. A leaking program does not crash and does not warn — only a tool such as valgrind will tell you.
  • After delete p; the pointer is unchanged and now dangling. Dereferencing it or deleting through it again is undefined behavior. Write p = nullptr; immediately after every delete: deleting null is a guaranteed no-op, and null can be tested.
  • A 2-D array on the heap is an array of pointers, each pointing at a row: m + 1 allocations, and m + 1 releases in the reverse order — rows first, then the array of pointers.
  • Because the rows are separate blocks, they may have different lengths: a ragged array. A statically declared array must be rectangular; this one need not be. The price is that nothing records the row lengths for you.
