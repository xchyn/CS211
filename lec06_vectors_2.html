Vectors II — Growing, Shrinking and Nesting

What size() and capacity() actually track, why push_back stays cheap even though a vector sometimes copies everything it owns, how to shrink a vector safely, and how to nest vectors to build a table.

Learning Objectives

By the end of today's class you should be able to:

  2. Describe what happens inside a vector during reallocation, and explain why repeated push_back calls are still cheap on average even though some of them are expensive.

  8. Build and use a vector of vectors to represent a two-dimensional table, including a ragged table whose rows are different lengths.

1.Size vs. capacity

Class 5 left off with the basics: declare a vector<int>, grow it with push_back, read its length with size(). That is enough to write correct programs, but it hides an interesting question. An array's length is fixed the moment you write int a[10]; — the compiler carves out exactly ten ints of memory and never touches that decision again. A vector's length changes while the program runs. Every time you call push_back, where does the new element's memory come from?

The vector cannot ask the operating system for one more int of space next to the ones it already has — there is no guarantee anything else isn't already using that memory. So instead, a vector keeps track of two different numbers, not one.

Definition— size and capacity

The size of a vector is the number of elements it actually holds right now — what size() returns, and what you have been using since Class 5.

The capacity of a vector is the number of elements it has room for in the block of memory it currently owns, before it would have to go get a bigger block. capacity() returns it.

Because a vector never holds more elements than it has room for, capacity() >= size() always holds. The gap between them is spare room the vector grabbed in advance, anticipating that you might call push_back again soon.

The professor's own notes put it in almost exactly those words: "the vector allocates extra space in case we wish to grow the vector (for example, using push_back)." The best way to see that extra space appear is to watch it happen, one push_back at a time.

Worked Example— watching capacity grow

This program pushes the integers 1 through 10 onto an empty vector, printing size() and capacity() after every single call. Predict which pushes change the capacity and which do not. Nothing here is guaranteed by the standard — you are about to see one real implementation's behavior, this machine's libstdc++.

capacity.cpp
// capacity.cpp -- watch size and capacity as a vector grows
#include <iostream>
#include <iomanip>
#include <vector>
using namespace std;

int main() {
    vector<int> vec_i;
    cout << "after           size   capacity" << endl;
    cout << "(nothing)  " << setw(8) << vec_i.size()
         << setw(11) << vec_i.capacity() << endl;

    for (int i = 1; i <= 10; ++i) {
        vec_i.push_back(i);
        cout << "push_back  " << setw(8) << vec_i.size()
             << setw(11) << vec_i.capacity() << endl;
    }
    return 0;
}

push_back         1          1

push_back         5          8
push_back         6          8
push_back         7          8
push_back         8          8
push_back         9         16
push_back        10         16

A brand-new, empty vector starts with capacity 0 — it has not asked for any memory yet. The very first push_back gives it capacity 1. From there the capacity jumps 1 → 2 → 4 → 8 → 16: every time the vector runs out of room, it doubles. Most calls to push_back — pushes 2, 4, 6, 7, 8, and 10 above — do not touch the capacity at all; there was already room. Only pushes 1, 3, 5, and 9 trigger a jump.

Key Idea

Most calls to push_back are nearly free: there is spare capacity, so the vector just writes the new element into the next slot and increments size. Only occasionally — when capacity runs out — does it have to go find a bigger block of memory. That occasional expensive step is called a reallocation, and it is the subject of §2.

Quick Check 6.1

Using the table above as your reference, suppose the same program kept going: pushes 11 through 17.

(a) After push 11, what is the capacity? After push 16?

After push 10 the capacity is 16 and the size is 10, so there is room for 6 more pushes (11–16) with no reallocation. Capacity stays 16 for pushes 11 through 16 — size climbs to match, but capacity does not move until it has to.

(b) At which push does the capacity change again, and to what value?

Push 17. Size 16 already fills capacity 16 exactly, so the very next push_back (the 17th) finds no room and reallocates. Following the doubling pattern (1, 2, 4, 8, 16, 32, …), the new capacity is 32.

Things to notice. You can answer this without running any code: capacity only ever changes at the pushes numbered one more than a power of two (1, 3, 5, 9, 17, 33, …), because that is exactly when size has just caught up to the previous power of two.

2.Why push_back is still cheap

Here is the part the professor's slides state as a bullet but never demonstrate: "if the size grows too large, the vector allocates extra memory automatically." What does "allocates extra memory" actually involve? Not just finding a bigger block — the vector has to move every single element it already owns into that new block, because the old block might not even be adjacent to anything free. Here is the sequence, spelled out:

Procedure— what a reallocation does
  1. The vector asks the memory manager for a new, bigger block — typically twice the current capacity, in libstdc++.
  2. It copies (or, for types that support it, moves) every existing element from the old block into the new one, in order.
  3. It frees the old block.
  4. Only then does it place the new element being pushed, in the newly freed slot at the end.

Step 2 is the expensive one, and it gets more expensive the bigger the vector already is. Copying a vector of 1,000,000 elements to grow it is not a cheap operation. So why do we still say push_back is "cheap"?

The answer is that reallocations become rarer exactly as fast as they become more expensive, and those two effects cancel out. Doubling means the vector reallocates at sizes 1, 2, 4, 8, 16, … — each reallocation is twice as costly as the last, but you have to push twice as many elements to trigger it. Averaged over all the pushes, the cost per push_back stays constant. This is worth seeing in real numbers, not just in the abstract.

Worked Example— counting the copies over 100 pushes

This program pushes 100 integers and, every time the capacity changes, prints the jump and tallies how many elements had to be re-copied that time (the old capacity — that is how many elements existed right before the move). Predict roughly how many reallocations happen before you look.

moves100.cpp
// moves100.cpp -- reallocation count and copy count for 100 push_back calls
#include <iostream>
#include <vector>
using namespace std;

int main() {
    vector<int> v;
    int reallocations = 0;
    long long moved = 0;
    size_t oldCap = v.capacity();

    for (int i = 0; i < 100; ++i) {
        v.push_back(i);
        if (v.capacity() != oldCap) {
            ++reallocations;
            moved += oldCap;
            cout << "capacity " << oldCap << " -> " << v.capacity()
                 << " while inserting element number " << (i + 1) << endl;
            oldCap = v.capacity();
        }
    }
    cout << "reallocations = " << reallocations << endl;
    cout << "elements moved = " << moved << endl;
    cout << "size = " << v.size() << ", capacity = " << v.capacity() << endl;
    return 0;
}

capacity 1 -> 2 while inserting element number 2
capacity 2 -> 4 while inserting element number 3
capacity 4 -> 8 while inserting element number 5
capacity 8 -> 16 while inserting element number 9
capacity 16 -> 32 while inserting element number 17
capacity 32 -> 64 while inserting element number 33
capacity 64 -> 128 while inserting element number 65

Only 8 of the 100 push_back calls triggered a reallocation — the other 92 were plain writes into already-owned memory. The total number of elements moved across all 8 reallocations, 127, is less than the 100 elements that got pushed. In fact that is not a coincidence: doubling guarantees the total copying work stays proportional to the final size, no matter how large the vector grows. Computer scientists call this amortized constant time — "amortized" meaning the expensive operations are rare enough that, spread out over every call, the average cost per push_back stays roughly constant, even though any individual call might be the expensive one.

Warning— the growth factor is not part of the C++ standard

The doubling pattern you just saw (1, 2, 4, 8, 16, …) is not guaranteed by the C++ standard. The standard only requires that push_back be amortized constant time overall — it does not say by how much a vector must grow when it reallocates. Every major implementation happens to double (or close to it): libstdc++ (the one g++ uses, and the one that produced every number on this page) doubles exactly; some other standard libraries use a factor like 1.5. Never write code that depends on the exact sequence of capacities you saw above — treat it as "implementation-defined, and doubling in the compiler this course uses," not as a rule of the language.

Quick Check 6.2

A vector starts empty and 1,000,000 integers are pushed onto it, one at a time, with libstdc++'s doubling behavior.

(a) Roughly how many reallocations happen in total? (You do not need the exact number — reason about orders of magnitude, the way §1's table let you predict push 17 without running the code.)

Capacity doubles: 1, 2, 4, 8, …, and it takes about log₂(1,000,000) ≈ 20 doublings to reach a capacity past a million. So roughly 20 reallocations — not 1,000,000, and not even close. This is the whole reason the amortized-cost argument works: the number of reallocations grows only logarithmically with the number of pushes.

(b) A classmate says: "Since most push_back calls are cheap, it never matters how you grow a vector." Give one situation from §1 or §2 where the occasional expensive call still matters in practice.

Any single call to push_back can be the expensive one — there is no way to tell from the call site alone. If that call happens to be, say, inside a function with a strict time budget (a game's per-frame update, a real-time system), an occasional reallocation that copies a million elements can cause a visible stutter even though the average cost is fine. This is exactly what reserve() (a brief add-on you'll meet in §6) is for: paying the reallocation cost once, up front, on your own schedule.

Things to notice. "Amortized cheap" is a statement about the total cost over many calls, not a promise about any one call. Keep the two separate when you reason about performance.

3.front() and back()

You already read arbitrary elements with v[i]. Two of the most common accesses — the first element and the last — get their own named methods, if only because writing v[0] and v[v.size() - 1] everywhere gets tiresome and that second expression is one off-by-one mistake waiting to happen.

Definition— front() and back()

v.front() returns a reference to the first element of v, equivalent to v[0]. v.back() returns a reference to the last element, equivalent to v[v.size() - 1]. Neither one removes anything or changes the vector — they only read.

Worked Example— reading both ends

Predict the three lines this prints.

frontback.cpp
// frontback.cpp -- front() and back()
#include <iostream>
#include <vector>
using namespace std;

int main() {
    vector<int> vec_i;
    vec_i.push_back(2);
    vec_i.push_back(4);
    vec_i.push_back(8);
    vec_i.push_back(16);

    int n = vec_i.size();       // get length of vector
    int f = vec_i.front();      // first element of vector
    int b = vec_i.back();       // last element of vector

    cout << "size = "  << n << endl;
    cout << "front = " << f << endl;
    cout << "back = "  << b << endl;
    return 0;
}
size = 4
front = 2
back = 16

Nothing surprising once you know the definitions: front() grabbed the first value pushed (2), back() grabbed the most recent one (16). Both are just convenience wrappers around indexing.

Now the question every vector method in this class is going to ask sooner or later: what happens if the vector is empty?

Common Mistake— front() / back() on an empty vector is undefined behavior

Calling front() or back() on a vector with size() == 0 is undefined behavior — not a guaranteed crash, not a guaranteed exception, nothing the language promises at all. There is no element to return a reference to, and neither method checks first. The professor's own slides describe the closely related out-of-bounds case (vec_i[i] past the end) as something that "compiles successfully, but generates a run-time error" — that claim is too strong. Sometimes it crashes. Sometimes it does not, and the program just keeps running with garbage. Watch what actually happens on this machine:

emptyback.cpp
// emptyback.cpp -- back() on an empty vector: undefined behavior, NOT an error
#include <iostream>
#include <vector>
using namespace std;

int main() {
    vector<int> v;
    v.push_back(7);
    v.pop_back();               // v is now empty

    cout << "size = " << v.size() << endl;
    cout << "back = " << v.back() << endl;   // *** undefined behavior ***
    cout << "still running" << endl;
    return 0;
}
size = 0
back = 0
still running

No crash. No warning. The program prints a 0 — happening, on this build, to be whatever value was left sitting in the memory back() read — and keeps going as if nothing were wrong. That is the dangerous part: undefined behavior that looks fine is worse than a crash, because nothing forces you to notice the bug. This exact output is machine- and library-dependent — do not treat the 0 as a fact about C++, treat "do not call back() on an empty vector" as the fact. The fix is always the same: check !v.empty() (or v.size() > 0) before you call front() or back().

Quick Check 6.3

Suppose instead the program had called v.front() after the same push_back / pop_back() pair, on an empty vector<int>.

(a) Is this guaranteed to crash the program?

No. Exactly like back(), front() performs no check. The result is undefined behavior: it might crash, might silently return garbage, or might appear to work. Nothing in the language guarantees any particular one of those outcomes.

(b) What one line of code, added right before the call, makes the program's behavior fully defined again?

if (!v.empty()) {
    cout << v.front() << endl;
}

Things to notice. Guarding with !v.empty() (or, equivalently, v.size() > 0) is the only fix that works in every case. There is no way to make front()/back() "safely" return something meaningful on an empty vector — there is no element to return, so the only correct move is to never call them when the vector is empty.

reverse_input.cpp
// reverse_input.cpp -- read numbers until -1, then report them back to front
#include <iostream>
#include <vector>
using namespace std;

int main() {
    vector<int> v;
    int x;

    cout << "Enter some positive integers until -1 to stop: ";
    cin >> x;
    while (x != -1) {
        v.push_back(x);
        cin >> x;
    }

    cout << "You entered " << v.size() << " numbers." << endl;
    if (v.empty()) {
        cout << "Nothing to report." << endl;
        return 0;
    }

    cout << "First: " << v.front() << endl;
    cout << "Last:  " << v.back()  << endl;

    cout << "Reversed: ";
    while (!v.empty()) {
        cout << v.back() << " ";
        v.pop_back();
    }
    cout << endl;
    cout << "Size is now " << v.size() << "." << endl;
    return 0;
}
Enter some positive integers until -1 to stop: You entered 2 numbers.
First: 3
Last:  7
Reversed: 7 3
Size is now 0.

Things to notice.

  • The if (v.empty()) early return matters: without it, an input of just -1 would fall straight through to v.front() on an empty vector — exactly the undefined behavior from §3.
  • The reversing loop never calls back() or pop_back() on an empty vector, because the loop condition !v.empty() is checked before every iteration, including the last one that leaves the vector empty.
  • By the time the loop ends, size() is 0 and every element is gone — but as §4 and §5 will show, the memory the vector allocated along the way is still sitting there, unused, until the vector itself is destroyed.

4.pop_back(): shrinking from the end

Just as push_back is the only way to add an element, pop_back() is the standard way to remove one. The professor's notes are precise about what it does: "we remove an element from the end of a vector via pop_back(). This decreases the length of the vector by one."

Definition— pop_back()

v.pop_back() removes the last element of v and decreases size() by one. It returns nothing — if you want the value before it disappears, read it with back() first, then call pop_back() as a separate statement.

Here is the question §1 sets up perfectly: when pop_back() shrinks the size, does the vector give any memory back?

Worked Example— pop_back() and capacity

Five squares get pushed on, then two get popped, then one more gets pushed back on. Predict size() and capacity() after each stage — in particular, predict whether the last push_back triggers a reallocation.

popcap.cpp
// popcap.cpp -- pop_back() lowers the size, not the capacity
#include <iostream>
#include <vector>
using namespace std;

int main() {
    vector<int> v;
    for (int i = 1; i <= 5; ++i) v.push_back(i * i);
    cout << "size = " << v.size() << ", capacity = " << v.capacity() << endl;

    v.pop_back();
    v.pop_back();
    cout << "size = " << v.size() << ", capacity = " << v.capacity() << endl;

    v.push_back(100);
    cout << "size = " << v.size() << ", capacity = " << v.capacity()
         << ", back = " << v.back() << endl;
    return 0;
}
size = 5, capacity = 8
size = 3, capacity = 8
size = 4, capacity = 8, back = 100

Popping twice drops the size from 5 to 3, but the capacity stays at 8 the whole time — pop_back() never shrinks capacity. That has a nice consequence: pushing 100 back on afterward does not reallocate at all. size climbs to 4, capacity is still 8, and the new element just reuses the slot that element index 3 (the popped 16) used to occupy. pop_back() only marks the slot as unused; it does not erase it, zero it, or free it.

Common Mistake— pop_back() on an empty vector is also undefined behavior

Just like front() and back(), pop_back() performs no check that there is anything left to remove. Calling it on an empty vector is undefined behavior. This one is especially easy to trigger by accident: a loop that pops once too many, or a while loop with the emptiness check on the wrong side of the pop. Here is what happens when a program pops twice after only one push_back:

emptypop.cpp
// emptypop.cpp -- pop_back() on an empty vector: also undefined behavior
#include <iostream>
#include <vector>
using namespace std;

int main() {
    vector<int> v;
    v.push_back(5);

    v.pop_back();
    cout << "after 1 pop: size = " << v.size() << endl;

    v.pop_back();               // *** one pop too many: undefined behavior ***
    cout << "after 2 pops: size = " << v.size() << endl;

    v.push_back(42);
    cout << "size = " << v.size() << ", back = " << v.back() << endl;
    return 0;
}
after 1 pop: size = 0
after 2 pops: size = 18446744073709551615
size = 0, back = 42
double free or corruption (out)

Two things went wrong at once, and both are worth understanding. First, size() after the second, illegal pop_back() prints 18446744073709551615, not some small negative number — because size() returns an unsigned type, size_type, and decrementing a size of 0 wraps around to the largest value that type can hold, exactly the way an odometer rolls over from all-zeros to all-nines. Second, the program does not just print a wrong number and move on: this run corrupts the vector's internal bookkeeping badly enough that glibc's memory allocator detects it and aborts the program ("double free or corruption", exit status 134) a few lines later, right after the harmless-looking push_back(42). The exact way this fails is entirely machine- and library-dependent — a different standard library might not detect anything and just silently corrupt memory instead. What is guaranteed, on every implementation, is that it is a bug, and it is your job to prevent it, never the vector's.

5.clear(): empty, but not given back

Sometimes you don't want to remove elements one at a time — you want the vector completely empty, right now. That is clear().

Definition— clear()

v.clear() removes every element from v, setting size() to 0. Unlike pop_back(), it takes no argument and needs no loop — one call, and the vector is empty.

Worked Example— what clear() does, and does not, reset

Four elements go on, then clear() runs, then one more push_back happens. Predict size() and capacity() at each of the three checkpoints — this is the exact question §4 was building toward.

clear_demo.cpp
// clear_demo.cpp -- clear() empties the vector but does not give the memory back
#include <iostream>
#include <vector>
using namespace std;

int main() {
    vector<int> vec_i;
    vec_i.push_back(2);
    vec_i.push_back(4);
    vec_i.push_back(8);
    vec_i.push_back(16);
    cout << "before clear: size = " << vec_i.size()
         << ", capacity = " << vec_i.capacity() << endl;

    vec_i.clear();

    cout << "after  clear: size = " << vec_i.size()
         << ", capacity = " << vec_i.capacity() << endl;
    cout << "empty()? " << vec_i.empty() << endl;

    vec_i.push_back(99);      // reuses the memory that was already there
    cout << "after push:   size = " << vec_i.size()
         << ", capacity = " << vec_i.capacity() << endl;
    return 0;
}
before clear: size = 4, capacity = 4
after  clear: size = 0, capacity = 4
empty()? 1
after push:   size = 1, capacity = 4

clear() drops size() from 4 to 0, exactly as promised — and empty() (a convenience method equivalent to v.size() == 0) confirms it. But capacity() stays at 4 the entire time. The block of memory the vector allocated is still there, still owned by the vector, just marked as holding zero elements. That is why the final push_back(99) needs no reallocation: clear() left behind exactly the capacity push_back needed.

Warning— after clear(), size() is 0 but capacity() is not

This is worth stating as its own rule, because it surprises almost everyone the first time: clear() resets the length, not the memory. If you need to actually give the memory back to the system — rare, and never required by anything in this course — you need the "swap trick" (vector<int>().swap(v);), which is out of scope here. For this class, remember only: clear() and repeatedly pop_back()-ing to empty behave identically with respect to capacity. Neither one shrinks it.

6.resize(): changing the length outright

push_back and pop_back change the length by exactly one element at a time. resize() jumps straight to whatever length you name, growing or shrinking in a single call.

Definition— resize()

v.resize(n) sets v's size to exactly n. If n is larger than the current size, the new elements at the end are value-initialized — 0 for numeric types. If n is smaller, the elements beyond the new length are destroyed and gone. v.resize(n, val) is the same, except the newly added elements (only when growing) are set to val instead of 0.

Worked Example— grow, then shrink

Four elements go on. Then the vector grows to 10 with fill value 1, then shrinks to 3 with fill value 9, then resizes to 6 with no fill value at all. Predict the full contents printed after every step — pay close attention to the shrink step.

resize_demo.cpp
// resize_demo.cpp -- resize() grows and shrinks the length
#include <iostream>
#include <vector>
using namespace std;

void print(const vector<int> &v) {
    cout << "size = " << v.size() << ":";
    int n = v.size();
    for (int i = 0; i < n; ++i) {
        cout << " " << v[i];
    }
    cout << endl;
}

int main() {
    vector<int> vec_i;
    vec_i.push_back(2);
    vec_i.push_back(4);
    vec_i.push_back(8);
    vec_i.push_back(16);
    print(vec_i);

    vec_i.resize(10, 1);        // *** reinitialize to larger size ***
    print(vec_i);

    vec_i.resize(3, 9);         // *** reinitialize to smaller size ***
    print(vec_i);

    vec_i.resize(6);            // no fill value supplied
    print(vec_i);
    return 0;
}
size = 4: 2 4 8 16
size = 10: 2 4 8 16 1 1 1 1 1 1
size = 3: 2 4 8
size = 6: 2 4 8 0 0 0

Growing to 10 with fill value 1 does exactly what you'd expect: the original 2 4 8 16 survive, and six new 1s get appended. The shrink is the one to look at twice: resize(3, 9) produces 2 4 8, not 9 9 9. Shrinking never uses the fill value at all — it simply drops every element past index 2, keeping whatever the survivors already held. The fill value only ever applies to elements that are newly created by a grow. That is confirmed by the last line: resize(6) with no fill value grows the vector back up from 3 to 6, and the three brand-new elements default to 0, the ordinary default for int.

Common Mistake— the fill value in a shrinking resize() is easy to misread

The professor's own slide comment for the shrink line reads "reinitialize to smaller size" — and "reinitialize" naturally suggests every surviving element gets reset to the fill value you passed. It does not. vec_i.resize(3, 9) on a vector already holding 2 4 8 16 gives 2 4 8, keeping the original values of the three surviving elements and simply discarding the fourth. The 9 in that call is never used for anything at all, because shrinking creates no new elements for a fill value to apply to. Rule to remember: the fill value argument to resize() only ever touches elements that grow the vector, never elements that already existed.

One more question resize() raises naturally: does it touch capacity the same way push_back does?

Things to notice. Growing past the current capacity with resize() reallocates exactly like push_back would — capacity jumps from 4 to (at least) 10 to make room. But shrinking with resize(3, 9) behaves just like pop_back(): size drops to 3, and capacity does not move, staying at 10. resize() can raise capacity when it needs to, but it never lowers it — the same rule that governs pop_back() and clear() governs every way of shrinking a vector.

The professor's lectures do not cover one closely related method, reserve() — it is worth a brief look here because the contrast with resize() sharpens what both of them do.

Worked Example— reserve() vs. resize() (added — not in the professor's slides)

v.reserve(n) asks for capacity n without creating any elements — size() does not change. Compare that to v.resize(n), which both grows the capacity and creates n real, value-initialized elements. Predict the size and capacity after each step for both vectors.

reserve_demo.cpp
// reserve_demo.cpp -- reserve() buys capacity without changing the size
#include <iostream>
#include <vector>
using namespace std;

int main() {
    vector<int> a;
    a.reserve(10);
    cout << "after reserve(10): size = " << a.size()
         << ", capacity = " << a.capacity() << endl;
    a.push_back(7);
    cout << "after push_back:   size = " << a.size()
         << ", capacity = " << a.capacity() << endl;

    vector<int> b;
    b.resize(10);
    cout << "after resize(10):  size = " << b.size()
         << ", capacity = " << b.capacity() << endl;
    b.push_back(7);
    cout << "after push_back:   size = " << b.size()
         << ", capacity = " << b.capacity() << endl;
    return 0;
}
after reserve(10): size = 0, capacity = 10
after push_back:   size = 1, capacity = 10
after resize(10):  size = 10, capacity = 10
after push_back:   size = 11, capacity = 20

a.reserve(10) grabs capacity for 10 elements but a is still empty — size() == 0. Pushing one element afterward uses that reserved room with no reallocation, landing at size 1, capacity 10. b.resize(10), on the other hand, actually creates 10 zero-valued elements — size() jumps straight to 10. So when b then gets one more push_back, it is already full (size 10 == capacity 10), and that call has to reallocate, growing capacity to 20 by the same doubling rule from §1.

Use reserve() when you know roughly how many elements are coming and want to avoid repeated reallocations, but are not ready to give them values yet. Use resize() when you want the elements to actually exist, right now, with real (possibly default) values. This distinction is not covered in the professor's lecture notes or tested on his exams — it is included here because understanding resize() well enough to predict §6's shrink trap requires seeing what it is not the same as.

trim.cpp
// trim.cpp -- remove the last k elements, without ever popping an empty vector
#include <iostream>
#include <vector>
using namespace std;

void print(const vector<int> &v) {
    cout << "size = " << v.size() << ":";
    int n = v.size();
    for (int i = 0; i < n; ++i) cout << " " << v[i];
    cout << endl;
}

void trim(vector<int> &v, int k) {
    int n = v.size();
    if (k >= n) {
        v.clear();                  // asking for more than there is empties it
    } else {
        v.resize(n - k);            // one call does the whole job
    }
}

int main() {
    vector<int> v;
    for (int i = 1; i <= 6; ++i) v.push_back(i * i);
    print(v);

    trim(v, 2);
    print(v);

    trim(v, 10);                    // more than the vector holds
    print(v);
    cout << "capacity = " << v.capacity() << endl;
    return 0;
}

size = 4: 1 4 9 16
size = 0:
capacity = 8

Things to notice.

  • trim(v, 2) removes the last two elements (25 and 36), leaving 1 4 9 16 exactly as they were — the shrink rule from §6 in action again.
  • trim(v, 10) asks to remove more than exists; the guard routes it to clear() instead of computing n - k = -4, which is not a valid size and would be undefined behavior to pass to resize().
  • Even after the vector is completely empty, capacity() still reports 8 — consistent with every other way of shrinking a vector you have seen today.

7.Vectors of vectors: a 2-D table

Everything so far has been a vector of plain numbers — a one-dimensional list. But nothing stops the element type of a vector from being another vector. A grid of exam scores, a chessboard, an image made of pixel rows — anything naturally laid out in rows and columns is a vector<vector<T>>.

Definition— vector of vectors

A vector<vector<int>> is a vector whose elements are themselves vector<int> objects. Think of the outer vector as the list of rows, and each inner vector as the contents of one row. grid[r] is the whole row r — a vector<int> in its own right — and grid[r][c] is the single element in row r, column c. Everything you already know about vectors (size(), push_back, []) applies at both levels, independently.

The declaration vector<vector<int>> grid(rows, vector<int>(cols, 0)); is exactly Class 5's "length and fill value" form, applied one level up: it makes rows copies of the inner vector vector<int>(cols, 0), so you get a rectangular table of zeros, ready to fill in.

Worked Example— a rectangular table, then a ragged one

First, a plain rectangular 3×4 grid, filled with 10*row + col and printed with setw for lined-up columns. Predict the shape and contents before you look.

grid.cpp
// grid.cpp -- a vector of vectors is a 2-D table
#include <iostream>
#include <iomanip>
#include <vector>
using namespace std;

int main() {
    int rows = 3, cols = 4;

    // 3 rows, each one a vector<int> of 4 zeros
    vector<vector<int>> grid(rows, vector<int>(cols, 0));

    cout << "rows = " << grid.size() << endl;
    cout << "cols in row 0 = " << grid[0].size() << endl;

    // fill it: grid[r][c] = 10*r + c
    for (int r = 0; r < rows; ++r) {
        for (int c = 0; c < cols; ++c) {
            grid[r][c] = 10 * r + c;
        }
    }

    // print it
    for (int r = 0; r < rows; ++r) {
        for (int c = 0; c < cols; ++c) {
            cout << setw(4) << grid[r][c];
        }
        cout << endl;
    }
    return 0;
}
rows = 3
cols in row 0 = 4
   0   1   2   3
  10  11  12  13
  20  21  22  23

grid.size() is the number of rows (3), and grid[0].size() is the number of columns in row 0 (4) — two completely separate calls to size(), one on the outer vector and one on an inner vector. The nested loop is exactly the pattern you use for a 2-D array, with [r][c] instead of [r][c] on a raw array — the syntax looks identical because operator[] chains the same way either time.

Now the case a plain 2-D array can never handle: rows that are not all the same length. Building each row with its own push_back calls, instead of a single fill-constructor, makes a ragged table possible — something Class 5's arrays-are-fixed-size limitation ruled out entirely.

ragged.cpp
// ragged.cpp -- the rows of a vector of vectors do not have to be the same length
#include <iostream>
#include <vector>
using namespace std;

int main() {
    vector<vector<int>> tri;        // no rows at all yet

    for (int r = 0; r < 4; ++r) {
        vector<int> row;            // build one row
        for (int c = 0; c <= r; ++c) {
            row.push_back(c + 1);
        }
        tri.push_back(row);         // push the whole row onto the outer vector
    }

    cout << "number of rows = " << tri.size() << endl;
    for (int r = 0; r < 4; ++r) {
        cout << "row " << r << " has " << tri[r].size() << " elements:";
        int n = tri[r].size();
        for (int c = 0; c < n; ++c) {
            cout << " " << tri[r][c];
        }
        cout << endl;
    }
    return 0;
}
number of rows = 4
row 0 has 1 elements: 1
row 1 has 2 elements: 1 2
row 2 has 3 elements: 1 2 3
row 3 has 4 elements: 1 2 3 4

Row r ends up with r + 1 elements — a triangle, not a rectangle. tri.push_back(row) pushes a whole vector onto the outer vector, copying every element of row into the new inner vector tri now owns. Each row's size() is independent of every other row's; there is nothing anywhere that forces vector<vector<int>> to be rectangular — rectangular is just what you get if you build every row the same length, and the fill constructor from grid.cpp above is one convenient way to guarantee that when you want it.

Quick Check 6.10

Using the ragged tri from the example above (rows of length 1, 2, 3, 4):

(a) What does tri[2][2] refer to, and what value does it hold?

Row index 2, column index 2 — the third element of the third row. Row 2 holds 1 2 3, so tri[2][2] is 3.

(b) What happens if you evaluate tri[2][3]?

Row 2 only has 3 elements, valid indices 0–2. Index 3 is out of bounds for that row — exactly the same undefined behavior Class 5 covered for a one-dimensional vector, just applied to the inner vector tri[2]. It compiles and it might run without visibly crashing, but it is a bug, and using tri[2].at(3) instead would turn it into a guaranteed, catchable exception.

Things to notice. "Ragged" means you cannot assume every row has the same valid range of columns. Always get the length of the specific row you are indexing into — tri[r].size(), not tri[0].size() — before looping over its columns.

Quick Check 6.12— wrap-up

For each pair below, say whether the two operations leave the vector's capacity() the same or different, assuming v starts with size() == 5 and capacity() == 8.

(a) v.clear(); vs. v.resize(0);

Same effect on capacity — both leave it at 8. resize(0) shrinks size() to 0 exactly the way clear() does; §6 showed shrinking with resize() never lowers capacity, and §5 showed the identical fact for clear(). Neither call gives any memory back.

(b) v.pop_back(); v.pop_back(); (called twice) vs. v.resize(3);

Same effect on both size and capacity. Both bring size() from 5 down to 3; both leave capacity() at 8. resize() shrinking and repeated pop_back() are two different-looking ways to reach the identical end state — this is the pattern every shrinking operation in this class follows: size can go down; capacity, once granted, only ever goes up (or stays put).

Things to notice. That one sentence is worth memorizing on its own — it answers Quick Checks 6.5 through 6.9 all at once, and it is exactly what makes push_back amortized-cheap in the first place: capacity is a one-way ratchet, so the expensive "ask for more memory" step happens as rarely as possible.

using namespace std;

int main() {
    vector<double> temps;                                    // (1)
    temps.reserve(100);                                      // (2)
    temps.push_back(98.6);                                   // (3)
    cout << temps.back() << " " << temps.size() << endl;     // (4)
    if (!temps.empty()) temps.pop_back();                    // (5)

    cout << "size = " << temps.size()
         << ", capacity = " << temps.capacity() << endl;
    return 0;
}
98.6 1
size = 0, capacity = 100

Things to notice.

  • The final capacity is still 100, even though size is back down to 0 — reserve() set it, and nothing in this program (or in pop_back, or in the language generally) ever lowers a vector's capacity.
  • On an exam that asks for "five statements," write exactly five and number them in comments, as done here. Rubrics for this style of question award points per statement, so a clearly labeled partial answer still scores even if one statement is wrong.
  • Without the reserve(100) in statement (2), the program's final output would be identical — reserve() is a performance hint, not something later output can detect by value. Its only visible effect anywhere is on capacity().

Problem 5 — A gradebook as a 2-D vector (added)

Three students each take four exams. Build a vector<vector<int>> to hold the scores, fill it in, then print each student's total and average, followed by each exam's class average.

Plan. A rectangular grid fits here — every student takes the same four exams — so the fill-constructor form from §7, vector<vector<int>>(students, vector<int>(exams, 0)), is the natural declaration. Two independent summary loops follow: one walking row by row for student totals, one walking column by column for exam averages. Neither loop needs to touch the other's data, so they are kept completely separate rather than combined into one pass.

gradebook.cpp
// gradebook.cpp -- a 2-D vector of exam scores
#include <iostream>
#include <iomanip>
#include <vector>
using namespace std;

int main() {
    int students = 3, exams = 4;
    vector<vector<int>> score(students, vector<int>(exams, 0));

    // fill in the scores
    int values[3][4] = { {80, 90, 100, 70},
                         {60, 65,  70, 75},
                         {95, 85,  75, 65} };
    for (int s = 0; s < students; ++s) {
        for (int e = 0; e < exams; ++e) {
            score[s][e] = values[s][e];
        }
    }

    // per-student totals
    for (int s = 0; s < students; ++s) {
        int total = 0;
        for (int e = 0; e < exams; ++e) total += score[s][e];
        cout << "student " << s << " total = " << setw(4) << total
             << ", average = " << total / (double)exams << endl;
    }

    // per-exam averages
    for (int e = 0; e < exams; ++e) {
        int total = 0;
        for (int s = 0; s < students; ++s) total += score[s][e];
        cout << "exam " << e << " average = " << total / (double)students << endl;
    }
    return 0;
}
student 0 total =  340, average = 85
student 1 total =  270, average = 67.5
student 2 total =  320, average = 80
exam 0 average = 78.3333
exam 1 average = 80
exam 2 average = 81.6667
exam 3 average = 70

Things to notice.

  • score[s][e] = values[s][e] copies from an ordinary, fixed-size 2-D array into the vector of vectors — a useful bridge when starting data is naturally written as a compile-time array literal, as it often is in a small test program.
  • total / (double)exams and total / (double)students both force floating-point division; leaving off the cast would silently truncate every average to a whole number, exactly the Class 1 integer-division trap.
  • 85 and 80 print with no decimal point, 67.5 and 81.6667 do — the same six-significant-digit cout default from Class 1, now showing up in a two-dimensional context.

Problem 6 — How far does doubling get you at 1,000 pushes? (added)

Extend §2's investigation from 100 push_backs to 1,000. Does the number of reallocations grow in proportion to the number of pushes, or much more slowly? Write a program that answers the question with real numbers, then explain the result.

Plan. Identical structure to §2's moves100.cpp, just with the loop bound raised to 1000 and the per-jump printing dropped (ten times the pushes would make ten times the printed lines, which is more noise than signal here) — only the final totals are printed.

reallocs.cpp
// reallocs.cpp -- how much copying does 1000 push_back calls really cost?
#include <iostream>
#include <vector>
using namespace std;

int main() {
    vector<int> v;
    int reallocations = 0;
    long long elementsMoved = 0;

    size_t oldCap = v.capacity();
    for (int i = 0; i < 1000; ++i) {
        v.push_back(i);
        if (v.capacity() != oldCap) {     // the vector just moved house
            ++reallocations;
            elementsMoved += oldCap;      // everything already stored got copied
            oldCap = v.capacity();
        }
    }

    cout << "push_back calls  = " << 1000 << endl;
    cout << "reallocations    = " << reallocations << endl;
    cout << "elements moved   = " << elementsMoved << endl;
    cout << "final size       = " << v.size() << endl;
    cout << "final capacity   = " << v.capacity() << endl;
    return 0;
}
push_back calls  = 1000
reallocations    = 11
elements moved   = 1023
final size       = 1000
final capacity   = 1024

Things to notice. Going from 100 pushes to 1,000 — ten times as many — raised the reallocation count from 8 to only 11, not 80. That is the logarithmic growth predicted in Quick Check 6.2: each extra reallocation lets the vector handle roughly double the pushes, so it takes only a few more reallocations to cover ten times the ground. The total elements moved, 1023, stays just barely above the final size of 1000 — the same "total copying work stays proportional to the final size" fact from §2, holding at ten times the scale. This is the concrete, measured version of "amortized constant time": the average cost per push_back, across all 1000 calls, barely moved from the 100-call case.

Lecture Summary
  • A vector tracks two numbers: size() (elements actually stored) and capacity() (elements there is currently room for). Always capacity() >= size().
  • When push_back runs out of room, the vector reallocates: it gets a bigger block, copies every existing element into it, and frees the old block. libstdc++ doubles the capacity each time this happens, but the exact growth factor is implementation-defined, not guaranteed by the standard.
  • Because reallocations get rarer exactly as fast as they get more expensive, the average cost of push_back over many calls stays roughly constant — amortized constant time — even though any individual call can be the expensive one.
  • front() and back() read the first and last elements. Calling either — or pop_back() — on an empty vector is undefined behavior, not a guaranteed crash or error. Always guard with !v.empty().
  • pop_back() removes the last element and lowers size() by one; it never lowers capacity(). clear() resets size() to zero for the whole vector, and it also leaves capacity() untouched. Neither one gives memory back.
  • resize(n) sets the length to exactly n, growing (new elements default to 0, or to a supplied fill value) or shrinking (surviving elements keep their old values — a fill value passed to a shrinking resize() is simply ignored). reserve(n) (added; not in the professor's notes) buys capacity without creating elements or changing size().
  • A vector<vector<T>> is a vector of vectors: size() and [] work at both levels independently, so rows do not have to be the same length — a ragged table is something a plain 2-D array can never represent.
  • Watch for this professor's favorite vector trap on exams: cout << v.size() << v.back() with no separator, after a run of conditional push_back/pop_back calls.
