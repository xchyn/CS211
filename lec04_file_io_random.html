1.Pseudorandom numbers: why "pseudo"

Every program you have written so far gets its data from exactly one place: a person typing at the keyboard, through cin. That is fine for a ten-line exercise and useless for anything else. Today we add the two other sources every real program uses — a random number generator, for simulations, games and test data, and a file on disk, for data that has to survive the program exiting.

Start with the random numbers, because there is a surprise waiting in them.

Definition— pseudorandom, PRNG

C++ provides a set of good-quality routines to generate pseudorandom numbers. They are called "pseudorandom" because a sequence of truly random numbers is difficult to obtain. Computer-generated sequences of "random numbers" are approximations to truly random numbers.

A pseudorandom number generator has the acronym PRNG.

Concretely: a PRNG is a function that takes its current internal state, scrambles it with some arithmetic, and returns a number. The scrambling is completely deterministic. Given the state, the next number is fixed — there is nothing random about it at all. What makes the output look random is only that the scrambling is hard to see through.

The simplest generator in C++ is the pair rand and srand, which live in the header <cstdlib>. rand() returns the next integer in the sequence, somewhere between 0 and a large implementation-defined maximum called RAND_MAX. Here is the whole interface in one program — and here is the surprise.

This program prints five values from rand(). Then we run the executable a second time, immediately, without recompiling. Before you open the toggle, commit to an answer: will the second run print the same five numbers or five different ones?

Identical. Not similar — identical, digit for digit, and they will be identical on the hundredth run too. Nothing is broken. This is exactly what the definition promised: the generator is a deterministic machine, and a deterministic machine started from the same state produces the same output.

The state it starts from is called the seed. If you never set a seed, C++ behaves as though you had called srand(1), so every run begins from the same place and walks the same path. That is a deliberate design choice, not an oversight — it means a program that misbehaves on random data can be run again and misbehave in exactly the same way, which is the only realistic way to debug a simulation.

Key Idea

A PRNG is a sequence, not a lottery. The seed picks which point in the sequence you start at. Same seed, same sequence, every time. If you want a different game every time you play, you have to hand the generator a different seed every time it starts.

Quick Check 4.1

A student writes a card game. Every time they run it, the deck comes out in the same order. They are convinced rand() is broken.

(a) Is rand() broken? Explain what is actually happening in one sentence.

No. The program never seeds the generator, so every run starts the same deterministic sequence from the same place — the shuffle is doing exactly what it was told, with exactly the same numbers.

(b) Give one situation in which "the same sequence every run" is the behavior you want.

Testing and debugging. If a simulation crashes on the 4,312th random value, you need to be able to reproduce that run exactly. It is also what makes a printed expected output possible at all — every random-number program on this page uses a fixed seed for precisely that reason.

A third case: grading. If an autograder has to compare your output against a reference, the sequence had better not depend on what time it is.

2.srand, seeding, and scaling into a range

Definition— seed, srand, rand

The seed is the starting state of a pseudorandom number generator.

srand(n) sets the seed to n. rand() returns the next value in the sequence, an int between 0 and RAND_MAX inclusive. Both are declared in <cstdlib>.

Call srand once, near the top of main, before the first rand(). Calling it again mid-program does not make the numbers "more random"; it restarts the sequence.

rand() on its own gives you a huge integer, which is almost never what you want. You want a die roll from 1 to 6, or a test score from 60 to 100. Getting from one to the other is the modulus operator, and it is worth deriving rather than memorizing.

Procedure— scaling a random integer into lo..hi
  1. rand() % k is the remainder after dividing by k, so its possible values are 0, 1, 2, …, k-1. That is k different values starting at zero. Fix that fact in your head; everything else follows from it.
  2. You want the values lo, lo+1, …, hi. How many is that? Count them: hi - lo + 1. The + 1 is there because both endpoints are included.
  3. So take k = hi - lo + 1 and shift the result up by lo: 
    int value = lo + rand() % (hi - lo + 1);
  4. Sanity-check the two ends. When rand() % k is 0 you get lo; when it is k-1 you get lo + hi - lo + 1 - 1, which is hi. Both endpoints are reachable, so the formula is right.

For a die, lo is 1 and hi is 6, so k is 6 and the expression is 1 + rand() % 6. Notice the 1 + is outside the modulus.

Worked Example— dice and scores, with a fixed seed

This program seeds with srand(42). A fixed seed is used here deliberately, so that the output printed below is the output you will get if you compile and run it yourself. A real game would seed from the clock instead — we get to that in a moment.

dice.cpp
// dice.cpp -- scaling rand() into a range, with a fixed seed so the run repeats
#include <iostream>
#include <cstdlib>          // rand(), srand()
using namespace std;

int main() {
    srand(42);              // fixed seed: reproducible on purpose

    cout << "ten dice rolls (1..6):" << endl;
    for (int i = 0; i < 10; ++i) {
        int roll = 1 + rand() % 6;
        cout << roll << " ";
    }
    cout << endl;

    cout << "five scores (60..100):" << endl;
    for (int i = 0; i < 5; ++i) {
        int score = 60 + rand() % (100 - 60 + 1);
        cout << score << " ";
    }
    cout << endl;
    return 0;
}

1 1 6 4 5 5 2 1 6 6
five scores (60..100):
74 66 84 70 91

Ten values on the first line, all between 1 and 6; five on the second, all between 60 and 100. Two details worth pausing on:

  • The sequence opens 1 1 — two identical values in a row. Students routinely report this as a bug. It is not. Genuine randomness produces repeats; a sequence with no repeats at all would be the suspicious one.
  • (100 - 60 + 1) is left unsimplified on purpose. Writing the count as hi - lo + 1 rather than as the number 41 keeps the reasoning visible, and if the range changes you edit two numbers instead of recomputing anything.

Run it again and you get the same twenty-five characters, because the seed is fixed. That is the whole point of a fixed seed.

Common Mistake— the off-by-one in rand() % 6

The most common bug in this material is writing rand() % 6 when you meant a die. Here are both expressions run from the same seed, side by side:

offbyone.cpp
srand(42);
cout << "rand() % 6      : ";
for (int i = 0; i < 10; ++i) cout << rand() % 6 << " ";
cout << endl;

srand(42);
cout << "1 + rand() % 6  : ";
for (int i = 0; i < 10; ++i) cout << 1 + rand() % 6 << " ";
cout << endl;
rand() % 6      : 0 0 5 3 4 4 1 0 5 5
1 + rand() % 6  : 1 1 6 4 5 5 2 1 6 6

The first line contains a 0, which no die has, and never contains a 6. The bug is invisible until a 0 happens to show up, which on a small test run it may not. Get in the habit of printing a hundred values and eyeballing the smallest and largest before you trust a range expression.

Equally wrong, and equally common: 1 + rand() % 7 (range 1–7) and rand() % (1 + 6) (range 0–6). Derive the formula, do not recall it.

Quick Check 4.2

Write a single C++ expression, using rand(), for each of the following.

(a) A random integer from 1 to 100 inclusive.

int n = 1 + rand() % 100;

Count the values: 1 through 100 is 100 - 1 + 1 = 100 of them, so the modulus is 100 and the shift is 1.

(b) A random integer from 5 to 15 inclusive.

int n = 5 + rand() % 11;      // 15 - 5 + 1 == 11

Check both ends: remainder 0 gives 5, remainder 10 gives 15. Correct.

(c) A random even integer from 0 to 20 inclusive.

There are eleven even numbers in that range: 0, 2, 4, …, 20. So pick one of eleven values and double it.

int n = 2 * (rand() % 11);

Things to notice. The tempting wrong answer is rand() % 21 followed by "keep it if it is even", which throws away half your values and needs a loop. Whenever the values you want are evenly spaced, generate the index and then map it — do not generate-and-reject.

The parentheses matter. 2 * rand() % 11 would multiply first and then take the remainder, giving 0 through 10 — and not even always even, since % and * have the same precedence and group left to right.

Now the other half of the story. A game needs a different sequence each time it runs, so it needs a seed that changes. The standard source of a changing number is the clock:

Definition— seeding from the clock

time(0), declared in <ctime>, returns the current time as a whole number of seconds since a fixed point in the past. Because that number is different every second, it makes a convenient seed:

#include <ctime>
srand(time(0));      // a different sequence on (almost) every run

"Almost" is doing real work in that sentence. Two runs inside the same second get the same seed and therefore the same sequence.

Worked Example— a clock-seeded run (values are representative)

This one cannot have a printed expected output in the usual sense — by construction it prints something different every time. The values below are from three real runs, roughly a second apart. Yours will differ, and that is the point.

timeseed.cpp
// timeseed.cpp -- seeding from the clock: a different sequence every run
#include <iostream>
#include <cstdlib>          // rand(), srand()
#include <ctime>            // time()
using namespace std;

int main() {
    srand(time(0));         // seed from the current time

    for (int i = 0; i < 6; ++i) {
        cout << 1 + rand() % 6 << " ";
    }
    cout << endl;
    return 0;
}
4 5 4 1 4 2
6 5 6 3 4 5
6 4 6 5 6 5

Three runs, three different sequences. Compare that with unseeded.cpp in §1, where three runs gave one sequence three times.

Because the seed comes from the clock, these values are representative only: nothing on this page can tell you what your copy will print, and any exam question about a time(0)-seeded program can only ask about the range of the values, never their identity.

Common Mistake— srand inside the loop

Seeding feels like "make it random", so people put it where the randomness is wanted — inside the loop. Watch what that does:

srandinside.cpp
for (int i = 0; i < 8; ++i) {
    srand(time(0));                  // WRONG: re-seeds on every iteration
    cout << 1 + rand() % 6 << " ";
}
cout << endl;
5 5 5 5 5 5 5 5

Eight identical values. All eight iterations run within the same second, so time(0) returns the same number eight times, so the sequence is restarted from the same seed eight times, so rand() returns its first value eight times.

The rule: srand is called exactly once per program, before the first rand(). If you find yourself writing srand inside a loop, or inside a function that gets called repeatedly, you have made this mistake.

Quick Check 4.3

Here are three seeding strategies. For each one, say what the program prints on two consecutive runs.

(a) No srand call at all.

Both runs print the identical sequence. With no srand, the generator behaves as if srand(1) had been called, so every run replays the same numbers — exactly what unseeded.cpp demonstrated.

(b) srand(42); as the first statement of main.

Both runs print the identical sequence — a different sequence from (a), because the seed is different, but the same as each other. This is the reproducible-on-purpose choice, and it is what every printed output on this page relies on.

(c) srand(time(0)); as the first statement of main.

The two runs print different sequences — unless you launch them within the same second, in which case time(0) gives the same seed twice and the sequences match. Try it with a shell loop that runs the program three times as fast as it can and you will very often see two identical lines.

Things to notice. This is why "did my program produce different output?" is a bad test of whether seeding works, and why a fixed seed is the right choice for anything you need to be able to grade, compare or debug.

3.The <random> recipe: generators and distributions

rand and srand come from C, and they are showing their age: the quality of the numbers is mediocre, and the % trick above is very slightly biased when the range does not divide RAND_MAX evenly. C++ ships a better toolkit in the header <random>, and the course reading uses it. It takes four steps instead of two, and the extra two steps are the interesting part.

Definition— generator and distribution

A generator (or engine) is the object that holds the internal state and produces raw pseudorandom bits. default_random_engine is the one the standard library hands you when you do not care which algorithm is used.

A distribution is an object that shapes those raw bits into the values you actually want — a whole number from 1 to 100, a real number from −1.0 to 1.0, a bell curve, and so on. uniform_int_distribution<int> and uniform_real_distribution<double> are the two we use.

The split is the whole design. One engine can feed many distributions, and you get to say what shape you want without knowing anything about how the bits are made.

Procedure— the four steps
  1. Include the header. #include <random>
  2. Instantiate a generator. default_random_engine generator;
  3. Seed it. generator.seed(iseed); — the value of the seed is up to you. Use the same seed every time and you obtain the same sequence every time; that is why the numbers are "pseudorandom" and not truly random.
  4. Declare your distributions, then call them with the generator as the argument. 
    uniform_int_distribution<int> i_prng(1, 100);
int a = i_prng(generator);
    The distribution is the thing you call; the generator is what you hand it.

Other statistical distributions are supported too — normal, Poisson, exponential and more. The two uniform ones cover everything we need this semester.

Worked Example— the course reading's PRNG program

This is the program from the additional reading, with a fixed seed of 0. The integers are uniformly distributed from 1 to 100; the doubles are uniformly distributed from −1.0 to 1.0. Predict the shape of the output — how many lines, and what is on each one — before you look.

prng.cpp
// prng.cpp -- the <random> recipe: one generator, two distributions
#include <iostream>
#include <random>
using namespace std;

int main() {
    int iseed = 0;                                       // initial seed

    default_random_engine generator;
    generator.seed( iseed );

    uniform_int_distribution<int> i_prng(1, 100);        // int 1 to 100
    uniform_real_distribution<double> r_prng(-1.0, 1.0); // double -1.0 to 1.0

    int n = 10;
    for (int i = 0; i < n; ++i) {
        int a = i_prng(generator);                // call prng for int
        double d = r_prng(generator);             // call prng for double
        cout << a << " " << d << endl;
    }
    return 0;
}

That is fine — it is one sequence of bits being shared — but it does mean you cannot reason about the integers in isolation.

One caution about reproducibility. The standard does not say which algorithm default_random_engine names, so a different compiler's standard library can legitimately print different numbers for seed 0. Warning— the reading's program will not link as printed

Quick Check 4.5

Complete the coin-flip exercise above and give the exact output. Then say what the two counts would have to add up to, and why that is a useful check.

Plan. A fair coin is a two-way choice, so rand() % 2 is exactly the right tool: it produces 0 or 1 and nothing else. Call one of them heads and the other tails, count in a loop, print at the end. No scaling formula is needed because the range starts at zero already.

excoins.cpp
// excoins.cpp -- 100 coin flips, counted
#include <iostream>
#include <cstdlib>
using namespace std;

int main() {
    srand(42);                       // fixed seed: reproducible

    int heads = 0;
    int tails = 0;
    for (int i = 0; i < 100; ++i) {
        if (rand() % 2 == 0) {
            ++heads;
        } else {
            ++tails;
        }
    }
    cout << "heads = " << heads << endl;
    cout << "tails = " << tails << endl;
    return 0;
}
heads = 47
tails = 53

Things to notice.

  • The counts must sum to 100, because every iteration takes exactly one of the two branches. Printing a total that is not the loop count means you have a path through the loop that counts nothing — usually an if with no else, or an else if chain with a gap. This kind of invariant is the cheapest debugging tool you own.
  • 47 and 53 is a perfectly ordinary result for 100 flips. Do not expect 50/50; expect something within about ten of it. If you got exactly 50/50 every time, the generator would be broken in the opposite direction.
  • rand() % 2 == 0 reads as "the value is even". Any other split of the two outcomes works equally well — rand() % 2 == 1, or comparing against RAND_MAX / 2 — but the modulus version is the one everybody recognizes.

4.File streams: opening a file and checking it worked

Now for the second half of the class. Everything your programs have produced so far vanished when the program exited. Files fix that, and the C++ interface to them is deliberately built to look like something you already know.

Definition— file streams

To read and write from and to files in C++, we employ file streams:

  • an ifstream (input file stream) reads from a file — it is the file-shaped version of cin;
  • an ofstream (output file stream) writes to a file — it is the file-shaped version of cout.

Both require #include <fstream>. Once you have one, you use it with >> and << exactly as you use cin and cout.

Read the letters. The i and the o say input and output, and the f says file. ifstream is input, so it reads; ofstream is output, so it writes. Students mix these up constantly for about a week and then never again.

You create a stream by handing the file name to its constructor:

#include <fstream>
#include <string>

string infile("scores.txt");
ifstream ifs(infile);              // open scores.txt for reading

ofstream ofs("report.txt");        // open report.txt for writing

A plain string literal works just as well as a string variable. Note that these are relative file names: the program looks for scores.txt in whatever directory it is run from, which is not necessarily where the source file lives. If your program insists a file is missing and you can see it right there, that is nearly always the reason.

Key Idea— the asymmetry that catches everybody

If the output file does not exist, the ofstream will create it. If the input file does not exist, the ifstream open will fail.

That is not arbitrary. "Write to a file that isn't there yet" has an obvious sensible meaning — make one. "Read from a file that isn't there" has none. The consequence for you is that every ifstream needs its open checked, and an unchecked one produces a program that silently reads nothing and reports a happy, wrong answer.

Worked Example— checking that the open succeeded

There is no file called nosuchfile.txt in the directory. Note that the constructor does not throw, crash, or print anything — it just quietly puts the stream into a failed state, which is why you have to ask.

openfail.cpp
// openfail.cpp -- what happens when the input file is not there
#include <iostream>
#include <fstream>
#include <string>
using namespace std;

int main() {
    string infile("nosuchfile.txt");
    ifstream ifs(infile);

    if (!ifs.is_open()) {
        cout << "Could not open " << infile << endl;
        return 1;
    }

    cout << "Opened " << infile << " successfully." << endl;
    ifs.close();
    return 0;
}
Could not open nosuchfile.txt

The program printed its message and stopped. Three things to take from this:

  • The return 1; is deliberate. Returning a nonzero value from main tells whatever launched the program that it failed — the convention we met in Class 1. Returning 0 after an error reports success, which is a lie.
  • is_open() asks the direct question: did this stream attach to a file? Two other tests are common and mean effectively the same thing right after construction: 
    if (!ifs)          { /* failed */ }        // streams convert to bool
if (ifs.fail())    { /* failed */ }
    The course reading uses a third, if (ifs.good() == false). That works here but is a weaker test: good() reports "no error bit of any kind is set", which conflates the open failing with several other conditions. Prefer is_open() for an open check and !ifs for a general one.
  • Do the check immediately, before any reading. A failed stream does not refuse to be read; it just never gives you any data.
Common Mistake— forgetting <fstream>

iostream gives you cin and cout. It does not give you ifstream and ofstream. Leave out the header and g++ says something distinctly unhelpful:

nofstream.cpp: In function 'int main()':
nofstream.cpp:6:17: error: variable 'std::ifstream ifs' has initializer but incomplete type
    6 |     ifstream ifs("scores.txt");
      |                 ^

Note that it did not say "ifstream was not declared in this scope". The name is visible — other standard headers declare that it exists — but its definition is not, so the compiler knows the type by name only and cannot work out how big it is or how to construct it. That is what "incomplete type" means, and the fix is always the same: include the header that defines the thing.

Quick Check 4.6

A program contains this, and nothing else touches the streams:

ifstream in("data.txt");
ofstream out("results.txt");
int x;
in >> x;
out << x << endl;

Neither data.txt nor results.txt exists when the program starts.

(a) Which of the two opens succeeds?

The ofstream. Opening a file for output creates it, so results.txt now exists (and is empty at that moment). The ifstream fails, because there is nothing named data.txt to attach to.

(b) The program compiles and runs without crashing. What ends up in results.txt?

A line containing 0.

Here is the chain. in >> x on a failed stream does not read anything, and since C++11 a failed extraction sets x to zero rather than leaving it untouched. So x is 0, and out << x faithfully writes 0 to the file that the ofstream happily created for it.

This is the worst possible failure mode: no crash, no message, no compiler warning — just a plausible-looking wrong answer sitting in a file. It is the entire argument for checking the open.

(c) Add the missing safety check, and say where it has to go.

ifstream in("data.txt");
if (!in.is_open()) {
    cout << "Could not open data.txt" << endl;
    return 1;
}
ofstream out("results.txt");
int x;
in >> x;
out << x << endl;

Things to notice. The check goes immediately after the construction and before the ofstream is even created — otherwise you leave behind an empty results.txt from a run that did nothing, which is its own small trap for whoever looks at the directory later.

Checking the ofstream too is not wasted effort. It can fail for reasons that have nothing to do with the file existing: a read-only directory, a full disk, a path with a typo in a directory name.

5.Reading with >> — and the loop that eats your data

Reading from an ifstream uses the same operator as reading from the keyboard. The course reading puts it plainly: the syntax ifs >> variable is the same as cin >> variable. Whitespace — spaces, tabs, newlines — separates one value from the next, and the type of the variable decides how much text gets consumed and how it is interpreted.

Here is the data file we will use for the rest of this section. It is the one from the course reading: three rows, each holding an int, a double and a string.

cat infile.txt
6 2.2 Alice
2 1.6 Bob
5 3.4 Charlie

So one record is read by

int a;
double d;
string s;
ifs >> a >> d >> s;

which chains three extractions left to right: a gets 6, d gets 2.2, s gets Alice. Three rows means three records, and now we need a loop — and this is where the trouble starts, because a program does not know in advance how many rows a file has.

Worked Example— the read loop exactly as the course reading writes it

Common Mistake— eof() is a report, not a forecast

Here is the sentence to memorize:

eof() tells you whether a read has already failed by running off the end of the file. It does not tell you whether the next read will succeed.

Every eof()-controlled loop is built on the hope that those two things are the same, and they are not. A stream carries several independent status bits:

TestMeansSet when
eof()end of file has been reacheda read consumed the last character, or a read ran off the end
fail()the last operation did not produce a valueran out of input, or the text did not match the variable's type
good()no error bit at all is set—

Notice the second row. A stream can fail without being at end of file — give it the word Alice when it wants an int and it fails on the spot, with plenty of file left. A loop that only watches eof() will spin forever on that input, re-reading the same character and failing again. So the eof() loop is not merely wrong at the boundary; it misses a whole category of error.

The correct idiom asks the only question that matters — did this read work?

while (ifs >> a >> d >> s) {
    // the body runs only when all three extractions succeeded
}

That works because ifs >> a >> d >> s is an expression whose value is the stream itself, and a stream used where a bool is wanted converts to true exactly when no error bit is set. Read it out loud as "while reading a record succeeds". It handles the trailing newline, the missing trailing newline, the empty file and the malformed line, all with the same four words.

6.Reading whole lines with getline

>> splits on whitespace, which is exactly what you want when a record is a fixed set of fields and exactly what you do not want when a field can contain a space. A person's full name, a street address, a book title — read any of those with >> and they arrive in pieces.

Definition— getline

getline(stream, str) reads characters from stream into the string str until it reaches a newline. The newline is consumed but is not stored in str.

It is a free function, not a member, so it is written getline(ifs, line) and not ifs.getline(line). Like >>, it returns the stream, so it drops straight into a loop condition:

string line;
while (getline(ifs, line)) {
    // one whole line, spaces and all
}

Common Mistake— mixing >> and getline

int howMany;

An empty first name, everything shifted down one, and Carol missing entirely.

Why. ifs >> howMany reads the digit 3 and stops. It does not consume the newline after it — >> stops at whitespace and leaves it in the stream. So the first getline starts at that leftover newline, immediately finds its terminator, and hands back the empty string between the 3 and the end of that line.

The fix is one line: read and discard the rest of the header line before switching modes.

mixfix.cpp
int howMany;
ifs >> howMany;

string junk;
getline(ifs, junk);             // swallow the rest of the header line

string name;
for (int i = 0; i < howMany; ++i) {
    getline(ifs, name);
    cout << i << ": [" << name << "]" << endl;
}
0: [Alice Nguyen]
1: [Bob Ortiz]
2: [Carol Diaz]

The rule to carry away: after any >>, the newline is still sitting in the stream. If the very next thing you do is a getline, clear it first. This applies to cin identically — the same bug shows up whenever you read a number from the keyboard and then try to read a full name.

7.Writing to a file: overwrite mode and append mode

Writing is the easy half. You create an ofstream and use << on it exactly as you use cout — the course reading says simply that writing to a file is similar to writing to the console, and it means that literally. The one decision you have to make is what should happen to whatever is already in the file.

Definition— overwrite mode and append mode

An ofstream can be opened in different modes:

  1. "Overwrite mode" overwrites anything already in the output file. Written ofstream ofs1(outfile, ios::out);
  2. "Append mode" appends to the end of the output file. Written ofstream ofs2(outfile, ios::app);
  3. The default is overwrite mode — so ofstream ofs(outfile); with no second argument throws away the old contents.

In both cases, if the file does not exist the ofstream will create it.

"Overwrite" deserves a sharper word: opening in ios::out truncates the file to zero length the moment the stream is constructed, before you have written a single character. If you open a file for output and then decide not to write anything, you have still destroyed it.

Worked Example— both modes on one file

This program writes three lines in overwrite mode, closes the stream, then reopens the same file in append mode and adds three more. It finishes by reading the file back so we can see what actually landed on disk. Predict the six lines.

    ifstream ifs(outfile);

Six lines, the fourth of them blank — that blank line is the lone ofs2 << endl;, which writes a newline and nothing else. The append-mode stream started exactly where the overwrite-mode stream stopped.

The teaching point is the pair of stream objects. ofs1 and ofs2 name the same file but are two different objects opened in two different modes, and ofs1.close() in between is what makes that safe. Opening a second stream on a file that is still open for writing is asking for trouble.

And run the program a second time: the output is identical. The overwrite-mode open at the top wipes the file clean each run, so the append later in the same run always starts from the same three lines.

The difference between the modes only really shows up when a program is run more than once. This one writes a single line to over.txt in overwrite mode and a single line to log.txt in append mode, then counts the lines in each. It is run three times in a row. Predict all three lines of output.

#include <fstream>
#include <string>
using namespace std;

    ofstream over("over.txt", ios::out);   // overwrite: starts empty every run
    over << "one line" << endl;
    over.close();

    ofstream app("log.txt", ios::app);     // append: grows every run
    app << "one line" << endl;
    app.close();

    ifstream a("over.txt");
    ifstream b("log.txt");

over.txt is stuck at one line forever; log.txt grows by one every run. That is the whole distinction, and it is why the two modes exist:

  • Overwrite is for a result: the current report, the current output, the answer for this run. You want yesterday's version gone.
  • Append is for a history: a log, an audit trail, a running record. You want yesterday's version kept.

Note that log.txt had to be deleted before the first of these three runs, or the count would have started higher. Append mode has a memory, and that is exactly what it is for.

Worked Example— read records, compute, write a report

The input is infile.txt — the file with no trailing newline, the one that broke the original loop in §5. Predict two things: the three debugging lines on the console, and the six lines that end up in outfile.txt.

records.cpp
// records.cpp -- read infile.txt, find max int / min double / longest string,
//                write the answers with overwrite mode, then append a summary
#include <iostream>
#include <fstream>          // header for file I/O
#include <string>
#include <vector>
using namespace std;

int main() {
    vector<int> iv;
    vector<double> dv;
    vector<string> sv;

    string infile("infile.txt");     // input file name
    string outfile("outfile.txt");   // output file name

    ifstream ifs(infile);            // ifstream object
    if (!ifs.is_open()) {            // check if the file opened successfully
        cout << "File not found: " << infile << endl;
        return 1;
    }

    int a;
    double d;
    string s;
    while (ifs >> a >> d >> s) {                     // read AND test
        cout << a << " " << d << " " << s << endl;   // print for debugging
        iv.push_back(a);
        dv.push_back(d);
        sv.push_back(s);
    }
    ifs.close();   // optional: the file closes when ifs goes out of scope

    if (iv.empty()) {                                // guard: no data at all
        cout << "No records in " << infile << endl;
        return 1;
    }

    // find max int, min double, longest string
    int a_max = iv[0];
    double d_min = dv[0];
    string s_long = sv[0];
    for (size_t i = 0; i < iv.size(); ++i) {
        if (a_max < iv[i]) a_max = iv[i];
        if (d_min > dv[i]) d_min = dv[i];
        if (s_long.length() < sv[i].length()) s_long = sv[i];
    }

    ofstream ofs1(outfile, ios::out);     // "write mode": overwrites outfile
    ofs1 << a_max << endl;
    ofs1 << d_min << endl;                // write to file
    ofs1 << s_long << endl;
    ofs1.close();                         // close the file

    ofstream ofs2(outfile, ios::app);     // "append mode": add to end of file
    ofs2 << endl;
    ofs2 << "append mode: add to end of file" << endl;
    ofs2 << a_max << " " << d_min << " " << s_long << endl;
    ofs2.close();                         // close the file

    return 0;
}

Common Mistake— iv[0] on a file that turned out to be empty

The if (iv.empty()) guard in the program above is not decoration. Remove it, point the program at an existing but empty file, and this is a real run:

touch empty.txt
./records_noguard
Segmentation fault

iv[0] on an empty vector is undefined behavior. There is no bounds check on operator[]; the program computes an address just past the vector's (null) storage and reads it. Under valgrind the diagnosis is unambiguous:

Invalid read of size 4
   at 0x10A954: main
 Address 0x0 is not stack'd, malloc'd or (recently) free'd
Process terminating with default action of signal 11 (SIGSEGV)

Note that the file opened perfectly well — is_open() was true, because an empty file is a real file. "The open succeeded" and "there is data" are two different claims, and you have to check both. Any time your code indexes element 0 of a container it filled from input, ask what happens when the input was empty.

Quick Check 4.12

Still with records.cpp in front of you.

(a) infile.txt is edited so that the last row reads 5 3.4 — the name is missing. What does the program print and write?

Two records on the console (Alice and Bob), and outfile.txt gets 6, 1.6, Alice, then the appended block.

The third iteration's condition reads 5 into a and 3.4 into d successfully, then the extraction into s runs out of input and fails. The whole chained expression is therefore false, so the loop stops without processing the partial record. Half-read values are discarded along with it — which is the right behavior, because half a record is not a record.

(b) Both ofs1 and ofs2 name outfile.txt. Why does the second one not wipe out what the first one wrote?

Because of the mode. ofs1 is opened with ios::out, which truncates; ofs2 is opened with ios::app, which positions the write cursor at the end and never truncates. Swap ios::app for ios::out on the second stream and the file ends up with only the appended block — the 6 / 1.6 / Charlie lines would be destroyed.

(c) The program calls ifs.close() and both ofsN.close(). Which of these calls, if any, could you delete without changing the behavior?

ifs.close() and ofs2.close() could go: each stream closes itself when its object is destroyed, and both objects live to the end of main.

ofs1.close() must stay. It is what flushes ofs1's buffered output to disk and releases the file before ofs2 opens the same file. Without it you have two output streams open on one file at once, with two independent buffers, and what ends up on disk depends on the order the buffers happen to be flushed. That is not a hypothetical worth risking.

Things to notice. The rule that follows: close a stream explicitly when something else is about to touch the same file, or when the stream would otherwise stay open far longer than it is needed. Otherwise it is optional — but the course reading writes close() every time, and matching that costs nothing.

Problem 1 — Write C++ statements (added)

Do not write complete programs, just give a single line, or a few lines, of C++ instructions for each task. Assume the standard headers are already included.

(a) Declare an input file stream called ifs attached to the file scores.txt.

ifstream ifs("scores.txt");

The file name goes in the constructor. ifstream ifs; followed by ifs.open("scores.txt"); is equally correct and is what you need when the name is not known until later.

(b) Print an error message and leave main with a failure status if that file could not be opened.

if (!ifs.is_open()) {
    cout << "Could not open scores.txt" << endl;
    return 1;
}

if (!ifs) and if (ifs.fail()) are accepted alternatives. return 1; — not return 0; — because the program did not do its job.

(c) Read every name score pair from ifs into a string and an int, printing each pair as it is read.

string name;
int score;
while (ifs >> name >> score) {
    cout << name << " " << score << endl;
}

The read goes in the condition. Any answer built on eof() loses the marks for this part, for the reasons worked through in §5.

(d) Declare an output file stream called ofs that adds to the end of log.txt rather than replacing it.

ofstream ofs("log.txt", ios::app);

The second argument is the whole answer. Omit it and you get overwrite mode, which is the opposite of what was asked. If log.txt does not exist it is created either way.

(e) Write the last name and score read to ofs on one line, then close both streams.

ofs << name << " " << score << endl;
ifs.close();
ofs.close();

Things to notice. name and score must be declared outside the loop in part (c) for this to compile — if they were declared inside, they would be out of scope here. That is one more reason the corrected read-loop form, which forces the declarations above the loop, is the better habit.

Writing to ofs looks exactly like writing to cout. That is not a coincidence or a convenience; it is the same operator on the same family of stream types, and it is why the course reading can dispose of the entire topic with "writing to file is similar to writing to the console."

Problem 2 — Read a file, compute an average, write a report (added)

Write a complete C++ program that reads scores.txt, a file with one name score pair per line. The program should store the names and scores in vectors, compute the average score, and write to a new file above.txt the average followed by every student whose score is strictly above it. Print a one-line confirmation to the console. Handle a missing file and an empty file.

Use this input:

Alice 88
Bob 92
Carol 79

Plan. This is a two-pass problem: you cannot decide who is above average until you have seen everybody, so the data has to be stored, not streamed. Two parallel vectors hold the names and the scores. The averaging step needs one piece of care — total and size() are both integer-like, so dividing them directly would give integer division and truncate 86.33 to 86. Cast one operand to double first. Then open above.txt in overwrite mode, since it is a fresh report, and loop a second time writing the ones that qualify.

p2_average.cpp
// p2_average.cpp -- read name/score pairs from a file, report who beat the average
#include <iostream>
#include <fstream>
#include <string>
#include <vector>
using namespace std;

int main() {
    ifstream ifs("scores.txt");
    if (!ifs.is_open()) {
        cout << "Could not open scores.txt" << endl;
        return 1;
    }

    vector<string> names;
    vector<int> scores;
    string name;
    int score;
    while (ifs >> name >> score) {
        names.push_back(name);
        scores.push_back(score);
    }
    ifs.close();

    if (names.empty()) {
        cout << "No records found." << endl;
        return 1;
    }

    int total = 0;
    for (size_t i = 0; i < scores.size(); ++i) {
        total += scores[i];
    }
    double average = static_cast<double>(total) / scores.size();

    ofstream ofs("above.txt", ios::out);
    ofs << "average = " << average << endl;
    for (size_t i = 0; i < names.size(); ++i) {
        if (scores[i] > average) {
            ofs << names[i] << " " << scores[i] << endl;
        }
    }
    ofs.close();

    cout << "read " << names.size() << " records, average = " << average << endl;
    cout << "wrote above.txt" << endl;
    return 0;
}

Console:

read 3 records, average = 86.3333
wrote above.txt

And above.txt:

average = 86.3333
Alice 88
Bob 92

Things to notice.

  • static_cast<double>(total) / scores.size() is the fix for integer division. Without the cast, 259 divided by 3 is 86, and Carol's 79 would still be below it, so the program would look right on this data and be wrong on other data. That is the most dangerous kind of bug there is — test the arithmetic separately from the file handling.
  • The two guards do different jobs. is_open() catches "the file is not there"; names.empty() catches "the file is there but has nothing in it", which would otherwise divide by zero.
  • The average prints as 86.3333 — six significant digits, the cout default. If you want two decimal places you need <iomanip> and setprecision, which is Class 3's material.
  • Parallel vectors are the honest answer with the tools we have today. Once we have classes, a single vector<Student> replaces both and makes it impossible for the two lists to fall out of step — which is the argument for classes in a nutshell, and where Class 9 picks up.

Problem 3 — Predict the output (added)

The file infile2.txt contains exactly this, with a newline at the end of the last line:

6 2.2 Alice
2 1.6 Bob
5 3.4 Charlie

Give the exact output of each of the following loops. Assume ifs is a freshly opened ifstream on that file in each case, and that a, d, s are declared int, double, string.

(a) while (ifs >> a >> d >> s) cout << s << endl;

Alice
Bob
Charlie

Three successful reads, then a fourth that fails on the empty remainder and ends the loop. The correct idiom, the correct answer.

(b) while (!ifs.eof()) { ifs >> a >> d >> s; cout << s << endl; }

Alice
Bob
Charlie
Charlie

Four lines. After Charlie is read the final newline has not yet been consumed, so eof() is still false and the loop runs a fourth time. That read fails, leaving s holding its previous value, and the body prints it anyway.

(c) The same as (b), but on a copy of the file with the final newline deleted.

Alice
Bob
Charlie

Three lines — the right answer, from the wrong loop. Reading Charlie consumes the last character, so eof() becomes true immediately and the fourth iteration never starts.

Things to notice. Put (b) and (c) side by side: the identical loop gives different answers on two files that look identical on screen. And the version in the course reading — read first, if (ifs.eof()) break; after — fails the other way round, printing three lines here and only two on the file without the newline.

Three loops, four combinations of loop and file, and only one of them is right on both files: while (ifs >> a >> d >> s). Output-prediction questions like this one carry no partial credit on this professor's exams, so the way to get them right is not to memorize the four cases but to internalize the one sentence: eof() reports a read that has already failed; it does not predict the next one.

Problem 4 — Dice histogram to a file (added)

Write a complete C++ program that rolls two six-sided dice 1000 times, counts how often each total from 2 to 12 comes up, and writes the eleven counts to histogram.txt, one total count pair per line. Seed with srand(42) so your run matches the one below.

Plan. The counts want an array indexed by the total itself — declare int count[13] and use elements 2 through 12, leaving 0 and 1 unused. Wasting two ints buys you count[a + b]++ instead of count[a + b - 2]++, and every off-by-one in the problem disappears. Initialize with = {0}, which zeroes the whole array. Each roll is two independent calls to the scaling expression — two calls, not one call used twice, or the dice are always equal.

p4_histogram.cpp
// p4_histogram.cpp -- roll two dice 1000 times and write a histogram to a file
#include <iostream>
#include <fstream>
#include <cstdlib>
using namespace std;

int main() {
    srand(42);                       // fixed seed so the run is reproducible

    const int ROLLS = 1000;
    int count[13] = {0};             // count[2] .. count[12]

    for (int i = 0; i < ROLLS; ++i) {
        int a = 1 + rand() % 6;
        int b = 1 + rand() % 6;
        count[a + b]++;
    }

    ofstream ofs("histogram.txt", ios::out);
    if (!ofs.is_open()) {
        cout << "Could not open histogram.txt" << endl;
        return 1;
    }
    for (int sum = 2; sum <= 12; ++sum) {
        ofs << sum << " " << count[sum] << endl;
    }
    ofs.close();

    cout << "wrote histogram.txt" << endl;
    return 0;
}

Things to notice.

  • The counts sum to 1000 — check it. Any histogram whose bars do not add up to the number of trials has a bucket you forgot.
  • The shape is the real payoff: 7 is the most common total by a wide margin (194 out of 1000, near the theoretical 1/6) and 2 and 12 are the rarest (20 and 28, near the theoretical 1/36 which would be about 28). Two dice are not a uniform distribution over 2–12, because there are six ways to make a 7 and only one way to make a 2. If your histogram comes out flat, you generated the total directly with 2 + rand() % 11 instead of rolling two dice.
  • srand(42) is stated in the problem so that the expected output can be printed. A real simulation would use srand(time(0)), and then no two runs would agree in the last digits — though the shape would be the same every time, which is the whole reason simulations are worth running.
  • The is_open() check on an ofstream is not paranoia. Output opens fail on read-only directories and bad paths, and a silent failure here would leave you staring at a file that never changes.

Problem 5 — A run log (added)

Write a complete C++ program that keeps a log of how many times it has been run. On each run it should count the lines already in runlog.txt (treating a missing file as zero), append a new line reading run N where N is one more than that count, and print the run number to the console. Running it three times in a row should produce a three-line log.

Plan. Two passes over the same file, in two different modes, and they must not overlap. First open it for reading and count lines with getline — and here a failed open is not an error, it just means this is the first run, so the count stays zero. Close it. Then open it for appending and write one line. Getting the order wrong is fatal: open the ofstream first in overwrite mode and you erase the very history you were about to count.

p5_runlog.cpp
// p5_runlog.cpp -- number each run by counting the lines already in the log
#include <iostream>
#include <fstream>
#include <string>
using namespace std;

int main() {
    string logfile("runlog.txt");

    // pass 1: count the lines already there (missing file counts as zero)
    int runs = 0;
    ifstream ifs(logfile);
    if (ifs.is_open()) {
        string line;
        while (getline(ifs, line)) {
            ++runs;
        }
        ifs.close();
    }

    // pass 2: append this run
    ofstream ofs(logfile, ios::app);
    if (!ofs.is_open()) {
        cout << "Could not open " << logfile << " for writing" << endl;
        return 1;
    }
    ofs << "run " << (runs + 1) << endl;
    ofs.close();

    cout << "this is run number " << (runs + 1) << endl;
    return 0;
}

Three consecutive runs, starting with no runlog.txt at all:

this is run number 1
this is run number 2
this is run number 3

And runlog.txt afterwards:

run 1
run 2
run 3

Things to notice.

  • This is the one place in these notes where a failed ifstream open is not an error. The if (ifs.is_open()) wraps the counting instead of aborting the program, because "the log does not exist yet" is a perfectly normal state on the first run. Checking the open is mandatory; what you do about a failure is a design decision.
  • ifs.close() before the ofstream is constructed is the important line, exactly as ofs1.close() was in §8. Two streams open on one file at once is a situation to avoid on purpose, not by luck.
  • ios::app is essential. With the default overwrite mode the file would be truncated at the moment ofs is constructed, the count would restart from zero on the very next run, and the log would never grow past one line.
  • An alternative design stores the number itself rather than counting lines — read one int, add one, write it back in overwrite mode. That is fewer lines of code and loses the history. Which one is better depends entirely on whether anyone will ever want to look at the history, which is the sort of question worth asking before you pick a file format.
Lecture Summary
  • A PRNG is deterministic. The seed chooses where in the sequence you start, so the same seed gives the same sequence every run. With no srand at all, every run repeats.
  • srand(n) seeds; rand() draws; both need <cstdlib>. Call srand once, before the first rand(). srand(time(0)) from <ctime> gives a different sequence per run; a fixed seed like srand(42) gives a reproducible one, which is what you want for testing and grading.
  • To get a value in lo..hi: lo + rand() % (hi - lo + 1). Derive it, do not recall it — rand() % 6 is 0 to 5, not 1 to 6.
  • The <random> recipe is four steps: include, instantiate a default_random_engine, seed() it, then declare a distribution such as uniform_int_distribution<int> and call it with the generator as its argument. Both endpoints are inclusive and no % is needed.
  • #include <fstream> gives you ifstream (reads, like cin) and ofstream (writes, like cout). An output file is created if it does not exist; an input file open simply fails. Check every open with is_open() or !ifs.
  • The read loop is while (ifs >> a >> d >> s) { ... }. Any loop controlled by eof() is wrong: it drops the last record on a file with no trailing newline, duplicates it on a file with one, and spins forever on a type mismatch. eof() reports a read that has already failed; it never predicts the next one.
  • >> reads one whitespace-delimited token with type checking; getline(ifs, line) reads a whole line into a string. After any >>, the newline is still in the stream — swallow it with a throwaway getline before switching modes.
  • ofstream ofs(name, ios::out) overwrites (and truncates the moment it is constructed); ios::app appends. Overwrite is for a result, append is for a history. close() is optional in general but required before another stream touches the same file.
  • Guard anything that indexes element 0 of a container you filled from a file. An empty file opens successfully and gives you an empty vector, and iv[0] on that is a segfault.
