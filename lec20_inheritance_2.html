Inheritance II — Construction Order and the Big Three

A derived object is built from the inside out: the base part first, then the members, then the body — and taken apart in exactly the opposite order. Everything else today follows from that one sentence.

Learning Objectives

1.Where we left off: the Rectangle base class

In Class 19 you met inheritance: class Square : public Rectangle says that a Square IS-A Rectangle, that every Square object physically contains a Rectangle sub-object, and that a Square can use the base class's protected and public members as if they were its own. What you have not seen is a single line of Square's implementation. Class 19 ended with two open questions:

  • How do you write constructors for a derived class? "The answer is not so obvious."
  • What about the Big Three — copy, assign, destroy?

Today we answer both, and along the way we nail down the single most-traced behavior in this course: the exact order in which the pieces of a derived object come into existence and go out of it. Here is the base class again, complete. Read it once; every example on this page uses it.

Worked Example— the base class, with instrumentation

Notice that every special member prints its own name. That is not decoration — it is the instrument we will use all day to see the order of events. The professor's exams do exactly the same thing, which is what makes an output-prediction question gradeable.

rectsquare.cpp (base class)
#include <iostream>
#include <cmath>
using namespace std;

class Rectangle {
public:
    Rectangle() {
        h = 1.0;
        w = 1.0;
        cout << "Rectangle: default constructor" << endl;
    }

    Rectangle(double ht, double wd) {
        h = ht;
        w = wd;
        cout << "Rectangle: non-default constructor" << endl;
    }

    ~Rectangle() {
        cout << "Rectangle: destructor" << endl;
    }

    double height() const { return h; }
    double width()  const { return w; }
    double area()   const { return fabs(h * w); }

    void print() const {
        cout << "Rectangle::print ";
        cout << "(" << 0 << "," << 0 << "), ";
        cout << "(" << w << "," << 0 << "), ";
        cout << "(" << w << "," << h << "), ";
        cout << "(" << 0 << "," << h << ")";
        cout << endl;
    }

protected:
    double h, w;
};

Four things to have straight before we build on it:

  • h and w are protected, not private. That is the whole reason Square will be able to read them directly. A private member would be locked out even from a derived class.
  • There are two constructors. The default one produces the unit square 1 by 1; the non-default one takes a height and a width.
  • The destructor does nothing useful — Rectangle allocates no memory — but it prints, so we can watch it run.
  • print() puts the bottom-left corner of the rectangle at the origin. The class stores no position at all, so that is a fixed convention, not a choice you can change per object.
Warning— two corrections to the original listing

The version of Rectangle printed in the course notes writes return abs(h*w); with no #include <cmath>. If only the C headers happen to be in scope, abs is the integer abs(int), so abs(2.5 * 2.5) truncates to 6 instead of 6.25. In a class about double arithmetic that is a real hazard. Use #include <cmath> and fabs, as above.

The same listing also uses cout and endl without #include <iostream> or using namespace std; — they came from the enclosing program on the slide. Both are added here so the file compiles on its own.

Common Mistake— you cannot forward-declare a derived class

The course notes abbreviate long listings by writing the class headers with a semicolon:

class Rectangle;
class Square : public Rectangle;

That is shorthand for the reader, not C++. A forward declaration announces that a name is a class; it may not carry a base list, and you could not derive from Rectangle there anyway because at that point Rectangle is an incomplete type — the compiler does not yet know how big its sub-object is. Really compiling it gives

fwddecl.cpp:5:32: error: expected '{' before ';' token
    5 | class Square : public Rectangle;
      |                                ^

A base class must be fully defined before any class derives from it. In practice that means the base's complete definition — or the header that contains it — comes first in the file.

Quick Check 20.1

Square is declared as class Square : public Rectangle and adds one protected data member, bool centered.

(a) How many double values does a single Square object contain, and where do they live?

Two — h and w. They live in the Rectangle sub-object that sits inside every Square. Square itself declares no double at all; it inherits those two. The full object is "a Rectangle part, plus a bool".

(b) Inside a Square method, can you write h = 5.0;? Could you if h were private in Rectangle?

Yes to the first — protected means "private to the outside world, public to derived classes", so Square's methods may read and write h by name.

No to the second. private is an absolute lock-out. It does not matter that a Square IS-A Rectangle or that the Rectangle sub-object is physically inside the Square; a derived class cannot touch a private base member, and would have to go through a public accessor or mutator instead.

2.Constructors of a derived class

Here is the problem. When you write Square s;, some code has to put a value into h, a value into w, and a value into centered. But Square's constructor is not allowed to be the thing that initializes h and w — those belong to Rectangle, and Rectangle already has perfectly good constructors that know how to set them. Duplicating that logic inside Square would be exactly the copy-and-paste that inheritance exists to eliminate.

So C++ takes a different route. A derived constructor does not initialize the base data itself; it asks the base class's constructor to do it, and it asks in the member initializer list.

Definition— base initializer

A base initializer is an entry in a constructor's member initializer list that names the base class instead of a data member:

Square::Square(double e, bool c) : Rectangle(e, e) {
    centered = c;
}

It means: build my Rectangle sub-object by calling Rectangle(e, e). It looks like a member initializer because it is one — the base sub-object is just another thing inside the object that has to be initialized, and it is initialized in the same list, using the same syntax. The only difference is that it names a class rather than a variable.

The professor puts it in one sentence, and it is worth memorizing verbatim:

Key Idea

Objects of derived classes are constructed in sequence. The base class constructor is invoked first, then the derived class constructor.

You are not initializing "the height of the square". You are initializing the Rectangle component of the Square object, and then filling in what Square adds on top.

That gives us Square's two constructors. The default one hands the job to Rectangle's default constructor; the non-default one hands it to Rectangle's non-default constructor. A square has equal sides, so we pass the same edge length twice:

rectsquare.cpp (Square's constructors)
Square::Square() : Rectangle() {
    centered = false;
    cout << "Square: default constructor" << endl;
}

Square::Square(double e, bool c) : Rectangle(e, e) {
    centered = c;
    cout << "Square: non-default constructor" << endl;
}

Read the second one out loud: "to build a Square of edge e, first build a Rectangle whose height and width are both e, then set centered to c." That is the whole idea.

Key Idea

A derived class constructor can call any constructor it likes in the base class — there is no rule that a default constructor must pair with a default constructor. In practice pairing default-with-default and non-default-with-non-default is what usually makes sense, but Square(double e, bool c) : Rectangle() is legal C++ if that is genuinely what you want. What you may not do is name two base constructors, or name the base twice.

Quick Check 20.2

For each derived constructor below, say which Rectangle constructor runs and what h and w end up holding. Use the Rectangle class from §1.

(a) Square::Square(double e, bool c) : Rectangle(e, e) { centered = c; } called as Square s(4.0, true);

The non-default Rectangle(double, double) runs with ht = 4.0 and wd = 4.0, so h == 4.0 and w == 4.0. Then the body sets centered = true.

(b) Square::Square(double e, bool c) : Rectangle() { centered = c; } called as Square s(4.0, true);

The default Rectangle() runs, so h == 1.0 and w == 1.0. The argument 4.0 is never used for anything — it is silently thrown away. This compiles without a single warning, and it is one of the easier ways to lose points on an exam. Legal, but almost never what you meant.

(c) Square::Square(double e, bool c) : Rectangle(e, e), centered(c) { } — is this legal, and is it different from (a)?

Legal, and slightly better. centered is a member of Square, so it can appear in Square's initializer list right alongside the base initializer. It is now initialized rather than default-initialized-and-then-assigned. For a bool the difference is invisible, but for a member with an expensive constructor — a string, a vector — initializing in the list instead of assigning in the body is the habit worth having.

Note the order in the list: the base initializer comes first. That is a convention, not a rule — and §4 explains why the compiler ignores the order you write anyway.

3.What if you don't name the base?

Nothing forces you to write a base initializer. So what does the compiler do when you leave it out? It does not skip the base — it cannot, because the base sub-object exists whether you mention it or not and its members have to be given values by somebody. Instead it quietly supplies the one initializer that needs no arguments:

Key Idea

If a derived constructor's initializer list does not name the base class, the compiler inserts a call to the base class's default constructor. If the base has no default constructor, that is a compile error, not a silent skip.

Worked Example— the base default constructor runs anyway

This Square takes an edge length and never passes it anywhere. Before you look: how many lines does it print, and what does s.edge() report?

implicitbase.cpp
class Square : public Rectangle {
public:
    // NOTE: no ": Rectangle(...)" anywhere in this constructor
    Square(double e) {
        centered = false;
        cout << "Square: constructor, edge asked for = " << e << endl;
    }
    ~Square() { cout << "Square: destructor" << endl; }
    double edge() const { return height(); }
protected:
    bool centered;
};

int main() {
    Square s(7.0);
    cout << "s.edge() = " << s.edge() << endl;
    return 0;
}

Square: constructor, edge asked for = 7

The first line is the giveaway. Nobody wrote Rectangle() anywhere, yet Rectangle's default constructor ran — the compiler inserted it. So h and w are 1.0, the 7.0 was received into the parameter e, printed, and then dropped on the floor. The object is a perfectly valid unit square that has nothing to do with the 7 the caller asked for.

This compiles clean with -Wall. There is no warning to save you. The only thing that catches it is reading the trace, which is exactly the skill the exam tests.

Common Mistake— "calling" the base constructor in the body

Every semester somebody notices that the base data is wrong and fixes it like this:

tempbase.cpp
Square(double e) {
    Rectangle(e, e);            // WRONG: this builds a throw-away temporary
    centered = false;
    cout << "Square: constructor" << endl;
}

It compiles. It does not do what you want:

Rectangle: default constructor
Rectangle: non-default constructor
Rectangle: destructor
Square: constructor
s.edge() = 1
Square: destructor
Rectangle: destructor

Read those first three lines. The real base sub-object was already default-constructed before the body started. Then the statement Rectangle(e, e); built a brand-new, nameless temporary Rectangle, which was destroyed at the semicolon. Your object never saw it, and s.edge() is still 1.

Initializing the base is not something a statement can do. It happens before the body runs, and the only place to say what you want is the initializer list.

Quick Check 20.4

A base class Account has exactly one constructor, Account(string owner). A derived class Savings is written as

class Savings : public Account {
public:
    Savings(string owner, double r) {
        rate = r;
    }
private:
    double rate;
};

(a) Does this compile? If not, quote the shape of the error.

No. The compiler inserts a call to Account::Account(), which does not exist — declaring any constructor suppresses the implicitly generated default one. You get error: no matching function for call to 'Account::Account()', reported inside Savings::Savings(std::string, double) with the caret on the opening brace.

(b) Fix it, without changing Account.

Savings(string owner, double r) : Account(owner) {
    rate = r;
}

Or better, initialize rate in the list too: Savings(string owner, double r) : Account(owner), rate(r) { }.

(c) Suppose instead you add Account() { } to the base and leave Savings as printed. It now compiles. Is the bug gone?

No — it got worse. It compiled, which means nothing complains any more, but the owner argument is still being discarded and every Savings object now has whatever empty owner Account() leaves behind. A loud compile error is a much better outcome than a quiet wrong answer. Adding a default constructor "so it compiles" is the wrong reflex; supplying the base initializer is the right one.

4.Construction order, in full

We have said "base first, then derived". The complete rule has three stages, and the middle one is where the exam trips people.

Procedure— what happens when a derived object is constructed
  1. The base sub-object is constructed — using the base initializer you wrote, or the base's default constructor if you wrote none. (If the base itself derives from something, this whole procedure repeats there first, all the way down to the root of the inheritance chain.)
  2. The derived class's data members are constructed, in the order they are declared in the class — not the order you listed them in the initializer list.
  3. The body of the derived constructor runs.

By the time the first statement of your constructor body executes, everything the object is made of already exists. That is the point of the whole arrangement: your body can safely use h, w, and any member, because they are all built.

Worked Example— all three stages, visible

To see stage 2 we need members that announce themselves, so here is a tiny Part class whose only job is to print on construction and destruction. Base has two Part members and Derived has two more. Work out the exact sequence of lines before you open the answer — there are fourteen of them.

Members are constructed in declaration order, no matter what order you write them in the initializer list. If the two disagree, the list is a lie about what will happen, and g++ tells you so:

Quick Check 20.6

Suppose class C : public B and class B : public A, and each of the three has a constructor that prints its own name.

(a) What does C c; print?

A, then B, then C. The rule applies recursively: before B's sub-object can be built, its base A must be built. Construction starts at the root of the inheritance chain and works outward.

(b) Can C's constructor write : A() in its initializer list to skip past B?

No. C's direct base is B, and B is the only class C may name in a base initializer. A is not C's business — choosing which A constructor to run is B's job, and C influences it only by choosing which B constructor to call. Trying it gives error: type 'A' is not a direct base of 'C'.

5.Destruction order: exactly the reverse

Destructors are the easy half of today, because there is nothing to decide. A class has many constructors but exactly one destructor, so there is never a question of "which destructor" to call. And you never write a call to the base destructor:

Key Idea

The destructor of the derived class does not explicitly call the destructor of the base class. The compiler does that automatically for us.

And: objects are destroyed in the opposite order to how they are constructed. The derived destructor body runs first, destroying the "Square part"; then the base destructor runs, destroying the implicit Rectangle object.

So Square's destructor looks exactly like the destructor of any non-derived class:

rectsquare.cpp (Square's destructor)
Square::~Square() {
    cout << "Square: destructor" << endl;
}

Square allocates no memory, so there is nothing to release. If it did — if it held a pointer to something built with new — the delete would go here, in the derived destructor, and Rectangle's destructor would still be responsible only for Rectangle's own resources. Each destructor cleans up exactly what its own class added, and the chain covers the whole object.

Procedure— what happens when a derived object is destroyed
  1. The body of the derived destructor runs. Release anything the derived class allocated.
  2. The derived class's data members are destroyed, in reverse declaration order.
  3. The base destructor is called automatically, and repeats these three steps for itself, all the way down the chain.

6.Calling a base-class version on purpose

Square inherits height(), width() and area() and overrides none of them — there is nothing to change. But print() is different. Rectangle::print() puts the bottom-left corner at the origin. For a square we would sometimes rather put the center at the origin, which is what the centered flag is for. So Square needs its own print().

Here is the design the professor lands on, and it is a nice one because it only half-overrides:

  • If centered is true, print the four vertices at ±half an edge — that is genuinely new behavior.
  • If centered is false, the base class already does the right thing. Use it.
Definition— explicit qualification

Writing Rectangle::print(); inside a Square method calls the Rectangle version specifically, bypassing the normal name lookup that would find Square::print. The ClassName:: prefix is called a qualified name, and it lets you name any version in the inheritance chain.

The professor's general rule: "if the base class is A and B derives from A and C derives from B, then we select the specific function we want by writing A::print() or B::print() or C::print()." As always, this reaches only public and protected methods — a derived class cannot call the private methods of its parent.

All of this resolution happens at compile time from the declared type of the object — the static binding you met in Class 19. Writing a qualified name is simply telling the compiler which candidate to bind to. When we make methods virtual in Class 24 the unqualified call starts being resolved at run time instead, and Base::method() becomes the only way left to reach the version you overrode.

7.The Big Three for a derived class

You already know the Big Three from Classes 14 and 15: if a class needs one of destructor, copy constructor, operator=, it almost certainly needs all three. The question today is what changes when the class is derived.

The destructor, we just saw, changes nothing at all — it looks exactly like any other destructor, and the base one is called for you. As the professor puts it, "this section is really about the Big Two, not the Big Three."

Neither Rectangle nor Square holds a pointer or allocates memory, so a shallow copy would work for them and the compiler-generated versions would be correct. We write them out anyway, because the shape is what you need — and because the moment a real base class does own memory, getting this shape wrong destroys the data silently. First, the base class's copy constructor and assignment operator:

bigthree_ok.cpp (base class)
Rectangle(const Rectangle &orig) {
    h = orig.h;
    w = orig.w;
    cout << "Rectangle: copy constructor" << endl;
}

Rectangle& operator=(const Rectangle &rhs) {
    if (this == &rhs) return *this;
    h = rhs.h;
    w = rhs.w;
    cout << "Rectangle: assignment operator" << endl;
    return *this;
}

Nothing new: the self-assignment guard, the member-wise copy, return *this;. Now the derived versions.

Procedure— the derived copy constructor
  1. The signature follows the same rule as any C++ class: Square(const Square &orig);
  2. Call the base class's copy constructor in the member initializer list, passing the whole orig object: : Rectangle(orig).
  3. The Rectangle copy constructor copies the Rectangle part.
  4. Then copy the data that belongs to the Square part.
Square::Square(const Square &orig) : Rectangle(orig) {
    centered = orig.centered;
    cout << "Square: copy constructor" << endl;
}

This is a shallow copy, which is all these classes need. If Square owned memory, step 4 would be a deep copy instead — the pattern is unchanged.

Look hard at Rectangle(orig). Rectangle's copy constructor takes a const Rectangle &, and we are handing it something of type Square. Why does that work?

Key Idea— IS-A, again

Every Square IS-A Rectangle, so a reference to the base class can bind to an object of a derived class. The reference binds to the implicit Rectangle sub-object living inside the Square. Rectangle's copy constructor therefore sees exactly the part of orig it knows how to copy, and copies it. The same holds for pointers: a Rectangle * can hold the address of a Square. We use that fact hard in Class 21.

Procedure— the derived assignment operator
  1. Signature: Square& operator=(const Square &rhs);
  2. Test for self-assignment: if (this == &rhs) return *this;
  3. Invoke the base class's assignment operator to assign the Rectangle part.
  4. Copy the data in the Square part.
  5. return *this;
Square& Square::operator=(const Square &rhs) {
    if (this == &rhs) return *this;
    Rectangle::operator=(rhs);
    centered = rhs.centered;
    cout << "Square: assignment operator" << endl;
    return *this;
}

Line 3 looks nothing like an assignment. There is no = between two operands, and rhs sits in parentheses like a function argument. That is because it is a function call:

Key Idea

The assignment operator is not only an operator, it is also a class method. Rectangle::operator= is its real name, and Rectangle::operator=(rhs) calls it on the current object — on this, whose Rectangle sub-object it therefore updates. When you write a = b the compiler turns it into a.operator=(b); here we just write that form out by hand, qualified so it picks the base version rather than recursing into Square::operator=.

As with the copy constructor, rhs is a Square and the parameter is a const Rectangle &, and it binds to the Rectangle part. IS-A pays for both.

8.Reading a construction trace

"Assuming your X class is correctly implemented and prints the corresponding messages, what will be the output of the following main program?" — some version of that sentence has appeared on seven of this professor's ten exam papers, and on every single final it comes with a derived class attached. It is worth a point per printed line and carries no partial credit, so the whole question is won or lost on being systematic.

Procedure— how to answer a trace question without guessing
  1. List the objects in the order they are declared. Note the type of each.
  2. Walk main one statement at a time. For each statement decide which special member runs: default constructor, non-default constructor, copy constructor, operator=, operator+, or nothing at all.
  3. For a derived object being constructed, write two lines, base then derived — that order is fixed by the language. For operator= the order is not fixed: read the class and see whether it prints before or after it calls the base version.
  4. Watch for initialization versus assignment: X c = a; is a copy constructor, not an assignment. a = b; on an object that already exists is operator=.
  5. At the closing brace, destroy every local object in reverse declaration order, writing derived-then-base for each.
  6. Count your lines. The rubric usually tells you how many there should be.

Step 2 has one subtlety that the professor's rubrics quietly depend on: what happens to the temporary returned by something like operator+.

Definition— copy elision

Copy elision is the compiler's permission — and since C++17, in some cases its obligation — to skip a copy that a naive reading of the code would predict. When a function returns an object by value and the caller uses it to initialize a new object, C++17 requires the result to be built directly in the destination. No copy constructor runs and no temporary is destroyed, because there was never a separate temporary at all.

Lecture Summary
  • A derived constructor initializes its base sub-object through a base initializer in the member initializer list: Square(double e, bool c) : Rectangle(e, e). It is not special syntax — the base sub-object is just another thing that has to be initialized, in the same list, the same way.
  • A derived constructor may call any constructor of its direct base, but only its direct base.
  • Name no base and the compiler inserts the base's default constructor. If the base has none, you get error: no matching function for call to 'Base::Base()' with the caret on the derived constructor's opening brace.
  • Writing Rectangle(e, e); as a statement in the body builds and destroys a temporary and changes nothing. Initialization happens before the body runs.
  • Construction order: base sub-object (recursively, from the root of the chain), then the derived class's members in declaration order, then the constructor body. The order you write the initializer list in is ignored; -Wreorder warns when they disagree.
  • Destruction order is exactly the reverse: derived destructor body, derived members in reverse declaration order, then the base destructor — called automatically. You never write a call to a base destructor.
  • Rectangle::print() calls a specific version by qualified name, bypassing the override. Use it when a derived method wants to do a bit extra and then let the base do the rest; omit the prefix and the method calls itself.
  • A derived class may add members the base never had — edge() — and should override only what genuinely differs.
  • A derived copy constructor must forward to the base copy constructor: Square(const Square &orig) : Rectangle(orig). It works because a base reference binds to the base sub-object of a derived object — IS-A.
  • A derived operator= must call Rectangle::operator=(rhs);. The assignment operator is a method as well as an operator, so that line is an ordinary function call.
  • Forget the base in a copy constructor and the base part is silently default-constructed; forget it in operator= and the base part is left stale. Both compile clean with -Wall.
  • Under C++17, copy elision removes the copy that a naive trace predicts for X d = a + b;. Answer trace questions with the -std=c++17 behavior.
