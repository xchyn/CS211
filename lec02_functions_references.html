1.Call by value: the function gets a copy

Class 1 ended with a promise. We looked at two functions called swap1 and swap2, identical except for two & characters in a parameter list. One of them swapped its caller's variables and one of them did nothing at all, and we said the explanation was Class 2's business. This is Class 2, so let's collect.

The whole thing turns on one question: when you call a function, what exactly does the parameter hold? Everyone's first instinct is "the variable I passed in." That instinct is wrong, and it is wrong by default in C++.

Definition— argument, parameter, call by value

An argument is the thing you write at the call site: the n in tryToChange(n);.

A parameter is the variable named in the function's own declaration: the x in void tryToChange(int x).

Call by value means that when the call happens, the parameter is created as a brand-new variable, in its own storage, and initialized with a copy of the argument's value. From then on the two have nothing to do with each other. The function can scribble on its parameter as much as it likes; it is scribbling on its own copy, and the copy is thrown away when the function returns.

Call by value is what you get in C++ unless you specifically ask for something else. Every parameter you have written since CSCI 111 has been call by value.

Now go back to Class 1's puzzle and it evaporates. swap1(int u, int v) received copies of a and b, swapped the two copies perfectly correctly, and then dropped them on the floor. The function was never broken; the parameter passing was.

Key Idea

A by-value parameter is a local variable of the function that happens to start out with a copy of the argument's value. Assigning to it is exactly as private as assigning to any other local. If a function has to change something in its caller, call by value cannot do it — not by being written more cleverly, not ever.

Quick Check 2.1

A student is told that swap1 does not work and tries to fix it like this, without touching the parameter list:

void swap1(int u, int v) {
    int t = u;
    u = v;
    v = t;
    return;             // "make sure the changes get sent back"
}

(a) Does the added return; change anything?

No. A bare return; in a void function means "stop here" and nothing else. Every void function already returns implicitly when it falls off the end, so the line is completely redundant — it neither helps nor hurts.

The bug is not that the changes fail to get "sent back". The bug is that the changes were never made to a and b in the first place. They were made to u and v, which are different variables in different storage.

(b) Could you fix it by writing return u, v; or by returning something?

No. A C++ function returns exactly one value. (return u, v; is legal syntax but it is the comma operator — it evaluates u, throws it away, and returns v. It would not even compile here, because the function is void.)

You could redesign the whole thing so the caller writes something like a = firstOf(a,b); b = secondOf(a,b);, but that is a different function with a different interface, and it is fragile. The right fix is to change how the parameters arrive — which is §2.

(c) Class 1 mentioned that gcd(int a, int b) deliberately modifies its parameters as it works. Why is call by value the *right* choice there?

Because gcd is a query: the caller wants an answer, not a side effect. Euclid's algorithm is easiest to write if you may chew up a and b as you go, and call by value hands you two scratch variables for free while guaranteeing the caller's originals survive.

That is the general rule and it is worth stating positively: call by value is not a mistake, it is a decision. Use it when the function should not be able to touch the caller's data. Reach for a reference only when the function genuinely has to.

2.Call by reference: another name for the same variable

C++ gives you a second option, and the syntax for it is a single character.

Definition— reference, call by reference

A reference is an alias — a second name for a variable that already exists. You declare one by putting & after the type:

int &r = a; makes r another name for a. There is no new integer anywhere. Reading r reads a; writing r writes a. The two names are bound together for the rest of r's life.

Call by reference is what you get when a parameter is declared as a reference: void f(int &x). No copy is made at the call. The parameter x is bound to whatever variable the caller passed, so everything the function does to x lands on the caller's variable.

Worked Example— the same function, one ampersand different

This is byte-for-byte the program from §1 with int x changed to int &x. Nothing else moved — not main, not the call, not the body. Predict the four lines again.

    x = 99;
    cout << "   inside, after x = 99: x = " << x << endl;

    int n = 5;

   inside, on arrival:  x = 5

Only the last line differs from §1, and it differs completely. Inside the function, the name x is main's n. There is one integer in this program, and it has two names.

Notice what did not change: main still writes tryToChange(n); with no decoration whatsoever. You cannot tell from a call site whether an argument is going to be modified. You have to go and look at the function's declaration. That is a genuine readability cost of references, and it is the reason experienced C++ programmers keep function declarations somewhere easy to find — a habit that turns into header files in §7.

If you want proof that no copy is made, ask the program where its variables live. The & operator applied to a variable — as in &n — yields that variable's address in memory. We study addresses properly in Class 7; for today just read them as identity tags. Two names with the same address are the same object.

Common Mistake— two jobs, one symbol

The character & does two unrelated things in C++, and they are easy to confuse:

  • In a declaration, after a type — int &r = a;, void f(int &x) — it means "this is a reference."
  • In an expression, in front of a variable — &n — it is the address-of operator.

Tell them apart by asking whether a type name is sitting to the left. If yes, it is a reference declaration. If no, it is address-of. (There is a third use, a & b for bitwise AND, which this course does not need, and a && b for logical AND, which it does.)

Worked Example— a copy lives somewhere else; a reference does not

These are the two one-line functions from the course notes, put into a runnable program and made to print the address of their parameter. Before you look: which of the three addresses do you expect to match?

// addresses.cpp -- a copy lives somewhere else; a reference does not

using namespace std;

void print_call_by_val(int x) {
    cout << "   by value:     x = " << x << "   at address " << &x << endl;

    cout << "   by reference: y = " << y << "   at address " << &y << endl;
}

int main() {
    int n = 7;

The exact hexadecimal numbers are representative, not reproducible: they change from machine to machine and even from run to run, because the operating system deliberately puts the stack somewhere different each time. What is completely reproducible is the pattern:

  • print_call_by_val's parameter sits at a different address from n. It is a separate object holding a copy of the value 7.
  • print_call_by_ref's parameter sits at exactly n's address. It is not a second object. It is n.

Both functions print the same value, which is why the professor's two slides look pointless side by side — and that is the lesson. When a function only reads its parameter, by value and by reference are indistinguishable from the outside. The difference is entirely about cost and about write access, and those are the two things §3 is built on.

Quick Check 2.2

References have two rules that surprise everybody the first time. Work these out before revealing.

(a) Does this compile? int a = 1; int &r; r = a;

No. A reference is a name for something, so there has to be a something at the moment you declare it. Here is g++ 13.3:

refinit.cpp: In function 'int main()':
refinit.cpp:6:10: error: 'r' declared as reference but not initialized
    6 |     int &r;         // no variable to bind to
      |          ^

Compare with an ordinary int a;, which is perfectly legal (and holds garbage). A reference has no "uninitialized" state to fall into — there is no such thing as a name for nothing.

Reference parameters look like an exception, but they are not: the argument at the call site is what initializes them, and a call always supplies one.

(b) Predict all three lines of this program.

rebind.cpp
#include <iostream>
using namespace std;

int main() {
    int a = 1, b = 2;
    int &r = a;
    cout << "a = " << a << ", b = " << b << ", r = " << r << endl;
    r = b;          // does this rebind r to b, or assign b's value into a?
    cout << "a = " << a << ", b = " << b << ", r = " << r << endl;
    b = 99;
    cout << "a = " << a << ", b = " << b << ", r = " << r << endl;
    return 0;

a = 2, b = 2, r = 2
a = 2, b = 99, r = 2

The line r = b; did not rebind r. It assigned b's value through r, which means it assigned into a. That is why a became 2.

The third line is the proof: setting b to 99 leaves r showing 2. If r had been rebound to b, it would now show 99.

Once a reference is bound, it is bound for life. Every later use of the name — read or write — goes to the original target. When we meet pointers in Class 7 you will see the contrast: a pointer can be pointed somewhere else, and that flexibility is exactly what makes pointers more dangerous than references.

3.const reference parameters

So far references look like a tool for changing your caller's variables. They have a second job that is used far more often, and it comes from a cost you have not had to think about yet.

Copying an int is free — four bytes, one machine instruction. Copying a string holding a paragraph of text means allocating memory and copying every character. Copying an object of one of the classes we build after Exam 1 can mean copying an entire array. When you pass such a thing by value to a function that only wants to read it, you pay for a full copy and get nothing for the money.

Definition— constant call by reference

A const reference parameter is written const T &name. The & says "do not copy the argument, bind to it"; the const says "and I promise not to modify it."

You get the speed of passing by reference together with the safety of passing by value. The compiler enforces the promise: any attempt to assign to the parameter inside the function is a compile-time error.

Worked Example— proving the copy really happens

A string keeps its characters in a block of memory of its own. If we print the address of that block, we can watch a by-value parameter make a whole second copy of 100,000 characters — and watch a const reference not bother. Which two of the three addresses will match?

constref.cpp
// constref.cpp -- a by-value string parameter really does copy every character
#include <iostream>
#include <string>
using namespace std;

void by_value(string s) {
    cout << "   by value:      characters at " << (const void*)s.data()
         << ", length " << s.size() << endl;
}

void by_const_ref(const string &s) {
    cout << "   by const ref:  characters at " << (const void*)s.data()
         << ", length " << s.size() << endl;
}

int main() {
    string big(100000, 'x');
    cout << "in main:       characters at " << (const void*)big.data()
         << ", length " << big.size() << endl;
    by_value(big);
    by_const_ref(big);
    return 0;
}
in main:       characters at 0x562bc3a732b0, length 100000
   by value:      characters at 0x562bc3a8c970, length 100000
   by const ref:  characters at 0x562bc3a732b0, length 100000

Again the hexadecimal values are representative — yours will differ. The pattern is the point. by_value got its own block of 100,000 characters at a different address: the program really did allocate and copy all of it, just so a function could print a number and throw the copy away. by_const_ref is looking straight at main's characters.

string(100000, 'x') is a constructor call that builds a string of 100,000 copies of the letter x; .data() hands back the address of the first character, and the cast to const void* is only there to make cout print the address rather than the 100,000 characters. Neither is exam material — the measurement is.

There is one more difference between int & and const int &, and it bites people who take references too far.

Worked Example— what a plain reference will not accept

Both functions only read their parameter, so both calls look harmless. Exactly one of them compiles. Which, and why?

#include <iostream>
using namespace std;

}

void print_const_call_by_ref(const int &z) {
    cout << z << endl;
}

int main() {
    print_const_call_by_ref(42);    // fine

}
litbind.cpp: In function 'int main()':
litbind.cpp:14:23: error: cannot bind non-const lvalue reference of type 'int&' to an rvalue of type 'int'
    14 |     print_call_by_ref(42);          // not fine
       |                       ^~

    4 | void print_call_by_ref(int &y) {

Strip the jargon out of that message and it says something reasonable. A plain int & parameter is a licence to modify the caller's variable — so the caller has to have a variable. The literal 42 is not a variable; there is nothing to write back into. C++ refuses the call rather than let you write into a value that will vanish.

A const int & has no such problem, because it has promised not to write anything. The compiler quietly makes a temporary int holding 42, binds z to it, and keeps it alive until the call finishes.

The vocabulary in the message is worth knowing even though this course does not lean on it: an lvalue is something with a place in memory that you could assign to (n, a[3]); an rvalue is a bare value with no home (42, x + 1, the result of a function that returns by value).

Procedure— choosing how to pass a parameter

For every parameter you ever write, ask two questions in this order:

  1. Does the function need to change the caller's variable? If yes → T &name. Stop.
  2. Is the type expensive to copy? A string, an array-holding object, any class of your own — yes. An int, double, char, bool — no.
    • Expensive → const T &name.
    • Cheap → plain T name. (Passing a double by const reference is not wrong, just pointless: the reference itself costs as much as the copy.)

That is the entire decision. Written out as a table:

SituationWriteExample
Must modify the caller's variableT &xvoid swap2(int &u, int &v)
Read-only, small typeT xint gcd(int a, int b)
Read-only, large typeconst T &xvoid report(const string &name)
Read-only arrayconst T x[] plus a lengthvoid print_const(int n, const int a[])
Quick Check 2.4

For each function below, decide whether the parameter list is right, and if not, fix it.

(a) void printReceipt(string customer, double total); — prints a receipt, changes nothing.

customer is read-only and expensive, so it should be a const reference. total is read-only and cheap, so leave it alone:

void printReceipt(const string &customer, double total);

The version as written compiles and behaves identically. It just copies the whole customer name on every single call for no reason. Multiply that by a loop over 50,000 receipts and it stops being academic.

(b) void addInterest(const double &balance, double rate); — is supposed to grow the balance.

Broken. The function must modify balance, so the const has to go — and with it the reason for the reference is now "I must change it" rather than "it is big":

void addInterest(double &balance, double rate);

As written, the body could not contain balance = balance * (1 + rate); at all — that is "assignment of read-only reference" at compile time. This is const doing its job: the mistake is caught in the signature, not discovered later by a customer whose balance never grew.

(c) int countVowels(string &text); — counts vowels, changes nothing. It compiles. What breaks?

Two things, and the second is worse than the first.

First, the missing const means nothing stops a future edit to the body from corrupting the caller's string. The signature no longer documents the function's intent.

Second — and this is the one that stings — countVowels("hello"); will not compile. A string literal is not a string variable, so there is nothing for a plain string & to bind to, exactly as with 42 above. Adding the const makes that call legal:

int countVowels(const string &text);

This is why const reference is the default for read-only parameters and not merely a nicety. Leaving it off restricts who is allowed to call you.

4.References as return values

A reference can also be what a function hands back. Write the & after the return type: int& f(...). This is a real and useful feature — the [] operator we write for our own classes in Class 17 depends on it — and it is also the easiest way in this course to write a program that crashes.

Worked Example— returning a reference to something that outlives the call

This is the professor's returnReference1. It takes a reference and gives the same reference straight back. In main, b is declared as a reference and initialized from the call. Predict both lines — especially the second, after b = 4;.

returnref1.cpp
// returnref1.cpp -- returning a reference to something that outlives the call
#include <iostream>
using namespace std;

int& returnReference1(int &x) {
    return x;
}

int main() {
    int a = 3;
    int &b = returnReference1(a);
    cout << a << " " << b << endl;
    b = 4;
    cout << a << " " << b << endl;
    return 0;
}
3 3
4 4

Follow the aliasing chain. x is bound to a. The function returns x as a reference, so what comes back is not the value 3 but "a itself." int &b = ... then binds b to that. Result: b is a third name for the one integer in this program.

So b = 4; writes into a, and the second line prints 4 4. The aliasing survived the round trip through the function.

Change one character and the whole thing changes. If main said int b = returnReference1(a); — no & — then b would be an ordinary int copied from a, and the output would be 3 3 then 3 4. Try it.

Quick Check 2.5

Using returnReference1 exactly as written above, what does each main print?

(a) int a = 3; int b = returnReference1(a); b = 4; cout << a << " " << b << endl;

3 4

b is a plain int, so the reference returned by the function is immediately read and its value copied into b. From then on b is an independent variable, and b = 4; leaves a at 3.

This is the single most important thing to see about returning a reference: whether the aliasing survives is decided at the call site, by the caller's declaration, not by the function.

(b) int a = 3; returnReference1(a) = 7; cout << a << endl;

7

Yes, you really can put a function call on the left-hand side of an assignment — provided the function returns a non-const reference. The call evaluates to a itself, so the statement means a = 7;.

It looks like a party trick. It is not: it is precisely how v[3] = 10; works for a class that defines operator[], which is Class 17. A function that returns by value could never appear on the left of =, because there would be nothing there to assign to.

Now the dangerous case. The course notes present this next function under exactly the same neutral heading as the one above, with no commentary and no output. Read it very carefully.

Worked Example— returning a reference to a local variable

returnReference2 declares a local double and returns a reference to it. Ask yourself one question before revealing: how long does y exist?

returnref2.cpp
// returnref2.cpp -- DO NOT WRITE THIS. Returns a reference to a dead variable.
#include <iostream>
using namespace std;

double& returnReference2() {
    double y = 3.1415;
    return y;
}

int main() {
    double d = returnReference2();
    cout << d << endl;
    return 0;
}

It compiles — but only with a warning, and the warning is telling you the program is broken:

returnref2.cpp: In function 'double& returnReference2()':
returnref2.cpp:7:12: warning: reference to local variable 'y' returned [-Wreturn-local-addr]
    7 |     return y;
      |            ^
returnref2.cpp:6:12: note: declared here
    6 |     double y = 3.1415;
      |            ^

And on this machine, running it does this:

$ ./returnref2
Segmentation fault

y is a local variable. It is created when the function starts and destroyed when the function returns — its storage on the stack is handed back and will be reused by the next function call that comes along. The reference that returnReference2 hands to main therefore names an object that no longer exists. Reading it in double d = returnReference2(); is undefined behavior: the language makes no promise at all about what happens.

"No promise at all" is the part students underestimate. On this machine it crashed. On another machine, or with different optimization settings, the same program may print 3.1415 and look completely fine — which is far worse, because then the bug ships. Never trust a program that only appears to work. Trust the warning.

Here is the fix, and it is a downgrade in a good way: if the value has to be computed fresh inside the function, return it by value.

returnref_fixed.cpp
// returnref_fixed.cpp -- the same function, returning by value
#include <iostream>
using namespace std;

double returnValue2() {
    double y = 3.1415;
    return y;
}

int main() {
    double d = returnValue2();
    cout << d << endl;
    return 0;
}
3.1415

One character removed and the program is correct. Returning by value copies y's value out before y is destroyed, so there is nothing dangling.

Warning— a defect in the course notes, and the rule that avoids it

The original Lecture 2 notes present returnReference2 under the same heading as returnReference1, with no output and no comment saying it is wrong. Copied into an assignment as if it were a model, it is a genuine bug — a dangling reference and undefined behavior. It is shown here only as the counter-example.

The rule, and it has no exceptions worth learning yet:

Return a reference only to something that will still be alive after the function returns. That means: a reference parameter the caller handed you (as in returnReference1), an element of an array or object owned by someone else, or a data member of the object the method belongs to. Never a local variable.

If you are unsure, return by value. It costs a copy and it is always correct.

Worked Example— a returned reference you can assign to

5.Function overloading

In C++ two different functions may share a name, as long as the compiler can tell the calls apart.

Definition— function overloading, signature

Function overloading is declaring two or more functions with the same name but different parameter lists. At each call, the compiler looks at the number and types of the arguments and picks the one that matches. This is called overload resolution, and it happens entirely at compile time.

The signature of a function is its name plus its parameter list. The return type is not part of the signature, which is why two functions cannot be distinguished by return type alone.

6.Forward declarations

The C++ compiler reads your file from top to bottom, once. It cannot use a name it has not seen yet. Usually that costs you nothing — you define your helper functions above main out of habit. Then you hit a case where no ordering works.

Definition— forward declaration (function prototype)

A forward declaration — also called a function prototype — is just the function signature, terminated with a semicolon instead of a body:

string f1(int a);

It tells the compiler "a function with this name, these parameter types and this return type exists somewhere; trust me and let me call it." The compiler then has everything it needs to check your calls. Where the body actually is — further down the file, or in a completely different file — is not its problem; that is the linker's job.

The parameter names in a forward declaration are optional and are ignored: string f1(int); declares the same function. Write the names anyway. They are documentation.

7.Splitting a program across files

Everything so far has lived in one .cpp file. Real projects do not. The course notes give three reasons, and all three are practical rather than aesthetic:

  • If all the code is in one file, editing even a small part means the entire project must be recompiled. On a large program that is the difference between two seconds and two minutes, every time you fix a typo.
  • Multiple developers can work simultaneously on different source files without fighting over the same file.
  • A source file can be included in multiple different projects — write a good set of matrix routines once, use it in three programs.

So we want main in one file and the functions it calls in another. But the compiler reads each file top to bottom and knows nothing about any other file, so a call to a function defined elsewhere is a name it has never seen — the exact error from §6. The course notes put it plainly: functions in one file may call functions defined in a different file, but this might cause a problem; to avoid the problem, C++ supports forward declarations.

Definition— header file

A header file is a file that holds declarations, so that any source file needing them can pull them in with #include. By convention it is named with a .h suffix.

Include one of your own headers with double quotes: #include "swap.h". The quoted form looks in your project directory first. The angle-bracket form — #include <iostream> — is for the standard library and looks only in the system directories.

A project therefore consists of a set of .cpp source files, which hold the definitions, and a set of .h header files, which hold the declarations. Each source file includes the headers describing whatever it needs to call.

Key Idea

#include "swap.h" is not magic and it is not "importing a module". The preprocessor literally pastes the text of the header into your file before the compiler sees it. Everything about headers — why they contain declarations and not definitions, why they need include guards — follows from that one fact.

The swap project

Here is the course notes' worked example. We want a driver that swaps a pair of ints, a pair of doubles and a pair of strings — three overloads of one name, tying §5 back in — with the swap functions living in their own source file.

The header declares the three overloads and nothing else:

swap.h
// swap.h -- declarations only

Three things about the command line:

  • You list every .cpp file, separated by spaces. Order does not matter.
  • You never list a .h file. Headers are not compiled — they are pasted into the .cpp files that include them, and get compiled as part of those. Typing g++ ... swap.h is a beginner tell.
  • -o prog names the single executable produced from all of them. There is one program at the end, not two.

What actually happens under that one command is two distinct phases, and knowing which phase an error came from tells you where to look for the mistake.

Procedure— from source files to one executable
  1. Preprocess. Each #include is replaced by the text of the file it names. Now each .cpp is one long self-contained chunk of code.
  2. Compile. Each chunk is compiled independently into an object file (main.o, swap.o). Calls to functions declared but not defined in that file are left as unresolved holes. This is the phase that checks your syntax and your types — and it is the phase the header exists to satisfy.
  3. Link. The object files are combined, and every hole is filled by finding the matching definition in one of the others. Anything still missing is a linker error.

You can run the phases yourself. -c means "compile only, do not link":

g++ -c main.cpp      # produces main.o
g++ -c swap.cpp      # produces swap.o
g++ main.o swap.o -o prog      # link them together

This is the payoff promised at the top of the section: edit main.cpp and you only need to recompile main.cpp, then relink. swap.o is reused untouched. On a project with two hundred source files, that is the difference between a workable edit-compile cycle and an unusable one.

Warning— three defects in the notes' swap.h

The header printed in the original course notes is shorter than the one above:

#include <string>
using namespace std;
void swap(int &u, int &v);
void swap(double &u, double &v);

It compiles and the project runs, but it has three problems, and since a header is exactly the kind of file you copy as a template, they are worth fixing now.

  1. No include guard. A header gets pasted in wherever it is included, and in a real project it is easy for one .cpp to end up including the same header twice through two different routes. Repeating a declaration is harmless; repeating anything else is not. This is a real error from a two-line header with no guard: 
    In file included from roster.h:1,
                 from main.cpp:3:
limits.h:2:11: error: redefinition of 'const int MAX_STUDENTS'
    2 | const int MAX_STUDENTS = 100;
      |           ^~~~~~~~~~~~
    The cure is the three lines in the corrected swap.h: #ifndef SWAP_H / #define SWAP_H at the top and #endif at the bottom. The first time through, SWAP_H is not defined, so the body is processed and the name gets defined; every later time, the body is skipped. Put one in every header you ever write, named after the file.
  2. using namespace std; inside a header. The header is pasted into every file that includes it, so this forces the entire std namespace on all of them whether they wanted it or not — and they cannot opt out. In a header, spell it std::string. Inside your own .cpp files, using namespace std; remains fine. We look at namespaces properly in Class 16.
  3. The name swap collides with std::swap. The standard library already has a function template called swap, and using namespace std; in main.cpp makes it visible. See the next example for what that costs.

Complete the exercise above: write all three files, give the compile command, and give the exact output.

Plan. Start from the signatures, because they decide everything else. mean reads an array and returns one number, so double mean(int n, const int a[]). minMax has to produce two answers, and a function can only return one value — so the two answers leave through reference parameters: void minMax(int n, const int a[], int &lo, int &hi). Note how the parameter list documents the direction of travel: the const things come in, the reference things go out.

Those two lines, wrapped in an include guard, are the header.

stats.h
// stats.h -- declarations only
#ifndef STATS_H
#define STATS_H

double mean(int n, const int a[]);
void minMax(int n, const int a[], int &lo, int &hi);

#endif
stats.cpp
// stats.cpp -- the definitions
#include "stats.h"

double mean(int n, const int a[]) {
    double sum = 0.0;
    for (int i = 0; i < n; ++i) {
        sum += a[i];
    }
    return sum / n;
}

void minMax(int n, const int a[], int &lo, int &hi) {
    lo = a[0];
    hi = a[0];
    for (int i = 1; i < n; ++i) {
        if (a[i] < lo) lo = a[i];
        if (a[i] > hi) hi = a[i];
    }
}
main.cpp
// main.cpp -- the driver
#include <iostream>
#include "stats.h"
using namespace std;

int main() {
    int data[] = {12, 4, 19, 7, 3};
    int lo = 0, hi = 0;

    cout << "mean = " << mean(5, data) << endl;
    minMax(5, data, lo, hi);
    cout << "min  = " << lo << endl;
    cout << "max  = " << hi << endl;
    return 0;
}
g++ main.cpp stats.cpp -o prog
./prog

min  = 3
max  = 19

Things to notice.

  • sum is declared double, not int. The five values add up to 45 and 45 divided by 5 is exactly 9, so this example would survive integer division — but change one value and sum / n with two ints would silently truncate. Make the accumulator a double and the bug cannot happen.
  • minMax seeds both answers with a[0] and starts the loop at i = 1. Seeding lo with 0 would report a minimum of 0 for an array of positive numbers.
  • lo and hi are initialized in main even though minMax overwrites them immediately. That habit costs nothing and saves you the day you call a function that returns early.
  • stats.cpp includes stats.h. It does not strictly need to — but if you later change the header and forget to change the definition, this include is what turns a silent link failure into a clear compile error.

A note on how const and references are examined. They are almost never asked about directly — you will not be asked "what is a reference?" — but they are required to be correct in every function signature you are asked to write, and a write-code question typically pays points for the signature line on its own. Problem 1 — Complete the multi-file swap project (from the course notes)

You are given this driver, which swaps three pairs of variables of three different types. Write the header file and the source file that make it work, and give the command that compiles the whole project into one executable.

int main() {
    int a = 3, b = 4;
    double x = 2.2, y = 3.3;
    string s("abcd"), t("alpha");
    cout << "original:" << endl;
    cout << a << " " << b << endl;
    cout << x << " " << y << endl;
    cout << s << " " << t << endl;
    swap(a, b);
    swap(x, y);
    swap(s, t);
    cout << "swap:" << endl;
    cout << a << " " << b << endl;
    cout << x << " " << y << endl;
    cout << s << " " << t << endl;
    return 0;
}

Plan. Work backwards from the three calls. swap(a, b) passes two ints and must change them, so it needs (int &u, int &v) — no const anywhere, since modification is the whole job. The same reasoning gives the double and string versions. Three functions, one name, three different parameter lists: legal overloads.

Then split them. The declarations go in swap.h so that main.cpp can be compiled without ever seeing the bodies; the definitions go in swap.cpp. main.cpp gains one line, #include "swap.h".

swap.h
// swap.h -- declarations only
#ifndef SWAP_H
#define SWAP_H

#include <string>

void swap(int &u, int &v);
void swap(double &u, double &v);
void swap(std::string &u, std::string &v);

#endif
swap.cpp
// swap.cpp -- the definitions
#include "swap.h"

void swap(int &u, int &v) {
    int t = u;
    u = v;
    v = t;
}

void swap(double &u, double &v) {
    double t = u;
    u = v;
    v = t;
}

void swap(std::string &u, std::string &v) {
    std::string t = u;
    u = v;
    v = t;
}
main.cpp
// main.cpp -- the driver
#include <iostream>
#include <string>
#include "swap.h"
using namespace std;

int main() {
    int a = 3, b = 4;
    double x = 2.2, y = 3.3;
    string s("abcd"), t("alpha");

    cout << "original:" << endl;
    cout << a << " " << b << endl;
    cout << x << " " << y << endl;
    cout << s << " " << t << endl;

    swap(a, b);
    swap(x, y);
    swap(s, t);

    cout << "swap:" << endl;
    cout << a << " " << b << endl;
    cout << x << " " << y << endl;
    cout << s << " " << t << endl;
    return 0;
}

Things to notice.

  • The three bodies are identical apart from the type of the temporary. That repetition is real, and C++ has a proper answer for it — function templates, in Class 25. Writing the three by hand now is what makes the template version obvious later.
  • The temporary must have the same type as the things being swapped. A double swap with an int temporary compiles and silently truncates.
  • The header uses std::string and does not say using namespace std;, for the reason given in the warning box in §7. main.cpp keeps its using namespace std;, which is fine because it is a source file.
  • If you name only main.cpp on the command line you get three "undefined reference to" errors from the linker, not from the compiler.
  • In your own work, prefer my_swap to swap. The standard library already defines std::swap, and with using namespace std; in scope the two can be confused — sometimes silently.

Problem 2 — Two functions that call each other (from the course notes)

Write a complete program containing two functions, f1 and f2, that each call the other, and a main that prints f1(3), f1(-3), f2(4) and f2(-4). f1 returns the string "f1" when its argument is non-negative and otherwise returns "f1 first, " followed by whatever f2 returns; f2 returns "f2" when its argument is negative and otherwise returns "f2 first, " followed by whatever f1 returns.

Plan. The bodies are straightforward; the difficulty is entirely structural. Whichever function is written first refers to a function the compiler has not met, and no ordering fixes that because the dependency is a cycle. So declare both signatures before either body: string f1(int a); and string f2(int a);. With the declarations in place the bodies may go anywhere, and putting main first reads nicely.

Two details the printed version in the notes gets wrong and you should not: the program returns string, so it needs #include <string>; and a forward declaration ends in a semicolon, not a body.

fwdgood.cpp
// fwdgood.cpp -- mutual recursion, made legal by two forward declarations
#include <iostream>
#include <string>
using namespace std;

string f1(int a);       // forward declaration
string f2(int a);       // forward declaration

int main() {
    cout << f1(3)  << endl;
    cout << f1(-3) << endl;
    cout << f2(4)  << endl;
    cout << f2(-4) << endl;
    return 0;
}

string f1(int a) {
    if (a >= 0) { return "f1"; }
    else {
        string s = string("f1 first, ");
        return s + f2(a);
    }
}

string f2(int a) {
    if (a < 0) { return "f2"; }
    else {
        string s = string("f2 first, ");
        return s + f1(a);
    }
}
f1
f1 first, f2
f2 first, f1
f2

Things to notice.

  • Only one of the two functions needs a forward declaration in principle — whichever is defined second. Declaring both is the normal practice: it costs one line, it puts the whole interface at the top of the file where a reader can find it, and it means you can reorder the definitions later without breaking anything.
  • s + f2(a) works because string overloads operator+ to mean concatenation. That is operator overloading, and you will write your own in Class 17.
  • The parameter int a is by value on purpose. Neither function modifies it and an int is cheap, so a reference would buy nothing.
  • An alternative structure the professor's version does not use: put the declarations in a header. That is exactly the same idea one file larger, which is what Problem 1 is about.

Problem 3 — Write C++ statements (added, in the style of the "write C++ statements" exam problem)

Do not write complete programs. Just give a single line, or a few lines, of C++ for each task.

(a) Declare an int called count initialized to 0, and then declare alias as a second name for it.

int count = 0;
int &alias = count;

The & goes after the type. A reference must be initialized in the same statement that declares it — int &alias; alias = count; is an error, and it is not the same thing.

(b) Write the forward declaration of a function scale that multiplies every element of an array of double by a factor, given the array's length. The factor must not be copied and must not be modified.

void scale(int n, double a[], const double &factor);

The array is not const here — the function's job is to change it. The factor is const double & because the task says so. And void, because the result comes back through the array.

(c) Write the forward declaration of a function longest that takes two strings it may not modify and does not copy, and returns a string.

string longest(const string &s, const string &t);

Both parameters are const string &: reference for "do not copy", const for "may not modify". The return type is a plain string, by value — returning const string& here would be the §4 disaster if the function ever built a new string locally.

(d) Write the lines that stop the header shapes.h being processed twice in one compilation.

#ifndef SHAPES_H
#define SHAPES_H

// ... declarations go here ...

#endif

The guard name is conventionally the file name in capitals with the dot replaced by an underscore. It only has to be unique within the project. The #endif goes at the very bottom of the file, after everything.

(e) Given void bump(int &n); and the count from part (a), write the statement that makes count equal to 1.

bump(count);

No & at the call site. The reference is declared in the function's parameter list, and the caller writes a perfectly ordinary call — which is exactly why you have to read the declaration to know that count is about to change.

Things to notice. Every one of these five answers is a signature or a declaration, and that is not an accident. On this course's exams the write-code problems award points for the signature line by itself, and a signature is right or wrong on three decisions: reference or not, const or not, and what comes back. Practice writing them until they are automatic.

Problem 4 — Write a complete C++ program (added, in the style of the Problem 1 exam question)

Write a complete C++ program that lets the user enter positive integers, one after another, until they enter 0 to stop. The program should then report how many numbers were entered, the average of those numbers, and finally print all the inputs that are above the average. Use a separate function for each of the three jobs, and give each function the correct parameter list.

A sample run, with the user's typing on the first line:

Enter positive integers, 0 to stop: 4 8 15 16 23 42 0

Plan. Three jobs, three functions, and the parameter list of each falls straight out of the §3 procedure:

  • readNumbers has to fill an array and report how many it read. The array parameter is already effectively by reference (§5), and the count has to come back to main, so it is int &count. Return type void.
  • average only reads, so (int n, const double a[])-style: double average(int n, const int a[]).
  • printAbove only reads, so the array is const and the limit is a const reference.

The sentinel loop is the standard shape: read one value before the loop, then loop while it is not the sentinel, storing and reading the next one. Guard against a user who types 0 immediately, otherwise the average divides by zero.

aboveavg.cpp
// aboveavg.cpp -- read numbers until 0, report the average, list those above it
#include <iostream>
using namespace std;

const int CAPACITY = 100;

// fills a[] from cin, stops at the sentinel 0, reports how many were read
void readNumbers(int a[], int &count) {
    count = 0;
    int x;
    cout << "Enter positive integers, 0 to stop: ";
    cin >> x;
    while (x != 0 && count < CAPACITY) {
        a[count] = x;
        ++count;
        cin >> x;
    }
}

double average(int n, const int a[]) {
    double sum = 0.0;
    for (int i = 0; i < n; ++i) {
        sum += a[i];
    }
    return sum / n;
}

void printAbove(int n, const int a[], const double &limit) {
    for (int i = 0; i < n; ++i) {
        if (a[i] > limit) {
            cout << a[i] << " ";
        }
    }
    cout << endl;
}

int main() {
    int data[CAPACITY];
    int count = 0;

    readNumbers(data, count);
    if (count == 0) {
        cout << "No numbers entered." << endl;
        return 0;
    }

    double avg = average(count, data);
    cout << "You entered " << count << " numbers." << endl;
    cout << "The average is " << avg << endl;
    cout << "Above the average: ";
    printAbove(count, data, avg);
    return 0;
}

Compiled and run with the six numbers and the sentinel fed in:

g++ aboveavg.cpp -o aboveavg
echo "4 8 15 16 23 42 0" | ./aboveavg
Enter positive integers, 0 to stop: You entered 6 numbers.
The average is 18
Above the average: 23 42

(The prompt and the first line of results run together because the input came from a pipe rather than the keyboard. Typed at a terminal, your six numbers would appear right after the colon.)

Things to notice.

  • readNumbers(data, count) changes two things in main by two different mechanisms: the array, because arrays are never copied, and count, because it was declared int &count. Only the second one is visible in the call — another reason to read declarations.
  • sum is a double. With int sum, the expression sum / n would be integer division and this run would report an average of 18 by luck, then get the next one wrong.
  • The comparison a[i] > limit compares an int with a double; C++ converts the int and compares as double, which is what you want. Writing >= would additionally print any value exactly equal to the average — read the question and decide deliberately.
  • The fixed CAPACITY array is a Class 2 answer. On the real exam this question expects a vector, which grows to fit and needs no capacity guess. Vectors are Class 5, and this program is three lines shorter once you have them.
  • Exam technique: the rubric for this style of question gives a point or two for the "standard beginning and standard ending" — the #includes, using namespace std;, int main(), return 0; — and then points per stage. Write the skeleton first, always. Partial credit is real on this problem.

Problem 5 — What is the output (added, in the style of the output-prediction exam problem)

State the exact output of this program. Answer for the whole program, line by line — and on an exam, remember that this style of question carries no partial credit, so trace it rather than guessing.

predict.cpp
// predict.cpp -- what does each line print?
#include <iostream>
using namespace std;

void mystery(int a, int &b, const int &c) {
    a = a + 1;
    b = b + 1;
    cout << a << " " << b << " " << c << endl;
}

void show(int x)    { cout << "int:    " << x << endl; }

Things to notice.

  • Line (a) is the whole lecture in one call: p survives untouched because it was copied, q changes because it was bound, r is reachable but write-protected.
  • Line (c) is the trap. Passing the same variable as two different parameters is called aliasing, and here it means c — the read-only parameter — sees a value change under it. const promises that this function will not write through c. It never promised the value could not change by some other route. This surprises experienced programmers too.
  • Line (f) prints 7, not 7.0: cout drops trailing zeros. Only the label reveals which overload ran.
  • Line (g): 'B' is character code 66. If you answered int: B you lost the point — the value was converted to int before it was printed, so the letter is gone by the time cout sees it.
Lecture Summary
  • Call by value is the default. The parameter is a new local variable holding a copy of the argument, so the function cannot touch the caller's data. That is why swap1 did nothing.
  • Call by reference — T &x in the parameter list — binds the parameter to the caller's variable. One object, two names. That is why swap2 worked.
  • A reference must be initialized when it is declared and can never be rebound afterwards. The call site looks identical either way, so you must read the declaration.
  • const T &x gives you the speed of a reference with the safety of a copy, and is the right default for any parameter that is read-only and expensive to copy. Breaking the promise is "assignment of read-only reference" at compile time. Unlike a plain T &, a const reference will also bind to a literal.
  • A function may return a reference, but only to something that outlives the call. Returning a reference to a local variable is undefined behavior; g++ warns "reference to local variable returned". When in doubt, return by value.
  • Overloading lets several functions share a name if their parameter lists differ. The return type is not part of the signature and cannot distinguish overloads.
  • An array parameter is never copied, so write const int a[] whenever the function only reads it — and pass the length separately, because an array parameter does not carry one.
  • A forward declaration is the signature plus a semicolon. It lets you call a function the compiler has not seen the body of — essential for mutual recursion and for every multi-file project.
  • A header file holds declarations; a .cpp file holds definitions. Include your own headers with #include "name.h", guard every header with #ifndef/#define/#endif, keep using namespace std; out of them, and compile with g++ main.cpp other.cpp -o prog — every .cpp, never a .h.
  • "was not declared in this scope" is a compiler error — you forgot an #include. "undefined reference to" is a linker error — you forgot a .cpp on the command line, or the definition's parameter list does not match the declaration's.
