1.From CSCI 111 to CSCI 211

In CSCI 111 you learned to give a computer instructions: declare some variables, loop over them, call a function, print the result. That style has a name — procedural programming — and it works fine right up until the program gets big. Then it stops working, and it stops working in a very specific way.

Picture a program that manages a library. In the procedural style you would have an array of book titles, a parallel array of authors, another of due dates, another of borrower IDs. Every function that touches a book has to be handed all four arrays and an index. Add one field — say, the ISBN — and you have to change the signature of every one of those functions. Worse, nothing stops some careless line halfway across the program from writing into dueDates[7] when it meant dueDates[8]. The data is naked. Anyone can touch it, and nothing in the language protects it.

Object-oriented programming is the response to exactly that problem. Instead of scattering a book across four arrays, you build a single thing called a Book that carries its own title, author, due date and borrower together, and that decides for itself which operations the outside world is allowed to perform on it. This semester is about how to build those things in C++.

Key Idea

Procedural programming organizes a program around what it does. Object-oriented programming organizes it around what it is made of. The payoff is not that OOP programs are shorter — often they are longer — it is that when the program changes, the change stays in one place.

Key Idea— if CSCI 111 feels far away

This course assumes you can already read and write a single-file C++ program: declare a variable, take a decision, run a loop, call a function. If any of that has gone rusty over the break, the CSCI 111 refresher has it in one place. It is background reading rather than a class, and it is available now.

It deliberately stops short of six topics — const, function overloading, forward declarations, header files, ++/--, and break/continue — because this course teaches those itself over the next three classes, in more depth and with the exam traps attached.

Here is the road map. The first ten classes are the raw materials: a fast refresher on the C++ you already know, then vectors, then pointers and dynamic memory, and finally your first classes. Everything after Exam 1 is the object-oriented machinery proper — constructors, copying, operator overloading, inheritance, polymorphism, templates, and the Standard Template Library. Every one of those topics rests on pointers, so the middle of the first unit is the part to take seriously.

2.Anatomy of a C++ program

Before we talk about any new ideas, let's be precise about the program skeleton you have been typing since CSCI 111. Every C++ program you write this semester has the same five structural parts, and being able to name them makes error messages far less mysterious.

Worked Example— the five parts, labelled

Read this program and predict exactly what it prints. Pay attention to the last line of output in particular — it is not as obvious as it looks.

anatomy.cpp
// anatomy.cpp -- the five parts of every C++ program
#include <iostream>          // 1. bring in a library
using namespace std;         // 2. use the standard names without "std::"

int main() {                 // 3. execution starts here
    int radius = 3;          // 4. the body: declarations and statements
    double area = 3.14159 * radius * radius;

    cout << "radius = " << radius << endl;
    cout << "area   = " << area   << endl;

    return 0;                // 5. tell the operating system "no errors"
}
radius = 3
area   = 28.2743

The five parts, in order:

  1. Preprocessor directives. #include <iostream> textually pastes the declarations for cout, cin and endl into your file before compilation starts. Without it the compiler has never heard of cout.
  2. The using directive. Everything in the standard library lives in a namespace called std. Its real name is std::cout. using namespace std; tells the compiler "if you see a name you don't recognize, look in std too", which is why you can write the short form. We will study namespaces properly in Class 16.
  3. int main(). The one function the operating system calls to start your program. Exactly one of these per program.
  4. The body. Declarations and statements, executed top to bottom.
  5. return 0;. The value main hands back to the operating system. Zero conventionally means "finished normally"; anything else means "something went wrong."

And the surprise: area is 28.274310 to six places, but cout printed 28.2743. By default cout shows a floating-point value to six significant digits and drops trailing zeros. That default is going to cost people points on exams, so we will look at it head-on in Class 3.

Quick Check 1.1

Using the program above as your reference:

(a) If you delete the line using namespace std; but change nothing else, will the program still compile? If not, what is the smallest edit that fixes it?

It will not compile. Without the using directive the names cout and endl are not visible by their short spellings.

The smallest fix is to qualify each use with the namespace:

    std::cout << "radius = " << radius << std::endl;
    std::cout << "area   = " << area   << std::endl;

Note that int, double and return are not affected — they are keywords built into the language, not names from a library.

(b) If you delete #include <iostream> instead, what does the compiler say?

This is the real message from g++ 13.3, trimmed:

noinclude.cpp: In function 'int main()':
noinclude.cpp:4:5: error: 'cout' was not declared in this scope
    4 |     cout << "hello" << endl;
      |     ^~~~
noinclude.cpp:1:1: note: 'std::cout' is defined in header '<iostream>'; did you forget to '#include <iostream>'?

Read compiler errors from the top down and stop at the first one. "was not declared in this scope" almost always means one of three things: you misspelled a name, you forgot an #include, or you used a variable before declaring it. Modern g++ even guesses the missing header for you in the note: line — do not skip past those.

(c) What would happen if you wrote return 1; instead of return 0;?

The printed output would be identical. The return value of main is not shown on screen — it is handed to whatever launched the program. Zero means success; a nonzero value signals failure, which matters when a script or a grading harness checks whether your program succeeded. In this course always write return 0; at the end of main.

3.Compiling and running

C++ is a compiled language. Nothing you type runs directly; a separate program called the compiler translates your source file into machine code first, and only that result runs. This is the reason C++ can catch so many of your mistakes before the program ever starts — and the reason those mistakes arrive as a wall of text.

Definition— compiler, source file, executable

A source file is the text you write, saved with a .cpp extension. A compiler is a program that translates a source file into an executable — a file of machine instructions your operating system can run directly. The compiler we use in this course is g++.

An error the compiler reports is a compile-time error: the executable is never produced, so the program cannot run at all. An error that only shows up while the program is running — a crash, a wrong answer — is a run-time error. Telling these two apart is the single most useful debugging skill you can have.

Procedure— compile and run one file
  1. Save your source as, say, anatomy.cpp.
  2. Compile it, naming the executable yourself with -o: 
    g++ anatomy.cpp -o anatomy
  3. If the compiler prints nothing, it worked. Run it: 
    ./anatomy
  4. If it printed errors, fix the first one and compile again. Later errors are very often just fallout from the first.

You can also leave out the -o part entirely:

g++ anatomy.cpp

That still compiles, but it names the executable a.out instead, whatever the source file was called. Use -o when you want to keep several programs around at once and be able to tell them apart.

Quick Check 1.2

A student compiles with g++ gcd.cpp, sees no errors, then types ./gcd and gets "No such file or directory." Nothing is wrong with their program. What happened, and what should they type?

They left out -o. With no -o, g++ names the executable a.out, regardless of what the source file was called. So the program compiled perfectly — it is just sitting there under a different name.

Either run it as it stands:

./a.out

or, better, recompile and name it:

g++ gcd.cpp -o gcd
./gcd

The leading ./ is not decoration. It means "the file named gcd in this directory." Without it the shell searches only its list of system directories and will not find your program.

Then compile with g++ gcd.cpp -o gcd and run it.

Quick Check 1.3

Complete the exercise above. Give the finished function and say what gcd(270, 192) is.

Plan. The GCD of a and b is the largest integer that divides both. Trying every integer from min(a,b) downwards works but is slow. Euclid's algorithm is the standard answer: any number that divides both a and b also divides a % b, so gcd(a, b) equals gcd(b, a % b). Each step gives a strictly smaller pair, so it must stop, and it stops when the second number reaches 0 — at which point the first number is the answer.

gcd.cpp
// gcd.cpp -- greatest common divisor of two positive integers
#include <iostream>
using namespace std;

int gcd(int a, int b) {
    while (b != 0) {
        int r = a % b;
        a = b;
        b = r;
    }
    return a;
}

int main() {
    cout << "gcd(48, 18) = " << gcd(48, 18) << endl;
    cout << "gcd(17, 5)  = " << gcd(17, 5)  << endl;
    cout << "gcd(270, 192) = " << gcd(270, 192) << endl;
    cout << "gcd(9, 9)   = " << gcd(9, 9)   << endl;
    return 0;
}
gcd(48, 18) = 6
gcd(17, 5)  = 1
gcd(270, 192) = 6
gcd(9, 9)   = 9

So gcd(270, 192) is 6. The trace is worth doing by hand once:

Things to notice. The parameters are taken by value on purpose: the function modifies a and b as it works, and copies mean the caller's variables are untouched. gcd(17, 5) is 1 because 17 and 5 share no factor — always test one of those. A recursive version is equally correct and shorter:

int gcd(int a, int b) {
    if (b == 0) return a;
    return gcd(b, a % b);
}

4.Objects: data plus behavior

Now the idea the rest of the semester hangs on. For the next four sections we are going to stay at the level of ideas — no C++ syntax at all. Get the picture straight first; the syntax arrives in Class 9 and it is much easier once the picture is in place.

Look up from the screen at any physical thing near you — a phone, a coffee cup, a bank card. Each of them has two kinds of facts attached. There are facts about what it is: the phone's battery level, its model, its number. And there are facts about what it can do: dial, ring, take a photo. Object-oriented programming takes that split seriously and builds it into the language.

Definition— object-oriented programming

Object-oriented programming (OOP) is a way of organizing a program around objects. An object represents a real-world entity, concept, or data structure, and it bundles together two things:

  • its data — the attributes or properties that describe it; and
  • its behaviors — the methods or functions that operate on that data.

Because the data and the code that manipulates it live in the same place, an object is a self-contained unit. That is what makes OOP a modular, organized way to design software.

Definition— attribute and method

An attribute (also called a data member or field) is a variable that belongs to an object and stores part of its state.

A method (also called a member function) is a function that belongs to an object and can read or change that object's attributes.

The two words to watch for when you read a problem statement: nouns tend to become attributes, verbs tend to become methods.

Quick Check 1.4

You are asked to model a bank account as an object.

(a) List four reasonable attributes.

Any four facts that describe an account and have to be remembered between operations. A standard set: account number, owner's name, current balance, interest rate.

Notice the test each one passes: if you erased it, the account would no longer be fully described. "The teller's name" fails that test — it belongs to a transaction, not to the account.

(b) List four reasonable methods.

  • deposit — add to the balance
  • withdraw — subtract from the balance, if there is enough
  • get balance — report the balance without changing it
  • apply interest — grow the balance by the interest rate

Each one is a verb, and each one needs the account's own data to do its job. That second property is the real reason it belongs to the object rather than sitting loose as an ordinary function.

(c) Why is it a bad idea to let any code anywhere in the program change the balance directly?

Because the balance is not just a number — it is a number with rules attached. A withdrawal must not push it below zero; a deposit must not be negative; every change might need to be logged. If outside code can set the balance to anything it likes, then none of those rules can be enforced, and worse, when a bad balance turns up you have no idea which of the thousand lines in the program did it.

If the only way to change the balance is through deposit and withdraw, the rules live in exactly two places, and those two are the only suspects. That is the argument for encapsulation, which we come to in §6.

5.Classes: the blueprint

If an object is a particular thing, something has to describe the kind of thing it is. That description is a class.

Definition— class, object, instance

A class is a blueprint or template that defines the structure and behavior of objects. It specifies what data attributes the object will have and what operations can be performed on it.

An object is an instance of a class — an actual thing created according to the class's definition, with its own copy of the data.

The blueprint of a house is not a house. You can build a hundred houses from one blueprint, and painting one of them blue does not change the others. In exactly the same way, one class can produce many objects, and changing one object's data leaves every other object alone.

Quick Check 1.5

A program models a course roster. It defines one description of what a student is, and then creates three students: Ada, Bo and Cy.

(a) How many classes exist here, and how many objects?

One class and three objects. The class is the single description of what "a student" is; each of Ada, Bo and Cy is one instance built from it.

A useful sanity check: if the answer to "how many classes" is ever the same as the number of individual things you are modelling, you have almost certainly misunderstood the question. You do not write a new class per student any more than an architect draws a new blueprint per house.

(b) If each student has a GPA, how many GPA values exist in memory? How many copies of the code that computes a GPA?

Three GPA values — one inside each object. Attributes are per-object; that is the entire point of an object.

One copy of the code. Methods are compiled once and shared by every object of the class. What changes from call to call is which object the method is working on. How the method knows that is a real question with a real answer, and we meet it as the this pointer in Class 15.

(c) Bo drops the course and Bo's object is destroyed. What happens to Ada's and Cy's data, and what happens to the class?

Nothing happens to either. Ada's and Cy's objects hold their own separate data and are untouched. The class is a description, not a container of objects — it does not shrink, and it is still there to build more students from.

This independence is exactly what the parallel-array design in §1 could not give you. There, "removing Bo" means deleting element 1 from four different arrays and hoping every other index in the program still lines up.

6.Encapsulation and the interface

We said a class decides which operations the outside world may perform on its data. The set of operations it offers has a name.

Definition— interface

An interface is a concept in programming and software development that defines a contract or set of methods that a class or object must implement. It acts as a blueprint for creating consistent and structured code, enabling multiple components to interact seamlessly without needing to know the internal details of each other.

In C++ the interface of a class is, concretely, the set of things it makes public. That is the promise the class makes to the rest of the program; everything else is private business.

Definition— encapsulation

Encapsulation is the practice of keeping an object's data private and exposing it only through a controlled public interface. The data is enclosed in a capsule; the methods are the only doors in and out.

Think about driving. The interface of a car is a steering wheel, two or three pedals, and a gear selector. That is a genuinely tiny interface for a machine with thousands of parts, and it is why you can rent a car you have never seen before and drive it out of the lot. You do not need to know whether the engine is a four-cylinder or an electric motor. The manufacturer is free to change the engine completely as long as the pedals still mean what they meant.

A class works the same way. If deposit and withdraw are the only doors into an account's balance, then the author of the class can later change how the balance is stored — from a decimal number to an exact count of cents, say — without breaking a single line of code anywhere else. That freedom is what encapsulation buys.

Common Mistake— "interface" is not a C++ keyword

If you have seen Java, you have met an interface keyword. C++ has no such keyword. In C++, "interface" is a design word, not a syntax word, and it means one of two things depending on context:

  • the public part of a class — this is the meaning we use for most of the semester; or
  • an abstract base class, the closest C++ equivalent of a Java interface, which we build in Class 25.

Do not go looking for an interface construct in C++. There isn't one.

Quick Check 1.6

A team writes a Temperature class that stores its value in degrees Fahrenheit, and makes that value public. Fifty other files across the project read and write it directly. A year later the team needs to store the value in Celsius instead.

(a) How many files have to change?

All fifty, plus the class itself. Every direct use of the stored value is now wrong.

And here is the part that should worry you: the compiler will only catch the uses that fail to compile. A line that sets the temperature to 100 still compiles perfectly and is now silently a bug, because it now means 100°C rather than 100°F. Those are the expensive ones.

(b) How many files would have had to change if the value had been private from the start, reachable only through a "get Fahrenheit" and a "set Fahrenheit" method?

One — the class itself. You change what is stored to Celsius and rewrite the two methods so that "get Fahrenheit" converts on the way out and "set Fahrenheit" converts on the way in.

The other fifty files still call the same two methods and never notice anything happened. This is the entire argument for encapsulation in one example: a public attribute is a promise about how you store things, and you can never take it back; a public method is a promise about what you can do, and you can keep it while changing everything behind it.

7.The big picture: inheritance and polymorphism

Two more ideas, in outline only. These are the subject of the second half of the course, from Class 19 onward. You are not expected to be able to use them today — only to know what problem each one solves, so that the rest of the semester has a shape.

Start with the problem. Suppose your drawing program needs circles, rectangles and triangles. All three have a color, all three have a position, all three can be moved, and all three can report their area. If you write three completely separate classes, you write "color", "position" and "move" three times — and when you fix a bug in move, you have to remember to fix it in three places.

Definition— inheritance

Inheritance lets you define a general class once and then define more specific classes that automatically get everything the general one has, adding or changing only what is different.

The general class is called the base class; the specific ones are derived classes. The relationship is read as IS-A: a circle is a shape.

Now the second idea, which is what inheritance is really for. Once every shape is a Shape, you can put all of them in one list and tell the whole list to draw itself — without your code knowing or caring which one is which. Each object runs its own version.

Definition— polymorphism

Polymorphism means "many forms." It is the ability to write one instruction — "draw yourself" — and have each object respond in the way that is right for what it actually is.

The code that gives the instruction does not need to be changed when you invent a new kind of shape. That is the payoff, and it is the reason this is the last big topic of the course.

Quick Check 1.6

You are designing a payroll program with salaried employees, hourly employees and contractors. All three have a name and an ID; all three can report how much they are owed this month, but each one calculates that differently.

(a) What should the base class be, and what should go in it?

A general Employee class, holding the things all three genuinely share — name and ID — plus the idea of "report how much you are owed."

The test for whether something belongs in the base class is not "do two of them have it" but "does every derived class have it, and does it mean the same thing for each." An hourly rate fails that test: a salaried employee does not have one.

(b) Which of the three ideas from today — encapsulation, inheritance, polymorphism — lets you write "print every worker's pay slip" as a single loop that never mentions the three kinds by name?

Polymorphism. The loop asks each worker for the amount owed; each one answers using its own calculation. Inheritance is what makes the loop possible — it is what lets all three be treated as employees in the first place — but polymorphism is what makes each one behave correctly.

The practical measure of whether you got this right: when the company adds a fourth kind of worker next year, how much existing code has to change? With this design, none of it. The new class is written, and the loop that prints the pay slips is not touched.

8.const: a promise to the compiler

Back to concrete C++. Some of an object's methods change it and some only read it — deposit changes an account, get balance does not. C++ lets you write that distinction down, and the keyword is const. From Class 10 onward it appears in almost every method we write, so it is worth pinning down now.

Definition— const

The const keyword is a promise to the compiler that something cannot be modified after its initial assignment or definition.

It is not a hint or a convention. The compiler checks it, and if you break the promise anywhere in the program, compilation fails. That is the point: a broken const promise becomes a compile-time error rather than a run-time bug.

Worked Example— keeping the promise, then breaking it

First, a legal program. DAYS_IN_WEEK never changes; weeks does. Predict the three lines of output.

constdemo.cpp
#include <iostream>
using namespace std;

int main() {
    const int DAYS_IN_WEEK = 7;
    int weeks = 3;

    cout << "weeks = " << weeks << endl;
    cout << "days  = " << weeks * DAYS_IN_WEEK << endl;

    weeks = 4;                       // fine: weeks is not const
    cout << "days  = " << weeks * DAYS_IN_WEEK << endl;
    return 0;
}
weeks = 3
days  = 21
days  = 28

Nothing surprising: a const variable can be read as often as you like. The restriction is only on writing to it. Naming constants in capitals is a widespread convention, not a language rule — but follow it, because it makes the promise visible at every use site.

Now the same program with one line changed, so that it breaks the promise. What does the compiler do?

constbad.cpp
#include <iostream>
using namespace std;

int main() {
    const int DAYS_IN_WEEK = 7;
    DAYS_IN_WEEK = 8;                // the promise is broken here
    cout << DAYS_IN_WEEK << endl;
    return 0;
}
constbad.cpp: In function 'int main()':
constbad.cpp:6:18: error: assignment of read-only variable 'DAYS_IN_WEEK'
    6 |     DAYS_IN_WEEK = 8;                // the promise is broken here
      |     ~~~~~~~~~~~~~^~~

No executable is produced. This is a compile-time error, and that is exactly what you want: the mistake is caught before the program ever runs, on your machine, rather than in front of a user. "assignment of read-only variable" is g++'s standard phrasing for a broken const promise — learn to recognize it, because you will see it many times this semester, usually because you called a non-const method on a const object.

Quick Check 1.6

Which of these four lines compile, and which do not? Assume each is the next statement after const double PI = 3.14159; and double r = 2.0;.

double c = 2 * PI * r;      // (i)
PI = 3.14;                  // (ii)
r = PI;                     // (iii)
const double E = PI;        // (iv)

Plan. Ask one question about each line: is anything being written into a const variable? Reading a const is always fine; only assignment to it is banned.

(i)CompilesPI is only read. Its value flows into a new, ordinary variable.
(ii)ErrorAssignment to a read-only variable. This is the broken promise.

The distinction in (iv) is subtle but it comes back hard later. const double E = PI; is legal, but splitting it into const double E; E = PI; is two errors: a const must be initialized where it is declared, and it cannot be assigned afterwards. When we reach member initializer lists in Class 13, this is precisely why const data members can only be set there.

9.A puzzle to take into Class 2

Here is a program from the CSCI 111 material you already know. It defines two functions that look almost identical and are supposed to do the same job — swap two integers. One of them works. One of them does absolutely nothing. Read them carefully before you reveal the output.

Worked Example— two swaps, one of which is a no-op

The only difference between the two functions is two & characters in the parameter list of the second one. Predict all three lines.

swap12.cpp
#include <iostream>
using namespace std;

void swap1(int u, int v) {
    int t = u;
    u = v;
    v = t;
}

void swap2(int &u, int &v) {
    int t = u;
    u = v;
    v = t;
}

int main() {
    int a = 3;
    int b = 4;
    int c = 5;
    int d = 6;
    cout << "original: " << a << " " << b << " " << c << " " << d << endl;
    swap1(a,b);
    cout << "swap1: " << a << " " << b << endl;
    swap2(c,d);
    cout << "swap2: " << c << " " << d << endl;
    return 0;
}
original: 3 4 5 6
swap1: 3 4
swap2: 6 5

swap1 did nothing. a and b came back exactly as they went in. swap2, which differs only by those two & characters, worked.

The reason, in one sentence: swap1(int u, int v) receives copies of a and b, so it dutifully swaps the copies and then throws them away when it returns; swap2(int &u, int &v) receives the caller's variables themselves, under the local names u and v, so swapping them swaps the originals.

That is the whole story of call by value versus call by reference, and it is the first thing we take apart properly in Class 2. It matters far beyond swapping: once objects enter the picture, passing by value means copying an entire object every time you call a function, and knowing when a copy happens is the difference between a correct program and a mysterious one.

Quick Check 1.6

Without changing main, what is the smallest edit that makes swap1 actually swap? And why is the function then indistinguishable from swap2?

Plan. The body of swap1 is already correct — the three-line temp swap is textbook. The bug is entirely in how the parameters arrive. So the fix is in the signature, not the body.

Add two ampersands:

void swap1(int &u, int &v) {
    int t = u;
    u = v;
    v = t;
}

At that point swap1 and swap2 are character-for-character the same function apart from the name, and both print a genuine swap.

Things to notice.

  • The & goes in the parameter list of the function, not at the call site. main still writes swap1(a,b); with no decoration at all. In C++ you cannot tell from the call whether an argument is being passed by value or by reference — you have to look at the function's declaration. That is a real readability cost of the feature, and a reason to keep function declarations visible.
  • The three-statement idiom int t = u; u = v; v = t; needs the temporary. Writing u = v; v = u; loses the original u on the first line and leaves both variables equal.

Problem 1 — Greatest common divisor (from the course notes)

Write a function that calculates the greatest common divisor (GCD) of two positive integers. Include a main that tests it on at least three pairs.

Plan. Euclid's algorithm, as worked through in Quick Check 1.3: while b is not zero, replace the pair (a, b) with (b, a % b). When the loop ends, a holds the answer.

gcd.cpp
// gcd.cpp -- greatest common divisor of two positive integers
#include <iostream>
using namespace std;

int gcd(int a, int b) {
    while (b != 0) {
        int r = a % b;
        a = b;
        b = r;
    }
    return a;
}

int main() {
    cout << "gcd(48, 18) = " << gcd(48, 18) << endl;
    cout << "gcd(17, 5)  = " << gcd(17, 5)  << endl;
    cout << "gcd(270, 192) = " << gcd(270, 192) << endl;
    cout << "gcd(9, 9)   = " << gcd(9, 9)   << endl;
    return 0;
}
gcd(48, 18) = 6
gcd(17, 5)  = 1
gcd(270, 192) = 6
gcd(9, 9)   = 9

Things to notice.

  • The parameters are taken by value on purpose. The function modifies a and b as it works, and taking copies means the caller's variables are untouched. This is a case where call by value is exactly what you want — it is not always the wrong choice.
  • gcd(17, 5) is 1 because 17 and 5 share no factor; such pairs are called relatively prime. Always test one of these.
  • A recursive version is equally correct and even shorter. Either is acceptable; the loop version uses constant stack space, which is the only practical difference at these sizes.
  • If the problem had allowed zero or negative inputs you would need a guard. As stated the inputs are positive, so no guard is required — but say so in a comment. On an exam, stating your assumption costs one line and protects you.

Problem 2 — The two swap functions (from the course notes)

Consider the two functions swap1 and swap2 from §9. State exactly what the program prints, and explain in your own words why the two functions behave differently.

Plan. Two things are being asked: the literal output, and the mechanism. For the output, trace main line by line, remembering that swap1 cannot affect main's variables. For the mechanism, describe what the parameter actually is in each case.

original: 3 4 5 6
swap1: 3 4
swap2: 6 5

Why. When main calls swap1(a, b), the parameters u and v are brand-new local variables inside swap1, initialized with copies of the values 3 and 4. The function swaps those two local variables perfectly well — and then the function returns, the locals are destroyed, and a and b in main have never been touched. This is call by value.

When main calls swap2(c, d), the & in int &u makes u a reference — another name for main's variable c, not a copy of it. Every read of u reads c, and every write to u writes c. So the swap lands on the originals. This is call by reference.

Things to notice.

  • Trace the first output line carefully: it prints all four variables before anything is swapped, hence 3 4 5 6.
  • The second and third lines each print only two variables, so the answer is 3 4 and 6 5, not four numbers each.
  • swap1 is not a typo in the original notes — it is deliberately broken to make the point. Do not "correct" it when you are asked to trace it.
  • The lesson generalizes: any function that must change its caller's variable needs a reference parameter (or, from Class 7, a pointer). A function that only needs to read its argument should take it by value if it is small, or by const reference if it is large — which is Class 2's material.

Problem 3 — Predict the output (added)

State the exact output of this program, line by line. Be careful with the arithmetic types.

qc_output.cpp
#include <iostream>
using namespace std;

int main() {
    int n = 7;
    double avg = 10.0 / 4;
    cout << "n = " << n << ", n / 2 = " << n / 2 << endl;
    cout << "avg = " << avg << endl;
    cout << "sum = " << 3 + 4 << endl;
    cout << 1.0 + 3.0 << endl;
    return 0;
}

Plan. Four independent lines. For each one, decide the type of every expression before deciding its value — in C++ the type is what determines whether you get integer division, and it determines how the result is printed.

n = 7, n / 2 = 3
avg = 2.5
sum = 7
4
LineReasoning
1n / 2 is int / int, so it is integer division: 7 divided by 2 is 3, remainder discarded. Not 3.5.
210.0 / 4 has one double operand, so the 4 is converted to 4.0 and the division is floating point: 2.5.
3+ binds tighter than <<, so this is cout << "sum = " << 7. Prints sum = 7.
4The value is the double 4.0, but cout's default formatting drops the trailing zeros, so it appears as 4.

Things to notice.

  • Line 4 is the trap, and it is a favourite on output-prediction questions. A double whose value happens to be a whole number prints with no decimal point at all. Writing 4.0 as your answer is wrong.
  • Line 3 is the other trap, in the opposite direction. cout << 3 + 4 works because + has higher precedence than <<. But cout << 3 < 4 would not do what you expect, because << and < group left to right. When in doubt, parenthesize.
  • Integer division is the most common source of silently wrong numeric answers in this course. If you want a real average, make sure at least one operand is a double — sum / 2.0, or static_cast<double>(sum) / count.

Problem 4 — Write five C++ statements (added)

Write five C++ statements, in order, that: (1) declare a constant integer MAX_SCORE equal to 100; (2) declare an integer score equal to 87; (3) declare a double called percent holding score as a percentage of MAX_SCORE; (4) print percent; (5) end main normally.

Plan. Statement (3) is the only one with any thought in it. Both score and MAX_SCORE are int, so score / MAX_SCORE would be integer division and evaluate to 0. The fix is to force floating-point arithmetic by making one operand a double; the cleanest way is to write the literal as 100.0 and to put it first so the conversion happens before the division.

five_statements.cpp
#include <iostream>
using namespace std;

int main() {
    const int MAX_SCORE = 100;                    // (1)
    int score = 87;                               // (2)
    double percent = 100.0 * score / MAX_SCORE;   // (3)
    cout << "percent = " << percent << endl;      // (4)
    return 0;                                     // (5)
}
percent = 87

Things to notice.

  • 100.0 * score / MAX_SCORE evaluates left to right: 100.0 * 87 is the double 8700.0, then dividing by 100 gives 87.0. Had you written score / MAX_SCORE * 100.0 you would get 0 * 100.0, that is 0 — a completely wrong answer that compiles without a murmur.
  • The output is 87, not 87.0 — the same default formatting rule as Problem 3.
  • MAX_SCORE is const because it is a fixed property of the problem. Marking it so means a later stray MAX_SCORE = 90; is a compile error rather than a bug.
  • On an exam that asks for "five statements", write exactly five and number them in comments. Rubrics for this style of question award points per statement, so a clearly labelled partial answer still scores.
Lecture Summary
  • Every C++ program has the same five parts: #include directives, the using directive, int main(), the body, and return 0;.
  • Compile with g++ file.cpp -o name and run with ./name. Leave off -o name and the executable is called a.out instead.
  • Compile-time errors stop the executable from being produced; run-time errors happen while it runs. Fix the first compiler error and recompile.
  • OOP organizes a program around objects, each bundling data (attributes) with behavior (methods). Nouns tend to become attributes; verbs tend to become methods.
  • A class is the blueprint; an object is an instance built from it. Many objects, one class. Each object has its own copy of the data; the method code is shared.
  • A class's interface is what it makes public — the contract it offers the rest of the program. Encapsulation means keeping the data private and reachable only through that interface, so the representation can change without breaking anyone.
  • Inheritance lets a specific class reuse everything a general class has, adding only what differs. Polymorphism lets one instruction produce the right behavior for whatever the object actually is. Those two are the second half of the course.
  • const is a promise to the compiler that something will not be modified. Break it and you get "assignment of read-only variable" at compile time.
  • By default cout prints a floating-point value to six significant digits and drops trailing zeros, so 4.0 appears as 4.
  • swap1 fails and swap2 works because of two & characters: copies versus the caller's own variables.
