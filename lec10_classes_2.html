1.A class can contain functions too

In Class 9 a class was a container of data. You wrote class Point { public: double x, y; };, you declared an object with Point apt;, and you reached into it with the dot operator: apt.x = 2.5;. Useful, but so far a class is only a way to keep related variables side by side. It has no behavior of its own.

Today it gets some. Here is the whole idea, in the course notes' own words:

Key Idea— from the course notes
  • A class can contain more than just data.
  • A class can also contain functions.
  • Functions which belong to a class are called class methods.
Definition— class method / member function

A class method — also called a member function — is a function declared inside a class. It is an ordinary C++ function in every respect except one: it belongs to the class, so when you call it, it is always called on some object, and inside the body the data member names refer to that object's data.

The two names mean exactly the same thing. The course notes say "method"; the C++ standard says "member function"; exam questions in this course use both. Get comfortable with each.

Three mechanical facts to notice before the example, all straight from the notes:

  • The dot operator applies to class methods using exactly the same syntax as for class data. You wrote apt.x; you now write bpt.print().
  • A class method must have a return type. In these first examples it is void, but it is written out just like any function's return type.
  • A method is a function just like any other C++ function. The only difference is that it belongs to a class.
Worked Example— the first class with methods

This is the course notes' program. The class now has a data section and a methods section. Read set and print carefully — notice that neither of them mentions any object at all, and neither of them declares x or y. Predict the output.

methods.cpp
// methods.cpp -- a class that contains functions as well as data
#include <iostream>
using namespace std;

class Point {
public:
    // data
    double x, y;

    // methods
    void set(double a, double b) {
        x = a;
        y = b;
    }
    void print() const {
        cout << "print x,y " << x << " " << y << endl;
    }
};

int main() {
    Point bpt;
    bpt.set(1.23, 4.56);    // dot operator for class methods
    bpt.print();            // dot operator for class methods
    return 0;
}
print x,y 1.23 4.56

The interesting part is what is not written. Inside set, the bare names x and y are not local variables and not globals — they are the data members of whichever object the method was called on. Because main wrote bpt.set(...), the assignment x = a; lands in bpt's x. If main had two points and called apt.set(...) instead, the identical line of code would land in apt's x.

Statement in mainWhat actually happens
Point bpt;Memory for one Point is set aside: two doubles. No method runs.
bpt.set(1.23, 4.56);The shared function set runs with bpt as its object. a becomes 1.23, b becomes 4.56, and the two assignments write into bpt.
bpt.print();The shared function print runs with bpt as its object, reads bpt's x and y, and sends them to cout.

And the formatting detail that costs points on exams: 4.56 prints as 4.56, but if you had called bpt.set(1.0, 2.0) the output would be print x,y 1 2. cout drops trailing zeros by default. Write it that way in an exam answer.

Common Mistake— naming a parameter after a data member

The professor named the parameters a and b, not x and y, and that is deliberate. If you write

    void set(double x, double y) {
        x = x;          // does nothing useful
        y = y;
    }

then inside the method the name x means the parameter, not the data member — the closer declaration wins. The line x = x; assigns the parameter to itself and the object is never touched. It compiles, it runs, and it silently does nothing. There is a fix using the this pointer, which we meet in Class 15; until then just give the parameters different names.

Quick Check 10.1

Using the Point class from the worked example above.

(a) How many copies of the function set exist in the compiled program if main creates five Point objects? How many copies of x?

One copy of set, and five copies of x.

Methods are compiled once and shared by every object of the class — there is only one set of machine instructions for set in the whole executable. Data members are per-object; that is the entire reason objects exist. What varies from call to call is which object the method operates on, and that is decided by whatever sits to the left of the dot.

(b) Inside print, would it be legal to write bpt.x instead of x?

No. The class knows nothing about a variable named bpt; that name exists only inside main. The class is a blueprint, written once, and it has to work for every object ever made from it — including objects that have not been given a name at all.

Inside a method, an unqualified data-member name already means "this object's copy". That is precisely what makes one shared function able to serve every object.

(c) Add a method void reset() that sets both coordinates to zero, written in terms of the existing set method. Can one method call another?

Yes, and with no dot in front of it:

    void reset() {
        set(0.0, 0.0);
    }

Inside a method, calling set(0.0, 0.0) means "call set on the same object I was called on." This is the same rule as (b), applied to methods instead of data. It is also why print in a class can call area() or getx() directly, which we lean on constantly from here on.

2.const member functions

You have already met const twice in this course: on a variable in Class 1 (const int DAYS_IN_WEEK = 7;) and on a reference parameter in Class 2 (void show(const string &s)). This is the third use, and syntactically it is the odd one, because the keyword goes in a place you have not seen before — after the parameter list.

Definition— const member function

A method written as

    void print() const {  ...  }

is a const member function. Tagging a class method const is a promise to the compiler that the method will not change the values of the internal data in the class.

The const goes after the parameter list and before the opening brace. It is part of the method's signature, so if you later define the body outside the class it must appear in both places (§7).

The course notes state the rule for our two methods directly:

  • Obviously print() does not change the values of x and y. Hence print() can be tagged as const.
  • However set(...) changes the values of x and y. Hence set(...) cannot be tagged as const.

So what does the promise actually buy? Two things, and the second one is the one that matters.

Worked Example— breaking the promise inside the method

The first thing const buys you is that the compiler checks the method's own body. Here someone has tagged the mutator const — perhaps out of a vague sense that const is always good. What does g++ say?

constbad.cpp
// constbad.cpp -- tagging a mutator const: the promise is broken
#include <iostream>
using namespace std;

class Point {
public:
    double x, y;
    void set(double a, double b) const {   // WRONG: set changes the object
        x = a;
        y = b;
    }
};

int main() {
    Point p;
    p.set(1.0, 2.0);
    return 0;
}
constbad.cpp: In member function 'void Point::set(double, double) const':
constbad.cpp:9:11: error: assignment of member 'Point::x' in read-only object
    9 |         x = a;
      |         ~~^~~
constbad.cpp:10:11: error: assignment of member 'Point::y' in read-only object
   10 |         y = b;
      |         ~~^~~

"assignment of member ... in read-only object" is the phrasing to memorize. Inside a const method, every data member of the object is treated as read-only, so the two assignments are rejected. Note that the error points at the body, not at the const keyword — g++ believes your promise and blames the code that breaks it. The fix is to delete the const, because a mutator genuinely does change the object.

Worked Example— the promise as seen from outside

The second and far more important payoff: once an object is const, or is reached through a const reference, only its const methods may be called. Here show takes a const Point & — the Class 2 idiom for "pass a big thing cheaply, and promise not to change it." It calls one method that is const and one that is not.

constobj.cpp
// constobj.cpp -- a const object may only call const methods
#include <iostream>
using namespace std;

class Point {
public:
    double x, y;
    void set(double a, double b) {
        x = a;
        y = b;
    }
    void print() const {
        cout << "print x,y " << x << " " << y << endl;
    }
};

void show(const Point &p) {
    p.print();               // fine: print is const
    p.set(0.0, 0.0);         // error: set is not const
}

int main() {
    Point bpt;
    bpt.set(1.23, 4.56);
    show(bpt);
    return 0;
}

constobj.cpp:19:10: error: passing 'const Point' as 'this' argument discards qualifiers [-fpermissive]
   19 |     p.set(0.0, 0.0);         // error: set is not const
      |     ~~~~~^~~~~~~~~~
constobj.cpp:8:10: note:   in call to 'void Point::set(double, double)'
    8 |     void set(double a, double b) {
      |          ^~~~

"discards qualifiers" is g++'s way of saying: you have a read-only handle on this object and you tried to call a method that reserves the right to write to it. The line p.print(); is accepted without complaint, because print is const and therefore safe.

The word this in the message is a forward reference — every method receives a hidden pointer to the object it was called on, and that pointer is what carries the const. We take this apart properly in Class 15. For now, read "discards qualifiers" as "non-const method, const object."

Here is why this matters more than the first example. The moment anyone in your program writes a function taking const YourClass &, every method they need must already be const. If you forgot the keyword when you wrote the class, their code will not compile, and the fix has to happen in your file. So the rule is not "add const when it seems tidy." It is:

Key Idea

If a method does not change the object, mark it const. Do it when you write the method, not later. It costs one word, it is checked by the compiler, and leaving it off quietly makes your class unusable through const references — which is how objects are passed to functions for the rest of this course.

Quick Check 10.2

For each method of a hypothetical BankAccount class, say whether it should be tagged const, and why.

(a) double getBalance()

Yes — double getBalance() const. It reads a data member and hands the value back; nothing in the object changes. Every accessor in this course should be const.

(b) void deposit(double amount)

No. deposit writes to the balance. Tagging it const produces exactly the "assignment of member ... in read-only object" error from the worked example above.

(c) void print(), which sends the balance to cout but does not touch a data member

Yes — void print() const. Printing changes the screen, not the object, and it is the object that const is about. This is the case people most often get wrong, and the professor's own print() is const in every version of Point in the notes.

(d) double applyInterest(), which grows the balance and returns the interest earned

No. Do not be fooled by the return value — the question is never "does this method return something", it is "does this method change the object." This one changes the balance, so it cannot be const.

The test to apply every time: read the method body and ask whether any data member appears on the left of an assignment, is passed somewhere by non-const reference, or is modified by ++/--. If the answer is no anywhere in the body, write const.

3.Accessor and mutator methods

Once a class has methods, a naming convention appears that you will see in every C++ codebase you ever touch. The course notes introduce it exactly here.

Definition— accessor and mutator

Accessor methods return the values of data members in a class. That is why accessor methods are also called "get" methods. Accessor methods can be tagged as const, because they do not change the values of the data members in a class.

Mutator methods set (or "mutate") the values of data members in a class. Mutator methods are called "set" or "put" methods.

So getx() and gety() are accessors; set(a, b) is a mutator. Accessors are const; mutators are not.

Worked Example— the professor's getx/gety/set

This is the course notes' class with accessors added, plus two extra lines at the end of main that were not in the notes. Those two lines are the point of the example: predict what the third line of output is, and think about whether you like the answer.

accessors.cpp
// accessors.cpp -- accessor (get) and mutator (set) methods
#include <iostream>
using namespace std;

class Point {
public:
    double getx() const { return x; }     // accessor method
    double gety() const { return y; }     // accessor method

    void set(double a, double b) {        // mutator method
        x = a;
        y = b;
    }
    void print() const {
        cout << "print x,y " << x << " " << y << endl;
    }

    // data
    double x, y;
};

int main() {
    Point bpt;
    bpt.set(1.23, 4.56);
    bpt.print();
    cout << "get: " << bpt.getx() << " " << bpt.gety() << endl;

    bpt.x = -99.0;                        // still legal: x is public
    bpt.print();
    return 0;
}
print x,y 1.23 4.56
get: 1.23 4.56
print x,y -99 4.56

The first two lines are the notes' own output. The third line is the problem. We built a tidy little interface — set to write, getx/gety to read — and then main ignored all of it and assigned straight into bpt.x. Nothing stopped it, because double x, y; is sitting under public: in the same class.

Notice also that a method body written on one line, double getx() const { return x; }, is completely ordinary C++. There is no special "one-line method" rule; it is just a function whose body happens to be short.

Common Mistake— accessors on public data are decoration

The class above is the version printed in the course notes, and taken on its own it is self-defeating: it offers getx() and gety() as the controlled way to read the coordinates while leaving x and y public, so bpt.x = -99.0; still compiles. Every guarantee the accessors were supposed to provide is worth nothing.

The notes fix this a few slides later, and so do we, in §4. But do not read this class as a finished design. Accessors and mutators are only meaningful once the data they guard is private. Writing getters and setters around public data is one of the most common things beginners do that looks professional and accomplishes nothing.

Quick Check 10.3

A Rectangle class stores width and height. A classmate proposes adding an accessor double getArea() const { return width * height; } and objects that it is not a real accessor because there is no data member called area.

(a) Is getArea() a legitimate method for this class? Should it be const?

Absolutely legitimate, and yes, const. A method that computes and returns a value derived from the data members is one of the most useful things a class can offer, precisely because the caller does not need to know whether the value is stored or computed.

That is encapsulation working in your favor: today area is computed on demand; if profiling later showed it was worth caching in a data member, you could change the class and no caller would notice.

(b) Would you name it getArea or just area?

Either is fine and both appear in real code. The get prefix is conventionally reserved for "hand me back a stored data member", so many programmers write area() for a computed value and getWidth() for a stored one. The course notes use the get prefix for the plain accessors getx/gety, and Class 1's Rectangle used a bare area(). Pick a convention and be consistent inside one class — that consistency is worth more than which convention you picked.

4.private: encapsulation becomes syntax

Class 1 defined encapsulation as keeping an object's data private and exposing it only through a controlled public interface, and then asked you to take it on faith that this was worth the trouble. Class 9 gave you public: and told you that private and protected existed but were "more complicated" and would come later. This is later. It is one keyword.

The course notes open the topic by naming the flaw in everything we have written so far:

Key Idea— from the course notes

An obvious weak feature of the Point class is that everything in the class is accessible to outside calling applications (keyword public).

  1. The data members x and y become private data members of the class.
  2. The keyword private means that outside applications cannot directly access the values of x and y.
  3. To access the class data, outside applications must go through a controlled interface (the accessor and mutator methods).
  4. We can therefore control outside access to the internal class data.
Definition— public and private

Anything which is tagged public — data or methods — is accessible to outside applications.

Anything which is tagged private — data or methods — is accessible inside the class only.

public: and private: are labels, not blocks: each one applies to every member written after it, until the next label. A class may switch back and forth as many times as you like, and the members do not have to be in any particular order.

Here is the professor's revised class. He renames it Point1 so both versions can coexist in the notes. Structurally, exactly one thing changed: the word public: above double x, y; became private:.

Worked Example— the same class, data moved behind the interface

The public section is identical to §3's. Only the last two lines of the class differ. Predict the output, then ask yourself what changed for the code in main.

private_point.cpp
// private_point.cpp -- the same Point, with its data moved behind the interface
#include <iostream>
using namespace std;

class Point1 {
public:                                   // keyword public
    double getx() const { return x; }
    double gety() const { return y; }

    void set(const double &a, const double &b) {
        x = a;
        y = b;
    }
    void print() const {
        cout << "print x,y " << x << " " << y << endl;
    }

private:                                  // keyword private
    double x, y;
};

int main() {
    Point1 bpt;
    bpt.set(1.23, 4.56);
    bpt.print();
    cout << "get: " << bpt.getx() << " " << bpt.gety() << endl;
    return 0;
}

get: 1.23 4.56

Byte for byte the same output as §3. That is the whole point: private changes nothing about what the program does and everything about what a future programmer is allowed to do. It is a compile-time restriction, not a run-time mechanism; it costs zero instructions.

Two smaller changes the professor made in the same step, worth noticing because they will show up in his exam answers:

  • set now takes const double &a, const double &b — const reference parameters, from Class 2. For a double this is a wash (a reference is typically the same size as the value), but it is the habit he wants: read-only parameters get const &.
  • The methods are written above the data. That is a common style, because the interface is what a reader of the class cares about and the data is an implementation detail. C++ does not care about the order.

Now the part that makes it real. Take that same class and add the line main used to be allowed to write.

Learn the first line of that message by heart, because you will see it constantly for the rest of the semester:

Three things to read out of it:

  • It is a compile-time error. No executable is produced. The mistake cannot reach a user.
  • The note: declared private here line points at the exact declaration, so you never have to guess which member it means — useful once classes have a dozen of them.
  • Modern g++ even suggests the accessor: "field ... can be accessed via Point1::getx() const". It has read your public section and found the intended door. Do not skip past note: lines.

Notice too that reading is blocked just as firmly as writing. private is not about protecting the data from corruption alone; it is about not letting anyone depend on the representation, in either direction.

Why this is worth the trouble

It is easy to hear "the compiler stops you writing bpt.x" and conclude that private is an annoyance invented to make simple things harder. Here is the argument in its concrete form.

Suppose Point1 had kept its data public and fifty files across a project read and wrote p.x and p.y directly. Now a requirement arrives: points must be stored in polar form, radius and angle, because that is what the graphics library wants. With public data, all fifty files are wrong, and worse, most of them still compile — they just silently mean something else now. With private data, you rewrite getx() as return r * cos(theta);, change set, and not one caller changes at all. That is the trade: a public data member is a promise about representation that you can never take back; a public method is a promise about behavior that you can keep while changing everything behind it.

The second payoff is enforcement. Once the only way in is a mutator, the mutator can refuse.

Worked Example— a mutator that says no

A circle's radius must not be negative. With a public data member there is nowhere to put that rule. With a private one there is exactly one door, and the rule lives in it. Predict all four lines.

circle.cpp
// circle.cpp -- private data lets the mutator enforce a rule
#include <iostream>
using namespace std;

class Circle {
public:
    void setRadius(double r) {
        if (r < 0.0) {
            cout << "Circle: negative radius rejected" << endl;
            radius = 0.0;
        } else {
            radius = r;
        }
    }
    double getRadius() const { return radius; }
    double area() const { return 3.14159 * radius * radius; }
    void print() const {
        cout << "Circle r = " << radius << ", area = " << area() << endl;
    }
private:
    double radius;
};

int main() {
    Circle c;
    c.setRadius(2.0);
    c.print();

    c.setRadius(-5.0);      // the class refuses
    c.print();

    cout << "radius is " << c.getRadius() << endl;
    return 0;
}
Circle r = 2, area = 12.5664
Circle: negative radius rejected
Circle r = 0, area = 0
radius is 0

The rule "radius is never negative" is now a property of the class, not a discipline that every caller has to remember. A statement like this is called an invariant: a fact about the object that is true before and after every public method call. Invariants are the real reason for private, and a good exam answer about encapsulation names one instead of reciting the definition.

Two details in the code: print calls area() with no dot, which is the §1 rule again; and area is const while setRadius is not, which is the §2 rule again. Every class you write from now on has this shape.

Private methods

The notes add one line that is easy to miss: "It is also possible to write private class methods." A private method is a helper — a piece of the implementation that the public methods use and that outside code has no business calling.

Worked Example— a helper that is not part of the interface

toF is a conversion used by two public methods. It is nobody else's business.

privhelper.cpp
// privhelper.cpp -- a private method: a helper the outside world cannot call
#include <iostream>
using namespace std;

class Temperature {
public:
    void setCelsius(double c) { celsius = c; }
    double getFahrenheit() const { return toF(celsius); }
    void report() const {
        cout << celsius << "C = " << toF(celsius) << "F" << endl;
    }
private:
    double toF(double c) const { return c * 9.0 / 5.0 + 32.0; }   // private helper
    double celsius;
};

int main() {
    Temperature t;
    t.setCelsius(100.0);
    t.report();
    cout << "as F: " << t.getFahrenheit() << endl;
    return 0;
}
100C = 212F
as F: 212

Warning— every Point so far is born uninitialized

None of the classes in Classes 9 and 10 has a constructor. So when you write Point1 bpt;, memory is set aside for x and y and nothing is written into it. The members hold whatever bytes happened to be there. Reading them before calling set is undefined behavior, and compiling bpt.print() before bpt.set(...) gets you this from -Wall:

uninit.cpp: In function 'int main()':
uninit.cpp:15:14: warning: 'bpt' may be used uninitialized [-Wmaybe-uninitialized]
   15 |     bpt.print();    // reading them is undefined behavior
      |     ~~~~~~~~~^~

and this at run time — the numbers are garbage from the stack and differ from run to run, so treat them as representative only:

print x,y 6.95335e-310 6.94338e-310
print x,y 1.23 4.56

Every example on this page calls set before reading, so all of them are safe. But note the hole in the encapsulation story: we can stop outside code from writing nonsense into x, and we still cannot stop an object from starting out as nonsense. Closing that hole is exactly what a constructor is for, and it is the first thing we build in Class 13.

Quick Check 10.4

Consider this class and the four lines of main beneath it.

5.Working through the interface

Making the data private changes how other code has to be written. The course notes make this concrete with a free function — an ordinary, non-member function — that needs to look inside two objects.

Worked Example— a free function over private data

distance computes the distance between two points. It is not a member of Point1, so it has no special access to anything. Look at how it gets at the coordinates, and at the parameter types. Predict the output — the numbers are chosen to make it come out exactly.

distance.cpp
// distance.cpp -- a free function that must go through the public interface
#include <iostream>
#include <cmath>
using namespace std;

class Point1 {
public:
    double getx() const { return x; }
    double gety() const { return y; }
    void set(const double &a, const double &b) {
        x = a;
        y = b;
    }
    void print() const {
        cout << "print x,y " << x << " " << y << endl;
    }
private:
    double x, y;
};

    double dx = a.getx() - b.getx();
    double dy = a.gety() - b.gety();
    return sqrt(dx*dx + dy*dy);
}

int main() {
    Point1 p1, p2;
    p1.set(1.5, 2.5);
    p2.set(4.5, -1.5);

    return 0;
}

The arithmetic: dx is 1.5 - 4.5 = -3 and dy is 2.5 - (-1.5) = 4, so the distance is the hypotenuse of a 3-4-5 triangle. sqrt comes from #include <cmath>, which you need any time you use it.

Now the two design points the notes emphasize.

First: because x and y are private, they cannot be accessed directly in the function distance. Their values must be obtained using the accessor methods getx and gety. Writing a.x - b.x would produce the "is private within this context" error from §4. The class does not make an exception for code that has a good reason.

Second, and this is the subtle one: the parameters are tagged as const references. That is a promise to the compiler that the code inside distance will not change the data in a and b. That promise can only be satisfied because getx and gety are const methods. The two uses of const compose — a const reference is only useful if the class offers const methods to call through it.

6.Pointers to objects and the arrow operator

Classes 7 and 8 gave you pointers, new and delete over ints and arrays. None of that machinery cares what type it is pointing at, so it all works on objects unchanged. As the notes put it: the compiler automatically knows how to create pointers for a user-defined class, and it automatically sets up the operators new and delete.

There is exactly one new piece of syntax, and it exists purely for convenience.

Definition— the arrow operator

The arrow operator -> is the "pointer member of" operator. It is the partner of the dot operator for objects. If p is a pointer to an object, the following two statements are equivalent:

    p->print();
    (*p).print();

It is simpler and more convenient to use the arrow operator for pointers. The arrow operator -> and the dot operator . have the same level of operator precedence.

Read p->print() out loud as "follow the pointer p, then call print on what you find."

Why the parentheses in (*p).print() are not optional is a direct consequence of Class 9's precedence rule: only () and [] bind more tightly than ., so * binds less tightly. That means *p.print() parses as *(p.print()) — "call print on the pointer, then dereference the result" — which is nonsense. Here is what g++ says about it:

starprec.cpp: In function 'int main()':
starprec.cpp:16:8: error: request for member 'print' in 'p', which is of pointer type 'Point*' (maybe you meant to use '->' ?)
   16 |     *p.print();         // missing parentheses
      |        ^~~~~

The arrow operator exists so you never have to type those parentheses. Use it.

Quick Check 10.8

Consider this fragment, using the Point class with private data and public set/print.

Point *q = p; copies an address, not an object. There is still exactly one Point on the heap and now two pointers aimed at it, so q->set(9.0, 9.0) and p->print() are talking about the same object. This is Class 7's "copying an address vs. copying a value" applied to a class.

(b) After delete p;, is it safe to write q->print();?

No. It is undefined behavior. q still holds the old address, but the object there has been destroyed and the memory handed back — q is a dangling pointer. It may print the old values, it may print garbage, it may crash, and which of those happens can change between runs.

Setting p = nullptr; after the delete protects p and does nothing for q. That asymmetry — one object, several pointers, one owner — is what makes manual memory management hard, and it is the reason the copy constructor and destructor in Classes 13 and 14 matter so much.

    Point *p = new Point;

7.Defining methods outside the class

Every method so far has had its body written inside the class body. That is called an inline definition, and for two-line methods it is perfect. For a class with real methods in it, the course notes point out the problem plainly: the declaration of the class becomes very long and is difficult to read and maintain.

Definition— inline vs. non-inline definition

An inline method is one where the body of the function (class method) is written inside the declaration of the class itself.

A non-inline method is declared in the class — return type, name, parameters, semicolon — and defined elsewhere, with its name prefixed by the class name and the scope-resolution operator ::.

The prefix Point2:: identifies the function as a method of the class Point2. Without it, the compiler has no idea that the function you are defining is the one the class promised.

Why you would bother: the header / implementation split

The real reason for non-inline definitions is the one Class 2 set up when we split a program into several files. The notes state it directly: it is possible to write the class declaration in a header file and to write the definitions of the method bodies in a separate .cpp file. There is also the nice feature that if the code in one .cpp file is edited, the rest of the project does not need to be recompiled — whereas if the code for an inline method is changed, all the code for the entire class must be recompiled.

Procedure— splitting a class into three files
  1. point2.h — the class declaration only: data members and method declarations, plus any tiny inline methods. Wrap it in an include guard.
  2. point2.cpp — #include "point2.h", then the method bodies, each prefixed with Point2::.
  3. main.cpp — any client of the class. It #includes the header and nothing else about Point2; it never sees the bodies.
  4. Compile each .cpp to an object file, then link them together.

Problem 1 — Distance between two points (from the course notes)

Given a Point1 class whose x and y are private, with public set, print, getx and gety, write a free function double distance(const Point1 &a, const Point1 &b) that returns the distance between the two points, and a main that tests it on the points (1.5, 2.5) and (4.5, -1.5). Explain why the function cannot read a.x directly and why the const on the parameters is safe.

Plan. The mathematics is the Pythagorean theorem: the distance is sqrt(dx*dx + dy*dy) where dx and dy are the coordinate differences. sqrt lives in <cmath>. The design questions are the interesting part — the function is not a member, so it has no access to private data and must go through the accessors, and it should take its arguments by const reference so no Point1 is copied.

distance.cpp
// distance.cpp -- a free function that must go through the public interface
#include <iostream>
#include <cmath>
using namespace std;

class Point1 {
public:
    double getx() const { return x; }
    double gety() const { return y; }
    void set(const double &a, const double &b) {
        x = a;
        y = b;
    }
    void print() const {
        cout << "print x,y " << x << " " << y << endl;
    }
private:
    double x, y;
};

double distance(const Point1 &a, const Point1 &b) {
    double dx = a.getx() - b.getx();
    double dy = a.gety() - b.gety();
    return sqrt(dx*dx + dy*dy);
}

int main() {
    Point1 p1, p2;
    p1.set(1.5, 2.5);
    p2.set(4.5, -1.5);
    double d = distance(p1, p2);
    cout << "distance = " << d << endl;
    return 0;
}

Things to notice.

  • Why not a.x? Because x is private and distance is not a member of the class. The compiler rejects it with 'double Point1::x' is private within this context. Outside applications must employ the public methods to manipulate the class data; that is what having an interface means.
  • Why is const safe here? Because getx and gety are const methods and so are callable through a const reference. If they were not const, this function would not compile at all — the two uses of const have to line up.
  • dx and dy are ordinary local doubles. Squaring a negative gives a positive, so no absolute value is needed anywhere.
  • Naming a free function distance while using namespace std; is in force risks a clash with std::distance. It happens to work here; point_distance would be safer.
  • A neater alternative is hypot(dx, dy) from <cmath>, which avoids overflow for huge values. Either is acceptable; sqrt is what the notes use.

Problem 5 — A fully encapsulated Rectangle (added)

Write a complete C++ program containing a Rectangle class whose width and height are private. Give it a mutator set, const accessors for both dimensions, a const area() and a const print(). Then write a free function that takes two rectangles by const reference and returns the larger of the two by area. In main, create one rectangle normally, one with new, compare them, and release the heap one.

Plan. Everything on this page appears in this one program, so build it in the order the class was taught. Data first, private. Then the mutator (not const), then the three reading methods (all const). Then the free function: it is not a member, so it may only use the public interface, and it takes const Rectangle & parameters, which is legal only because area() is const. Returning const Rectangle& avoids copying, and is safe here because both arguments outlive the call. Finally main exercises both an ordinary object and a heap one, so we need . in one place and -> in the other, plus one delete for the one new.

rectangle.cpp
// rectangle.cpp -- a complete encapsulated class used through its interface
#include <iostream>
using namespace std;

class Rectangle {
public:
    void set(double w, double h) {
        width  = w;
        height = h;
    }
    double getWidth()  const { return width;  }
    double getHeight() const { return height; }
    double area() const { return width * height; }
    void print() const {
        cout << "Rectangle " << width << " x " << height
             << ", area = " << area() << endl;
    }
private:
    double width, height;
};

// free function: it can only use the public interface
const Rectangle& bigger(const Rectangle &a, const Rectangle &b) {
    if (a.area() >= b.area()) return a;
    return b;
}

int main() {
    Rectangle r;
    r.set(3.0, 4.0);
    r.print();

    Rectangle *q = new Rectangle;
    q->set(2.0, 8.0);
    q->print();

    cout << "bigger area = " << bigger(r, *q).area() << endl;

    delete q;
    q = nullptr;
    return 0;
}

Rectangle 2 x 8, area = 16

Things to notice.

  • bigger(r, *q) — the second argument is *q, not q. The function wants a Rectangle, and q is a Rectangle*, so it has to be dereferenced. This is where the arrow operator does not help you: -> reaches a member, but here we are passing the whole object.
  • bigger returns const Rectangle&, so no rectangle is copied anywhere in this program. That is safe because both arguments are alive for the whole statement. Returning a reference to a local object would be a serious bug — the Class 2 rule about returning references still applies.
  • Because the return type is const Rectangle&, we can only call const methods on the result — bigger(r, *q).area() works precisely because area() is const. Try it with the const removed and you get "discards qualifiers" again.
  • One new, one delete, and q = nullptr; afterwards. Under valgrind this program reports "All heap blocks were freed — no leaks are possible."
  • Both objects need set called before anything reads them, because the class has no constructor yet. From Class 13, Rectangle r(3.0, 4.0); will do both jobs in one line and remove the possibility of forgetting.

    void bump() { count++; }
    void show() const { cout << "count = " << count << endl; }
private:
    int count;
};

int main() {
    Counter c;
    Counter *p = new Counter;
    c.set(5);
    p->set(10);
    const Counter &r = c;

    c.show();                          // (a)
    p.show();                          // (b)
    (*p).bump();  p->show();           // (c)
    cout << c.count << endl;           // (d)
    r.bump();                          // (e)

    delete p;
    return 0;
}

(a) c.show();

count = 5

c is an ordinary object, show is public and const, and c.set(5) ran earlier. Nothing to trip over.

(b) p.show();

ERROR. p is a pointer, so the member must be reached with ->.

trace_err.cpp:23:7: error: request for member 'show' in 'p', which is of pointer type 'Counter*' (maybe you meant to use '->' ?)
   23 |     p.show();                          // (b)
      |       ^~~~

The fix is p->show();, which would print count = 10.

(c) (*p).bump(); p->show();

count = 11

Both halves are legal. (*p).bump() is the long form of p->bump(); it dereferences the pointer and then calls bump, taking the heap object's count from 10 to 11. Then p->show() prints it.

Note that bump is not const — it increments a data member — and that is fine here, because p is a plain Counter*, not a pointer to const.

(d) cout << c.count << endl;

ERROR. count is private, and main is outside the class.

trace_err.cpp:25:15: error: 'int Counter::count' is private within this context
   25 |     cout << c.count << endl;           // (d)
      |               ^~~~~
trace_err.cpp:12:9: note: declared private here
   12 |     int count;
      |         ^~~~~
trace_err.cpp:25:15: note: field 'int Counter::count' can be accessed via 'int Counter::get() const'
   25 |     cout << c.count << endl;           // (d)
      |               ^~~~~
      |               get()

The fix is the one g++ suggests: cout << c.get() << endl;, which prints 5.

(e) r.bump();

ERROR. r is a const Counter &, so only const methods may be called through it, and bump is not one.

trace_err.cpp:26:11: error: passing 'const Counter' as 'this' argument discards qualifiers [-fpermissive]
   26 |     r.bump();                          // (e)
      |     ~~~~~~^~
trace_err.cpp:9:10: note:   in call to 'void Counter::bump()'
    9 |     void bump() { count++; }
      |          ^~~~

There is no fix that keeps the meaning — r is a read-only handle by design, and bump writes. You could call a const method instead: cout << r.get() << endl; prints 5.

Things to notice. With (b), (d) and (e) commented out and (e) replaced by r.get(), the surviving program prints:

count = 5
count = 11
5

The three errors are the three big traps of this class, one each: dot on a pointer, outside code touching private data, and a non-const method through a const handle. Learn to recognize those three g++ messages on sight and you will diagnose most of your class bugs from the first line of the error.

Two exam habits this question is drilling: read the declaration of anything on the left of a . or -> before deciding which one is legal, and, when a line fails, say which rule it broke rather than just "it does not compile" — the rubric for this style of question pays for the explanation.

Lecture Summary
  • A class can contain functions as well as data. Functions that belong to a class are class methods (member functions). They are called with the dot operator, bpt.print(), and inside the body the bare data-member names mean this object's data.
  • A method that does not change the object should be tagged const, written after the parameter list: void print() const. Accessors are const; mutators are not.
  • Break the promise inside the body and you get "assignment of member ... in read-only object". Call a non-const method through a const object or reference and you get "discards qualifiers".
  • Accessor ("get") methods return data members; mutator ("set" or "put") methods change them. They are only meaningful once the data is private.
  • public members are reachable from anywhere; private members are reachable inside the class only. Both data and methods can be either. Outside code that touches a private member gets 'double Point1::x' is private within this context at compile time.
  • That one keyword is what makes encapsulation real: it lets the class enforce invariants and lets you change the representation without touching a single caller.
  • A pointer to an object works exactly like any other pointer. new Point allocates one object; delete p releases it. One new, one delete.
  • The arrow operator -> is "pointer member of": p->print() is identical to (*p).print(). Use . when the left-hand thing is an object or a reference, -> when it is a pointer.
  • A method can be declared in the class and defined outside it with the scope-resolution operator: void Point2::print() const { ... }. The const must appear in both places.
  • That split lets the class declaration live in a header file and the bodies in a .cpp file, so editing one body recompiles one file instead of the whole project.
  • None of these classes has a constructor yet, so every object is born with indeterminate data and must be set before it is read.
