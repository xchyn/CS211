1.base = derived; compiles — and that is the problem

Classes 19 and 20 built the machinery: class Square : public Rectangle, a base sub-object inside every derived object, base initializers, construction order, and the derived Big Three. Today we spend the whole hour on the consequences of one fact you already know — that a Square IS-A Rectangle — and the consequences turn out to be much stranger than the fact.

Start with a question that looks like it has an obvious answer. Given a Square and a Rectangle, does this compile?

Square s(3.0, true);
Rectangle r;
r = s;

It does. It compiles clean with -Wall, it runs, and it produces no warning of any kind. Which should immediately make you suspicious, because r is sixteen bytes and s is twenty-four. Three values are going into a container that has room for two. Something has to be thrown away, and C++ throws it away without telling you.

Definition— object slicing

Object slicing is what happens when a derived object is copied or assigned into a variable of a base type. Only the base part travels; the derived part is silently discarded. The compiler, in the professor's words, "slices off the non-Rectangle part of s and copies only its Rectangle part."

It is not an error and it is not a warning. It is a legal, well-defined operation that the language performs on purpose, and roughly half the time it is not what you meant.

Here is the base class and the derived class we are using for the whole page. They are exactly the ones from Class 20 — Rectangle with the Big Three added, and the completed Square — with print() changed only so that the two versions are easy to tell apart in a trace. Read it once; every program below includes it.

rectsquare.h
// rectsquare.h -- the Class 20 Rectangle and Square, instrumented.
#include <iostream>
#include <cmath>
using namespace std;

class Rectangle {
public:
    Rectangle() {
        h = 1.0;  w = 1.0;
        cout << "Rectangle: default constructor" << endl;
    }
    Rectangle(double ht, double wd) {
        h = ht;  w = wd;
        cout << "Rectangle: non-default constructor" << endl;
    }
    Rectangle(const Rectangle &orig) {
        h = orig.h;  w = orig.w;
        cout << "Rectangle: copy constructor" << endl;
    }
    Rectangle& operator=(const Rectangle &rhs) {
        if (this == &rhs) return *this;
        h = rhs.h;  w = rhs.w;
        cout << "Rectangle: assignment operator" << endl;
        return *this;
    }
    ~Rectangle() { cout << "Rectangle: destructor" << endl; }

    double height() const { return h; }
    double width()  const { return w; }
    double area()   const { return fabs(h * w); }

    void print() const {
        cout << "Rectangle::print  h = " << h << ", w = " << w << endl;
    }
protected:
    double h, w;
};

class Square : public Rectangle {
public:
    Square() : Rectangle() {
        centered = false;
        cout << "Square: default constructor" << endl;
    }
    Square(double e, bool c) : Rectangle(e, e) {
        centered = c;
        cout << "Square: non-default constructor" << endl;
    }
    Square(const Square &orig) : Rectangle(orig) {
        centered = orig.centered;
        cout << "Square: copy constructor" << endl;
    }
    Square& operator=(const Square &rhs) {
        if (this == &rhs) return *this;
        Rectangle::operator=(rhs);
        centered = rhs.centered;
        cout << "Square: assignment operator" << endl;
        return *this;
    }
    ~Square() { cout << "Square: destructor" << endl; }

    double edge() const { return height(); }

    void print() const {
        cout << "Square::print     edge = " << edge()
             << ", centered = " << (centered ? "true" : "false") << endl;
    }
protected:
    bool centered;
};

r = s; produced one line, not three, not two. Here is the whole story of that one statement:

QuestionAnswer
What is the declared type of the left-hand side?Rectangle. That is the only thing the compiler looks at.
Which operator= is a candidate?Only Rectangle::operator=(const Rectangle &). Square::operator= is not a member of Rectangle, so it is not even considered.
Does the argument fit?Yes. s is a Square, a Square IS-A Rectangle, so the const Rectangle & parameter binds to the Rectangle sub-object living inside s.
What gets copied?Exactly what Rectangle::operator= copies: h and w. Literally r.h = s.h; r.w = s.w;
What happens to s.centered?Nothing. Rectangle::operator= has never heard of centered — it was compiled before Square existed. The value is not copied, not converted, not stored anywhere. It is simply not part of the operation.

Notice what did not appear in the output: there is no Square: assignment operator line. Square::operator= was never called. Students often expect to see both lines, reasoning "well, it is a Square, so its assignment operator must run". It does not, because the choice of operator is made from the type on the left, and the left is a plain Rectangle.

And the destructor lines at the bottom confirm that nothing has changed about s itself. s is still a whole Square — slicing copied out of it, it did not damage it. r is destroyed first (one line, it is a lone Rectangle), then s (two lines, derived then base).

Key Idea

In r = s; the compiler picks the assignment operator from the declared type of the left-hand side. When that type is the base class, the base class's operator= runs, it copies the base members and only the base members, and the derived data is gone. The derived class's operator= never gets a chance to object.

Quick Check 21.1

Using the Rectangle and Square above:

(a) After r = s;, what is the value of r.area(), and why is that number correct even though r lost half of s?

9. area() is fabs(h * w), and both h and w are base members, so both were copied. The slice removed centered, which area() never used.

This is worth dwelling on: slicing does not produce garbage. It produces a perfectly valid, perfectly consistent base object. That is exactly why it is so easy to miss — nothing crashes, no number is wrong, information simply vanishes.

(b) A student adds cout << r.edge(); right after r = s; to check that the edge survived. What happens?

It does not compile. edge() is a member of Square, and r is a Rectangle:

error: 'class Rectangle' has no member named 'edge'

Which is the language being consistent. r is not a Square and never was, so the Square interface is not available on it. If you want the edge you have to ask the object that still has one — s.edge().

(c) Suppose Rectangle had no user-written operator= at all. Would r = s; still compile, and would it still slice?

Yes to both. With no operator= written, the compiler generates one for Rectangle — the member-wise assignment of h and w — and that generated operator has exactly the same signature, Rectangle& operator=(const Rectangle &). So it is still selected, and it still copies only the base members.

Slicing is not something the Big Three cause. It is a property of the type system. Writing your own operator= only makes it visible, because your version prints.

2.The other two ways to slice: copying and passing by value

Assignment is the version everybody meets first, but it is not the dangerous one — at least r = s; is a line you wrote on purpose. The copy constructor slices too, and it does it in places where there is no = sign anywhere in sight.

Procedure— the three places slicing happens
  1. Assignment to a base variable: r = s; → the base operator= runs.
  2. Copy construction of a base object from a derived one: Rectangle r_copy(s); or the equivalent Rectangle r_copy = s; → the base copy constructor runs.
  3. Passing or returning by value where the parameter or return type is the base class: void display_rectangle(Rectangle r) called with a Square → the base copy constructor runs on the way in. This is case 2 in disguise, and it is the one that bites, because the copy is invisible at the call site.

Storing into a container of base objects — vector<Rectangle> — is case 3 again: push_back takes its argument and copy-constructs a Rectangle into the vector.

The reason the pass-by-value case is worse than the assignment case is that the call site looks identical either way. display_rectangle(s); and display_square(s); are the same seven characters of argument. Nothing at the point of the call tells you that one of them is about to throw away half the object. You have to go read the function's signature.

Common Mistake— a container of base objects

This is the shape the bug usually takes in real code. You have a Rectangle base and several derived shape classes, and you want to keep them all in one list, so you write

vector<Rectangle> shapes;
shapes.push_back(mySquare);      // slices

Every element of a vector<Rectangle> is a Rectangle and nothing more — the vector allocated sizeof(Rectangle) bytes per slot. push_back copy-constructs a Rectangle from your argument, so the derived half never makes it in. The compiler is silent because, again, it is a legal conversion.

The fix is to store pointers: vector<Rectangle *>. A pointer is the same size whatever it points at, so nothing is truncated. We start using base pointers in §4, and Class 24 supplies the missing half of the answer — the part that makes the pointers actually call the derived methods.

(c) The sizes printed are 16 and 24. Where did those numbers come from, and what does the difference tell you?

A Rectangle is two doubles: 8 + 8 = 16. A Square is a Rectangle sub-object plus a bool: 16 + 1 = 17, rounded up to 24 so that the object's double members stay eight-byte aligned in an array. (Padding is a compiler detail; the 16 and the "bigger than 16" are the parts that matter.)

The difference is the slice. Eight bytes of the Square — the bool and its padding — have nowhere to go in a 16-byte destination.

3.Why the converse does not work

If a Square goes into a Rectangle, does a Rectangle go into a Square? No, and this time the compiler does say so. The professor's slide shows the two failing lines but the error text was lost from the extraction, so here they are, really compiled.

slice_converse_bad.cpp

#include "rectsquare.h"

int main() {
    Rectangle r(2.0, 5.0);
    Square s(3.0, true);

    Square s_copy(r);   // no matching constructor
    s = r;              // no matching operator=

}

Read the notes rather than the errors — they are where the reasoning is. g++ lists every Square constructor as a candidate and rejects each one. The interesting rejection is "no known conversion for argument 1 from Rectangle to const Square&". The conversion from derived to base exists automatically, because the base part is physically there. The conversion from base to derived does not exist, and could not, because the derived part is not there to be found.

Key Idea— conversion runs one way only

Derived → base is automatic and lossy. Base → derived is impossible.

The professor states the reason directly: "the compiler does not automatically know how to construct the Square part of s_copy", and "the compiler does not know what to do to assign the data in the Square part of s." There is no value of centered anywhere in a Rectangle to copy, and C++ will not invent one for you.

You can make it work, if the conversion is genuinely meaningful, by giving Square a constructor that takes a Rectangle and supplies the missing information yourself — Square(const Rectangle &r) : Rectangle(r) { centered = false; }. But now it is your decision, written in your code, that a converted rectangle is not centered. That is the difference: the one-way conversion is free because it throws information away, and the reverse costs you a design decision because it has to make information up.

4.Base pointers and base references to derived objects

Slicing came from copying a derived object into a base-sized box. The obvious escape is not to copy it at all — keep the object where it is and refer to it. Class 20 already used this without naming it: the derived copy constructor passes a whole Square to a const Rectangle & parameter, and that works because the reference binds to the base sub-object. Now we use it directly.

Definition— base pointer, base reference

The professor states the rule in four parts:

  1. "In general, a reference to the base class can bind to an object of a derived class."
  2. "The reference binds to the implicit base class object in the derived class object."
  3. "A pointer to the base class can point to the address of an object of a derived class."
  4. "The pointer points to the address of the implicit base class object in the derived class object."

Both are direct consequences of IS-A. No copy is made and no cast is needed — you simply write it:

Square s(3.0, true);
Rectangle &r_ref = s;      // legal
Rectangle *r_ptr = &s;     // legal
Worked Example— one object, three names

(a) Square s(3.0, true); Rectangle *p = &s;

Compiles. p holds the address of the Rectangle sub-object inside s, which for single inheritance is the same address as s itself. No copy, no slice.

(b) Rectangle r; Rectangle &ref = r; Square *p = &ref;

Does not compile. &ref has type Rectangle *, and error: invalid conversion from 'Rectangle*' to 'Square*'. Going through a reference changes nothing — a reference is just another name for the object, and the object is a plain Rectangle.

(c) Square s(3.0, true); Rectangle r = *(&s);

Compiles — and slices. &s is a Square *, * gives you back the Square, and initializing a Rectangle from it calls Rectangle's copy constructor. One line of output, Rectangle: copy constructor, and centered is gone.

The lesson: pointers and references dodge slicing only as long as you keep working through them. The moment you dereference into a base-typed variable, you are back to §2.

(d) Function void f(Rectangle *p); called as f(&s); with s a Square. Anything sliced?

Nothing is sliced. What gets copied into the parameter is the pointer — eight bytes — not the object. The Square stays exactly where it is, whole. This, plus the const Rectangle & form from Quick Check 21.3, is how you write functions that take "any kind of rectangle" without losing data.

What f can do with that pointer is the subject of the next section, and the answer is less than you want.

5.What runs when you call through a base pointer

You now have a way to refer to a Square without copying it. The natural next step is to use it: write one function, or one loop, that handles rectangles and squares alike. Let's find out how far that gets.

That one is defensible. The compiler is looking at a Rectangle *, and it has to be able to check the call without knowing what the pointer will hold at run time — the same pointer might be pointing at a plain Rectangle on the next line. So the rule is: through a Rectangle * you may call Rectangle's members, and only those. Adding a member in a derived class does not add it to the base's interface.

Procedure— how the compiler resolves p->f()
  1. Look at the declared type of p — here Rectangle *. Not at what p currently holds; the compiler does not run your program.
  2. Look for a member named f in that class, then in its base classes, walking up. Take the first match.
  3. No match anywhere in that chain? Compile error, as above.
  4. A match? Emit a call to that function. The decision is now frozen into the executable and cannot change while the program runs.

This is exactly the resolution procedure from Class 19, and it is called static binding for the reason step 4 gives — it is settled statically, before the program starts.

Quick Check 21.6

A classmate looks at the loop above and says: "the objects got sliced when we put them in the array — that is why Rectangle::print runs." Explain, with evidence from the output, why that diagnosis is wrong, and give the right one.

The right diagnosis. The distinction matters practically: a slicing bug is fixed by changing how you store the object (use a pointer or a reference), a static-binding bug is fixed by changing how you declare the method (add virtual). Diagnose the wrong one and you will make the wrong change.

Rectangle as written has a non-virtual destructor, so Rectangle *p = new Square(...); delete p; is undefined behavior. When the derived class owns memory, the practical effect is a guaranteed leak — the derived destructor holds the delete [] and it never runs. Practice Problem 5 measures one: 400 bytes, gone.

It costs one keyword — virtual ~Rectangle() { ... } — and it makes delete p; call the derived destructor first and then the base one, exactly as the stack version does.

Until Class 24 gives you that keyword, the safe rule is narrower: do not delete a derived object through a base pointer. Delete it through a pointer of its own type, or let it be an ordinary local object and let scope do the work.

7.Non-public inheritance

Everything so far — and everything in Classes 19 and 20 — used class Square : public Rectangle. The public there is a choice, and it is not the only one.

Definition— the three kinds of inheritance

"There are actually three types of inheritance: public, private and protected."

class B1 : public A    { /* ... */ };
class B2 : private A   { /* ... */ };
class B3 : protected A { /* ... */ };

The keyword does not change what is inherited — B2 and B3 still physically contain an A sub-object with all of its members. It changes how accessible those inherited members are to everybody else.

  • public: the base's public members stay public in the derived class, its protected members stay protected.
  • protected: "the public and protected members of the base class become protected members of the derived class."
  • private: "all public and protected members of the base class become private members of the derived class."

In every case, the base's private members remain inaccessible — private was an absolute lock-out in Class 19 and it stays one here. And in every case the derived class's own methods can use whatever the base gave it; the restriction is on what leaks further out.

The whole rule fits in one table. Find the base member's access down the side and the inheritance keyword across the top; the cell is the access that member has as seen from inside the derived class and from everyone the derived class talks to.

Access in the base : public A : protected A : private A
public public in the derived class protected private
protected protected protected private
private inaccessible in all three — only the base's own methods and friends may touch it

Read the middle column and the right column and you will notice the pattern: the inheritance keyword acts as a ceiling. Nothing comes out of the base with more access than the keyword allows. public inheritance raises no ceiling at all, which is why it is the one that preserves the class's interface.

8.Multiple inheritance

"A C++ class can inherit from more than one base class. This is called multiple inheritance. What we have studied up to now is called single inheritance."

Definition— multiple inheritance

List the bases, separated by commas, each with its own access specifier:

class B12 : public A1, public A2 {
    // ...
};

A B12 object contains an A1 sub-object and an A2 sub-object, in the order the bases are listed. A B12 IS-A A1 and also IS-A A2, so both A1 *p1 = &b; and A2 *p2 = &b; are legal.

Construction order extends the Class 20 rule in the obvious way: base classes in the order they are listed in the base clause, then the derived class's own members in declaration order, then the constructor body. Destruction is the exact reverse.

Common Mistake— the access specifier does not distribute

The course notes write the declaration as class B12 : public A1, A2;. Two things are wrong with it. The trailing semicolon makes it a forward declaration, which may not carry a base list (Class 20 covered that error). And — the subtle one — public applies only to A1. A2 has no specifier of its own, and for a class the default is private.

So class B12 : public A1, A2 privately inherits A2, which quietly contradicts everything the notes then say about a B12 being both an A1 and an A2. Really compiling it:

Quick Check 21.10

class B12 : public A1, public A2 where A1 and A2 both define void f1() const and A1 alone defines void only1() const.

(a) B12 does not override anything. Which of b.only1(); and b.f1(); compile?

b.only1(); compiles — the name appears in exactly one base, so lookup finds one candidate. b.f1(); does not: error: request for member 'f1' is ambiguous, with both candidates listed as notes.

An ambiguity is per-name, not per-class. Sharing a base clause does not poison every inherited member.

(b) Without adding anything to B12, write a line in main that calls A2's version.

b.A2::f1();

The scope-resolution operator names the exact function, so there is nothing left to resolve. This is the same mechanism as Rectangle::print() from Class 20 — there it reached past an override, here it picks between two bases.

It works, but writing it at every call site is miserable. Overriding f1() in B12 fixes the problem once, for everyone.

(c) B12 b; prints A1: constructor, A2: constructor, B12: constructor. What single change to B12's declaration makes the first two lines swap?

Reverse the base clause: class B12 : public A2, public A1. Bases are constructed in the order they are listed there.

And, as in Class 20, the member initializer list does not control the order. Writing B12() : A2(), A1() { } with the original base clause still constructs A1 first, and -Wreorder will tell you the list is misleading.

The diamond

The ambiguity above came from two unrelated bases that happened to share a name. The harder case is when the two bases are related — when they share a base of their own.

Take the professor's tree: a base A with two derived classes B and E, and now a class BE that inherits from both. The extraction lost the diagram, so here is the structure written out. Read each row as "contains":

ClassIts base classesSub-objects inside one object of this class
A—one A
Bpublic Aone A, plus B's own members
Epublic Aone A, plus E's own members
BEpublic B, public Ea whole B (which contains an A) and a whole E (which contains a different A), plus BE's own members — two A sub-objects in total

The professor's chain of reasoning, step by step: B IS-A A, so it contains an A object. E IS-A A, so it contains an A object. BE IS-A B and also IS-A E, so it contains both a B object and an E object. "However, both of those B and E objects contain their own A objects, and the A objects in B and E are not the same. Hence BE contains two copies of A objects."

Warning— two corrections to the course notes

The notes say it is "undefined which of the A objects should be used". "Undefined" is a loaded word in C++ — undefined behavior means the compiler owes you nothing and anything may happen at run time. That is not this. This is ambiguous, and ambiguity is diagnosed: the program does not compile, and g++ tells you exactly which candidates it could not choose between. Ambiguity is a compile-time problem with a compile-time message.

The notes also say "multiple inheritance is such a bad feature that it is not supported in the Java language." That is true only of classes. Java classes have exactly one superclass, but a Java class may implement any number of interfaces, and since Java 8 those interfaces may carry default method implementations — which is multiple inheritance of behavior, with rules for resolving conflicts. The accurate statement: Java allows single inheritance of classes and multiple inheritance of interfaces.

Key Idea— there is a fix, and it has a name (added)

The professor mentions that "there is a mechanism to resolve the ambiguity so that the implicit A objects in the B and E components are the same object" but never names it. It is called virtual inheritance: write class B : virtual public A and class E : virtual public A, and a BE then contains exactly one shared A, so be.setTag(5) is unambiguous again.

This course does not use it and you will not be examined on it — it is mentioned only so that you have the search term. It brings its own rules (the most-derived class becomes responsible for constructing the shared base), which is a good hint about how much complexity multiple inheritance is hiding.

Which brings us to the professor's verdict, which is worth quoting because it is also the professional consensus: "in general multiple inheritance leads to a mess." Use single inheritance. If you genuinely need to combine two capabilities, prefer composition — a data member of each type — which is HAS-A, has no ambiguity rules, and does not care what the two classes call their members.

Problem 4 — Trace BookShelf and Library (from the Summer 2025 Final)

BookShelf owns a dynamic array: protected: string *titles; int count;. It has a default constructor (empty shelf), a non-default constructor taking const string arr[] and a count, a deep-copy copy constructor, an operator=, a destructor that delete []s the array, and a display(). Each special member prints its message as its first instruction. Library inherits publicly from BookShelf, adds a string name, and prints name + ": non-default constructor" and name + ": destructor"; its print() is display() with the library's name in place of "BookShelf".

What is the output? There are ten lines.

int main() {
    string genres[4] = {"sci-fi", "romance", "thriller", "comedy"};
    BookShelf shelf;
    shelf.display();
    Library mainLib("Downtown", genres, 4);
    mainLib.print();
    shelf = mainLib;
    shelf.display();
    return 0;
}

Plan. Same shape as Problem 3, with two extra things to watch. First, the messages come first in this family, not last — but for constructors that changes nothing about which line comes first overall, because the base is fully constructed before the derived body starts. Second, this base owns memory, so shelf = mainLib; is not just a cosmetic slice: BookShelf::operator= deletes shelf's old array and deep-copies the four titles out of mainLib's base part. The titles survive the slice; the name does not.

Problem 5 — The destructor that never ran (added)

Shelf is a base class with a constructor and destructor that print. Library derives from it publicly and allocates new int[count] in its constructor, releasing it in its destructor. Neither destructor is virtual.

Write the two classes and a main that creates a Library on the heap twice — once through a Library * and once through a Shelf * — and deletes each. Predict the output, then explain precisely what the difference costs.

Plan. The only difference between the two halves is the declared type of the pointer that delete is applied to. Since ~Shelf is not virtual, delete is resolved statically: through a Library * it calls Library::~Library and then, automatically, Shelf::~Shelf; through a Shelf * it calls Shelf::~Shelf and stops. Library's delete [] lives in the destructor that gets skipped, so the array is leaked. Make the allocation large enough to be obvious — 100 ints, 400 bytes — and confirm with valgrind rather than by eye.

Problem 6 — Fix the shape list (added)

A student wants to keep a mixed collection of Rectangles and Squares and print them all in one loop. Their first attempt is:

vector<Rectangle> shapes;
shapes.push_back(Rectangle(2.0, 5.0));
shapes.push_back(Square(3.0, true));
for (unsigned i = 0; i < shapes.size(); i++)
    shapes[i].print();

Every line prints Rectangle::print, including the square's. Diagnose the two separate problems in this code, fix the one that is fixable today, and say plainly which one is not.

Plan. There are two independent failures stacked on top of each other, and it matters that you can name them apart.

  1. Slicing. A vector<Rectangle> element is a Rectangle. push_back copy-constructs one from the Square, so centered never reaches the vector. This is data loss and it is fixable now: store Rectangle * instead, so the objects stay where they are and only addresses go into the container.
  2. Static binding. Even after the fix, shapes[i]->print() resolves from the declared type Rectangle * and calls Rectangle::print. This one is not fixable with anything on this page — it needs virtual, in Class 24.

So the honest fix today is: stop losing the data, and prove the data is still there by reaching it deliberately. The loop still prints the base version, and that is the point of the exercise.

Lecture Summary
  • Object slicing: assigning or copying a derived object into a base-typed variable copies the base part and silently discards the derived part. r = s; runs Rectangle::operator= and prints one line, not two — the operator is chosen from the declared type of the destination.
  • Slicing happens in three places: assignment to a base object, copy-construction of a base object, and passing or returning by value where the type is the base. A vector<Base> is the third case in disguise.
  • It compiles clean with -Wall, produces a perfectly valid base object, and never touches the source object. That is exactly what makes it hard to spot.
  • The converse never compiles. Square s_copy(r); gives no matching function for call to 'Square::Square(Rectangle&)' and s = r; gives no match for 'operator='. Derived-to-base is automatic and lossy; base-to-derived is impossible.
  • A base reference binds to a derived object and a base pointer holds its address — both are consequences of IS-A, both bind to the implicit base sub-object, and neither copies anything. That is how you pass a derived object around without slicing it.
  • Through a base handle you get the base class's interface only. edge() is not reachable through a Rectangle *, and an overridden method resolves to the base version — static binding, decided at compile time from the declared type.
  • So slicing loses the data and base pointers lose the behavior. virtual, in Class 24, fixes the second one.
  • delete through a base pointer with a non-virtual destructor is undefined behavior. The derived destructor never runs; if the derived class owns memory, it leaks — measurably. Until Class 24, delete through a pointer of the object's own type.
  • Non-public inheritance caps the access of every inherited member: protected inheritance makes the base's public members protected, private inheritance makes them private. From inside the derived class nothing changes; from outside, the IS-A conversion disappears, which is why the course — and almost all real code — writes public.
  • Multiple inheritance lists several bases: class B12 : public A1, public A2. Write the access keyword on every base — it does not distribute. Bases are constructed in base-clause order and destroyed in reverse.
  • When two bases declare the same name, an unqualified call is a compile error — request for member 'f1' is ambiguous — not a warning. Resolve it by overriding the method in the derived class, or at the call site with b.A1::f1().
  • In the diamond (BE from B and E, both from A), a BE contains two A sub-objects with independent state, and any unqualified access to an inherited A member is ambiguous. The mechanism that merges them is called virtual inheritance; this course does not use it. Prefer single inheritance and composition.
