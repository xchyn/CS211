1.What Exam 2 actually looks like

Nothing on this page is new material. Every definition, every code listing and every rule below appeared in Classes 13 to 21. What is new is the arrangement: today we organize the last nine classes the way the exam organizes them, which is not the way the lectures did.

Warning— this paper is cumulative

The syllabus is explicit: every exam in this course may draw on all the material up to the day it is given. Exam 2 concentrates on Classes 13–21, and most of the points will be there — but Classes 1–10 are not off the table, and in practice they are not really separable anyway.

Look at what the headline question actually requires. Writing the Big Three for a class that owns memory is impossible without Class 8: you cannot write a deep copy without new and delete, a destructor without knowing what a leak is, or a self-assignment guard without understanding what two pointers aiming at one buffer means. Classes 9 and 10 supply the class syntax that all of it is written in.

So the honest revision advice is not "go back and redo Exam 1." It is: if any of pointers, new/delete, or private data with public methods is still shaky, fix that first, because it is load-bearing for everything on this page. Class 11 has the drills if you need them.

Start with the shape of the paper, because it changes how you should spend the next few days. Exam 2 is a 50-minute, closed-book, 40-point paper. The last time this course ran in the same shape — Fall 2023 — the cover sheet said "4 questions out of 40 points" but the body was really three blocks:

Definition— title line

The professor's word for the declaration part of a function or class: the return type, the name, the parameter list, and (for a class) the base-class clause. This is the one piece of exam vocabulary on this page that is not C++ — it is grading vocabulary. His rubrics say things like "2 points for each title line and 2 points for implementation", which means the marks are split roughly one-third signature, two-thirds body.

How to spend fifty minutes

Procedure— a 50-minute plan for a 40-point paper
  1. Minute 0–2. Read all four problems. Find the special-members question — it is worth half the paper.
  2. Minute 2–5. On the special-members question, write every title line first, all four or five of them, with nothing underneath. You have now banked 8–10 points in three minutes.
  3. Minute 5–22. Fill in the bodies, in this order: destructor (easiest), copy constructor, operator=, operator+ (hardest).
  4. Minute 22–34. Do the derived-class problem. Its title line, its }; and its protected:/public: labels are all separately worth points.
  5. Minute 34–47. Do the trace. Write one line of output per line, in order, then re-read your own class implementation to check every announcement message matches.
  6. Minute 47–50. Count destructor lines. One per object that was ever constructed, temporaries included. This is the single most common place to drop points.

2.The Big Five, written out once

This is the most important section on the page. Everything here is a compression of Classes 13, 14, 15 and 17; nothing is new. What is new is that it is all in one place, on one class, so you can memorize it as a single block of text rather than four separate lectures.

Definition— the Big Three, and the Big Five on an exam

The Big Three (Class 15) are the destructor, the copy constructor and the assignment operator. The rule is: if a class needs one of them it needs all three, and a class needs them exactly when it owns a resource — in this course, memory from new or new[].

On this professor's exams the Big Three arrive with two companions: a non-default constructor and a binary operator+ (sometimes operator*). Those five together are what the question always asks for, so those five are what you rehearse. We will call them the Big Five for the rest of this page. That name is a study label, not standard C++ terminology.

Definition— deep copy

A shallow copy copies the pointer; a deep copy allocates fresh memory in the destination and copies the contents. The compiler-generated copy constructor and assignment operator are always shallow, which is why writing your own is the whole point of the question.

Four points worth pausing on, because each one is a place students lose marks:

  • BookShelf s3 = s1; prints "copy constructor", not "assignment operation". s3 is being created, so the = is initialization syntax, not assignment (Class 15). Only the later s3 = s2;, where s3 already exists, calls operator=.
  • The self-assignment s3 = s3; still prints its announcement line. The message is the first statement, so it runs before the guard returns. The guard prevents the damage, not the printing.
  • operator+ prints two lines, its own and then "non-default constructor", because it builds its result with the non-default constructor. Traces routinely lose a point here.
  • Four destructor lines, not five. Four named objects exist: s1, s2, s3, s4. The result inside operator+ was elided — the compiler built it directly into s4 rather than copying it out — so there is no fifth object and no extra destructor.
Procedure— writing the Big Five under pressure

Do it in this order every time. The order is chosen so that each step reuses the previous one, which is what makes it reproducible when you are nervous.

  1. Non-default constructor. Announce, size, allocate, copy. No delete — there is nothing there yet. 
    BookShelf(const string arr[], int n) {
    cout << "BookShelf: non-default constructor" << endl;
    count = n;
    titles = new string[count];
    for (int i = 0; i < count; i++) titles[i] = arr[i];
}
  2. Destructor. Announce, release. No parameters, no return type, one delete [] for every new[] in the class. 
    ~BookShelf() {
    cout << "BookShelf: destructor" << endl;
    delete [] titles;
}
  3. Copy constructor. It is the non-default constructor with orig as the source instead of a parameter array. Same four steps, and the parameter is const BookShelf &orig. 
    BookShelf(const BookShelf &orig) {
    cout << "BookShelf: copy constructor" << endl;
    count = orig.count;
    titles = new string[count];
    for (int i = 0; i < count; i++) titles[i] = orig.titles[i];
}
  4. operator=. It is the copy constructor plus three lines: a guard at the top, a release before reallocating, and a return *this; at the bottom. Return type BookShelf&. 
    BookShelf& operator=(const BookShelf &rhs) {
    cout << "BookShelf: assignment operation" << endl;
    if (this == &rhs) return *this;     // guard
    delete [] titles;                   // release
    count = rhs.count;
    titles = new string[count];
    for (int i = 0; i < count; i++) titles[i] = rhs.titles[i];
    return *this;                       // chaining
}
  5. operator+. Announce, build the combined raw data, hand it to a constructor, clean up the scratch, return by value. 
    BookShelf operator+(const BookShelf &other) {
    cout << "BookShelf: operator+" << endl;
    int n = count + other.count;
    string *temp = new string[n];
    for (int i = 0; i < count; i++) temp[i] = titles[i];
    for (int i = 0; i < other.count; i++) temp[count + i] = other.titles[i];
    BookShelf result(temp, n);
    delete [] temp;
    return result;
}
Key Idea— the four lines rubrics single out

Past rubrics for this question award separate, named points for these. Write them even if the rest of your body is shaky:

  1. The title line of each member — 1 to 2 points each, every time.
  2. if (this == &rhs) return *this; — the self-assignment guard, its own point.
  3. delete [] titles; before reallocating inside operator= — its own point.
  4. return *this; at the end of operator= — its own point.

Worked Example— the cost of a missing copy constructor

s2 is copy-constructed from s1, then s2 renames its first title. Predict both printed lines, and predict what happens at return 0;.

and then the program dies. Run under valgrind the diagnosis is unambiguous:

Invalid free() / delete / delete[] / realloc()
   Address 0x4e26080 is 0 bytes inside a block of size 72 free'd

Two separate failures from one missing function:

  • Aliasing. Renaming through s2 changed s1 too, because both objects hold the same titles pointer. s1 never asked to be modified.
  • Double free. s2 is destroyed, delete [] titles; runs; s1 is destroyed, the same delete [] runs on the same address. That is the crash.

The compiler-generated copy is not "broken" — it does exactly what it promises, which is to copy each data member. Copying a pointer copies the address, not the array. That is the whole argument for the Big Three in one sentence.

Quick Check 22.2

A student hands in this operator= for the BookShelf class. It compiles. Find every defect that a rubric would deduct for.

BookShelf operator=(BookShelf rhs) {
    cout << "BookShelf: assignment operation" << endl;
    count = rhs.count;
    titles = new string[count];
    for (int i = 0; i < count; i++) titles[i] = rhs.titles[i];
}

Five defects, four of which are individually named in past rubrics:

  1. Return type is BookShelf, not BookShelf&. Returning by value copies the object on every assignment and breaks the intent of chaining. Title-line points lost.
  2. Parameter is by value, not const BookShelf &rhs. Every assignment now copy-constructs an extra object — which, in a trace question, prints an extra "copy constructor" line and destroys your answer. Title-line points lost.
  3. No self-assignment guard. if (this == &rhs) return *this; is missing. Its own point, every time.
  4. No delete [] titles; before reallocating. The old array is abandoned — a leak on every assignment. Its own point.
  5. No return *this;. The function claims to return something and returns nothing; with a non-void return type this is undefined behavior, and g++ warns under -Wall. Its own point.

Corrected:

BookShelf& operator=(const BookShelf &rhs) {
    cout << "BookShelf: assignment operation" << endl;
    if (this == &rhs) return *this;
    delete [] titles;
    count = rhs.count;
    titles = new string[count];
    for (int i = 0; i < count; i++) titles[i] = rhs.titles[i];
    return *this;
}

Common Mistake— "first instruction" or "last instruction"?

Every version of this question tells you where the announcement message goes, and the wording changes between terms. Fall 2023 and all three midterms say the message is the first instruction. The Summer 2024 and Winter 2025 finals say last. Summer 2025 went back to first.

It matters, because it flips the body of the destructor:

// "prints ... as its FIRST instruction"        // "prints ... as its LAST instruction"
~BookShelf() {                                  ~BookShelf() {
    cout << "BookShelf: destructor" << endl;        delete [] titles;
    delete [] titles;                               cout << "BookShelf: destructor" << endl;
}                                               }

Underline the words "first instruction" or "last instruction" in the question before you write anything. The trace question that follows it is graded against your choice.

3.Reading a constructor/destructor trace

The special-members question almost always has a twin immediately after it: "Assuming your X class is correctly implemented and prints the corresponding messages, what will be the output of the following main program?" It is worth 10–15 points, one point per printed line, and it has no partial credit per line — you either produce that line, in that position, or you do not.

It is really a reading-comprehension exercise about six sentences of C++. There are only six things a line of main can do, and each maps to exactly one announcement.

Procedure— converting a line of main into printed lines
What you seeWhat it callsLines printed
X a;default constructor"default constructor"
X b(1,2);non-default constructor"non-default constructor"
X c = b; or X c(b);copy constructor — c is being created"copy constructor"
a = b; (both already exist)operator="assignment operation"
X d = a + b;operator+, whose body constructs the result"operator+" then whichever constructor the body uses
b = a + c;operator+, then operator=, then the temporary dies"operator+", the result's constructor, "assignment operation", "destructor"
end of maindestructors, in reverse order of constructionone "destructor" per surviving object

Then the two rules that finish the job:

  1. Count the objects that were ever constructed, and make sure your answer has one destructor line for each one that is still alive at the end of the scope.
  2. A temporary returned from operator+ and then used to initialize a new object is normally elided — built directly in place, so no extra copy constructor and no extra destructor. A temporary returned and then assigned is a real object: it is destroyed at the end of the statement, which is where the extra "destructor" line in the middle of a trace comes from.
Worked Example— the 16-line trace, in full

This is a complete past question: the class, with all five members supplied, and the main that traces it. matrix_trace.cpp
#include <iostream>
using namespace std;

class Matrix {
public:
    Matrix() {
        cout << "default constructor" << endl;
        rows = new int;
        cols = new int;
    }
    Matrix(int r, int c) {
        cout << "non-default constructor" << endl;
        rows = new int; cols = new int;
        *rows = r; *cols = c;
    }
    ~Matrix() {
        cout << "destructor" << endl;
        delete rows; delete cols;
    }
    Matrix(const Matrix &orig) {
        cout << "copy constructor" << endl;
        rows = new int; cols = new int;
        *rows = *(orig.rows); *cols = *(orig.cols);
    }
    Matrix& operator=(const Matrix &rhs) {
        cout << "assignment operation" << endl;
        if (this == &rhs) return *this;
        delete rows; delete cols;

        *rows = *(rhs.rows); *cols = *(rhs.cols);
        return *this;

        cout << "operator*" << endl;
        int newRows = *rows;

4.Operator overloading: member or free, and what to return

Classes 17 and 18 covered a lot of ground: member operators, free operators, unary operators, stream operators, friend. For Exam 2 you need a much smaller subset than that, and it is worth knowing which subset, so you spend your revision time in the right place.

Definition— overloaded operator, restated

An overloaded operator is a function whose name is the keyword operator followed by an operator symbol. p1 + p2 is rewritten by the compiler as a call to operator+. Its inputs are called operands; two operands makes it binary, one makes it unary.

Written as a member function a binary operator takes one parameter — the left operand is the object itself, reachable as *this — and it can touch private data directly. Written as a free function it takes two parameters and must go through public accessors (or be a friend).

Key Idea— what is actually examined

In every past paper, the overloaded operator asked for is operator+, operator* or operator=, and it is always written as a member function. operator<< has never been asked for, and neither has friend. Drill the member form until it is automatic; know the free form well enough to recognize when it is forced on you.

6.Slicing, base pointers, and what each one loses

Class 21's two big results turn up on every final and are fair game on Exam 2. They are easy to state and easy to confuse, so here they are side by side.

Definition— object slicing

Assigning or copy-constructing a derived object into a base-typed variable copies the base part and silently discards the derived part. It compiles clean, produces a perfectly valid base object, and never touches the source. The operator that runs is chosen from the declared type of the destination, so shelf = mainLib; runs BookShelf::operator= and prints one line, not two.

Definition— static binding

The compiler decides which function a call refers to at compile time, from the declared type of the object or handle — not from what the object actually is at run time. Through a BookShelf * you get BookShelf's interface and BookShelf's method bodies, even when the pointer holds the address of a Library. Its opposite, dynamic binding, arrives with virtual in Class 24 — which is after this exam.

Look again at the trace in Section 5. The line shelf = mainLib; is a slice, and the output proves it: one line, "BookShelf: assignment operation", and then shelf.display() prints the four titles but nothing about "Downtown". The books survived because they live in the base part; the name did not, because it lives in the derived part. This exact pattern — baseObject = derivedObject; in the middle of a trace — appears on three of the four past finals.

Problem 1 — The Big Four on a dynamic-array class (from the Fall 2023 Exam 2, Problems 1 & 2)

[20 points · suggested 25 minutes] Given the following program with a Polynomial class:

#include <iostream>
using namespace std;

class Polynomial {
public:
    Polynomial(double c[], int d) {
        degree = d;
        coefficients = new double[degree+1];
        for (int i = degree; i >= 0; i--) { coefficients[i] = c[i]; }
    }
    void print() {

            cout << coefficients[i] << "*x^" << i << " + ";
        }
        cout << coefficients[0] << endl;
    }

    // destructor, copy constructor, assignment operation, and
    // operator+ overloading omitted here

    double *coefficients; int degree;
};

int main () {
    double a1[3] = {1.1, 2.2, 3.3}, a2[2] = {2, 1};

    p1.print();

}

(a) Give an implementation for the destructor. [3 points]

Plan. The class allocates with new double[degree+1], so the destructor releases with delete []. Nothing else: degree is a plain int and needs no cleanup.

~Polynomial() {
    delete [] coefficients;
}

Things to notice. The published point split was 1 point for the title line and 2 points for deleting the dynamic array. The title line is ~Polynomial() — a tilde, the class name, empty parentheses, and no return type. A destructor takes no parameters, ever, which is why a class has exactly one.

delete [], not delete. The array came from new[].

(b) Give an implementation for the copy constructor to do the deep copy. [4 points]

Plan. Four steps: take the size from orig, allocate a fresh array of that size, copy the elements one at a time, and never touch orig.

Polynomial(const Polynomial &orig) {
    degree = orig.degree;
    coefficients = new double[degree+1];
    for (int i = 0; i <= degree; i++) {
        coefficients[i] = orig.coefficients[i];
    }
}

Things to notice. The split was 1 point for the title line, 1 point for allocating, 2 points for copying the data.

  • The parameter is const Polynomial &orig — a const reference. Drop the & and the code does not compile at all.
  • The loop bound is i <= degree, not i < degree. A polynomial of degree d has d+1 coefficients, which is why the constructor allocates degree+1. Off-by-one here loses the constant term.
  • No delete anywhere. This object is being created; there is no old array to release. That is the one structural difference between the copy constructor and operator=.

(c) Give an implementation for the assignment operation. [6 points]

Plan. The copy constructor, plus the three things assignment needs and construction does not: guard against self-assignment, release the array this object already owns, and return *this.

Polynomial& operator=(const Polynomial &rhs) {
    if (this == &rhs) return *this;
    delete [] coefficients;
    degree = rhs.degree;
    coefficients = new double[degree+1];
    for (int i = 0; i <= degree; i++) {
        coefficients[i] = rhs.coefficients[i];
    }
    return *this;
}

Things to notice. This is the most explicitly itemized rubric in the whole bank: 1 point title line, 1 point checking self-assignment, 1 point deleting the dynamic array, 2 points assigning the data, 1 point return *this;. Four of those six points are single lines you can write from memory before you have thought about the class at all.

Order matters. The guard has to come before the delete [], because when rhs is *this the delete destroys the very data the copy loop is about to read.

(d) Give an implementation for operator+ overloading. [7 points]

Plan. The sum of two polynomials has the degree of the larger one. Build a scratch array of that size, add whichever coefficients exist at each index, hand the scratch array to the constructor, free the scratch, return the result by value.

polynomial_exam2.cpp
Polynomial operator+(const Polynomial &p) {
    int maxDegree = degree;
    if (maxDegree < p.degree) maxDegree = p.degree;

    double *newCoefficients = new double[maxDegree+1];
    for (int i = 0; i <= maxDegree; i++) {
        double coefficient = 0;
        if (i <= degree) {
            coefficient += coefficients[i];
        }
        if (i <= p.degree) {
            coefficient += p.coefficients[i];
        }
        newCoefficients[i] = coefficient;
    }

    Polynomial result(newCoefficients, maxDegree);
    delete [] newCoefficients;
    return result;
}

With all four members in place, the program in the stem compiles, runs and is leak-free:

3.3*x^2 + 2.2*x^1 + 1.1
1*x^1 + 2
3.3*x^2 + 3.2*x^1 + 3.1

Things to notice. Seven points, one each for: the title line, finding the larger degree, allocating the new array, computing the coefficients, constructing the result, deleting the scratch array, returning the result. Every one of those is a separate line you can tick off as you write.

  • The two if statements exist because the shorter polynomial has no coefficient at the high indices. Adding p.coefficients[i] unconditionally would read off the end of its array.
  • delete [] newCoefficients; before the return. The constructor copied the scratch array into result, so the scratch is nobody's data afterwards. Forget this line and every addition leaks — and it is a listed point.
  • Return type is Polynomial by value. Returning Polynomial& here would hand back a reference to result, which is destroyed the instant the function returns.
  • operator+ can reach p.coefficients even though it is protected, because a member function of a class may touch the private and protected members of any object of that same class, not just its own.

  • The answer key does not compile. Its operator= opens with if (this == &other) return *this; and its operator+ tests if (i <= other.degree), but the parameters are named rhs and p. There is no other anywhere. Written as printed, g++ says "'other' was not declared in this scope". Use the parameter names from your own signature — the corrected answers above are what compiles.
  • The class in the stem is missing its semicolon. It ends } and not };, immediately before int main. Your own answers must end };, and on the derived-class question that semicolon is separately worth a point.
  • The stem's comments do not match its own code. Things to notice. Three of these four defects are lines that a rubric lists individually — the guard, the release, the return *this;. Reading someone else's broken answer is the fastest way to find out whether your own checklist is actually memorized, because you cannot spot a missing line unless you know it should be there.

Notice also what the compiler did not catch. The shallow copy, the missing guard and the mismatched delete all compile silently with -Wall. On this exam nobody runs your code — but on this exam, the marker is looking for exactly those lines.

Lecture Summary
  • Exam 2 is 50 minutes and 40 points, entirely code. You either write C++ or say exactly what C++ prints. There is no true/false, no multiple choice and no definition to recite.
  • Half the paper is one question: implement the special members of a class that owns heap memory. Its companion — trace a main that exercises them — is the next largest. Rehearse those two until they are automatic and everything else is a bonus.
  • The Big Five, in order: non-default constructor (announce, size, allocate, copy); destructor (announce, release); copy constructor (the non-default constructor sourced from orig); operator= (the copy constructor plus guard, release and return *this;); operator+ (build the combined data, hand it to a constructor, free the scratch, return by value).
  • Write every title line first. Rubrics pay 1–4 points for a signature with no body. The guard if (this == &rhs) return *this;, the delete [] before reallocating, and return *this; are each separately worth a point.
  • X b = a; is the copy constructor; b = a; is operator=. The difference is whether the object on the left is being created. It changes the trace by a whole line.
  • Traces have two hidden lines: the constructor that runs inside operator+, and the destructor of the temporary when the operator's result is assigned rather than used to initialize.
  • Count destructor lines. One per object still alive at the closing brace, plus one for every temporary destroyed on the way. Output prediction carries no partial credit.
  • Derived classes: class D : public B {, a base initializer in the member initializer list, protected data in the base so the derived class can reach it, an override with an identical signature, and the closing }; — all of which are individually worth points.
  • Construction goes base, then members in declaration order, then the body; destruction is exactly the reverse.
  • Slicing loses the data; a base pointer loses the reach. base = derived; copies only the base part and runs the base's operator=. A base pointer keeps all the data but sees only the base interface, and delete through one skips the derived destructor.
  • static members, friend, operator<< and file I/O have never been examined in this course. Namespaces have been, exactly once, as an output trace — be able to read one.
