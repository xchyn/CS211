Static Members and Namespaces

One variable shared by every object instead of one per object — and the mechanism, promised back in Class 1, that keeps two people's identically named classes from colliding.

1.Why share data across every object?

Today is two short topics stitched into one class, and they are unrelated at first glance — one is about a keyword you put on a data member, the other is about organizing whole chunks of a program. What they share is a common shape: both exist to answer "who owns this, and how many copies of it should there be?" Keep that question in mind and both halves of today click into place.

Start with a class that has no business duplicating its data. Here is a Day class: it stores the names of the seven days of the week, plus a count, so that any object can look up "what is day number 3 called?"

day.cpp
#include <iostream>
#include <string>
using namespace std;

class Day {
public:
    Day() : numDays(7), day{"Sunday", "Monday", "Tuesday", "Wednesday",
                             "Thursday", "Friday", "Saturday"} {}

    int num() const { return numDays; }

    string getDayOfWeek(int n) const {
        if ((n < 0) || (n >= numDays)) { return string(""); }
        return day[n];
    }

private:
    int numDays;
    string day[7];
};

int main() {
    Day dw;
    for (int n = 0; n < dw.num(); ++n) {
        cout << dw.getDayOfWeek(n) << endl;
    }
    return 0;
}
Common Mistake— the professor's original slide will not compile

The version above is a repaired one. As printed in the course notes, the constructor reads:

Day() : numDays(7) {},
day({"Sunday","Monday","Tuesday","Wednesday","Thursday",
     "Friday","Saturday"}) {}

This does not compile, for two reasons at once. A member initializer list is one comma-separated sequence between the : and the single {} body — you cannot close the body early with {} in the middle and then keep listing members after a comma. And even fixed up, a C-style array member like string day[7] cannot be initialized with parentheses — day({...}) — only with braces. The corrected member initializer list is:

Day() : numDays(7), day{"Sunday", "Monday", "Tuesday", "Wednesday",
                         "Thursday", "Friday", "Saturday"} {}

Note the braces, not parentheses, around the day names, and no stray {} in the middle. This form needs C++11 or later (which is all we use in this course). Before C++11 there was no way to initialize an array member in the initializer list at all — you had to assign each element inside the constructor body, one line per day.

Now imagine a program that creates a thousand Day objects — one per employee shift record, say. Every single one of those thousand objects carries its own private copy of the same seven strings and the same number 7. Nothing about numDays or the day names is specific to any one object; every Day that will ever exist agrees on them completely. That is a thousand redundant copies of exactly the same eight values, for no benefit.

Key Idea

When a value is the same for every object of a class, giving each object its own copy is pure waste. What you want is one variable shared by the whole class — something that behaves like a global variable, except that it belongs to the class instead of floating loose in the program. That is exactly what static gives you.

Quick Check 16.1

Consider the Day class above.

(a) Which of Day's two data members is a genuinely bad candidate for per-object storage, and why?

Both of them, actually — numDays and day are both the same for every Day object that will ever be constructed. Neither depends on which particular object you are looking at. A data member earns its own per-object copy only when different objects are expected to hold different values; numDays and day fail that test completely.

(b) If you built 500 Day objects, roughly how much memory is wasted compared with a design where the day names and the count are stored once?

499 redundant copies of the whole string day[7] array plus the int numDays. Each object's copy is identical byte-for-byte to every other object's copy, so 499 out of 500 of them are pure duplication. The fix is not to make the array smaller — it is to make there be only one array, shared by every object. That is the static member you meet next.

2.Static data members and the out-of-class definition

Definition— static data member

A static data member is a data member that belongs to the class itself, not to any individual object. Every object of the class shares the exact same variable — change it through one object and every other object sees the new value, because there is only ever one copy of it, no matter how many objects exist (including zero). You tag it with the keyword static in the class declaration.

Here is Day rewritten as SDay ("static day"), with both data members made static:

sday.cpp
class SDay {
public:
    SDay() {}

    // static data -- declared here, defined outside the class
    static int numDays;
    static string day[7];
};

// non-inline initialization of static data members
int SDay::numDays = 7;
string SDay::day[7] = {"Sunday", "Monday", "Tuesday", "Wednesday",
                        "Thursday", "Friday", "Saturday"};

int main() {
    for (int n = 0; n < SDay::numDays; ++n) {   // static member "SDay::numDays"
        cout << SDay::day[n] << endl;           // static member "SDay::day[n]"
    }
    return 0;
}

Two things jump out. First, SDay's constructor does absolutely nothing — it does not initialize numDays or day. That is not an oversight. A constructor's job is to set up one particular object, and static data does not belong to any particular object; there is nothing per-object for the constructor to do. Second, main never creates an SDay object at all, yet reads SDay::numDays and SDay::day[n] perfectly well, using the class name and :: instead of an object and ..

Key Idea

A static data member is really a global variable that happens to be scoped inside a class. It exists independently of any object — even before the first object is ever constructed, and even if no object is ever constructed at all.

Now look at the two lines directly under the class:

int SDay::numDays = 7;
string SDay::day[7] = {"Sunday", "Monday", "Tuesday", "Wednesday",
                        "Thursday", "Friday", "Saturday"};

These are the out-of-class definitions, and they are not optional. Declaring static int numDays; inside the class only tells the compiler "this class has a static int member named numDays" — it does not create storage for it and does not give it a value. Somewhere, exactly once, a separate statement outside any class has to actually define the variable. Three rules govern that statement:

  1. It is written in a .cpp file, never in a header.
  2. It appears in exactly one .cpp file of the whole project.
  3. If it appeared in more than one file, the variable would be defined more than once, which the linker rejects.

The compiler will not write this statement for you the way it writes a default constructor. If you forget it, your program compiles cleanly — every use of SDay::numDays type-checks fine — and then fails at the very last step, linking, because the linker cannot find the storage the compiled code refers to.

Worked Example— the linker error you get for forgetting

Same class, same main, with the two out-of-class definitions deleted. Predict what happens when you try to build it — and specifically, at which stage (compiling or linking) it fails.

class SDay {

    static int numDays;
    static string day[7];
};

// the two definitions that belong here were left out on purpose

/usr/bin/ld: /tmp/ccxBYnFL.o: in function `main':
sday_nodef.cpp:(.text+0x24): undefined reference to `SDay::day[abi:cxx11]'
/usr/bin/ld: sday_nodef.cpp:(.text+0x55): undefined reference to `SDay::numDays'

Notice the message says "undefined reference", not "undefined variable" or a g++ compiler diagnostic with a line number in your source — that is the tell that you have crossed from compiling into linking. The compiler was completely satisfied: it saw the declaration static int numDays; and trusted that storage for it exists somewhere. Only the linker, which stitches together every compiled piece of the program and needs to find one real memory location per variable, discovers that no such location was ever created.

Quick Check 16.2

Suppose a project spans two files, sday.cpp and main.cpp, both of which #include "sday.h" (a header containing the SDay class declaration with its two static members).

(a) Where should the two out-of-class definitions, int SDay::numDays = 7; and the array definition, be written?

In exactly one of the .cpp files — conventionally sday.cpp, the source file that implements the class. Never in the header sday.h, because the header gets #included into every .cpp file that uses the class, and each inclusion would produce its own definition.

(b) What goes wrong if you put the definitions in the header instead?

Both sday.cpp and main.cpp #include the header, so both translation units end up with their own definition of SDay::numDays. When the linker tries to combine them it finds the same symbol defined twice and reports a multiple definition error — the mirror image of the "undefined reference" error above, and just as fatal.

3.Static member functions: no this, and private statics

Data members are not the only thing that can be static. A class's methods can be static too, and in practice they almost always are, because keeping the underlying data private and exposing it through public static methods is exactly the encapsulation habit you already use for ordinary objects.

Definition— static member function

A static member function is associated with the class, not with any individual object, and so — exactly like a static data member — can be called without an object in existence. You call it as ClassName::functionName(args).

psday.cpp
class PSDay {
public:
    PSDay() {}

    static int num() { return numDays; }              // public static method

    static string getDayOfWeek(int n) {                // public static method
        if ((n < 0) || (n >= numDays)) { return string(""); }
        return day[n];
    }

private:
    // static data
    static int numDays;
    static string day[7];
};

int PSDay::numDays = 7;
string PSDay::day[7] = {"Sunday", "Monday", "Tuesday", "Wednesday",
                         "Thursday", "Friday", "Saturday"};

int main() {
    for (int n = 0; n < PSDay::num(); ++n) {
        cout << PSDay::getDayOfWeek(n) << endl;
    }
    return 0;
}

Now the static data is private, exactly the way you would hide it in an ordinary class, and the only access is through the public static methods num() and getDayOfWeek(int). main never constructs a PSDay object — it calls PSDay::num() and PSDay::getDayOfWeek(n) directly on the class.

Static member functions come with two hard restrictions, and both trace back to the same fact: a static method has no associated object.

Common Mistake— a static method cannot be const

Tagging an ordinary method const is a promise "calling this will not modify the object it was called on." A static method has no object it was called on — there is no receiving object for the promise to be about — so the combination is meaningless, and g++ refuses it outright:

static int num() const { return numDays; }   // ERROR: static + const
static_const_bad.cpp:8:22: error: static member function 'static int PSDay::num()' cannot have cv-qualifier
    8 |     static int num() const { return numDays; }   // ERROR: static + const
      |                      ^~~~~
Common Mistake— a static method cannot touch a non-static member

Non-static data belongs to one particular object. A static method is not called on any particular object, so if it tried to read a non-static member, the compiler would have no way to know whose copy of that member you meant.

class PSDay {
public:
    PSDay() : label("weekday") {}

    static int num() {
        cout << label << endl;   // ERROR: static method touching a non-static member
        return numDays;
    }

private:
    static int numDays;
    string label;               // non-static
};
static_nonstatic_bad.cpp: In static member function 'static int PSDay::num()':
static_nonstatic_bad.cpp:10:17: error: invalid use of member 'PSDay::label' in static member function
   10 |         cout << label << endl;   // ERROR: static method touching a non-static member
      |                 ^~~~~
static_nonstatic_bad.cpp:16:12: note: declared here
   16 |     string label;               // non-static
      |            ^~~~~

A static member function is free to touch other static members — those exist with or without an object — but never a non-static one.

Quick Check 16.3

For each pair, say whether it is legal C++, and if not, why.

(a) A static method that calls another static method of the same class.

Legal. Both methods are class-level, associated with the class rather than an object, so one can freely call the other — there is no object involved on either side.

(b) A non-static (ordinary) method that reads a static data member.

Legal, and common. An ordinary method has both an object (through this) and access to the class's static members, so it can read (or write) either kind freely. The restriction only runs one direction: static code cannot see non-static data, but non-static code can always see static data.

(c) A static method that declares a local variable inside its own body and modifies it.

Legal. A local variable is not a data member at all — it lives on the stack for the duration of the call, exactly as in an ordinary free function. The static/non-static rule is only about class data members.

4.const static members, and why copying skips them

numDays and the array of day names are not just shared — they never change. That makes them a natural fit for const as well as static. And although a static method cannot be const (§3), a static data member can be, and should be whenever the value is a true constant.

cpsday.cpp
class CPSDay {
public:
    CPSDay() {}

    static int num() { return numDays; }

    static string getDayOfWeek(int n) {
        if ((n < 0) || (n >= numDays)) { return string(""); }
        return day[n];
    }

private:
    static const int numDays;          // const static data
    static const string day[7];        // const static data
};

const int CPSDay::numDays = 7;
const string CPSDay::day[7] = {"Sunday", "Monday", "Tuesday", "Wednesday",
                                "Thursday", "Friday", "Saturday"};

int main() {
    for (int n = 0; n < CPSDay::num(); ++n) {
        cout << CPSDay::getDayOfWeek(n) << endl;
    }
    return 0;
}

The out-of-class definition still exists and still follows the same three rules from §2 — const does not remove the requirement, it just adds const to both the declaration and the definition. (A common modernization you will see in other people's code, though not what this course uses, is static const int numDays = 7; written directly inside the class for an integral constant like this one, which avoids repeating the value; we keep the out-of-class form here because it is what generalizes to every type, including the array.)

Definition— static data and the Big Three

The copy constructor and the assignment operator (Classes 14 and 15) exist to copy one object's data into another object. Static data does not belong to any object, so there is nothing for either of them to copy — every object, old and new, was already looking at the same single static variable. Likewise the this pointer (Class 15) does not exist inside a static method, for the identical reason: this points at the object a method was called on, and a static method has no such object.

That statement is easy to accept in the abstract and easy to forget in practice, so make it concrete with a static member whose whole job is to count.

Worked Example— a static counter of "how many objects exist right now" (added)

Counter::objectsAlive is a single static int, shared by every Counter that will ever exist. Every constructor — including the copy constructor — increments it, and the destructor decrements it. Predict the four printed numbers before opening the toggle, paying special attention to the middle two.

counter.cpp
#include <iostream>
using namespace std;

class Counter {
public:
    Counter() { ++objectsAlive; }
    Counter(const Counter &other) { ++objectsAlive; }   // still just increments
    ~Counter() { --objectsAlive; }

    static int howManyAlive() { return objectsAlive; }

private:
    static int objectsAlive;
};

int Counter::objectsAlive = 0;

int main() {
    cout << "alive: " << Counter::howManyAlive() << endl;

    Counter a;
    cout << "alive: " << Counter::howManyAlive() << endl;

    {
        Counter b = a;   // copy constructor runs
        cout << "alive: " << Counter::howManyAlive() << endl;
    }   // b goes out of scope here

    cout << "alive: " << Counter::howManyAlive() << endl;
    return 0;
}
alive: 0
alive: 1
alive: 2
alive: 1

Look closely at the copy constructor: Counter(const Counter &other) { ++objectsAlive; }. It receives other, the object being copied from — and never reads a single field out of it. That is the point. Copying an object's static data would not even mean anything, because there is only one objectsAlive in the whole program; b's "copy" of it and a's "original" are the same variable. All the copy constructor does, correctly, is register that one more object now exists. When b is destroyed at the closing brace, the destructor decrements the same shared counter back down.

Quick Check 16.4

In the Counter example, suppose someone "forgot" to write a copy constructor at all, relying on the compiler-generated one from Class 14.

The compiler-generated copy constructor copies every non-static data member one-for-one from the source object. Counter has no non-static data members at all — objectsAlive is static, and the implicitly generated copy constructor never touches static members, exactly like the hand-written one above. So in this particular case the generated version would behave identically: it still would not increment objectsAlive, which means the count would be wrong after a copy (it would report one too few objects alive) unless you write the increment yourself, as the example does. Relying on the default here would silently break the whole point of the class.

id is an ordinary, non-static member — each Widget really does need its own copy, since every object's id is different. nextId is the opposite: it is the single shared "next number to hand out," so it has to be static. The constructor reads the current shared value into the new object's own id, then advances the shared counter for the next object. Getting this backward — making id static instead of nextId — would give every Widget the same id, because there would be only one id for the whole class to share.

5.The name-collision problem: Alice, Bob, and why namespaces exist

Switch topics completely now — from one variable shared inside a class to organizing whole blocks of code across a project. The motivating story the professor uses is worth walking through in full, because the reasoning is exactly what you will reach for the next time two pieces of code want the same name.

Two students, Alice and Bob, are each assigned the same homework: write a Point1 class with a set, some accessors, and a free function distance that computes the distance between two points. They work completely independently — nothing wrong with that so far. The trouble starts when the instructor collects both submissions into one project, because now there are two classes named Point1 and two functions named distance in the same program. "How will we distinguish the class Point1 and function distance written by Alice and Bob?"

Two tempting fixes both turn out to be bad ideas.

  • Rename the classes — AlicePoint1 and BobPoint1. This works for two people, but it does not scale: good naming practice says a name should describe what a thing does, and AlicePoint1 says nothing about that. In a project with many contributors you would be prepending everyone's name to everything they wrote, which produces code that is confusing to read and to maintain.
  • Only compile one submission at a time — comment out Bob's code while using Alice's, and vice versa. That sidesteps the immediate collision, but it fails the moment the project needs both functionalities at once, and in a large real project it means recompiling everything every time you switch, which is not remotely practical.

The real fix keeps both names exactly as written and separates them a different way: by where they live, not by what they are called.

Definition— namespace

A namespace is a named region of a program that groups together a set of declarations — classes, functions, variables, anything — under one unique identifier. Two names that would otherwise collide can coexist peacefully as long as they live in different namespaces, because a namespace becomes part of a name's full identity.

Syntax: namespace Name { ... }. To use something declared inside, you normally write its qualified name: Name::thing.

Wrapped in namespaces, Alice's and Bob's submissions become Alice::Point1 / Alice::distance and Bob::Point1 / Bob::distance. Both compile into the same program with no collision at all, because Alice::Point1 and Bob::Point1 are, as far as the compiler is concerned, completely different names — the fact that they end in the same four letters is irrelevant.

Quick Check 16.6

Explain, in your own words, why "just rename one of the classes" is not the same solution as "put one of the classes in a namespace" — even though both make Point1 appear only once in the raw source.

Renaming permanently changes the class's own name to something that has to carry extra information (whose code this is) forever, in every file that uses it. A namespace leaves the class's own name exactly as its author chose — still Point1, still meaningful on its own — and adds the "whose code is this" information as a separate, optional prefix that you can drop entirely inside code that only ever needs one namespace (more on that in §7). The identity information and the class's own name are two different jobs, and a namespace keeps them separate instead of mashing them into one identifier.

6.Defining and using a namespace

Here are Alice's and Bob's submissions, side by side. The professor deliberately gives Bob's class different internals — long coordinates instead of double — specifically to demonstrate that two classes can share a name and even a namespace-qualified identity while doing something genuinely different underneath.

Common Mistake— Bob::Point1 as printed does not compile

The course notes say, in prose, "we change data members x and y... to the type long," but the class as printed still declares private: double x, y; while the accessors are declared to return const long&:

const long& getx() const { return x; }   // x is a double -- this does not compile

You cannot bind a const long& reference to a double object: the two types are different, so the compiler would have to manufacture a temporary long to bind the reference to, and returning a reference to a temporary that is about to be destroyed is exactly the kind of thing the language forbids. The class as printed in the source does not compile at all.

This page resolves it by actually making the data long, matching the prose's stated intent, and returning the accessors by value rather than by const& — matching the Point1 you have been using since Class 13, which also returns by value. (A second version of Point1 circulates in the original course notes with const double&-returning accessors; the two versions are equivalent in behavior for a type this small, and by-value is used consistently on this page.) There was also a copy-paste slip in the original: the comment closing Bob's namespace reads } // namespace Alice, which should say Bob.

alice_bob.cpp
#include <iostream>
#include <cmath>
using namespace std;

namespace Alice {
    class Point1 {
    public:
        void set(const double &a, const double &b) {
            x = a;
            y = b;
        }
        double getx() const { return x; }
        double gety() const { return y; }
        void print() const {
            cout << "print x,y " << x << " " << y << endl;
        }
    private:
        double x, y;
    };

    double distance(const Point1 &a, const Point1 &b) {
        double dx = a.getx() - b.getx();
        double dy = a.gety() - b.gety();
        return sqrt(dx * dx + dy * dy);
    }
} // namespace Alice

namespace Bob {
    class Point1 {
    public:
        void set(const long &a, const long &b) {
            x = a;
            y = b;
        }
        long getx() const { return x; }
        long gety() const { return y; }
        void print() const {
            cout << "print x,y " << x << " " << y << endl;
        }
    private:
        long x, y;
    };

    double distance(const Point1 &a, const Point1 &b) {
        long dx = a.getx() - b.getx();
        long dy = a.gety() - b.gety();
        return sqrt(double(dx * dx + dy * dy));
    }
} // namespace Bob
Worked Example— both namespaces in one program

Predict the two distances printed before opening the toggle. Bob's points use whole-number coordinates, so watch what that does to his numbers.

alice_bob_main.cpp
int main() {
    Alice::Point1 ap1, ap2;
    ap1.set(1.1, 2.2);
    ap2.set(2.1, 3.2);

    Bob::Point1 bp1, bp2;
    bp1.set(-1, -2);
    bp2.set(-3, -4);

    cout << "Alice: " << Alice::distance(ap1, ap2) << endl;
    cout << "Bob:   " << Bob::distance(bp1, bp2) << endl;
    return 0;
}
Alice: 1.41421
Bob:   2.82843

Every use of either Point1 is qualified — Alice::Point1, Bob::Point1, Alice::distance(...), Bob::distance(...) — so the compiler never has to guess which class or which function you mean. Bob's version truncates its coordinates to long before computing anything, which is intentional here (it is the whole point of giving his class different internals), but it is worth flagging as lossy: passing bp1.set(-1, -2) is fine since -1 and -2 are already whole numbers, but any fractional Bob coordinate would be silently truncated the moment set is called.

Because Alice::Point1 and Bob::Point1 are unrelated types as far as the compiler is concerned, mixing them in a call to either namespace's distance is a compile-time error — there is no overload of Alice::distance that accepts a Bob::Point1 argument.

Worked Example— mixing namespaces, and the fix

Predict whether this compiles.

mixmatch_bad.cpp
cout << "mix and match: " << Alice::distance(ap1, bp2) << endl;
mixmatch_bad.cpp: In function 'int main()':
mixmatch_bad.cpp:46:55: error: invalid initialization of reference of type 'const Alice::Point1&' from expression of type 'Bob::Point1'
   46 |     cout << "mix and match: " << Alice::distance(ap1, bp2) << endl;
      |                                                       ^~~
mixmatch_bad.cpp:14:52: note: in passing argument 2 of 'double Alice::distance(const Point1&, const Point1&)'
   14 |     double distance(const Point1 &a, const Point1 &b) {
      |                                      ~~~~~~~~~~~~~~^

Alice::distance only ever declared to take two const Alice::Point1& parameters; a Bob::Point1 is not one of those, and the compiler will not silently convert between two unrelated class types. To call distance on one point from each namespace, you have to write a new function that is not inside either namespace and explicitly names both types:

mixmatch_fixed.cpp
// not inside either namespace: takes one Alice::Point1 and one Bob::Point1
double distance(const Alice::Point1 &a, const Bob::Point1 &b) {
    double dx = a.getx() - b.getx();
    double dy = a.gety() - b.gety();
    return sqrt(dx * dx + dy * dy);
}
mix and match: 7.43303

Notice dx and dy are declared double here, not long. a.getx() returns double and b.getx() returns long; if you declared dx as long (as the original course-notes version of this bridging function did), the subtraction result would be truncated to a whole number before the distance is even computed, silently throwing away Alice's fractional coordinates. Declaring the locals with the wider, more precise type avoids that.

A namespace does not have to be written as one unbroken block. It can be split into several pieces — even across different files of the same project — and the compiler simply merges everything tagged with the same namespace name.

Worked Example— one namespace, two blocks

Alice is written here as two separate namespace Alice { ... } blocks — the class in one, the free function in the other. In a real project these two blocks could be in two entirely different .cpp files. Predict the output.

    public:
        void set(const double &a, const double &b) {
            x = a;
            y = b;
        }
        double getx() const { return x; }
        double gety() const { return y; }

7.using declaration vs. using directive, and std

Typing Alice:: in front of every single name gets old fast if a piece of code only ever uses one namespace — there is no ambiguity to resolve, so the prefix is pure ceremony. C++ gives you two different ways to drop it, and they are not the same thing.

Definition— using directive vs. using declaration

A using directive, using namespace Alice;, tells the compiler "for any name I use that you don't otherwise recognize, also search inside Alice." It brings in everything in the namespace, unqualified, for the rest of the scope.

A using declaration, using Alice::Point1;, brings in one specific name and nothing else. Every other name from Alice still needs its full Alice:: prefix.

using_alice.cpp
namespace Alice {
    class Point1 { /* ... as before ... */ };
    double distance(const Point1 &a, const Point1 &b) { /* ... as before ... */ }
}

using namespace Alice;   // a using DIRECTIVE

int main() {
    Point1 ap1, ap2;      // compiler searches Alice for "Point1"
    ap1.set(1.1, 2.2);
    ap2.set(2.1, 3.2);

    cout << distance(ap1, ap2) << endl;
    ap1.print();
    ap2.print();
    return 0;
}
1.41421
print x,y 1.1 2.2
print x,y 2.1 3.2

Compare that with a using declaration, which is more surgical: it brings in Point1 by name but leaves distance requiring its full Alice:: prefix.

using_decl.cpp
using Alice::Point1;   // using DECLARATION: only Point1 is unqualified now

int main() {
    Point1 ap1, ap2;              // fine -- Point1 was brought in
    ap1.set(1.1, 2.2);
    ap2.set(2.1, 3.2);

    cout << Alice::distance(ap1, ap2) << endl;   // distance still needs the prefix
    return 0;
}
1.41421

None of this is new to you, even if the vocabulary is. Since Class 1, every program you have written has started with using namespace std;. Now you know exactly what that line does and why it was necessary: the entire standard library — cout, cin, endl, string, vector, all of it — lives inside one enormous namespace called std, written across many separate blocks (one per standard header). Without the directive, every one of those names needs the std:: prefix:

std_qualified.cpp
#include <iostream>

int main() {
    std::cout << "hello, world!" << std::endl;   // "std::" required
    return 0;
}
hello, world!
Quick Check 16.8

Now that using namespace std; has a name, revisit it directly.

(a) Every program in this course, including today's, has started with #include <iostream> followed by using namespace std;. What kind of using is that — a directive or a declaration?

A directive — it names the whole namespace (std), not one specific name inside it. After that line every unqualified name the compiler cannot otherwise resolve is also searched for inside std.

(b) Rewrite using namespace std; as a handful of using declarations that bring in only the three names cout, cin, and endl.

using std::cout;
using std::cin;
using std::endl;

This is more typing but more precise: any other std name — string, vector, sqrt from <cmath>, and so on — would still need its std:: prefix, or its own using declaration.

Warning— never put using namespace in a header

A #include is a textual copy-paste: everything in the included file lands, unqualified, inside whatever file included it. If a header contains using namespace Alice;, then every single .cpp file that ever includes that header silently gets Alice's names dumped into its unqualified name lookup — whether that file wanted them or not, and often without the author of that file even knowing the header did this. The whole reason namespaces exist is to let two pieces of code coexist without their names colliding; a using namespace directive sitting in a widely included header quietly defeats that, reintroducing exactly the ambiguity the namespace was built to prevent. Keep using directives — if you use them at all — inside .cpp files, never headers.

Warning— using namespace can reintroduce the very ambiguity it is meant to fix

Look again at the directive example above: it has both using namespace std; and using namespace Alice; in scope, and both std and Alice declare something related to a function called distance (std::distance, from <iterator>, is pulled in transitively by <iostream>). With this standard library the call resolves cleanly to Alice::distance, because std::distance requires iterator arguments and template deduction simply fails for a Point1. But that is a property of overload resolution succeeding to pick the right one, not a guarantee — a differently-shaped call, or a different standard library implementation, could produce a genuinely ambiguous call or a confusing error. This is the sharpest irony of using namespace: the mechanism that exists to resolve name collisions can, if you stack enough directives, quietly bring two colliding names back into the same scope.

8.Nested namespaces

Namespaces can be nested inside one another, which matters the moment your "unique name" problem itself has more than one dimension. The professor's example: suppose there are two students both named Alice, but in different lab sections, taught by different lab instructors — call the sections Alpha and Beta. There is also a Bob in Alpha's section and a Charlie in Beta's. Put each lab section in its own outer namespace, and each student inside it:

nested_ns.cpp
namespace Alpha {
    namespace Alice {
        void print() { cout << "Alice, Alpha" << endl; }
    }
    namespace Bob {
        void print() { cout << "Bob, Alpha" << endl; }
    }
}

namespace Beta {
    namespace Alice {
        void print() { cout << "Alice, Beta" << endl; }
    }
    namespace Charlie {
        void print() { cout << "Charlie, Beta" << endl; }
    }
}

int main() {
    Alpha::Alice::print();
    Beta::Alice::print();
    Alpha::Bob::print();
    Beta::Charlie::print();
    return 0;
}
Alice, Alpha
Alice, Beta
Bob, Alpha
Charlie, Beta

Each fully qualified call chains the outer namespace, then the inner one, then the function: Alpha::Alice::print(). Now there is no ambiguity at all between the two students named Alice — Alpha::Alice and Beta::Alice are completely distinct, the same way Alice::Point1 and Bob::Point1 were distinct in §6.

Key Idea

Nesting is just namespaces containing namespaces — there is no special syntax beyond writing one namespace block inside another and chaining :: one extra level for every level of nesting. (C++17 also allows the compact spelling namespace Alpha::Alice { ... } for a nested pair that is only ever written as one block; you will see both forms.)

Quick Check 16.10

Using the nested-namespace example above:

(a) Write the statement that calls Bob's (in section Alpha) print().

Alpha::Bob::print();

(b) If you wrote using namespace Alpha; before main, would Alice::print(); (with no Alpha:: prefix) now compile, and if so, whose print would it call?

Yes, it would compile, and it would call Alpha::Alice::print() — printing "Alice, Alpha". The directive using namespace Alpha; makes everything declared directly inside Alpha, including the nested namespace Alice, reachable without the Alpha:: prefix. Beta::Alice::print() would still need its full prefix, since the directive only opened up Alpha.

Quick Check 16.11

Summarize, in one sentence each: what problem does a namespace solve, and what is the difference between a using directive and a using declaration?

A namespace lets two pieces of code declare things with the same name without those names colliding, by making the namespace part of each name's full, qualified identity. A using directive (using namespace X;) opens up an entire namespace for unqualified lookup, while a using declaration (using X::name;) opens up only one specific name from that namespace, leaving everything else in it still requiring the X:: prefix.

Quick Check 16.12

A teammate proposes writing using namespace std; at the very top of a shared header file, utils.h, that is #included by twelve different .cpp files in the project, "to save everyone from typing std:: over and over." Is this a good idea? Explain.

No. #include is a textual copy-paste, so using namespace std; inside utils.h gets pasted, unqualified, into all twelve .cpp files that include it — whether or not each of those files' authors wanted std's names dumped into their own scope, and often without them even realizing the header did it. If any of those twelve files declares its own name that happens to collide with something in std (or in some other namespace also opened this way), the collision reappears project-wide, silently, exactly the failure mode namespaces exist to prevent. The directive belongs in individual .cpp files — never in a header.

Problem 1 — Namespace and access-specifier trace (from the Fall 2023 Exam 2, Problem 4)

examp4.cpp

namespace Alpha {
    class Number {
      public:
        Number() : x(2023) {}
        int value() const { return x; }
        void print() const { cout << "Alpha Number: " << x << endl; }
      private:
        int x;
    };

}

      public:

Problem 2 — Trace a static counter through construction, copying, and destruction (added)

Predict the exact output of the following program, line by line, before running it.

prac_ticket.cpp
#include <iostream>
using namespace std;

class Ticket {
public:
    Ticket() {
        id = nextId;
        ++nextId;
        cout << "Ticket #" << id << " created" << endl;
    }
    ~Ticket() {
        cout << "Ticket #" << id << " destroyed" << endl;
    }
    int getId() const { return id; }

private:
    int id;
    static int nextId;
};

int Ticket::nextId = 100;

int main() {
    Ticket a;
    {
        Ticket b;
        cout << "a=" << a.getId() << " b=" << b.getId() << endl;
    }
    Ticket c;
    cout << "c=" << c.getId() << endl;
    return 0;
}

Plan. Track two things separately: the shared static nextId, which only ever goes up, and each object's own id, which is frozen the moment that object's constructor runs. nextId starts at 100. a is constructed first and takes id = 100, advancing nextId to 101. b, inside the nested block, takes id = 101, advancing nextId to 102, then b is destroyed at the closing brace — note that destroying b does not lower nextId back down, since nextId only tracks "next id to hand out," not "how many are currently alive." c then takes id = 102. Finally a and c are destroyed, in the reverse of their construction order, when main ends.

Ticket #100 created
Ticket #101 created
a=100 b=101
Ticket #101 destroyed
Ticket #102 created
c=102
Ticket #102 destroyed
Ticket #100 destroyed

Things to notice.

  • nextId never decreases, even though b is destroyed partway through. This is a sequence-number counter, not a currently-alive counter like the Counter example in §4 — the difference is entirely in what the constructor and destructor do (or, for nextId, don't do) with the shared value.
  • c is destroyed before a at the very end because C++ destroys local variables in the reverse of the order they were constructed, and a was constructed first.

Problem 3 — Implement a class that assigns unique account numbers (added)

Write a BankAccount class that stores an owner's name (a string) and assigns each new account a unique account number, starting at 1001 for the first account ever created and incrementing by one for each account after that. Give it a static method howManyAccounts() that reports how many accounts have been opened in total. Test it with three accounts.

Plan. Exactly one static data member is needed: nextAccountNumber, initialized to 1001. Each constructor call copies the current shared value into that object's own accountNumber, then advances the shared value for the next account — the identical pattern as the Widget exercise in §4, just wearing different names. howManyAccounts() can be computed entirely from the static member, with no extra counter needed: however many the shared "next number" has advanced past 1001 is exactly how many accounts have been opened.

prac_bankid.cpp
class BankAccount {
public:
    BankAccount(const string &ownerName) : owner(ownerName) {
        accountNumber = nextAccountNumber;
        ++nextAccountNumber;
    }

    int getAccountNumber() const { return accountNumber; }
    const string& getOwner() const { return owner; }

    static int howManyAccounts() { return nextAccountNumber - 1001; }

private:
    string owner;
    int accountNumber;
    static int nextAccountNumber;
};

int BankAccount::nextAccountNumber = 1001;

int main() {
    BankAccount a("Priya");
    BankAccount b("Devon");
    BankAccount c("Marcus");

    cout << a.getOwner() << ": " << a.getAccountNumber() << endl;
    cout << b.getOwner() << ": " << b.getAccountNumber() << endl;
    cout << c.getOwner() << ": " << c.getAccountNumber() << endl;
    cout << "accounts opened: " << BankAccount::howManyAccounts() << endl;
    return 0;
}
Priya: 1001
Devon: 1002
Marcus: 1003
accounts opened: 3

Things to notice.

  • owner and accountNumber are both ordinary, non-static members — every account legitimately needs its own copy of each. Only the "what number comes next" bookkeeping is shared.
  • getOwner() returns const string& rather than string by value, which avoids an unnecessary copy of the owner's name on every call — a small habit worth having once a member is a class type rather than a small built-in type like int.

Problem 5 — Diagnose and fix a missing static definition (added)

The following program compiles with no warnings but fails to build. Explain, precisely, at which stage it fails and why, then fix it.

prac_robot_bad.cpp
#include <iostream>
using namespace std;

class Robot {
public:
    Robot() { ++fleetSize; }
    static int getFleetSize() { return fleetSize; }
private:
    static int fleetSize;   // declared, never defined

  • The compiler gave zero warnings, even with -Wall, because nothing about the class declaration itself is wrong — the missing piece is a separate statement the language requires but does not check for at compile time.
  • Every constructor call increments the same shared fleetSize, which is exactly why three Robot objects produce a fleet size of 3 rather than three separate values of 1.
Lecture Summary
  • A static data member belongs to the class, not to any object — every object shares the exact same variable. Declaring it inside the class is not enough; it needs a separate out-of-class definition, in exactly one .cpp file, or the program fails at link time with "undefined reference."
  • A static data member can also be const, using the same declare-in-class, define-outside-the-class pattern.
  • A static member function is called on the class (ClassName::method()), not on an object. It has no this pointer, cannot be const (there is no object to promise not to modify), and cannot touch non-static members (there is no object to say which one).
  • The copy constructor and assignment operator never copy a class's static data, because copying is about one object's data, and static data was never any one object's to begin with.
  • A namespace groups declarations under a unique name so that two identically named classes or functions (Alice's Point1 and Bob's Point1) can coexist; you reach into one with Namespace::name. A namespace can be split across several blocks, even in different files.
  • A using directive (using namespace X;) opens an entire namespace to unqualified lookup; a using declaration (using X::name;) opens only one name. using namespace std;, in every program since Class 1, is a directive.
  • Namespaces can nest (Alpha::Alice::print();), and a using namespace directive never belongs in a header file — it leaks into every file that includes it.
  • Exam note: static members have never appeared on any of this professor's ten graded exams. Namespaces appear exactly once — the Fall 2023 Exam 2 trace question worked as Problem 1 above — so if you have limited review time, prioritize being able to read a namespace-qualified trace like that one over memorizing every static-member rule.
