1.Why pointers exist at all

Before any syntax, here is the honest warning that opens this topic in the course notes, and it is worth reading twice:

Warning— from the course notes, verbatim
  1. Pointers are useful but also tricky things.
  2. The misuse of pointers is the single largest source of bugs in C++ programs.
  3. In fact, it was (at least) partly for this reason that references were introduced into C++.

The subject of pointers is vast, and we shall study only a few basic topics. That is not modesty — it is a scoping decision. The few basic topics are the ones that appear on every single exam in this course, usually twice.

So why bother, if they are that dangerous? Start with a picture of what memory actually is.

Your computer's memory is one enormous row of numbered byte-sized boxes. Box number 0, box number 1, box number 2, and so on, for billions of boxes. When you write int i = 4; the compiler picks some run of four consecutive boxes, writes the bit pattern for 4 into them, and records "from now on, the name i means those four boxes." The number of the first of those boxes is what we call the address of i.

Definition— memory address

A memory address is the numeric position of a byte in the computer's memory. Every variable in a running program occupies some run of bytes, and the address of the first of those bytes is called the address of the variable.

How many bytes a variable occupies depends on its type. The operator sizeof reports that number.

Worked Example— how much memory does a variable take?

Three variables of three different types. Predict the three sizes before you open the toggle — you have almost certainly seen these numbers before.

motivate.cpp
// motivate.cpp -- three variables, three addresses
#include <iostream>
using namespace std;

int main() {
    int i = 4;
    double d = 1.2345;
    char c = 'Q';

    cout << "value of i = " << i << ",  size = " << sizeof(i) << " bytes" << endl;
    cout << "value of d = " << d << ",  size = " << sizeof(d) << " bytes" << endl;
    cout << "value of c = " << c << ",  size = " << sizeof(c) << " byte"  << endl;
    return 0;
}
value of i = 4,  size = 4 bytes
value of d = 1.2345,  size = 8 bytes
value of c = Q,  size = 1 byte

An int occupies four consecutive bytes, a double eight, a char one. Only the last of those three is guaranteed by the C++ standard (sizeof(char) is always exactly 1); the other two are what essentially every machine you will use does, and what we will assume for the rest of the semester. Say "on a typical platform" when you write it in an exam answer and you cannot be marked wrong.

The point of the example is not the numbers. It is that a variable is a location, of a known size, at a known place. Locations can be numbered. Numbers can be stored in variables. That one observation is the whole idea of a pointer.

Now the motivation. You already know two situations where you needed to reach a variable that was not yours:

  • Class 1 and Class 2. swap1(int u, int v) did nothing at all, because it got copies. To change the caller's variables the function had to be handed the variables themselves, which we did with reference parameters, int &u.
  • Arrays. You have been passing arrays to functions since CSCI 111 without ever copying them, and without ever thinking about why that works. It works because an array argument is secretly a pointer — we will see exactly that in §6.

And here are three things you cannot do at all with what you know so far:

  1. Write a function that returns "the element that matched" — not a copy of it, but the element itself, so the caller can change it.
  2. Have one function say "there is no answer" in a way that the caller can test for. A double has no spare value that means "nothing."
  3. Create a variable while the program is running, sized by something the user typed, and destroy it later. That is Class 8, and it is impossible without pointers.
Key Idea

A pointer lets you refer to a piece of memory without owning it or copying it. Every advanced thing C++ can do — dynamic arrays, linked structures, polymorphism, the whole second half of this course — is built on that one capability.

2.Declaring a pointer, and the & operator

Definition— pointer

A pointer is a variable which holds the memory address of another variable.

For every data type — char, int, double, and so on — C++ supports a matching pointer type: pointer to char, pointer to int, pointer to double. A pointer is an ordinary variable in every respect. It has a type, it lives somewhere in memory, it can be assigned to, and it can be passed to functions. What is unusual is only what it stores: an address rather than a value.

Compare the two declaration syntaxes side by side. On the left, the plain declarations you already write; on the right, the pointer versions.

// plain variables
char   c;
int    i;
double d;
double x, y;        // multiple variables on same line

// pointers to those same types
char   *c_ptr;      // pointer to char
int    *i_ptr;      // pointer to int
double *d_ptr;      // pointer to double
double *px, *py;    // multiple pointers declared on same line

Read a pointer declaration right to left, starting at the name: double *d_ptr is "d_ptr is a pointer, and what it points to is a double." Never read it as "double-star, called d_ptr", however much the spacing tempts you to — and here is exactly why.

Common Mistake— int* p, q; does not declare two pointers

The * binds to the declarator, that is to the individual name, not to the type at the front of the line. So in

int* p, q;

p is a pointer to int and q is a plain int. The spacing lies to you. This is the reason the course notes lay down a house style and state it explicitly:

The * is associated with the pointer. Hence the notation is double *px, *py, etc.

Write the star next to the name, and the multi-declarator case reads correctly:

int *p, *q;     // now BOTH are pointers to int

What does the compiler say if you get it wrong? Here is a real program with int* p, q; in it, where the next line tries to store an address into q:

startrap.cpp: In function 'int main()':
startrap.cpp:9:9: error: invalid conversion from 'int*' to 'int' [-fpermissive]
    9 |     q = &x;         // q is an int, not a pointer to int
      |         ^~
      |         |
      |         int*

"invalid conversion from int* to int" is the compiler telling you, in its own words, that q is not the pointer you thought it was. Learn to recognize that sentence; it is one of the most common errors in this half of the course.

There is one more rule to state before we can put an address into a pointer, and it is the first rule the course notes give:

Key Idea— a pointer's type must match what it points at
  1. A pointer can only hold the address of a variable of the same type.
  2. A pointer to int can only hold the memory address of a variable of type int.
  3. Similarly, a pointer to double can only hold the memory address of a variable of type double.
  4. We cannot "mix and match" pointers to different data types.

The reason is that the pointer's type is what tells the compiler how many bytes to read and how to interpret them when you later follow the pointer. An address by itself is just a number; without the type there is no way to know whether the bytes there are an int, half of a double, or four chars.

Definition— the address-of operator &

The & symbol, written in front of a variable, is the address-of operator. It returns the memory address of that variable.

So if d is a double, then &d has type pointer to double, and it is exactly the thing you may store in a double *.

char   c;
int    i;
double d;

char   *c_ptr = &c;     // points to address of c
int    *i_ptr = &i;     // points to address of i
double *d_ptr = &d;     // points to address of d
double *px = &d;        // multiple pointers can point to the same address
double *py = &d;        //   "        "

Notice the last two lines. Several pointers may hold the same address at the same time. There is nothing exclusive about a pointer; it is not ownership, it is just a signpost, and any number of signposts may point at the same building. That fact is the source of a great deal of both power and grief, and we come back to it hard in §5.

Warning— & is now doing double duty

You met & in Class 2 in a declaration: void swap2(int &u, int &v) made u a reference. Today you are meeting it in an expression: &i takes an address. These are two different jobs for one character, decided entirely by context, exactly as we are about to see for *:

Where it appearsWhat & meansExample
In a declaration, after a typeDeclares a referenceint &r = x;
In an expression, before a variableAddress-of operatorint *p = &x;
Between two expressionsBitwise AND (rare in this course)x & 1
Worked Example— a pointer really does hold the address

This program prints an address. Addresses are machine-dependent: the exact hexadecimal number differs between machines, between compilations, and even between two runs of the same executable, because modern operating systems deliberately randomize where a program's memory is placed. So do not try to predict the hexadecimal number. Predict instead the relationships — which printed lines must agree with each other, and what the three comparisons at the bottom evaluate to.

addrof.cpp
// addrof.cpp -- the address-of operator, and what a pointer holds
#include <iostream>
using namespace std;

int main() {
    int i = 4;
    double d = 1.2345;

    int *i_ptr = &i;        // declare and initialize
    double *d_ptr = &d;     // declare and initialize

    cout << "i     = " << i     << endl;
    cout << "&i    = " << &i    << endl;   // an address -- differs every run
    cout << "i_ptr = " << i_ptr << endl;   // the same address
    cout << "*i_ptr= " << *i_ptr << endl;  // back to the value

    cout << endl;
    cout << "(i_ptr == &i) is " << (i_ptr == &i) << endl;
    cout << "(*i_ptr == i) is " << (*i_ptr == i) << endl;
    cout << "(*d_ptr == d) is " << (*d_ptr == d) << endl;
    return 0;
}

One real run. The two hexadecimal values below are representative only — your machine will print something different, and so will the next run on this machine:

i     = 4
&i    = 0x7ffef77d592c
i_ptr = 0x7ffef77d592c
*i_ptr= 4

(i_ptr == &i) is 1
(*i_ptr == i) is 1
(*d_ptr == d) is 1

Everything you can actually check is in that output:

  • &i and i_ptr printed the same hexadecimal number. They must, because i_ptr was initialized from &i and nothing changed it. That agreement is the point of the example; the digits are not.
  • The three comparisons all printed 1. cout prints a bool as 1 for true and 0 for false unless you ask otherwise — so 1 here means "yes, those are equal."
  • Addresses print in hexadecimal with a leading 0x. That formatting is cout's built-in behavior for pointer values; you do not have to do anything.

Run the same executable twice in a row and you get two different addresses. On the machine these notes were built on, a second run printed 0x7ffe66fd27dc. That is normal and expected. It is also why an exam question will never ask you for the numeric value of an address — and why, when you see a question like Practice Problem 4 that says "print the address of var", the graded answer is the statement, not the number.

The two errors both read "invalid conversion from ... to ...". Note that this is not like ordinary arithmetic types, where C++ quietly converts an int to a double for you. Pointer types do not convert silently, and that strictness is protecting you.

(b) How many pointers does double *px, py, *pz; declare, and what is the type of each name?

Two pointers, not three.

  • px — pointer to double
  • py — a plain double, because it has no star of its own
  • pz — pointer to double

This is why the course notes insist on attaching the star to the name. Written as double *px, py, *pz; the mistake is at least visible; written as double* px, py, pz; it is invisible and you will lose an hour to it.

(c) Is int *p = i; legal, given int i = 4;? What about int *p = &i;?

int *p = i; is not legal. i is an int with value 4; p wants an address. The compiler says "invalid conversion from int to int*" — note it is the same message as before with the two types in the opposite order, which is a useful clue about which side of the assignment you got wrong.

int *p = &i; is legal and is the normal way to initialize a pointer.

Things to notice. One historical wart: int *p = 0; is legal even though 0 is an int, because the literal 0 is a special case meaning "the null pointer". That special case is the whole reason nullptr was invented; see §4.

Pointers to pointers

The course notes pause here to ask a question and answer it immediately:

Can we declare a pointer to a pointer? — Oh yes! And we can declare a pointer to a pointer to a pointer, without limit.

double **ppx;       // pointer to pointer to double
double ***pppx;     // pointer to pointer to pointer to double

A pointer is a variable, a variable has an address, and an address can be stored in a pointer. There is nothing new here, only one more application of the same rule. Here is the shortest program that makes it concrete:

ptrptr.cpp
// ptrptr.cpp -- a pointer to a pointer
#include <iostream>
using namespace std;

int main() {
    double d = 1.2345;
    double *px = &d;        // pointer to double
    double **ppx = &px;     // pointer to pointer to double

    cout << "d     = " << d     << endl;
    cout << "*px   = " << *px   << endl;
    cout << "**ppx = " << **ppx << endl;

    **ppx = 9.9;            // two hops: reaches d itself
    cout << "d after **ppx = 9.9 : " << d << endl;
    return 0;
}
d     = 1.2345
*px   = 1.2345
**ppx = 1.2345

Before we get lost in silliness (the notes' phrase, and a fair one), park this. Two stars will matter exactly once in this course — in Class 8, where int ** is how you build a two-dimensional array at run time. Everything else today uses one star.

3.Dereferencing: the * that is an operator

You can now make a pointer hold an address. The other half of the deal is getting back to the variable it points at.

Definition— dereferencing

The operation of reading the data contained at the memory address held by a pointer is called dereferencing the pointer. The dereferencing operator is again the * symbol — and yes, in this context it is an operator.

If i_ptr holds the address of i, then the expression *i_ptr is the variable i. Not a copy of it. The variable itself, under a different spelling.

That last sentence is the one to memorize, because it has a consequence students consistently miss: since *i_ptr is the variable, you can put it on the left of an assignment and write through it.

Worked Example— writing through a pointer

Nothing in this program ever mentions i or d after the two pointers are set up. Predict both printed lines.

deref.cpp
// deref.cpp -- writing through a pointer
#include <iostream>
using namespace std;

int main() {
    int i = 4;
    double d = 1.2345;

    int *i_ptr = &i;        // declare and initialize
    double *d_ptr = &d;     // declare and initialize

    cout << "before: i = " << i << ", d = " << d << endl;

    *i_ptr = 3;             // dereference, value of i is now 3
    *d_ptr = 7.2;           // dereference, value of d is now 7.2

    cout << "after:  i = " << i << ", d = " << d << endl;
    return 0;
}
before: i = 4, d = 1.2345
after:  i = 3, d = 7.2

The course notes spell the reasoning out in three steps, and they are worth copying into your own notes exactly as stated:

  1. "Dereference" means the variable at the memory address pointed to by i_ptr.
  2. The variable is i.
  3. Therefore the value of i is set to 3.

Read *i_ptr = 3; out loud as "store 3 into whatever i_ptr points at." Reading it as "set i_ptr to 3" is the mistake, and that mistake is exactly what the next section is about.

Key Idea— * means two entirely different things
Where the * appearsWhat it meansExample
On a declaration line, attached to a name"this name is a pointer" — it is part of the type, not an actionint *p;
In an expression, in front of a pointerthe dereference operator — "the variable that is pointed at"*p = 3;
Between two numbersordinary multiplicationx * y

The course notes put it plainly: the * is used on the declaration line to tell the compiler that px and py are pointers. However, in assignment statements, we write "px = ..." etc. The names of the pointers are really px and py — not *px and *py.

The test: is there a type name at the front of the line? If yes, the star is declaring a pointer. If no, the star is dereferencing one.

Quick Check 7.2

For each line below, say whether the * is declaring a pointer, dereferencing one, or multiplying. Assume double d = 2.0; and double *p = &d; already exist.

(a) double *q = &d;

Declaring. There is a type name (double) at the front of the line, so this line introduces a new name q whose type is "pointer to double". After it runs, p and q hold the same address.

(b) *p = 5.0;

Dereferencing. No type name at the front. This stores 5.0 into d. Afterwards d is 5.0 and p is completely unchanged — it still holds the same address it always did.

(c) double area = *p * 3.0;

Both, in one line. The first * (immediately in front of p) dereferences; the second (between two values) multiplies. The line means area = d * 3.0;.

Note that the leading double declares area, not a pointer — the star is not attached to area. If you find this line hard to read, you are right, and the cure is parentheses: double area = (*p) * 3.0; compiles to exactly the same thing and reads far better.

(d) p = 5.0;

None of the three — there is no * at all, and that is the bug. This tries to store the number 5.0 into the pointer, i.e. to make p point at memory address 5. It does not compile: "cannot convert double to double* in assignment".

Things to notice. Missing star and extra star are the two classic pointer typos, and they usually announce themselves with an "invalid conversion" or "cannot convert" message naming one type with a star and one without. When you see that message, count the stars.

4.Null pointers, and pointers that point at garbage

A pointer holds an address. But what should it hold when there is no sensible address to hold — when a search found nothing, or when you have declared the pointer but do not yet know what it will point at? C++ reserves one special value for exactly that.

Definition— the null pointer

A null pointer is a pointer that deliberately points at nothing. It is a valid, testable, well-defined state, and it is the standard way for a pointer to say "no answer".

There are three spellings of it in C++, and you will meet all three:

SpellingStatusNotes
NULLInherited from C; used throughout the course notesA macro. Expands to 0 (or something like it). Requires no header in practice because <iostream> pulls it in.
0Legal, and used in the course notesThe literal zero is special-cased by the language to mean "null pointer" when the context wants a pointer.
nullptrThe modern C++ form (since C++11)A keyword with its own type. This is the one to write in new code.
Key Idea— why nullptr is better than NULL or 0

NULL and 0 are integers that the language agrees to treat as pointers in certain contexts. nullptr is a genuine pointer value with its own type, so it can never be mistaken for the number zero. The difference bites when overloading:

void f(int n);
void f(char *p);

f(NULL);        // ambiguous or surprising: NULL is an integer, so this may call f(int)
f(nullptr);     // unambiguous: only f(char *) can accept it

It also reads better. if (p == nullptr) says "is this pointer null"; the older if (p == 0) reads like an arithmetic test on a number.

What to write in this course. The course notes use NULL and 0 throughout, so you must be able to read both, and both are perfectly acceptable in exam answers — the professor's own rubrics use NULL. These notes use nullptr in new code because it is the correct modern form, and say so wherever the original wrote NULL. All three compile to the same thing. (nullptr is an addition to the course notes, not a change to them.)

Worked Example— testing a pointer before using it

The pattern in this program — check, then dereference — is the single most important defensive habit with pointers. Predict all four lines.

nullptrdemo.cpp
// nullptrdemo.cpp -- a null pointer is a pointer that points at nothing
#include <iostream>
using namespace std;

int main() {
    double d = 1.2345;
    double *px = &d;        // px points to the address of d
    double *py = nullptr;   // py deliberately points at nothing

    cout << "px is null? " << (px == nullptr) << endl;
    cout << "py is null? " << (py == nullptr) << endl;

    // The guard: check BEFORE you dereference.
    if (py != nullptr)
        cout << "*py = " << *py << endl;
    else
        cout << "py points at nothing -- not dereferencing it" << endl;

    py = px;                // now py is safe to use
    if (py != nullptr)
        cout << "*py = " << *py << endl;
    return 0;
}
px is null? 0
py is null? 1
py points at nothing -- not dereferencing it
*py = 1.2345

Three things to take from this:

  • Testing a pointer against null is completely safe. Only dereferencing a null pointer is dangerous. You may compare, assign, and print a null pointer all day long.
  • The line py = px; is a pointer assignment — it copies an address, so py stops being null and starts pointing where px points. That is §5's subject.
  • The guard costs one line and converts a crash into a message. Write it every time you use a pointer whose origin you did not personally control — and every function that returns a pointer produces exactly such a pointer (§8).

What happens if you dereference null anyway

The course notes give two deliberately symmetric error cases — reading through null, and writing through null:

double d = 1.2345;
double *px = &d;        // px points to address of d
double *py = NULL;      // py set to NULL

*px = *py;              // ERROR *** dereference of NULL pointer *** (read through null)
*py = *px;              // ERROR *** dereference of NULL pointer *** (write through null)

Of the first the notes say: "this illustrates the danger of using pointers: they can be NULL. Attempting to dereference a NULL pointer causes a run-time fault." Of the second: "the error here is that we attempt to store the value of d at a NULL memory address."

Warning— this is undefined behavior, not a defined crash

Dereferencing a null pointer is undefined behavior. The C++ standard says nothing whatsoever about what your program will do. In practice, on a normal desktop operating system, it crashes — which is the best possible outcome, because it is loud. But "it crashes" is an observation about one platform, not a guarantee.

Here is a real terminal session with the first of the two lines above, compiled and run on the machine these notes were built on. This is one possible outcome, not "the" output:

$ g++ nullcrash.cpp -o nullcrash
$ ./nullcrash
about to dereference py...
Segmentation fault

Note that the program got as far as printing its first line before dying. A crash tells you where execution stopped, not where the bug is. And note also that the compiler said nothing — not even with -Wall turned on. This is a run-time fault, and no amount of compiling will find it for you. The guard if (p != nullptr) is your only defense.

Common Mistake— an uninitialized pointer is worse than a null one

A null pointer at least points somewhere known. A pointer you never initialized contains whatever bit pattern happened to be lying in those eight bytes — an address, of a sort, pointing at some arbitrary place in memory.

uninit.cpp
// uninit.cpp -- UNDEFINED BEHAVIOR: an uninitialized pointer
#include <iostream>
using namespace std;

int main() {
    int *p;                 // never initialized: holds garbage
    cout << "about to dereference p..." << endl;
    cout << *p << endl;     // undefined behavior
    return 0;
}

g++ does warn you, and this warning is the reliable part of the story — it is the same every time:

uninit.cpp: In function 'int main()':
uninit.cpp:8:14: warning: 'p' is used uninitialized [-Wuninitialized]
    8 |     cout << *p << endl;     // undefined behavior
      |              ^
uninit.cpp:6:10: note: 'p' was declared here
    6 |     int *p;                 // never initialized: holds garbage
      |          ^

It is only a warning, so the program still builds and runs. What it then does is undefined. Running the same executable three times in a row on the machine these notes were built on printed -1876000916, then 1663836012, then -1921683604 — different garbage each time, and no crash at all. On another machine, or on another day, it may well segfault instead.

That is the danger. A crash is a bug that announces itself. A program that quietly reads garbage and keeps going is a bug that shows up three weeks later in someone else's module. The rule is absolute:

Initialize every pointer at the point of declaration — either to a real address, or to nullptr. Never int *p; on its own. Write int *p = nullptr; and pay the zero-cost insurance.

(c) A student writes int *r; and then, twenty lines later, if (r != nullptr) *r = 9;. Explain why the guard does not save them.

Because r was never set to nullptr in the first place. It holds garbage, and garbage is almost certainly not zero — so the test r != nullptr passes, and *r = 9; writes the number 9 into some arbitrary location in memory.

That is strictly worse than a crash. The write may land in unmapped memory and segfault; it may land in another variable and silently corrupt it; it may land somewhere harmless and the program appears to work until the code around it changes.

Things to notice. A null check only works if every path to that line either set the pointer to a real address or set it to null. That is why the rule is "initialize at declaration" and not "check before use" — the check is worthless without the initialization.

5.Copying an address vs. copying a value

Here is the centerpiece of the whole lecture. Two statements that look almost identical do completely different things:

StatementWhat is copiedEffect
p1 = p2;an addressp1 now points where p2 points. The variables they point at are untouched.
*p1 = *p2;a valueThe variable p1 points at is overwritten with the value of the variable p2 points at. Both pointers keep pointing where they were.

6.Pointers and arrays

Now the connection that explains a great deal of C++ you have been using without knowing why.

Definition— array decay

In C++, an array is allocated as a block of memory, and the name of the array is implemented as a pointer to the start of that block. In almost every expression you can write, an array name automatically converts to a pointer to its first element. That automatic conversion is called array decay.

So if a is double a[3];, then in an expression a means &a[0], and its type is double *.

Two consequences follow immediately, and the course notes state both:

  • You initialize a pointer from an array by writing p = a;. Not p = &a;. The notes are explicit: "the syntax is p = a and not p = &a. This is because a itself is an array."
  • Once p points at the start of the array, p[i] is the same variable as a[i], for every valid i. And since p holds the address of a[0], the dereference *p is the array element a[0].
int n = 3;
double a[n];
double *p = a;          // p points to the start of the array "a"

Pointer arithmetic: a[i] is *(a + i)

If an array name is a pointer, what does it mean to add 1 to it? The course notes lay out the rules, and they have one peculiarity worth stating up front.

Procedure— the rules of pointer arithmetic
  1. You cannot add or multiply two pointers, and you cannot multiply a pointer by a number. Those are compilation errors.
  2. You can add an integer to a pointer. The result is a new address. Adding 1 advances by one whole element, not by one byte: if ip is an int *, then ip + 1 is 4 bytes further along on a typical platform, and if dp is a double *, then dp + 1 is 8 bytes further along.
  3. For an array a, the expression a + n is the address of a[n], and therefore *(a + n) means exactly the same thing as a[n]. Subscripting is pointer arithmetic with a nicer face.
  4. You can subtract two pointers of the same type pointing into the same array. The result is an integer: the number of elements between them. If ip_m is &a[m] and ip_n is &a[n], then ip_n - ip_m equals n - m.
  5. You can compare two such pointers with <, >, == and so on. ip_n > ip_m is true exactly when n - m is positive.

7.Pointers as function parameters

This is where pointers start earning their keep, and it is also where the professor's exams concentrate. Recall the problem from Class 1 and Class 2: a function that takes its parameters by value cannot change the caller's variables, because it only ever sees copies. Class 2's answer was the reference parameter. Today you get the other answer.

Worked Example— three swaps, only two of which swap

The course notes give swap_using_ptr and swap_using_ref back to back for exactly this comparison; swap_broken is the by-value version from Class 1, included here so all three sit side by side. swapptr.cpp
// swapptr.cpp -- swapping with pointers, and with references, side by side
#include <iostream>
using namespace std;

void swap_using_ptr(double *u, double *v) {
    double tmp = *u;    // save temporary value (dereference)
    *u = *v;            // copy dereference
    *v = tmp;           // finish the swap
}

void swap_using_ref(double &a, double &b) {
    double tmp = a;
    a = b;
    b = tmp;
}

void swap_broken(double u, double v) {   // by value: swaps nothing
    double tmp = u;
    u = v;
    v = tmp;
}

int main() {
    double x = 1.5, y = 9.25;
    cout << "start:            x = " << x << ", y = " << y << endl;

    swap_broken(x, y);
    cout << "after swap_broken:    x = " << x << ", y = " << y << endl;

    swap_using_ptr(&x, &y);              // note the & at the CALL site
    cout << "after swap_using_ptr: x = " << x << ", y = " << y << endl;

    swap_using_ref(x, y);                // no decoration at the call site
    cout << "after swap_using_ref: x = " << x << ", y = " << y << endl;
    return 0;
}

The mechanism of swap_using_ptr, in the notes' own words:

  1. The dereferences of u and v inside the function operate on the variables in the calling application.
  2. Hence *u = *v is an assignment of the variables in the calling application.
  3. Next *v = tmp is also an assignment of a variable in the calling application.

The parameters u and v are still copies — C++ always passes by value. But what is copied is an address, and both the caller's pointer and the function's copy of it point at the same variable. Copying a signpost still leaves you pointing at the same building.

Quick Check 7.6

A function is declared void bump(int *n); and its body is *n = *n + 1;.

(a) Write the call that increments a variable int count = 0;.

The function wants an address, so you must supply one. Writing bump(count); fails to compile with "invalid conversion from int to int*" — which is a mercy, because it means this particular mistake cannot survive to run time.

(b) A student writes the body as n = n + 1; instead. Does it compile, and what does it do?

It compiles, and it does nothing useful. n is the local copy of the pointer; n + 1 is pointer arithmetic, producing the address one int further along. The local pointer is moved, the function returns, the local pointer is destroyed, and the caller's count is untouched.

This is the single most dangerous pointer typo, precisely because the compiler accepts it. A missing star turns "change the value" into "move the pointer".

(c) Rewrite bump to use a reference parameter instead. What changes at the call site?

}

If print's body were changed to assign into p1[i], the promise breaks and the compiler stops you:

Things to notice.

  • -2.0 printed as -2. Default cout formatting drops trailing zeros, exactly as in Class 1. Writing -2.0 as your answer on an exam is wrong.
  • The parameter list mixes both kinds of pointer deliberately: const double *a is an input (read, never written) and double *lo is an output (written). A reader can tell which is which from the signature alone, without opening the body. That is what const is for.
  • Inside the loop, a[i] < *lo compares an element with the value currently in the caller's lo. Forget the star and you get invalid operands to binary < — comparing a double with a double *.
  • You could also write this with two reference parameters, double &lo, double &hi, and drop every star. Both are correct. The pointer version has the advantage that the call site, min_max(n, a, &lo, &hi), visibly announces that lo and hi are about to be modified.

8.Pointers as return values

The return value of a function can be a pointer. That is how you write a function that hands back the element itself rather than a copy of it — and, just as importantly, how a function says "there is no answer" by returning null.

Worked Example— the course notes' get_element

getelement_warn.cpp:7:24: warning: comparison of integer expressions of different signedness: 'int' and 'std::vector<double>::size_type' {aka 'long unsigned int'} [-Wsign-compare]
    7 |     if ((n >= 0) && (n < v.size()))
      |                      ~~^~~~~~~~~~

v.size() is an unsigned type. Warning— never return a pointer to a local variable

Returning a pointer is safe when the thing pointed at outlives the function. In get_element it does: v belongs to the caller. This does not:

int* broken() {
    int local = 42;
    return &local;      // local dies when the function returns
}

The variable local is destroyed the instant broken returns, and the caller is left holding the address of memory that no longer belongs to anything. Following it is undefined behavior. g++ warns: "address of local variable 'local' returned".

So a function may safely return a pointer to: something the caller passed in, something with a lifetime longer than the call — or, from Class 8, memory the function allocated with new, which deliberately outlives the function that created it. That last one is the reason the next class exists.

// findvalue.cpp -- return a pointer to the element found, or null

Quick Check 7.10

Three short judgment questions about returning pointers.

(a) Why can a function that returns double never report "no answer" as cleanly as one returning double *?

Because every double is a legitimate answer. Whatever sentinel you pick — -1, 0, -999.0 — is a value the data might genuinely contain, and then the caller cannot tell "the answer is -1" from "there is no answer."

double * has one value, nullptr, that can never be the address of a real element. So "no answer" is representable without stealing a legal answer to say it.

(b) Is return &v[n]; inside get_element an address-of or a dereference?

Address-of. v[n] is the element (a double), and the & in front of it produces its address, which is a double * — matching the declared return type.

Contrast return v[n];, which would return a copy of the element and would not compile against a double * return type: "cannot convert double to double* in return".

(c) What goes wrong if the caller of get_element writes cout << *get_element(v, 99) << endl;?

Index 99 is out of range, so get_element returns nullptr, and the star in front of the call dereferences it. That is undefined behavior; on a typical desktop system it is a segmentation fault.

The call compiles perfectly — the types are all correct — and it may even work fine for months if nobody ever passes an out-of-range index. This is exactly the class of bug that makes the null check non-negotiable:

double *p = get_element(v, 99);
if (p != nullptr)
    cout << *p << endl;
else
    cout << "no such element" << endl;

Things to notice. The general rule for this whole class: a pointer that came from somewhere else is guilty until proven innocent. Every pointer you did not personally initialize on the line above needs a null check before its first dereference.

Lecture Summary
  • A pointer is a variable that holds the memory address of another variable. A pointer's type must match the type of what it points at — no mixing and matching.
  • Declare with the star attached to the name: double *px, *py;. Written double* px, py;, only px is a pointer.
  • &x is the address-of operator; it produces a pointer to x. *p is the dereference operator; it names the variable p points at, and may appear on either side of an assignment.
  • The star means "pointer" on a declaration line and "dereference" in an expression. The test is whether there is a type name at the front of the line.
  • A null pointer points at nothing. The course notes write NULL or 0; modern C++ writes nullptr. Testing a pointer against null is always safe; dereferencing a null pointer is undefined behavior, in practice a crash.
  • An uninitialized pointer is worse than a null one, because a null check will not catch it. Initialize every pointer where you declare it.
  • p1 = p2; copies an address and moves an arrow. *p1 = *p2; copies a value and changes a variable. This is the single most examined distinction in the topic.
  • An array name decays to a pointer to its first element, so p = a; — never p = &a;. Then a[i], p[i], *(a + i) and *(p + i) are four spellings of one variable.
  • Pointer arithmetic counts elements, not bytes. p + 1 advances by one whole element, and &a[n] - &a[m] is n - m.
  • A pointer parameter lets a function change the caller's variable, like a reference parameter, but the call site must write & and the pointer may be null or be repointed. Arrays reach functions this way, and the length must be passed separately. Tag read-only pointer parameters const.
  • A function may return a pointer — to something the caller owns, never to one of its own locals. Every such call needs a null check before the first dereference.
