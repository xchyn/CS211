Key Idea— why this class matters more than most

Look at any exam this professor has ever given and you will find the same question: "give an implementation for the destructor, the copy constructor, and the assignment operator." It is on nine of his ten graded papers, and it is always worth 20 to 40 points. Today you learn two of those three; Class 15 finishes the set.

There is no way to bluff it. Either you can write these four or five lines from memory, or you cannot. So today's material is worth over-learning.

1.Where the memory goes when the object dies

Everything so far in Classes 9, 10 and 13 has used classes whose data members are plain values — two doubles, an int, a string. Those classes are easy: when the object goes away, its members go away with it, and that is the end of the story.

Today's class is different, and the difference is the whole lecture. Here is the professor's running example for the next two classes: a class whose object owns a block of heap memory.

pstrings.cpp
// pstrings.cpp -- a class that owns dynamic memory but never releases it
#include <iostream>
#include <string>
using namespace std;

class PStrings {
public:
    PStrings(int n, string s[]) {
        length = n;
        pstr = new string[length];
        for (int i = 0; i < length; ++i)
            pstr[i] = s[i];
    }
    // destroy
    // copy
    // assign
    void print() const {
        cout << "length = " << length << endl;
        cout << "pstr: ";
        for (int i = 0; i < length; ++i)
            cout << pstr[i] << " ";
        cout << endl;
    }
private:
    int length;
    string *pstr;
};

int main() {
    int n = 3;
    string s[] = {"a", "b", "c"};
    PStrings ps(n, s);
    ps.print();
    return 0;
}

Read the constructor carefully, because that one line is the source of every problem in this lecture:

pstr = new string[length];

The object ps itself lives on the stack in main, and it is small — an int and a pointer. But the array of three strings that pstr points at lives on the heap, and from Class 8 you know the rule for heap memory: memory obtained from new is released only by delete. Nothing else releases it. Not the end of a function, not the end of a scope, not the end of main.

Now look at the three comment lines the professor left in the middle of the class:

    // destroy
    // copy
    // assign

Those are placeholders for the three functions this class needs and does not have. We write destroy and copy today; assign is Class 15.

Definition— memory leak

A memory leak is heap memory that your program allocated and can no longer reach — the last pointer to it was destroyed or overwritten — and which therefore can never be released. The block stays checked out from the operating system until the process exits.

A leak is not a crash. The program runs, prints the right answer, and exits with status 0. That is exactly what makes leaks dangerous: nothing tells you. A server that leaks a kilobyte per request looks perfect in testing and falls over after three weeks in production.

So the question is: who is supposed to call delete []? Not main — main cannot even see pstr, it is private. The only code that knows this object owns a heap block is the class itself. So the class has to clean up after itself, and C++ gives it a place to do exactly that.

Quick Check 14.1

For each of these three classes, decide whether it needs you to write a destructor, and say why in one sentence.

class A {
private:
    double x, y;
};

class B {
private:
    string name;
    int count;
};

class C {
private:
    int size;
    double *data;      // set with data = new double[size];
};

(a) Class A

No. Two doubles are plain values living inside the object itself. When the object dies, the storage that held them is reclaimed automatically, whether that storage was on the stack or inside a bigger object. There is nothing left over to release.

(b) Class B

No — and this one is the interesting case. A string usually does own heap memory: a long string keeps its characters in a heap buffer. But string is itself a class, and it has its own destructor that frees that buffer. When a B object dies, the destructor of its name member runs automatically.

That is the rule to remember: the compiler cleans up members that know how to clean up themselves. You inherit correct behavior for free from every well-written class you use as a member.

(c) Class C

Yes. data is a raw pointer. A raw pointer is a plain value — a machine address, eight bytes. Destroying it destroys the eight bytes and does nothing whatever to the memory those eight bytes pointed at.

Things to notice. The test that separates (c) from (a) and (b) is not "does the class use the heap?" It is: does this class hold the only pointer to a heap block that nobody else will free? If the answer is yes, the class owns that block, and an owner must have a destructor. Every exam question in this course that asks for a destructor has exactly this shape — one or two raw pointer members and a new in the constructor.

2.The destructor

Definition— destructor

A destructor is a special member function that is invoked automatically when an object is destroyed. In the professor's words: "the destructor of a class is invoked when an object goes out of scope." Its job is to release any resource the object acquired and is responsible for.

It is the mirror image of a constructor. A constructor is the last thing that happens as an object comes into existence; a destructor is the last thing that happens before it stops existing.

Procedure— destructor syntax, all three rules
  1. The name is a tilde ~ followed by the name of the class: ~PStrings.
  2. There is no return type. Not void, not anything. Just the name.
  3. There are no parameters. The parentheses are always empty.

Rules 2 and 3 together have a consequence worth stating separately: a class has exactly one destructor. Constructors can be overloaded because they differ in their parameter lists; destructors have no parameter list to differ in. As the professor puts it: "there is only one destructor for a C++ class. Unlike constructors, there are no 'non-default' destructors."

Applied to our class, the whole thing is three lines:

class PStrings {
public:
    // destroy
    ~PStrings() {
        delete [] pstr;
    }
    // etc
};

delete [], with the brackets, because the memory came from new string[length], with the brackets. That pairing was the rule in Class 8 and it has not changed.

Key Idea— you never call a destructor yourself

You write the destructor. You do not call it. The compiler emits the call for you at exactly the right moment, and there is no situation in this course where writing obj.~ClassName(); by hand is the right thing to do.

Common Mistake— "cleaning up early" by calling the destructor

Every semester someone decides to be tidy and calls the destructor explicitly when they are finished with an object. Here is what that costs:

int main() {
    int n = 3;
    string s[] = {"a", "b", "c"};
    PStringsD psd(n, s);
    psd.~PStringsD();          // "cleaning up early"
    cout << "back in main" << endl;
    return 0;
}
PStringsD: destructor
back in main
Segmentation fault

The destructor ran twice: once because you called it, and once again automatically when psd went out of scope at the closing brace of main. The second run called delete [] on a pointer whose memory was already released, and the program died. Under valgrind the same run reports "Invalid free() / delete / delete[] / realloc()" and "3 allocs, 4 frees" — one more release than allocation.

Trust the compiler. Destruction is automatic, and it is one of the few things in C++ that is genuinely hard to get wrong if you leave it alone.

What the compiler generates when you write nothing

Just as with the default constructor in Class 13, if you do not write a destructor the compiler generates one for you. And just as with the default constructor, the professor's warning applies: the generated one "may not do exactly what we want". He goes further and says it "typically does nothing."

That is very nearly right, and the precise version is worth having, because it explains Quick Check 14.1 (b) as well as (c). The compiler-generated destructor:

For a member of this kindThe generated destructor…
built-in type (int, double, char)does nothing at all — there is nothing to do
raw pointer (string *pstr)does nothing at all — it destroys the pointer, not the memory
class type (string name, another object)calls that member's destructor

So for a class made entirely of ints and pointers, "does nothing" is literally true. And on our PStrings, the professor's rhetorical question answers itself: "How could it know to do such a thing?" The compiler sees a string *. It has no way to know whether that pointer owns a heap array, points into the middle of somebody else's array, or is a borrowed reference to an object that will outlive us. Calling delete [] on it would be a catastrophe in two of those three cases. So the compiler does the only safe thing and does nothing.

Warning— the tilde that is not a tilde

In the original slides for this lecture, the destructor rule is printed as "the name of the destructor is ‘∼’ followed by the name of the class" — and the character on the slide is not the ASCII tilde ~ you type. It is U+223C, the mathematical tilde operator. The two look nearly identical in a slide font and are completely different characters to a compiler.

A student who copies that character straight off the slide into a source file gets this:

tilde_err.cpp:7:5: error: extended character ∼ is not valid in an identifier
    7 |     ∼Widget() { delete [] p; }
      |     ^
tilde_err.cpp:7:5: error: ISO C++ forbids declaration of '\U0000223cWidget' with no type [-fpermissive]

Always type the tilde from your own keyboard — on a US layout it is Shift plus the backtick key, above Tab. If you have pasted code from a slide, a PDF or a web page and get an "extended character" error, that is what happened, and the fix is to retype the offending character rather than hunt for it.

Quick Check 14.3

Write the destructor for Roster, and explain why delete people; would be wrong even though it compiles.

Plan. One member owns heap memory: people, allocated with new string[count]. The destructor's only job is to hand that block back. The array form of new demands the array form of delete.

    ~Roster() {
        delete [] people;
    }

That is the whole answer. Notice what is not in it: no loop, no people[i] = "";, no setting count to zero. The object is about to cease to exist; tidying its members is wasted work. The one thing that outlives the object is the heap block, so the heap block is the one thing you deal with.

Why delete people; is wrong. It compiles — the type is right, it is a string * either way — so the compiler says nothing. But new string[3] constructed three string objects and recorded somewhere that there are three of them. Plain delete runs one destructor and releases the block from the wrong starting address. This is undefined behavior; in practice it aborts. Here is what really happens to this exact Roster with delete people; in its destructor — it prints correctly, then dies on the way out:

Aborted

Things to notice. On this professor's exams, the destructor sub-part is worth 3 or 4 points, of which 1 is for the signature line alone. Writing ~Roster() { and nothing else already scores. Writing delete where delete [] belongs loses the rest.

3.new calls the constructor, delete calls the destructor

Now we can complete the class. The professor names the result PStringsD — PStrings plus a Destructor — and demonstrates it on both kinds of object at once: one built on the stack, one built with new.

pstringsd.cpp
// pstringsd.cpp -- PStrings plus a destructor; a stack object and a heap object
#include <iostream>
#include <string>
using namespace std;

class PStringsD {
public:
    PStringsD(int n, string s[]) {
        length = n;
        pstr = new string[length];
        for (int i = 0; i < length; ++i)
            pstr[i] = s[i];
    }
    // destroy
    ~PStringsD() {
        delete [] pstr;
    }
    void print() const {
        cout << "length = " << length << endl;
        cout << "pstr: ";
        for (int i = 0; i < length; ++i)
            cout << pstr[i] << " ";
        cout << endl;
    }
private:
    int length;
    string *pstr;
};

int main() {
    int n = 3;
    string s[] = {"a", "b", "c"};
    PStringsD psd(n, s);
    psd.print();

    PStringsD *ppsd = new PStringsD(n, s);
    ppsd->print();
    delete ppsd;
    return 0;
}

Run it and valgrind now reports "5 allocs, 5 frees" and "All heap blocks were freed — no leaks are possible." Five rather than two because there are two PStringsD objects now, and the second one is itself on the heap.

Key Idea— the two operators, restated for classes
  • Operator new invokes a suitable default or non-default constructor to instantiate the object, then hands you a pointer to it.
  • Operator delete invokes the destructor, then releases the object's own storage.

So delete ppsd; in the program above does two separate things in order: it runs ~PStringsD(), which releases the array of three strings, and only then releases the PStringsD object itself. Forget the delete and you leak both.

Definition— the three moments a destructor runs
  1. End of scope. A local object is destroyed at the closing brace of the block that declared it. That includes the closing brace of a function, so a parameter or local object dies when the function returns.
  2. delete. An object created with new is destroyed exactly when someone calls delete on its pointer — and never otherwise.
  3. End of the program. Objects in main are destroyed as main returns.

Within a single scope, objects are destroyed in reverse order of construction. Last one built is first one destroyed — the stack of objects unwinds like any other stack.

4.Copy an object that owns memory, and watch it explode

We now have a class that allocates in its constructor and releases in its destructor. It is balanced, it is leak-free, and it is still badly broken. All it takes to find out is to pass one of these objects to a function.

The professor writes an ordinary-looking free function, one you have written a hundred times:

void print(PStringsD psd_copy) {      // by value: a copy is made
    psd_copy.print();
}                                     // the copy dies here

Nothing about that is unusual. It takes its argument by value, like swap1 back in Class 1, so the function gets a copy and cannot disturb the caller's object. That is the whole point of call by value. It is supposed to be the safe option.

5.Shallow copy versus deep copy

To see what went wrong, ask the question nobody asked: when main called print(psd), and the parameter psd_copy was created as a copy of psd… who wrote the code that made that copy?

You did not. Just as the compiler will generate a default constructor and a destructor for you, it will generate a copy constructor — the function whose job is to build a new object as a duplicate of an existing one. And its generated version does the obvious thing, which here is the wrong thing. In the professor's words, the compiler-generated copy "simply copies all the data members":

psd_copy.length = psd.length;
psd_copy.pstr = psd.pstr;   // pstr in copy points to same
                            // memory address as pstr in object
                            // in main program
Definition— shallow copy and deep copy

A shallow copy copies the values of all the data members, including pointer members. Both objects end up holding the same address, so both point at one single block of memory. This is the compiler's default behavior.

A deep copy allocates a fresh block of memory for the new object and copies the contents of the original's block into it. The two objects then own two independent blocks that happen to hold equal values.

For a class with no pointer members the two are the same thing, which is why you have never had to think about this before. The moment a raw pointer appears in a class, they diverge completely.

Here is the picture. After the shallow copy, memory looks like this:

lengthpstrpoints at
psd (in main)30x4e26080one array: "a" "b" "c"
psd_copy (the parameter)30x4e26080

Two objects. Two pstr members. One array. (The address shown is the real one from the run above; it will differ on your machine.)

Everything now follows mechanically. The function print returns, its parameter psd_copy goes out of scope, and its destructor runs — because we wrote one, and it is doing exactly what we told it to:

delete [] pstr;   // releases memory in object in main program

The copy has released the array that main's object is still using. psd is now holding a pointer to freed memory, and it does not know it. That is a dangling pointer, and reading through it is the segfault we saw. When main ends and psd's own destructor runs, it calls delete [] on the same address a second time — the invalid free valgrind reported.

Key Idea— destructor without copy constructor is worse than neither

The version of the class with no destructor leaked memory but never crashed. Adding the destructor fixed the leak and introduced a crash, because the class now frees memory it does not exclusively own.

The lesson is not "don't write destructors." It is: a class that owns heap memory needs the destructor and the copy constructor and the assignment operator, as a set. Writing one of the three and not the others is how you build a class that is worse than the naive version. Class 15 gives this rule its name.

The other half of the damage

The double free is the loud failure. There is a quieter one, and in a large program it is worse, because nothing crashes and you get wrong answers instead.

6.Writing the copy constructor

Definition— copy constructor

A copy constructor is the constructor that builds a new object as a duplicate of an existing object of the same class. Like every constructor it runs at the moment an object comes into existence — the object it builds is brand new and has never held a value before.

Procedure— copy constructor syntax
  1. The name is the class name, like any constructor.
  2. There is no return type, like any constructor.
  3. It takes exactly one parameter: a const reference to an object of the same class.

The professor's own gloss on that list: items 1 and 2 tell the compiler this is a constructor; item 3 is what makes it the copy constructor rather than an ordinary non-default constructor. Get item 3 slightly wrong — take an int, take a different class — and you have written a perfectly legal constructor that the compiler will never call to make a copy.

ClassName(const ClassName &other);

The parameter name is up to you. The professor writes orig in the copy constructor (the object being copied is the original) and rhs in the assignment operator you will meet in Class 15.

And the body, for a class that owns a heap array, is always the same three moves: copy the size, allocate fresh memory, copy the contents one element at a time.

class PStringsD {
public:
    // copy
    PStringsD(const PStringsD &orig) {
        length = orig.length;
        pstr = new string[length];          // allocate fresh memory
        for (int i = 0; i < length; ++i)
            pstr[i] = orig.pstr[i];         // copy the contents
    }
    // etc
};

Compare that with what the compiler generates — pstr = orig.pstr; — and the whole lecture is in the difference between those two lines. The compiler copies the pointer. We copy what the pointer points at.

Common Mistake— accessing a private member of another object

Look at orig.length and orig.pstr. Both are private, and we are reading them from outside the object that owns them. Is that legal?

Yes. private is per class, not per object. Any member function of PStringsD may touch the private members of any PStringsD object it can reach, not merely its own. Without that rule no copy constructor or assignment operator could ever be written.

Students routinely add a public getter for this, or make the members public "so the copy constructor can see them." Neither is necessary, and the second throws away your encapsulation for nothing.

Why the parameter must be a reference

Rule 3 said const reference. The const is good manners — you are not going to modify the thing you are copying, so say so, and it lets you copy from a const object. But the & is not manners at all. Without it the code does not compile, and the reason is a small piece of pure logic worth walking through.

Worked Example— a copy constructor taking its parameter by value

Suppose you forget the ampersand:

    PStringsD(PStringsD orig) {          // ERROR: not a reference
        length = orig.length;
        pstr = new string[length];
        for (int i = 0; i < length; ++i)
            pstr[i] = orig.pstr[i];
    }

Before you read the compiler's answer, reason it out. The parameter orig is taken by value, so calling this function requires making a copy of the argument. What function makes a copy of a PStringsD?

The copy constructor. Which is the function we are trying to call. Which would need to copy its argument, which would need the copy constructor, which would need… The call can never begin. It is infinite recursion, and not the kind that eventually hits a base case — the kind that cannot execute a single step.

The compiler refuses outright. This is the real message from g++ 13.3:

copyval_err.cpp:17:5: error: invalid constructor; you probably meant 'PStringsD (const PStringsD&)'
   17 |     PStringsD(PStringsD orig) {          // ERROR: not a reference
      |     ^~~~~~~~~

It is one of the few g++ diagnostics that hands you the corrected line. "You probably meant PStringsD (const PStringsD&)" — take the hint.

A reference parameter breaks the cycle because binding a reference copies nothing. The name orig simply becomes another name for the caller's object, for the duration of the call. No copy is required to start making a copy.

Note also what the const buys once the ampersand is there. With PStringsD(PStringsD &orig) — a reference but not const — the code compiles, but you can no longer copy from a const object:

prac_bugs.cpp:31:17: error: binding reference of type 'Names&' to 'const Names' discards qualifiers

Since passing objects as const references is the normal way to pass them, a non-const copy constructor breaks in practice almost immediately. Write both the const and the &, every time.

7.The three places a copy constructor fires

We found the copy constructor by way of a function call, but the professor is careful to point out that "a function call is not the only occasion". There are three, and exam trace questions test all of them.

Procedure— when does a copy constructor run?
  1. Initializing a new object from an existing one. Both of these spellings do it, and they are the same thing: 
    PStringsDC psdc2(psdc1);      // copy
PStringsDC psdc3 = psdc1;     // also copy
  2. Passing an object to a function by value. The parameter is a new object, initialized from the argument.
  3. Returning an object from a function by value. The value handed back to the caller is a new object — though see the warning below about what C++17 does here.

His remark on case 1 is worth keeping: if an object already exists and you want a second one that is mostly the same, it is simpler to copy it and then change what differs than to build the second one from scratch. "In this respect, a copy constructor is a non-default constructor where the input is a reference to an object of the same class."

Definition— copy elision

Copy elision is the compiler's right to skip a copy that a strict reading of the language would require, when the copy would only move a value from a temporary into its final home.

Since C++17 this is mandatory in one specific case: when an object is initialized from a temporary of the same type — including the temporary produced by return ClassName(args); — there is no copy to elide, because the standard says the object is simply constructed in place. Not "the copy is optimized away." There is no copy.

That is why lines (5) and (6) print only "non-default constructor". Their two cases are subtly different, and it is worth separating them because only one of the two is guaranteed:

(5) return local; feeding PStringsD psd4 = makeNamed(...);Permitted, not required. This is called named return value optimization. Every real compiler does it, but a copy constructor must still be available, and in principle it could be called.

Warning— elision does not excuse you from writing the copy constructor

It would be a serious mistake to read the trace above as "returning by value is free, so I don't need a copy constructor." Cases (2), (3) and (4) all called it, and there is no elision anywhere in sight for them. Copying from a named object that continues to exist afterwards is a real copy and always will be.

On this professor's exam trace questions, the rubrics assume exactly the behavior shown here: no copy line for a returned temporary, a copy line for an initialization from a named object. Your job is to write a correct copy constructor and then trace as the compiler actually behaves.

Key Idea— reading the qualified names

PStringsDC::~PStringsDC() looks alarming the first time. Take it apart:

  • PStringsDC:: — "the thing being defined belongs to class PStringsDC";
  • ~PStringsDC() — "and its name is ~PStringsDC", the destructor.

The constructor is the same pattern with the name repeated for a different reason: PStringsDC::PStringsDC(...) is "class PStringsDC, member named PStringsDC". Once you see the :: as a separator rather than part of either name, all of these read easily.

The one thing to watch: const on a method is part of the signature, so a print declared void print() const; must be defined void PStringsDC::print() const {. Drop the trailing const and the compiler tells you the member does not exist.

Common Mistake— a mutator taking a string by value

The original notes declare the mutator as void set(int n, string s) — string by value. It works, but it copies the whole string on every call, and it is inconsistent with every other interface in this course, which takes objects by const reference. It is written here as void set(int n, const string &s).

The general rule, and it is the one Class 2 established: pass small built-in types (int, double, char, bool) by value, and pass everything else — string, vector, your own classes — by const reference unless you specifically need a copy. (c) A classmate writes the copy constructor as rows = orig.rows; cols = orig.cols;. Describe the two separate failures this causes.

Failure 1 — double free. Both objects hold the same two addresses. When both are destroyed, delete rows; runs twice on one block. That is an invalid free; the usual symptom is an abort or a segfault, and valgrind reports more frees than allocs.

Failure 2 — aliasing. Before either is destroyed, any change to one object is visible through the other, because there is only one double behind both. Code that modifies a copy silently corrupts the original.

Things to notice. Both failures come from the same missing pair of news, and both are invisible at compile time — the shallow version compiles cleanly with -Wall. The only defenses are knowing the rule and running valgrind.

Quick Check 14.12

True or false, with a one-line reason for each: a class whose only data members are an int, a double and a string still needs you to write a destructor and a copy constructor.

False for both, and this is worth being able to say out loud in an exam room.

  • Destructor: not needed. int and double have nothing to release, and string releases its own storage through its own destructor, which the compiler-generated destructor calls for you.
  • Copy constructor: not needed. The compiler-generated one copies the int, copies the double, and calls string's own copy constructor for the string — which itself does a deep copy of the characters. Member-by-member copying is exactly right when every member copies correctly.

Things to notice. The professor's Fall 2023 Final asks for the "five special members" of a Box class whose members are three plain doubles, and the Summer 2024 Final does the same for a Circle. For those classes the deep copy is vacuous — the correct answer is a copy constructor that copies the three doubles and prints its announcement, and a destructor whose only job is to print. Write them anyway; that is what the question asks for and the points are there. Just do not go inventing a delete for a class that never called new.

The one-sentence test for the whole lecture: does this class contain a raw pointer that it allocated? If yes, you owe it a destructor and a deep copy. If no, the compiler's versions are already correct.

//                  the destructor and the deep-copy copy constructor are the answer.

public:

        degree = d;
        coefficients = new double[degree + 1];
        for (int i = degree; i >= 0; i--) { coefficients[i] = c[i]; }

    // (b) copy constructor -- deep copy

        for (int i = 0; i <= degree; i++) {

Lecture Summary
  • A class whose constructor calls new owns heap memory, and memory from new is released only by delete. Without a destructor, every object of that class leaks.
  • A destructor is named ~ClassName, has no return type and no parameters. Because it has no parameter list, a class has exactly one destructor; there is no such thing as a "non-default" destructor.
  • A destructor runs at end of scope, on delete, and at the end of the program. Within a scope, objects are destroyed in reverse order of construction. You never call a destructor by hand.
  • The compiler-generated destructor calls the destructors of class-type members and does nothing at all for built-in types and raw pointers. That is why string members clean themselves up and string * members do not.
  • The compiler-generated copy constructor performs a shallow copy — it copies every data member, pointers included — so both objects point at the same block. That causes two failures: writes through one object are visible through the other, and both destructors free the same block.
  • A deep copy allocates fresh memory in the new object and copies the contents. The copy constructor that does it has the signature ClassName(const ClassName &orig): class name, no return type, one const-reference parameter.
  • The parameter must be a reference. By value, calling the copy constructor would first require calling the copy constructor — g++ refuses with "invalid constructor; you probably meant 'X (const X&)'".
  • A copy constructor fires in three situations: initializing a new object from an existing one (X b(a); and X b = a; are the same thing), passing by value, and returning by value — except that C++17 guarantees no copy at all when the returned thing is a temporary.
  • Splitting a class puts declarations in the body and definitions outside, qualified with ClassName::. The two must agree exactly, trailing const included.
  • The test for whether all of this applies to a given class: does it hold a raw pointer to memory it allocated? If not, the compiler's generated versions are already correct.
