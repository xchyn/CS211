Polymorphism, Virtual Functions and Virtual Destructors

One keyword changes which function a call runs — and that is the point of the whole inheritance edifice we have been building since Class 19.

Learning Objectives

By the end of today's class you should be able to:

1.Polymorphism, and the loose ends from Class 21

Welcome back from Exam 2. Everything you have built since Class 19 — derived classes, base initializers, construction order, the derived Big Three, base pointers — has been machinery. Today is the payoff, and it arrives as a single keyword.

Start with the word itself. The professor's own framing: "The term 'polymorphism' derives from two root words poly and morph. 'poly' means 'many' and 'morph' means to change shape or appearance. Hence 'polymorphism' means the ability of an object to have many different appearances."

Definition— polymorphism

Polymorphism is the ability of one pointer or reference to the base class to behave correctly for objects of many different derived classes — choosing, at run time, the version of a method that belongs to the object actually present rather than the version named by the declared type.

In the professor's words: "In the context of inheritance, we have seen that an object of a derived class IS-A object of the base class. Polymorphism takes the concept a step further. It is an important step and allows some very general/powerful/flexible software to be written."

Note where polymorphism lives: not in the object, but in the pointer or reference through which you reach it. That is why an object passed by value can never behave polymorphically — we come back to that in §4.

Class 21 ended by showing you two things that did not work, and promising the fix would arrive today. Here they are again, in one short program, so that the whole class starts from the same place.

Worked Example— the two loose ends, side by side

A Square IS-A Rectangle, so a Rectangle * may point at a Square. Both classes have a print(), and both destructors announce themselves. Three things happen in main: a direct call, a call through a base pointer, and a delete through a base pointer. Predict all of the output, including how many destructor lines appear and in what order.

Quick Check 24.1

Look at line (2) of the program above.

(a) Which rule from Class 19 predicts that p->print() runs Rectangle::print? Name the rule and use its proper term.

Static binding (also called early or compile-time binding). The compiler decides which function body a call will run while it is compiling the call, using the declared type of the expression to the left of the dot or arrow. p is declared Rectangle *, so the compiler searches Rectangle and its ancestors for a print, finds Rectangle::print, and hard-wires that call into the executable.

Nothing about the object p happens to point at enters into the decision. The compiler cannot know what it will point at — that is a run-time fact.

(b) A student says "the fix is to cast: write ((Square *)p)->print();". Why is that not a solution to the real problem?

It "works" for exactly this line and destroys the whole point of the exercise. To write the cast you must already know that p points at a Square. The situation we care about is a function that receives a Rectangle * and has no idea what it points at — possibly a class that did not exist when the function was compiled. You cannot cast to a type you have never heard of.

What we need is for the object to answer the question, not the programmer. That is what virtual arranges.

2.The design: one base class, three sums

The professor motivates all of this with a small numerical problem, and it is a well-chosen one because the three jobs are obviously similar and obviously different. Given an array of n values x0 … xn-1, compute three totals:

NameWhat it computesFor x = {-1, 0, 1, 2}
S1the plain sum x0 + x1 + …-1 + 0 + 1 + 2 = 2
S2the sum of absolute values1 + 0 + 1 + 2 = 4
S3the sum of squares1 + 0 + 1 + 4 = 6

His software design is three sentences long:

Procedure— the professor's design
  1. A base class SumBase holds the array x, with an accessor and a mutator.
  2. SumBase has a method double sum() which simply returns 0 — a placeholder meant to be overridden.
  3. Three derived classes SumVec, SumAbs and SumSq each override sum() with the formula they are responsible for.

x is protected, precisely so the derived classes can read it directly. This is the one situation Class 19 accepted protected data for: a base class designed from the start to be inherited from.

Worked Example— the four classes, used directly

Here is the whole design, with a main that calls sum() on each derived object by name. There is no virtual anywhere in this program. Predict the one line of output.

sums_direct.cpp
// sums_direct.cpp -- three kinds of sum, called directly on the derived objects
#include <iostream>
#include <vector>
#include <cmath>
using namespace std;

class SumBase {
public:
    vector<double> get() const { return x; }
    void set(const vector<double> &v) { x = v; }

    double sum() const { return 0; }   // the derived classes override this

    void print() const {
        for (size_t i = 0; i < x.size(); ++i) {
            cout << x[i] << " ";
        }
        cout << endl;
    }

protected:
    vector<double> x;
};

class SumVec : public SumBase {          // S1 = x0 + ... + xn-1
public:
    double sum() const {
        double s = 0;
        for (size_t i = 0; i < x.size(); ++i) { s += x[i]; }
        return s;
    }
};

class SumAbs : public SumBase {          // S2 = |x0| + ... + |xn-1|
public:
    double sum() const {
        double s = 0;
        for (size_t i = 0; i < x.size(); ++i) { s += fabs(x[i]); }
        return s;
    }
};

class SumSq : public SumBase {           // S3 = x0*x0 + ... + xn-1*xn-1
public:
    double sum() const {
        double s = 0;
        for (size_t i = 0; i < x.size(); ++i) { s += x[i] * x[i]; }
        return s;
    }
};

int main() {
    vector<double> x = {-1, 0, 1, 2};
    SumVec sv;
    SumAbs ab;
    SumSq  sq;
    sv.set(x);
    ab.set(x);
    sq.set(x);
    cout << sv.sum() << " " << ab.sum() << " " << sq.sum() << endl;
    return 0;
}
2 4 6

All three answers are correct, and — this is the part that trips people — they are correct without virtual. sv is declared SumVec, so sv.sum() binds statically to SumVec::sum. Static binding is doing exactly the right thing here, because the declared type and the actual object are the same thing.

File that away. It means the failure we are about to see is not a failure of overriding. Overriding works fine. The failure appears only when the call goes through a base reference or pointer.

Common Mistake— four repairs to the original listing

The listing above is the professor's design with four small corrections, each worth knowing because each is a bug you will write yourself:

  • abs on a double. The original writes s += abs(x[i]); in SumAbs while including only <iostream> and <vector>. If the only visible overload is C's int abs(int), then abs(-1.5) truncates to 1 and the sum of absolute values is silently wrong. The demo prints the right answer only because the test data are whole numbers. Use <cmath> and fabs for floating point.
  • int i against x.size(). vector::size() returns an unsigned type, so i < x.size() compares signed with unsigned and -Wall warns on every loop. Use size_t.
  • void set(vector<double> &v). A non-const reference parameter means you cannot pass a temporary, and it advertises that set might modify the caller's vector. Take it by const reference.
  • sum() was not const. print() is const in the original but sum() is not, even though it changes nothing. As written you cannot call sum() on a const SumBase &. Mark it const — and once you do, every override must be const too, which is the subject of a trap in §5.

The brace initializer vector<double> x = {-1, 0, 1, 2}; also needs C++11 or later. Everything on this page is compiled with -std=c++17.

Before we go on, the professor stops to defend the design, because two objections are obvious and both are worth answering.

ObjectionThe answer
"Why three classes? Write one class MiscSum with sum1(), sum2(), sum3()." "This is a valid criticism, for such a simple example. However, what if we want to add a fourth sum?" You would add a method to MiscSum and recompile all the code. In a large project a lot of code has to be recompiled and retested.
"Then write three independent classes, with no base class at all." A new sum needs no recompilation of the others — but now the shared parts are copied three times. Add a print() and you "have to copy and paste print() in each class." "It is therefore not a good idea to write independent classes."
Key Idea

Inheritance buys three things at once: new classes can be added to the tree without touching the existing ones; a change made in the base class is instantly available to the whole tree; and any individual class can override what it inherits. "Hence inheritance helps to avoid duplication of code and duplication of functionality."

And then the professor's own next sentence, which is the hinge of the whole lecture: "Nevertheless, we can write a better software design."

Quick Check 24.2

About sums_direct.cpp above.

(a) SumBase::sum() returns 0 and is never a useful answer. Why write it at all instead of leaving it out of the base class?

Because the base class is the contract. Any code that wants to work for all the sum classes — the library function in §3 — can only mention names that exist in SumBase. If sum() were not declared there, sb_ref.sum() would not compile at all: name lookup starts from the declared type and walks upward, never down into derived classes.

The body return 0; is a placeholder that makes the class compile. In Class 25 you will meet a better way to say "this method exists but the base class has nothing sensible to put in it" — the pure virtual function, written = 0, which forces derived classes to supply a body.

(b) Suppose someone adds a fourth sum by writing a class SumQuad : public SumBase in their own file. Which files have to be recompiled: only theirs, or all four class files as well?

Only theirs. SumBase, SumVec, SumAbs and SumSq do not mention SumQuad and are entirely unaffected by its existence — a derived class depends on its base, never the other way round.

That is exactly the property the one-big-MiscSum design throws away: adding sum4() to MiscSum changes the class definition, so every translation unit that includes its header must be recompiled and re-tested. On a project of any size, that is the difference between a five-minute change and a two-day change.

3.One library function, three wrong answers

Now the better design. Add print() to SumBase so that every derived class inherits it, and write a single function that takes a reference to the base class and does something useful with whatever it is handed:

void library_func(SumBase &sb_ref) {
    sb_ref.print();
    cout << "sum = " << sb_ref.sum() << endl;
    cout << endl;
}

The professor is explicit about the ambition here: "As the name suggests, it is the beginning of a software library." One function, written once, that works for SumVec, for SumAbs, for SumSq, and for classes nobody has written yet. He is equally explicit about what is coming: "It will not work exactly correctly at first, but we shall examine why and improve on it."

The professor's diagnosis, verbatim:

  • "The weakness is that the reference sb_ref binds only to the base class part of the input object."
  • "Therefore the reference sb_ref invokes only the base class version of the method sum()."
  • "The reference sb_ref does not know that the derived classes override the method sum()."

Key Idea

This is the same failure as line (2) of §1, wearing a suit. It did not matter that the derived classes override sum() correctly; it did not matter that print() worked. What mattered is that the compiler chose the function, from the declared type SumBase &, and the choice was frozen into the executable.

Quick Check 24.3

Still with no virtual anywhere:

(a) If you changed the parameter to void library_func(SumSq &sb_ref), would the sums come out right?

For SumSq objects, yes — sb_ref.sum() would now statically bind to SumSq::sum and print 6. But the function would no longer accept a SumVec or a SumAbs at all: those are not SumSq objects, and the compiler would reject the calls with "invalid initialization of reference".

So you can have one correct sum, or three wrong ones. That is precisely the dilemma polymorphism resolves.

(b) Overloading is another idea: write three library_func functions, one per derived class. What is wrong with that as a library design?

It works today and is unusable tomorrow. A library is compiled and shipped before its users write their classes. The professor's whole scenario is: "we do not know what the derived classes will be". You cannot overload a function for a type that does not exist yet, so every new derived class would require the library author to add an overload, recompile and re-ship — the MiscSum problem all over again, one level up.

It also duplicates the body of library_func three times, which is the second objection from §2.

4.virtual: static binding versus dynamic binding

Here is the fix. The professor introduces it with admirable understatement: "Let us make a peculiar looking but significant change to the method sum(). We tag sum() as a virtual method."

    virtual double sum() const { return 0; }

One word, in one place: the base class. Nothing else in the program changes — not the derived classes, not library_func, not main.

Definition— static binding and dynamic binding

Binding is the act of deciding which function body a call will run.

Static binding (early binding, compile-time binding) is the decision made by the compiler from the declared type of the expression to the left of the dot or arrow. The executable contains a call to one specific function and cannot change its mind. This is what C++ does by default, and it is what every call before today used.

Dynamic binding (late binding, run-time binding) defers the decision until the program is running, and makes it from the type of the object that is actually there. C++ gives you dynamic binding only where you ask for it, with the keyword virtual.

The professor's own gloss on the keyword: "The keyword virtual tells the compiler that a 'reference to the base class' is actually bound to an object which may belong to a derived class. If a method is tagged as virtual, the compiler searches through the inheritance tree until it finds the correct override." And on the word itself: "The word 'virtual' signifies that something is not real. That is exactly correct." Just because sb_ref is declared a reference to the base class does not mean the base version runs: "During program execution, the function call sb_ref.sum() may invoke many different versions of sum()."

Warning— the same words, two different mechanisms

The course notes describe both mechanisms with almost the same sentence — "the compiler searches up the inheritance tree until it finds the method". That description is true of both and therefore distinguishes neither. Keep the two apart with this test:

  • Non-virtual call: the search starts at the declared type and happens once, at compile time. Whatever it finds is burned into the executable.
  • virtual call: the search effectively starts at the actual object's class and happens every time the call executes. Two consecutive executions of the same line can run two different function bodies.

If you can only remember one sentence: without virtual the pointer decides; with virtual the object decides.

Take sums_virtual.cpp as printed. For each change below, say what the three sums become.

This is the single most common way students "add virtual" and see nothing happen. The word belongs in the base class.

There is one more condition, and it is easy to miss because it is about the parameter, not about the class.

Worked Example— by reference, by pointer, by value

sum() is virtual here. The same SumSq object is passed to three functions that differ only in how the parameter is declared. Two of them print 6. Which one does not, and why?

slice_virtual.cpp
// slice_virtual.cpp -- virtual cannot help a parameter passed by value
#include <iostream>
#include <vector>
using namespace std;

class SumBase {
public:
    void set(const vector<double> &v) { x = v; }
    virtual double sum() const { return 0; }
protected:
    vector<double> x;
};

class SumSq : public SumBase {
public:
    double sum() const {
        double s = 0;
        for (size_t i = 0; i < x.size(); ++i) { s += x[i] * x[i]; }
        return s;
    }
};

void by_reference(const SumBase &sb) { cout << "by reference: " << sb.sum() << endl; }
void by_value(SumBase sb)            { cout << "by value:     " << sb.sum() << endl; }
void by_pointer(const SumBase *p)    { cout << "by pointer:   " << p->sum() << endl; }

int main() {
    vector<double> x = {-1, 0, 1, 2};
    SumSq sq;
    sq.set(x);
    by_reference(sq);
    by_pointer(&sq);
    by_value(sq);
    return 0;
}
by reference: 6
by pointer:   6
by value:     0

by_value takes a SumBase object, so the argument is copied into it by SumBase's copy constructor — which copies only the SumBase part. This is object slicing, from Class 21. The parameter sb is not a sliced SumSq; it is a genuine, complete SumBase, and SumBase::sum() really is the right answer for it. Dynamic binding worked perfectly; the object it dispatched on was simply no longer a SumSq.

This is why the definition in §1 says polymorphism lives in the pointer or reference. No pointer, no reference, no polymorphism.

Quick Check 24.5

A student writes a container of shapes as vector<SumBase> v; and pushes SumVec, SumAbs and SumSq objects into it, then loops calling v[i].sum(). Every answer is 0. Explain, and give the standard fix.

Explanation. A vector<SumBase> stores SumBase objects. push_back copies the argument into an element of that type, so each derived object is sliced down to its base part on the way in. The vector never contained a SumVec at all. Calling sum() on a real SumBase correctly returns 0.

The fix is to store pointers, so that the objects themselves live elsewhere and are never copied:

    SumVec sv;  SumAbs ab;  SumSq sq;
    // ... set them ...
    vector<SumBase *> v = { &sv, &ab, &sq };
    for (size_t i = 0; i < v.size(); ++i) {
        cout << v[i]->sum() << " ";
    }

Things to notice. "A polymorphic container is a container of pointers" is one of those rules you can apply mechanically, and it is worth memorizing in that form. If the objects are created with new instead of living on the stack, you must delete each one — and that delete goes through a SumBase *, which is exactly the situation §8 is about.

Now the payoff the whole design was for. The professor asks: "What would happen if we wrote a new derived class to implement the sum S4?" — the sum of fourth powers. His answer: the library function will work correctly, "without modification", because sum() was declared virtual in the base class and is therefore automatically virtual in every derived class.

5.The rules for virtual functions

virtual has a small number of rules, and every one of them shows up as an exam trap. Take them one at a time.

Rule 1 — virtual is inherited, and dispatch finds the nearest override

You tag the method once, in the base class. From there down it is virtual in every descendant, whether or not they repeat the word. When a call is dispatched, the version that runs is the one belonging to the object's own class — or, if that class did not override it, the nearest ancestor that did.

Worked Example— four objects, one call site

A::f is virtual. B does not override it. C overrides it without writing virtual. D derives from C and overrides nothing. All four objects are visited through an array of A *, and the call list[i]->f() is the same line of code every time. Predict the four lines.

Rule 2 — the signature must match exactly, or you get hiding, not overriding

To override a virtual function, the derived declaration must have the same name, the same parameter list, and the same const-ness. Get any of that wrong and you have not overridden anything — you have declared a different function that merely happens to share a name, and which hides the base version for calls made on the derived type. The program still compiles. That is what makes this bug expensive.

Quick Check 24.8

Decide each of the following, briefly.

(a) In selective_virtual.cpp, SumVec::print is not an override. Would adding override to it compile?

No — and that is the point of override. SumBase::print is not virtual, so there is nothing to override, and the compiler would say "marked 'override', but does not override", exactly as in the Savings example. override catches both kinds of mistake: a signature that does not match, and a base method that was never virtual in the first place.

(b) A base class declares virtual void audit() const; in its protected section. A derived class overrides it in its public section. Legal?

Legal. The access level of an override does not have to match the base — the professor says so explicitly: "a virtual function which is protected in the base class can be made public in a derived class."

The reason it works is that access is checked statically, at the call site, against the declared type of the expression. Through a Base * the call is rejected (protected); through a Derived * it is allowed (public); if it is allowed, the dispatch that follows is dynamic as usual. Access control and binding are two independent mechanisms, and it is worth knowing they can disagree.

(c) Why can a constructor not be virtual, in one sentence?

Because dynamic binding needs an existing object to ask "what class are you?", and a constructor's whole job is to bring that object into existence — there is nothing to ask yet. (The compiler's phrasing: "constructors cannot be declared 'virtual'".) §7 shows what goes wrong when you call a virtual function from inside one.

6.How it works: the vtable, and what it costs

The professor poses the mechanism question sharply. Ordinary name lookup goes up the tree from the declared type, and that is easy. But "for a virtual function, the compiler must go in the opposite direction… How does the compiler go UP the inheritance tree, to determine the appropriate override?" — and remember, when the library is compiled, "the derived classes do not exist yet."

Definition— virtual function table (vtable) and vptr

If a class has any virtual functions, the compiler builds a hidden table for that class — the virtual function table, or vtable — holding the address of the correct function body for each virtual method of that class.

Every object of such a class carries one hidden pointer, the vptr, aimed at its own class's vtable. The constructor sets it. A virtual call then compiles to roughly: follow the object's vptr to a table, read slot k, call that address.

The professor draws the line we will draw too: "We shall not analyze the contents or operation of the virtual function table." The exact layout is the compiler's business and is not standardized. What you need is the shape of the cost: one extra pointer per object, one extra indirection per call.

Warning— correcting the course notes on when vtables are built

The original notes state that entries are made in the virtual function table "at run time, not at compile time, since we compile our library without knowing anything about the derived classes." The conclusion is right — the library really does work with classes it was never compiled against — but the mechanism described is not what happens.

What actually happens:

  • Each class with virtual functions gets its own vtable, generated by the compiler at compile time, when that class is compiled. A derived class does not add an entry to the base's table; it has a table of its own, whose slots hold its overrides where it has them and the inherited addresses where it does not.
  • The derived class's vtable is created when the derived class is compiled — years after the library, in a different translation unit, by a different programmer. Nothing is added to anything the library owns.
  • At run time the only thing that happens is the lookup: the constructor stored a vptr in the object, and each virtual call follows it and calls whatever address it finds.

That is why the library works: it does not need to know the derived classes, it only needs to know which slot to read. The slot number is fixed by the base class, which the library was compiled against.

The consequence you can actually observe is the professor's: "the memory allocation to create an object is not equal to the sum of the sizes of all the class data members… That is why the size of an object should always be determined by calling the sizeof operator."

(b) The same colleague says "a virtual call is slow because the program searches the inheritance tree at run time." What actually happens at run time?

No searching happens at run time. A virtual call is therefore: load the vptr from the object, load the address in slot k, call it — two loads and an indirect call, with no loop and no lookup by name.

The real costs are subtler: the compiler usually cannot inline a virtual call, because it does not know at compile time which body will run. For a tiny function called in a tight loop that can matter; for anything else it is noise.

7.Never call a virtual function from a constructor

The professor flags this one as "a serious mistake that some programmers make", and it is the kind of bug that survives code review because the code looks completely reasonable. Recall construction order from Class 20: when a derived object is created, the base constructor runs first, and the derived part does not exist yet.

Warning— what the course notes get slightly wrong here

The original notes say the run-time system "invokes the wrong virtual function, with possibly unpredictable and/or dangerous consequences." The advice — do not do this — is right. The description overstates the danger and understates the trap.

  • For an ordinary virtual function with a body, the behavior is completely well-defined: during base construction and base destruction, the base version runs. Nothing is unpredictable. That is what the output above shows.
  • The danger is that this is silent. The program does not crash, the compiler does not warn, and the initialization you carefully wrote as an override simply never happens.
  • The case that is undefined behavior is calling a pure virtual function (Class 25) from a constructor, because there is no base version to fall back to. Then you typically get a run-time abort with the message "pure virtual method called".

The rule to carry away is unchanged and absolute: do not call virtual functions from constructors or destructors. If you need per-class initialization, do it in each class's own constructor body, or add a separate init() that the caller invokes after construction. "Do not mess with the virtual function table when an object is being created or destroyed."

(b) Give two ways to fix it.

  • Two-phase initialization. The constructor does not call header() at all; the caller writes FileLogger f; f.start(); and start() makes the virtual call on a fully built object. This is the standard fix when the base class genuinely needs to drive the sequence.

What does not work: making header() "more virtual", adding override, or casting inside the base constructor. The derived part does not exist yet, and no keyword can conjure it.

8.Virtual destructors

Key Idea

If a class has any virtual function, its destructor must be virtual too. Not as a style preference — as a correctness requirement, because the moment you have virtual functions you have base pointers, and the moment you have base pointers somebody will delete one.

Return to line (3) of §1: delete q on a Rectangle * that pointed at a Square ran only ~Rectangle. There, nothing was lost but a message. Now do it with a derived class that owns memory.

Procedure— when to write virtual ~Base()
  1. Does the class have any virtual function? If yes, give it a virtual destructor. Full stop. A class with virtual functions is meant to be used through base pointers, and that is the situation that breaks.
  2. Is the class ever deleted through a base pointer? If yes, virtual destructor — even if it has no other virtual functions.
  3. If neither, do not add one. A virtual destructor makes an otherwise non-polymorphic class pay the vptr cost (§6) for nothing, and it stops the class from being trivially copyable.
  4. The body may be empty: virtual ~Shape() { } is the common case. What matters is the dispatch, not the body.
  5. Every destructor in the tree below it is then automatically virtual — virtual is inherited (Rule 1), and destructors are no exception even though their names differ.

Quick Check 24.12

Rapid fire — one sentence each.

(a) A base class has one virtual method and no data at all. Is a virtual destructor still needed?

Yes. The base class having nothing to release is irrelevant — what matters is whether the derived class's destructor gets called, and derived classes you have never seen may own anything at all. That is the whole premise of a polymorphic library: you do not know what the derived classes will be.

(b) Square s(3); and Rectangle r(s);, no new anywhere, non-virtual destructors. Does anything leak?

No. Objects with automatic storage duration are destroyed by their own declared type at the end of their scope, so s runs ~Square then ~Rectangle, and r — a genuine Rectangle built by slicing — runs ~Rectangle. The virtual-destructor problem is specifically a delete-through-a-base-pointer problem.

(c) Why does making the destructor virtual not require you to also write virtual on ~Derived?

Because virtual is inherited (Rule 1 of §5). Destructors are the one family of functions where the derived version has a different name from the base version, yet the language still treats ~Derived as overriding ~Base for dispatch purposes. Once ~Base is virtual, every destructor below it is virtual, and delete on any base pointer in the tree finds the right one.

Things to notice.

  • The string Vehicle: I am a vehicle appears three times, produced by three different mechanisms: a constructor-time call that could not dispatch, an explicit qualification that chose not to, and an ordinary call on an object that really is a Vehicle. Being able to say which is which is the whole of §5 and §7.
  • If ~Vehicle were not virtual, Car: destructor would disappear and the trace would be nine lines. Roughly one point per line on this professor's finals.
  • Car writes neither virtual nor override on describe(). It is still an override, because the signature matches exactly, including const. Change void describe() const to void describe() in Car and lines 4 and 5 both become Vehicle: I am a vehicle.
Lecture Summary
  • Polymorphism is one base pointer or reference behaving correctly for many derived types. It lives in the pointer or reference — pass by value and you slice the object and lose it.
  • Static (early) binding is the default: the compiler picks the function from the declared type, once, at compile time. Dynamic (late) binding picks it from the actual object, at run time, and you get it only by writing virtual. Without virtual the pointer decides; with virtual the object decides.
  • Tag the method virtual in the base class. It is then virtual in every derived class automatically, and dispatch runs the version in the object's own class or the nearest ancestor that supplied one.
  • A library function written against a base reference works for derived classes that did not exist when it was compiled. That is the entire point of the machinery.
  • An override must match the base name, parameter list and const exactly. Miss one and you get hiding, which compiles and silently misbehaves. Write override (C++11) and the compiler turns it into an error.
  • Base::method() is a statically bound call that deliberately bypasses the override — the way a derived version reuses the base behavior.
  • Data members, static methods and constructors cannot be virtual. Destructors can, operators can, const methods can, and any access level can.
  • A class with virtual functions gets a vtable, built at compile time; each object carries a hidden vptr to it. Cost: one pointer per object (measured here: 16 bytes becomes 24) and one indirection per call.
  • Never call a virtual function from a constructor or destructor. During base construction the object's dynamic type is the base class, so the base version runs — well-defined, silent, and almost never what you meant.
  • A class with any virtual function needs a virtual destructor. Without one, delete through a base pointer runs only the base destructor: the derived destructor never runs and everything it owned leaks. Verified here with valgrind: 8,000 bytes definitely lost before, no leaks possible after.
